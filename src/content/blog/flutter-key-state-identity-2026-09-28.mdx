## 결론부터 말하면

Flutter에서 `Key`는 "widget에 이름표를 붙이는 장식"이 아닙니다. 같은 위치에 새 widget이 들어왔을 때 기존 `Element`와
`State`를 재사용해도 되는지 판단하게 해 주는 정체성 힌트입니다.

Spring Boot 개발자에게 익숙한 비유로 말하면, 화면 목록의 `Key`는 JPA entity의 primary key나 React list key와 비슷한
역할을 합니다. 같은 데이터인지 구분하지 못하면 update가 아니라 delete 후 insert처럼 처리되고, 사용자가 입력하던 폼 상태나
애니메이션 상태가 엉뚱한 행에 붙을 수 있습니다.

## 이번 주 개념

Flutter의 UI는 `Widget -> Element -> RenderObject` 축으로 움직입니다. `Widget`은 설정값이고, `Element`는 tree 안의
자리이며, `State`는 `StatefulWidget`이 유지하는 값입니다. 공식 Inside Flutter 문서는 `Element`를 재사용하면 state와
layout 정보를 보존할 수 있어 성능에 중요하다고 설명합니다.

| Flutter 개념 | 역할 | Spring Boot에 비유하면 |
|---|---|---|
| `Widget` | 화면 설정을 담은 불변 객체 | request DTO 또는 view model snapshot |
| `Element` | widget이 tree에서 차지하는 자리 | persistence context 안의 관리 객체 |
| `State` | 사용자가 입력 중인 값, animation controller 등 | transaction 동안 유지되는 변경 상태 |
| `Key` | 같은 위치의 widget 정체성을 비교하는 힌트 | entity id, natural key |
| `GlobalKey` | tree 전체에서 하나뿐인 key, subtree 이동과 state 접근 가능 | 전역 registry를 건드리는 강한 식별자 |

## Java/Spring에서는 어떻게 다뤘는가

서버에서 주문 항목을 수정한다고 가정해 보겠습니다.

```java
record OrderLineCommand(Long lineId, String name, int quantity) {}
```

`lineId` 없이 배열 순서만 믿고 수정하면 문제가 생깁니다. 사용자가 두 번째 행과 세 번째 행을 바꾼 뒤 저장했는데, 서버가
"두 번째 줄"이라는 위치만 보고 처리하면 기존 상태가 잘못된 항목에 붙을 수 있습니다.

Flutter 목록도 같습니다. 데이터 목록이 재정렬되거나 중간에 삽입될 수 있다면, 화면도 "이 카드가 어떤 데이터의 카드인가"를
알아야 합니다. 그 힌트가 `ValueKey(order.id)` 같은 key입니다.

## Flutter에서는 무엇이 다른가

Flutter는 widget을 자주 새로 만듭니다. 이것 자체는 문제가 아닙니다. 문제는 framework가 새 widget을 이전 `Element`와
맞춰 볼 때, 위치와 type만으로는 충분하지 않은 경우입니다.

아래 코드는 보기에는 자연스럽지만, 사용자가 행을 재정렬하거나 중간 삽입을 할 때 state가 헷갈릴 수 있습니다.

```dart
class OrderList extends StatelessWidget {
  const OrderList({super.key, required this.orders});

  final List<Order> orders;

  @override
  Widget build(BuildContext context) {
    return ListView(
      children: [
        for (final order in orders)
          OrderTile(order: order),
      ],
    );
  }
}
```

각 행이 독립적인 입력값, checkbox, animation state를 가진다면 데이터 id를 key로 넣습니다.

```dart
class OrderList extends StatelessWidget {
  const OrderList({super.key, required this.orders});

  final List<Order> orders;

  @override
  Widget build(BuildContext context) {
    return ListView(
      children: [
        for (final order in orders)
          OrderTile(
            key: ValueKey(order.id),
            order: order,
          ),
      ],
    );
  }
}
```

핵심은 "key를 많이 붙이면 안전하다"가 아닙니다. **정체성이 바뀔 수 있는 형제 목록에 안정적인 key를 붙인다**가 규칙입니다.
공식 `Widget.key` 문서도 단일 자식 widget에는 보통 명시적 key가 필요 없다고 설명합니다.

## 대응 개념 비교

| 상황 | key 없음 | key 있음 |
|---|---|---|
| 단순 정적 layout | 대체로 충분 | 굳이 필요하지 않음 |
| 같은 type의 목록 재정렬 | 위치 기준으로 state가 따라갈 수 있음 | 데이터 id 기준으로 state 보존 |
| 중간 삽입과 삭제 | 아래 행의 state가 밀릴 수 있음 | 각 행의 state가 자기 데이터에 남음 |
| 폼 여러 개 | 입력 중인 값이 다른 폼에 보일 수 있음 | 폼마다 정체성 분리 |
| subtree를 다른 부모로 이동 | 일반 key로는 부족 | `GlobalKey`가 가능하지만 비용과 제약 확인 |

`GlobalKey`는 더 강한 도구입니다. 공식 문서는 global key가 subtree를 다른 위치로 옮길 수 있고 `State` 접근도 가능하지만,
reparenting 비용이 있으며 필요 없으면 `Key`, `ValueKey`, `ObjectKey`, `UniqueKey`를 고려하라고 안내합니다.

## 최소 실행 예제: 체크 상태가 다른 행에 붙는 문제

아래 예제는 할 일을 중요도순으로 다시 정렬합니다. key가 없으면 framework는 같은 위치의 `TodoRow`를 재사용하려고 하므로,
row 안의 local state가 데이터가 아니라 위치에 붙는 느낌을 만들 수 있습니다.

```dart
class TodoRow extends StatefulWidget {
  const TodoRow({super.key, required this.todo});

  final Todo todo;

  @override
  State<TodoRow> createState() => _TodoRowState();
}

class _TodoRowState extends State<TodoRow> {
  bool selected = false;

  @override
  Widget build(BuildContext context) {
    return CheckboxListTile(
      value: selected,
      title: Text(widget.todo.title),
      onChanged: (value) => setState(() => selected = value ?? false),
    );
  }
}
```

목록을 그리는 쪽에서 데이터 id를 key로 넘기면 row state가 위치가 아니라 todo id에 묶입니다.

```dart
ListView(
  children: [
    for (final todo in sortedTodos)
      TodoRow(
        key: ValueKey(todo.id),
        todo: todo,
      ),
  ],
)
```

서버에서 `lineId` 없이 update command를 보내지 않는 것과 같은 감각입니다. 사용자가 보고 있는 한 줄이 어떤 domain object를
대표하는지 UI tree에도 알려 줍니다.

## `GlobalKey`를 먼저 꺼내지 않습니다

`GlobalKey`는 form validation 예제에서 자주 보여 익숙해 보이지만, 일반 목록 정체성 문제의 기본 답은 아닙니다. 공식
`GlobalKey` 문서는 매 build마다 새 global key를 만들면 기존 subtree state를 버리고 새 subtree를 만들 수 있어 성능과
동작에 문제가 생긴다고 경고합니다.

| 필요한 일 | 먼저 볼 선택지 |
|---|---|
| 같은 형제 목록에서 데이터 정체성 유지 | `ValueKey(id)` |
| 객체 자체가 정체성이고 equality가 안정적임 | `ObjectKey(object)` |
| 매번 새 상태가 필요함 | `UniqueKey()` |
| form field 값을 상위 state로 모음 | controller, callback, state management |
| subtree를 부모 밖으로 이동하며 state 유지 | 비용을 알고 `GlobalKey` 검토 |

Spring에서 모든 것을 singleton registry에 넣지 않는 것처럼, Flutter에서도 `GlobalKey`를 전역 손잡이처럼 남발하지 않습니다.
필요한 범위의 식별자를 가장 좁게 둡니다.

## 실무 점검 순서

목록 상태 버그가 보이면 아래 순서로 좁혀 봅니다.

1. 같은 type의 stateful row가 형제로 반복되는지 확인합니다.
2. row 안에 입력값, focus, animation, controller, checkbox state가 있는지 봅니다.
3. 데이터가 정렬, 필터, 삽입, 삭제될 수 있는지 확인합니다.
4. domain id가 있으면 `ValueKey(id)`를 row 최상단에 붙입니다.
5. id가 없다면 서버 계약부터 다시 봅니다. 화면 key를 위해 임시 index를 id처럼 쓰는 것은 대개 문제를 미룹니다.
6. `GlobalKey`가 이미 있다면 매 build마다 생성되는지, 정말 subtree 이동이나 state 접근이 필요한지 확인합니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 "widget이 새로 만들어지면 state도 항상 새로 만들어진다"입니다. Flutter는 새 widget을 이전 element와
맞춰 보고 재사용할 수 있습니다. 그래서 key가 중요합니다.

두 번째 오해는 "index를 key로 쓰면 충분하다"입니다. 정렬과 삽입이 없는 고정 목록이라면 문제가 드러나지 않을 수 있지만,
순서가 바뀌는 목록에서 index는 데이터 정체성이 아니라 위치입니다.

세 번째 오해는 "`GlobalKey`가 더 강하니 항상 더 안전하다"입니다. 더 강한 식별자는 더 넓은 비용과 제약을 가져옵니다.
목록 row 식별에는 보통 local key가 더 작고 명확합니다.

## 연습 문제

1. 기존 Flutter 화면에서 같은 type의 row가 반복되는 목록을 하나 고릅니다.
2. row 안에 local state가 있는지 확인합니다.
3. 목록을 정렬하거나 필터링했을 때 입력값, checkbox, focus가 올바른 데이터에 남는지 봅니다.
4. 문제가 보이면 row 최상단에 `ValueKey(domainId)`를 붙입니다.
5. `GlobalKey`를 쓰는 곳이 있다면 생성 위치가 `build()` 안인지 확인하고, 더 좁은 key로 바꿀 수 있는지 검토합니다.
