## 결론부터 말하면

Flutter 접근성은 마지막에 `Semantics(label: ...)` 하나를 얹는 작업이 아닙니다. **화면이 무엇을 의미하는지**와
**키보드가 어디로 이동하는지**를 별도로 설계하는 일입니다. 화면에 보이는 순서가 보조 기술이 읽는 순서나 Tab 키의 이동 순서와
항상 같지는 않습니다.

Spring Boot 개발자라면 서버가 HTTP request를 받아 validation, authorization, response 순서를 책임지는 것처럼,
Flutter 화면도 입력 장치와 보조 기술에 일관된 interaction contract를 제공해야 한다고 생각하면 좋습니다. widget tree는
구현 구조이고, semantics tree와 focus traversal은 사용자가 실제로 만나는 계약입니다.

## 이번 주 개념

| Flutter 개념 | 책임 | Spring/웹 감각으로 비유하면 |
|---|---|---|
| `Semantics` | control의 이름·역할·상태 전달 | label, role, state를 포함한 접근 가능한 form contract |
| `FocusNode` | 현재 키보드 입력을 받을 대상 | 현재 request를 받는 controller의 명시적 핸들 |
| `FocusTraversalGroup` | Tab/방향키 이동의 지역 규칙 | 한 form 단계 안의 validation·다음 단계 흐름 |
| `FocusTraversalOrder` | 시각 배치와 다른 이동 우선순위 | 명시적인 처리 순서와 route priority |
| `ExcludeSemantics` | 중복되거나 장식적인 읽기 제거 | response DTO에서 내부 구현 필드를 숨김 |

<Mermaid title="보이는 widget과 접근성 경로를 분리하는 흐름">

## Java/Spring에서는 어떻게 다뤘는가

서버 화면이나 API에서도 사람이 보는 HTML 순서와 기계가 해석하는 계약을 구분합니다. 예를 들어 form의 label은
표시 문구일 뿐 아니라 입력 field를 설명하는 계약이고, 오류 응답은 status code와 field name으로 client가 처리할 수 있어야 합니다.

```java
record ShippingForm(String recipient, String postalCode) {}

record FieldError(String field, String message) {}

@PostMapping("/shipping")
ResponseEntity<?> submit(@Valid @RequestBody ShippingForm form) {
  return ResponseEntity.accepted().build();
}
```

Flutter에서도 눈에 보이는 제목만으로 control의 의미가 전달된다고 가정하면 안 됩니다. icon-only button, 상태가 바뀌는
switch, 읽기 전용 summary는 의미와 state를 보조 기술에 제공해야 합니다. 반대로 같은 정보를 title, icon, helper text가
모두 읽게 하면 사용자는 중복 안내를 듣습니다.

## 먼저 semantics를 확인하기

가능하면 Flutter의 Material/Cupertino control을 그대로 쓰세요. `FilledButton`, `Switch`, `TextField`는 기본
semantics를 이미 제공합니다. custom paint나 `GestureDetector`로 control을 만들 때에만 역할과 label을 직접 보강합니다.

```dart
Semantics(
  button: true,
  label: '배송 주소 검색',
  hint: '우편번호를 입력하거나 주소 검색을 시작합니다',
  child: IconButton(
    tooltip: '배송 주소 검색',
    icon: const Icon(Icons.search),
    onPressed: openAddressSearch,
  ),
)
```

이 예제는 icon 자체를 설명하려는 것이 아니라 사용자가 수행할 action을 설명합니다. 이미 `tooltip`과 child가 충분한
semantics를 만들면 wrapper를 중복하지 않는 편이 낫습니다. Flutter DevTools의 accessibility 도구와 screen reader로
실제 읽기 결과를 확인해야 합니다.

## focus는 widget 위치가 아니라 업무 순서입니다

wide layout에서는 주소와 연락처 field를 두 column으로 배치하고, narrow layout에서는 한 column으로 바꿀 수 있습니다.
이때 render position에만 기대면 Tab이 의도하지 않은 곳으로 건너뛸 수 있습니다. 업무 입력 순서를 `FocusTraversalGroup`에
명시하면 layout 변경과 focus contract를 분리할 수 있습니다.

```dart
class ShippingFields extends StatefulWidget {
  const ShippingFields({super.key});

  @override
  State<ShippingFields> createState() => _ShippingFieldsState();
}

class _ShippingFieldsState extends State<ShippingFields> {
  final recipientFocus = FocusNode(debugLabel: 'recipient');
  final postalCodeFocus = FocusNode(debugLabel: 'postal-code');

  @override
  void dispose() {
    recipientFocus.dispose();
    postalCodeFocus.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return FocusTraversalGroup(
      policy: OrderedTraversalPolicy(),
      child: Column(
        children: [
          FocusTraversalOrder(
            order: const NumericFocusOrder(1),
            child: TextField(
              focusNode: recipientFocus,
              textInputAction: TextInputAction.next,
              onSubmitted: (_) => postalCodeFocus.requestFocus(),
              decoration: const InputDecoration(labelText: '받는 사람'),
            ),
          ),
          FocusTraversalOrder(
            order: const NumericFocusOrder(2),
            child: TextField(
              focusNode: postalCodeFocus,
              decoration: const InputDecoration(labelText: '우편번호'),
            ),
          ),
        ],
      ),
    );
  }
}
```

`FocusNode`는 controller처럼 lifecycle을 가집니다. `build()`마다 새 node를 만들면 focus가 사라지거나 listener가
누적될 수 있으므로 `State`가 소유하고 `dispose()`에서 정리합니다. route가 바뀌거나 dialog가 열릴 때도 현재 focus를
어디로 옮길지 명시적으로 판단하세요.

## 읽는 순서와 Tab 순서는 같은 문제가 아닙니다

screen reader는 semantics tree를 탐색하고, 키보드는 focusable widget 사이를 이동합니다. 두 경로를 한 property로
억지로 맞추지 마세요.

| 상황 | semantics 판단 | focus 판단 |
|---|---|---|
| 장식 이미지 | `ExcludeSemantics` 또는 빈 의미 | focus 대상 아님 |
| icon-only 삭제 버튼 | action과 대상 이름 제공 | keyboard로 도달 가능해야 함 |
| disabled 제출 버튼 | disabled 이유를 이해할 수 있게 설명 | 이동 가능 여부를 일관되게 유지 |
| responsive 2-column form | 읽는 내용이 논리적으로 이어지는지 확인 | 업무 입력 순서로 Tab 이동 |
| modal dialog | dialog title과 close action을 제공 | 첫 focus와 close 후 복귀 위치를 결정 |

특히 visual order와 semantic order를 CSS/위치 속성처럼 뒤집는 것은 마지막 수단입니다. 먼저 widget tree를 논리적인
순서로 두고, 반응형 grid는 그 구조를 표현하는 역할만 맡기는 편이 테스트와 유지보수에 안전합니다.

## 테스트는 화면 캡처만으로 끝나지 않습니다

최소한 다음을 자동화 또는 수동 점검표로 유지하세요.

1. keyboard만으로 주요 action까지 Tab과 Shift+Tab으로 도달할 수 있는가
2. focus outline이 대비를 가지며 현재 위치를 분명히 보이는가
3. icon-only control과 변경 가능한 state가 읽히는가
4. error message가 field와 연결되고, error 발생 뒤 focus 이동이 예측 가능한가
5. 200% text scale과 390px 화면에서도 focus 대상이 화면 밖으로 잘리지 않는가

Flutter의 semantics debugger는 구조 확인에 유용하지만 실제 TalkBack, VoiceOver, desktop screen reader의 동작을
완전히 대체하지는 않습니다. 지원 대상 플랫폼마다 하나의 핵심 form을 골라 직접 확인하는 release checklist가 필요합니다.

## Java 개발자가 자주 하는 오해

1. **"보이는 label이 있으니 읽힐 것이다."**  custom widget과 icon-only action은 그렇지 않을 수 있습니다.
2. **"Tab 순서는 위치 순서면 충분하다."**  responsive layout은 위치를 바꾸지만 업무 흐름까지 바꾸지는 않습니다.
3. **"FocusNode는 local variable이어도 된다."**  lifecycle을 가진 객체이므로 owner와 dispose 경계가 필요합니다.
4. **"semantics는 장애가 있는 사용자만을 위한 기능이다."**  keyboard, large text, switch input, 자동화 테스트의
   예측 가능성도 함께 좋아집니다.

## 연습 문제

1. 앱의 icon-only button 하나를 골라 action 중심의 accessible name이 있는지 확인하세요.
2. two-column form을 390px과 desktop에서 열고 Tab 경로를 종이에 적어 보세요. 업무 순서와 다른 곳이 있나요?
3. validation error 뒤 첫 오류 field로 focus를 옮길지, summary를 먼저 읽을지 팀 contract를 정해 보세요.
