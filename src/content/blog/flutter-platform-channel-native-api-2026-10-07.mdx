## 결론부터 말하면

Flutter에서 네이티브 기능을 붙일 때 가장 먼저 정할 것은 **Dart UI가 플랫폼 API를 직접 안다고 착각하지 않게 하는 경계**입니다.

Spring Boot 개발자에게 익숙한 표현으로 바꾸면 platform channel은 외부 결제사, 파일 시스템, 사내 레거시 API를 감싼 adapter에
가깝습니다. controller가 DB driver를 직접 부르지 않듯, Flutter 화면도 Android `BatteryManager`, iOS `UIDevice`,
OS 권한 API를 직접 아는 구조로 만들면 테스트와 장애 처리가 빠르게 무너집니다.

## 이번 주 개념

Flutter 공식 문서는 platform channel을 Dart code와 host platform code 사이의 메시지 통로로 설명합니다. Dart 쪽은
`MethodChannel`로 method call을 보내고, Android Kotlin이나 iOS Swift 쪽은 같은 channel name을 가진 handler에서
요청을 받아 결과를 돌려줍니다. 메시지는 비동기로 오가지만, 플랫폼 API에 닿는 thread 규칙은 플랫폼마다 따로 봐야 합니다.

| Flutter 개념 | 역할 | Spring Boot에 비유하면 |
|---|---|---|
| `MethodChannel` | Dart와 host platform 사이의 method call 통로 | 외부 시스템 adapter interface |
| channel name | 양쪽이 합의한 통신 주소 | base URL 또는 message topic |
| codec | Dart 값과 Kotlin/Swift 값의 직렬화 규칙 | JSON serializer 또는 message converter |
| `PlatformException` | host side 실패를 Dart로 전달 | 외부 API error response |
| plugin wrapper | channel 호출을 앱 도메인 API로 감쌈 | infrastructure adapter 구현체 |
| mock channel | 테스트에서 host API를 대체 | WireMock, fake repository |

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 외부 API를 부를 때 `Controller`에서 바로 HTTP client를 만들기보다 port와 adapter를 나눕니다.

```java
public interface DeviceTokenReader {
    String readToken();
}

@Component
class HttpDeviceTokenReader implements DeviceTokenReader {
    private final WebClient webClient;

    HttpDeviceTokenReader(WebClient webClient) {
        this.webClient = webClient;
    }

    @Override
    public String readToken() {
        return webClient.get()
            .uri("/device-token")
            .retrieve()
            .bodyToMono(String.class)
            .block();
    }
}
```

핵심은 업무 코드가 "HTTP로 가져온다"보다 "토큰을 읽는다"에 의존하게 만드는 것입니다. Flutter에서도 같은 감각이 필요합니다.
화면은 `MethodChannel`이 아니라 `BatteryReader`, `PushPermissionGateway`, `HealthPermissionGateway` 같은 작은 Dart
interface에 의존하고, channel 구현은 그 뒤로 숨기는 편이 좋습니다.

## Flutter에서는 무엇이 다른가

Flutter의 platform channel은 한 process 안에서 UI code와 host code가 만나는 통로입니다. HTTP처럼 network hop이 있는 것은
아니지만, 실패 방식은 외부 시스템 호출과 비슷합니다.

```dart
import 'package:flutter/services.dart';

class BatteryGateway {
  static const _channel = MethodChannel('example.app/battery');

  Future<int> readBatteryLevel() async {
    try {
      final result = await _channel.invokeMethod<int>('getBatteryLevel');
      if (result == null) {
        throw const BatteryUnavailable('battery level was null');
      }
      return result;
    } on PlatformException catch (error) {
      throw BatteryUnavailable(error.message ?? error.code);
    }
  }
}

class BatteryUnavailable implements Exception {
  const BatteryUnavailable(this.message);
  final String message;
}
```

이 예제에서 중요한 점은 세 가지입니다.

1. channel name은 앱 안에서 유일하게 잡습니다. 공식 예제처럼 domain prefix를 붙이면 충돌 가능성을 줄일 수 있습니다.
2. `invokeMethod<T>`의 결과는 nullable로 다룹니다. host side가 기대와 다른 값을 돌려줄 수 있기 때문입니다.
3. `PlatformException`을 화면까지 그대로 흘리지 않고 앱 도메인 예외로 바꿉니다.

## Android Kotlin handler는 작은 adapter로 둡니다

Android 쪽 구현도 controller처럼 비대해지면 곤란합니다. Flutter 문서는 Android host code에서 `MethodChannel` handler를 붙여
method 이름에 따라 결과를 돌려주는 구조를 보여줍니다.

```kotlin
class MainActivity : FlutterActivity() {
    private val channelName = "example.app/battery"

    override fun configureFlutterEngine(flutterEngine: FlutterEngine) {
        super.configureFlutterEngine(flutterEngine)

        MethodChannel(flutterEngine.dartExecutor.binaryMessenger, channelName)
            .setMethodCallHandler { call, result ->
                when (call.method) {
                    "getBatteryLevel" -> result.success(readBatteryLevel())
                    else -> result.notImplemented()
                }
            }
    }

    private fun readBatteryLevel(): Int {
        val manager = getSystemService(BATTERY_SERVICE) as BatteryManager
        return manager.getIntProperty(BatteryManager.BATTERY_PROPERTY_CAPACITY)
    }
}
```

실무에서는 `MainActivity`가 커지기 쉽습니다. 권한 요청, intent 처리, SDK 초기화, channel handler가 한 파일에 쌓이면
변경 위험이 커집니다. Spring Boot에서 controller와 service를 나누듯, Android도 channel 등록부와 실제 platform service를
분리하는 편이 유지보수에 좋습니다.

## Threading은 "비동기니까 안전하다"가 아닙니다

공식 platform channel 문서는 메시지가 비동기로 오가더라도 플랫폼 main thread 규칙을 따로 지켜야 한다고 설명합니다.
Android에서는 UI thread, iOS에서는 main thread 규칙이 있고, background task queue를 써야 할 때도 있습니다.

Spring Boot에서 `@Async`를 붙였다고 JPA transaction, security context, MDC가 자동으로 안전해지는 것은 아닙니다. Flutter도
마찬가지입니다. channel 호출이 `Future`를 반환한다고 해서 host API가 어떤 thread에서나 안전하게 실행되는 것은 아닙니다.

| 상황 | 권장 판단 |
|---|---|
| UI 권한 dialog, system UI 호출 | main thread 규칙을 우선 확인 |
| 긴 파일 처리, 암호화, 압축 | channel handler 안에서 오래 막지 말고 background 처리 검토 |
| host에서 Flutter로 event push | root isolate 또는 등록된 background isolate 조건 확인 |
| web target | platform channel보다 JS interop 또는 web 전용 adapter 검토 |

## 테스트는 channel mock보다 도메인 adapter fake가 먼저입니다

Flutter testing 문서는 plugin이나 platform channel이 테스트에서 실제 host API를 호출하지 않도록 mock을 둘 수 있다고 설명합니다.
하지만 모든 widget test가 channel message format까지 알아야 하면 테스트가 너무 깨지기 쉽습니다.

먼저 Dart interface를 둡니다.

```dart
abstract interface class BatteryReader {
  Future<int> readBatteryLevel();
}

class BatteryBannerController {
  BatteryBannerController(this.reader);

  final BatteryReader reader;

  Future<String> label() async {
    final level = await reader.readBatteryLevel();
    return level < 20 ? '충전이 필요합니다' : '배터리 여유가 있습니다';
  }
}
```

그리고 대부분의 테스트는 fake reader로 갑니다.

```dart
class FakeBatteryReader implements BatteryReader {
  FakeBatteryReader(this.level);
  final int level;

  @override
  Future<int> readBatteryLevel() async => level;
}
```

channel mock은 adapter 자체를 테스트할 때만 사용합니다. Spring Boot에서 service test는 fake repository를 쓰고,
adapter integration test에서만 WireMock이나 Testcontainers를 쓰는 것과 같은 구분입니다.

## Java 개발자가 자주 하는 오해

1. **"플러그인을 쓰면 platform channel을 몰라도 된다."**  
   plugin도 내부에서는 channel, FFI, platform API 중 하나로 host와 통신합니다. 장애를 해석하려면 경계를 알아야 합니다.

2. **"`MethodChannel`은 RPC니까 아무 값이나 주고받아도 된다."**  
   codec이 지원하는 타입과 nullable, map key, list shape를 계약처럼 관리해야 합니다.

3. **"Android에서 잘 되면 iOS도 같은 의미다."**  
   같은 Dart API 뒤에 다른 권한 모델, lifecycle, thread 규칙이 숨어 있을 수 있습니다.

4. **"테스트에서 channel을 전부 mock하면 충분하다."**  
   화면과 도메인 로직은 channel format을 몰라야 합니다. channel mock은 가장 바깥 adapter 검증에 남깁니다.

## 실무 점검표

| 점검 항목 | 질문 |
|---|---|
| channel name | domain prefix가 있고 충돌 가능성이 낮은가 |
| method name | string literal이 여러 파일에 흩어져 있지 않은가 |
| result type | `null`, type mismatch, unsupported platform을 다루는가 |
| error mapping | `PlatformException`을 사용자 메시지와 로깅 코드로 분리하는가 |
| threading | platform main thread와 background task 조건을 확인했는가 |
| 테스트 | 도메인 fake, channel mock, 실제 device 확인 범위를 나눴는가 |

## 연습 문제

1. 현재 앱의 native 기능 후보를 `권한`, `device 정보`, `background 작업`, `외부 SDK` 네 가지로 분류합니다.
2. 각 후보에 대해 Dart interface 이름과 channel name을 적어 봅니다.
3. `PlatformException` code를 사용자 메시지, 재시도 가능 여부, 로그 severity로 매핑해 봅니다.
4. widget test, adapter test, 실제 device smoke test 중 어디에서 무엇을 확인할지 표로 나눕니다.
