## 결론부터 말하면

소프트 삭제를 엔티티 어노테이션 하나로 숨기면 처음에는 편합니다. 일반 조회에서 삭제된 행이 자동으로
빠지기 때문입니다. 하지만 시간이 지나면 어떤 조회가 활성 데이터만 다루는지, 어떤 운영 조회가 삭제된
데이터까지 봐야 하는지 코드만 보고 판단하기 어려워졌습니다.

이번 회고의 핵심은 단순했습니다.

- 기본 업무 조회는 `deletedAt IS NULL`을 저장소 메서드와 JPQL에 명시합니다.
- 삭제된 데이터까지 필요한 조회는 이름과 반환 모델로 별도 계약을 둡니다.
- 업데이트 쿼리도 조회와 같은 조건을 가져야 합니다.

Spring Boot 개발자에게 익숙한 표현으로 말하면, 소프트 삭제는 매핑 편의 기능이 아니라 도메인 조회
계약입니다. 컨트롤러가 `findById()`를 호출했을 때 "삭제된 행은 보이지 않는다"가 중요한 규칙이라면,
그 규칙은 저장소 API 이름과 테스트에서 보이는 편이 오래 유지됩니다.

> 검증일: 2026-08-20. Spring 공식 문서 기준 Spring Boot 안정 버전 `4.1.0`, Spring Data JPA 안정 버전
> `4.1.0`을 확인했습니다. Hibernate 문서는 안정 사용자 가이드와 `@SQLRestriction` Javadoc을 기준으로
> 확인했습니다.

## 문제가 된 모양

소프트 삭제 컬럼은 보통 단순합니다. `deleted_at`이 `null`이면 활성, 값이 있으면 삭제된 행입니다. 문제는
단순한 컬럼보다 이 컬럼을 적용하는 위치였습니다.

엔티티에 전역 SQL 제한을 걸어 두면 대부분의 조회에서 삭제된 행이 자동으로 빠집니다. 하지만 운영 기능이
늘어나면서 다음 질문이 계속 생겼습니다.

| 질문 | 전역 제한에 숨겼을 때의 문제 |
|---|---|
| 삭제된 행을 복구해야 하면 어디서 조회하는가 | 일반 조회와 복구 조회의 차이가 코드에 잘 보이지 않음 |
| 벌크 업데이트는 삭제된 행을 건드리지 않는가 | 업데이트 JPQL에 조건이 빠져도 리뷰에서 놓치기 쉬움 |
| 연관 컬렉션은 같은 조건을 적용하는가 | 엔티티 제한, 조인 테이블 제한, 직접 JPQL 조건이 섞임 |
| 운영 감사에서는 삭제된 행도 봐야 하는가 | 예외 조회가 암묵적인 우회처럼 보임 |

Hibernate의 `@SQLRestriction`은 정적 조건을 매핑 시점에 적용할 수 있습니다. 공식 Javadoc도 이 제한은
항상 적용되고 비활성화하거나 파라미터화할 수 없다고 설명합니다. 이 특성은 "항상 숨겨야 하는 데이터"에는
맞지만, 삭제된 행을 업무 상황에 따라 다르게 다뤄야 하는 도메인에는 점점 부담이 됩니다.

<Mermaid title="소프트 삭제 조회 계약 이동">
{`flowchart TD
  Controller["서비스 또는 컨트롤러"] --> Repository["저장소 API"]
  Repository --> ActiveQuery["활성 조회: deletedAt IS NULL"]
  Repository --> AuditQuery["감사/복구 조회: 삭제 상태 명시"]

  ActiveQuery --> Domain["업무 도메인 처리"]
  AuditQuery --> Admin["운영 또는 복구 처리"]

  EntityRestriction["엔티티 전역 제한"] -. 숨은 조건 .-> ActiveQuery
  Repository -. 명시 조건으로 대체 .-> ActiveQuery
`}
</Mermaid>

## 조회 메서드 이름이 정책을 말해야 합니다

첫 번째 변경은 저장소 메서드 이름을 더 노골적으로 만드는 일이었습니다. `findById`처럼 일반적인 이름은
편하지만, 소프트 삭제 조건을 반드시 포함해야 하는 도메인에서는 너무 많은 의미를 숨깁니다.

```java
interface DeviceRepository extends JpaRepository<Device, Long> {
    Optional<Device> findByIdAndDeletedAtIsNull(Long id);

    List<Device> findByOwnerIdAndDeletedAtIsNullOrderByCreatedAtDesc(Long ownerId);

    @Query("""
        select d
        from Device d
        where d.ownerId = :ownerId
          and d.deletedAt is null
        """)
    List<Device> findActiveDevicesForOwner(Long ownerId);
}
```

메서드 이름이 길어지는 단점은 있습니다. 하지만 이 길이는 의미 없는 장황함이 아니라 계약입니다. 호출하는
서비스가 "활성 행만 필요하다"는 사실을 코드 리뷰에서 바로 확인할 수 있습니다.

반대로 삭제된 행까지 봐야 하는 조회는 의도적으로 다른 이름을 붙입니다.

```java
interface DeviceAdminRepository {
    Optional<DeviceSnapshot> findIncludingDeletedById(Long id);

    List<DeviceSnapshot> findDeletedCandidatesForRestore(Long ownerId);
}
```

여기서 중요한 점은 `includingDeleted` 같은 이름을 숨기지 않는 것입니다. 이 이름이 보여야 운영 조회와
일반 업무 조회가 섞이지 않습니다.

## 업데이트 쿼리도 같은 계약을 가져야 합니다

소프트 삭제 조건은 조회에만 필요한 것이 아닙니다. 상태 종료, 소유자 변경, 마지막 사용 시각 갱신 같은
업데이트 쿼리에도 같은 조건이 필요합니다. 삭제된 행이 업데이트 대상에 섞이면 "보이지 않는 데이터"가
다시 활성 흐름에 영향을 줄 수 있습니다.

```java
@Modifying
@Query("""
    update DeviceSession s
       set s.endedAt = :endedAt
     where s.deviceId = :deviceId
       and s.endedAt is null
       and s.deletedAt is null
    """)
int closeActiveSession(Long deviceId, Instant endedAt);
```

이 코드는 조금 반복적입니다. 그래도 반복이 낫습니다. 업데이트 쿼리는 반환 엔티티가 없어서 전역 조회 제한을
기대하기 더 어렵고, 한 줄의 `deletedAt is null` 누락이 운영 데이터 변경으로 이어질 수 있습니다.

중복이 많아지면 Specification, Querydsl, 커스텀 저장소 같은 선택지도 있습니다. 다만 처음부터 추상화를
만드는 것보다, 실제로 반복되는 조회 모양이 보일 때 묶는 편이 안전했습니다.

## 복구와 감사 조회는 별도 모델로 둡니다

삭제된 행을 보는 기능이 모두 위험한 것은 아닙니다. 복구, 감사, 운영 확인에는 삭제 상태가 필요합니다.
문제는 이 조회가 일반 업무 엔티티를 그대로 반환할 때 생깁니다. 삭제된 행을 가져온 객체가 다시 일반
서비스로 흘러가면 계약이 흐려집니다.

그래서 삭제 포함 조회는 가능하면 별도 스냅샷 모델로 받는 편이 좋았습니다.

```java
public record DeviceSnapshot(
    Long id,
    Long ownerId,
    Instant createdAt,
    Instant deletedAt
) {
    boolean active() {
        return deletedAt == null;
    }
}
```

업무 서비스는 `Device`를 받고, 운영 화면은 `DeviceSnapshot`을 받습니다. 같은 테이블을 읽더라도 호출자가
무엇을 해도 되는지 달라집니다. 복구 API라면 `deletedAt`이 있는 스냅샷을 확인한 뒤 별도 명령으로 복구를
수행해야 합니다.

## 회귀 테스트는 빠진 조건을 잡아야 합니다

이번 유형의 변경은 테스트가 없으면 쉽게 되돌아갑니다. 특히 "삭제된 행이 일반 목록에 안 보인다"만
확인하면 부족합니다. 업데이트 대상, 연관 조회, 복구 조회까지 함께 봐야 합니다.

| 테스트 | 기대값 |
|---|---|
| 일반 상세 조회 | 삭제된 행은 `Optional.empty()`로 처리 |
| 일반 목록 조회 | 활성 행만 정렬되어 반환 |
| 세션 종료 업데이트 | 삭제된 세션은 업데이트하지 않음 |
| 연관 컬렉션 조회 | 삭제된 자식 행이 업무 화면에 섞이지 않음 |
| 복구 후보 조회 | 삭제된 행을 별도 스냅샷으로 반환 |
| 감사 조회 | 삭제 상태와 삭제 시각을 명시적으로 노출 |

JUnit 예시는 아래처럼 계약 이름을 그대로 드러내는 편이 좋습니다.

```java
@Test
void activeLookupDoesNotReturnSoftDeletedDevice() {
    Device deleted = repository.save(deviceWithDeletedAt(now()));

    Optional<Device> result = repository.findByIdAndDeletedAtIsNull(deleted.id());

    assertThat(result).isEmpty();
}

@Test
void closeActiveSessionDoesNotUpdateSoftDeletedSession() {
    DeviceSession deleted = sessionRepository.save(deletedOpenSession());

    int updated = sessionRepository.closeActiveSession(deleted.deviceId(), now());

    assertThat(updated).isZero();
    assertThat(sessionRepository.findIncludingDeletedById(deleted.id()).endedAt()).isNull();
}
```

테스트 이름이 장황해 보여도 괜찮습니다. 이 회귀의 핵심은 "삭제된 행이 조회되지 않는다"보다 "삭제된 행이
업무 업데이트 대상이 되지 않는다"에 가깝기 때문입니다.

## 언제 전역 제한을 그대로 둘 수 있나

전역 SQL 제한이 나쁜 선택이라는 뜻은 아닙니다. 조건이 정말 정적이고, 어떤 업무에서도 해당 행을 일반
엔티티로 다루면 안 된다면 유용합니다.

| 선택 | 적합한 상황 | 피해야 할 상황 |
|---|---|---|
| `@SQLRestriction` | 항상 같은 정적 조건으로 숨길 데이터 | 복구, 감사, 운영 조회가 자주 필요 |
| Hibernate `@Filter` | 런타임 파라미터로 조건을 켜고 끄는 조회 | 필터 활성화 누락이 치명적인 기본 업무 조회 |
| 저장소 메서드 조건 | 업무 조회 계약을 명시해야 하는 도메인 | 같은 조건이 수십 곳에서 무의미하게 반복 |
| 별도 스냅샷 조회 | 삭제 포함 조회를 운영 모델로 격리 | 도메인 엔티티 변경 로직을 그대로 재사용 |

이번 선택은 "어노테이션 대신 JPQL을 쓰자"가 아니었습니다. 기본 업무 흐름과 운영 예외 흐름을 코드에서
구분하자는 결정이었습니다. 전역 제한은 숨겨도 되는 규칙에 쓰고, 도메인 판단이 필요한 소프트 삭제는
저장소 계약으로 드러내는 편이 더 읽기 쉬웠습니다.

## 작은 실습: 저장소 메서드 점검표

소프트 삭제 엔티티가 있다면 저장소를 보며 아래 표를 채워 볼 수 있습니다.

| 질문 | 확인할 것 |
|---|---|
| 일반 조회 메서드에 삭제 조건이 보이는가 | `findBy...AndDeletedAtIsNull`, JPQL 조건 |
| 업데이트 쿼리에도 삭제 조건이 있는가 | `update`, `delete`, 벌크 상태 변경 |
| 삭제 포함 조회 이름이 분명한가 | `includingDeleted`, `deletedCandidates` |
| 삭제 포함 조회가 일반 엔티티를 그대로 반환하는가 | 가능하면 스냅샷 또는 운영 DTO 사용 |
| 테스트가 업데이트 대상까지 확인하는가 | 반환 행 수와 실제 DB 상태 확인 |
| 복구 API가 일반 저장 API를 우회하지 않는가 | 별도 복구 명령과 감사 로그 |

이 표가 비어 있으면 소프트 삭제는 매핑 설정으로만 남습니다. 반대로 저장소 API가 정책을 말하기 시작하면
서비스 코드는 조금 더 길어져도 운영 중 판단은 쉬워집니다.

## 오늘의 결론

소프트 삭제 조건을 전역 매핑에 숨기면 코드가 짧아집니다. 하지만 복구, 감사, 운영 조회가 생기는 순간
짧은 코드보다 명시적인 계약이 더 중요해집니다.

이번 정리의 방향은 간단했습니다. 일반 업무 조회는 활성 데이터만 본다고 저장소 이름과 JPQL에 적습니다.
삭제된 행을 보는 조회는 별도 이름과 모델을 둡니다. 업데이트 쿼리에도 같은 조건을 넣고, 테스트는 삭제된
행이 조회뿐 아니라 변경 대상에서도 빠지는지 확인합니다. 소프트 삭제는 컬럼 하나의 문제가 아니라,
도메인이 어떤 데이터를 현재 상태로 인정하는지에 대한 조회 계약이었습니다.
