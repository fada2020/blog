## 이번 주 개념

[지난 글](/blog/posts/flutter-list-key-identity-2026-11-10/)에서는 Key로 목록 항목의 상태를 유지했습니다.
이번에는 상태를 유지한 채 **부모가 다른 입력 객체를 전달할 때 구독도 교체해야 한다**는 경계를 다룹니다.
처음 연결한 객체를 계속 듣고 있으면 새 값이 화면에 도착하지 않거나 이전 객체의 알림이 남을 수 있습니다.

## Java와 Spring에서는 어떻게 다뤘는가

서버 요청마다 DTO를 새로 받는 Controller와 달리, Flutter State는 여러 build에 걸쳐 살아 있습니다.
Spring singleton에 이벤트 리스너를 등록한 뒤 이벤트 공급자를 교체한다고 생각하면 구독 수명 문제가 보입니다.
새 객체를 필드에 넣는 것과 이전 리스너를 해제하는 것은 별개 작업입니다.
`initState`를 요청마다 실행되는 메서드처럼 이해하면 부모 입력 변경을 놓칩니다.

| 익숙한 문제 | Flutter의 대응 |
|---|---|
| 최초 의존 객체 연결 | initState에서 구독 |
| 실행 중 공급자 변경 | didUpdateWidget에서 비교·재연결 |
| 소비자 종료 | dispose에서 구독 해제 |

## Flutter에서는 무엇이 다른가

같은 위치의 새 위젯이 타입과 Key를 유지하면 기존 State에 새 설정이 전달됩니다.
[공식 생명주기 문서](https://api.flutter.dev/flutter/widgets/State/didUpdateWidget.html)는 이때
`didUpdateWidget`을 사용하고 이후 build가 호출된다고 설명합니다. 이 메서드 안에서 새 입력을 반영하려고
다시 setState를 호출할 필요는 없습니다. 반면 비동기 알림 콜백은 화면 갱신을 요청해야 합니다.

## 최소 실행 예제

빈 Flutter 앱의 lib/main.dart를 다음으로 바꿉니다. 외부 패키지는 필요 없습니다.
학습을 위해 구독을 직접 관리하며, 값 하나를 표시하는 실제 화면에서는
[ValueListenableBuilder](https://api.flutter.dev/flutter/widgets/ValueListenableBuilder-class.html)로 단순화할 수 있습니다.
직접 정의한 변수는 스네이크케이스를 사용하고 프레임워크 override 이름은 유지했습니다.

```dart
import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: CounterPage()));

class CounterPage extends StatefulWidget {
  const CounterPage({super.key});
  @override
  State<CounterPage> createState() => _CounterPageState();
}

class _CounterPageState extends State<CounterPage> {
  final _first_counter = ValueNotifier<int>(1);
  final _second_counter = ValueNotifier<int>(10);
  bool _use_second = false;

  @override
  void dispose() {
    _first_counter.dispose();
    _second_counter.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(title: const Text('구독 교체 실습')),
    body: Column(children: [
      ElevatedButton(
        onPressed: () => setState(() => _use_second = !_use_second),
        child: const Text('입력 교체'),
      ),
      ElevatedButton(
        onPressed: () => _first_counter.value++,
        child: const Text('첫 값 증가'),
      ),
      ElevatedButton(
        onPressed: () => _second_counter.value++,
        child: const Text('둘째 값 증가'),
      ),
      CounterView(counter: _use_second ? _second_counter : _first_counter),
    ]),
  );
}

class CounterView extends StatefulWidget {
  const CounterView({super.key, required this.counter});
  final ValueNotifier<int> counter;
  @override
  State<CounterView> createState() => _CounterViewState();
}

class _CounterViewState extends State<CounterView> {
  void _on_change() => setState(() {});

  @override
  void initState() {
    super.initState();
    widget.counter.addListener(_on_change);
  }

  @override
  void didUpdateWidget(covariant CounterView old_widget) {
    super.didUpdateWidget(old_widget);
    if (!identical(old_widget.counter, widget.counter)) {
      old_widget.counter.removeListener(_on_change);
      widget.counter.addListener(_on_change);
    }
  }

  @override
  void dispose() {
    widget.counter.removeListener(_on_change);
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => Text('값: ${widget.counter.value}');
}
```

처음에는 `값: 1`입니다. 입력 교체를 누르면 같은 CounterView State가 두 번째 객체를 받아 `값: 10`을 표시합니다.
그 후 첫 값 증가를 눌러도 표시값은 10이고, 둘째 값 증가를 누르면 11이 됩니다.
다시 교체하면 첫 객체에서 증가해 있던 2를 표시합니다. 요청·응답·상태 코드·시간 형식·DB 저장값은 변경 없음입니다.

## 소유권과 구독권은 다릅니다

CounterView는 전달받은 객체의 **리스너만** 해제합니다. 객체를 만든 부모가 두 notifier를 dispose합니다.
자식이 주입받은 notifier 자체를 종료하면 다른 소비자까지 사용할 수 없게 됩니다.
반대로 리스너를 해제하지 않으면 화면을 제거한 뒤 알림에서 종료된 State를 갱신하려 할 수 있습니다.

객체 교체 여부는 값의 같음이 아닌 참조로 비교했습니다. 서로 다른 notifier가 둘 다 10을 담아도 구독 대상은 다릅니다.
새 Key를 강제로 만들어 State 전체를 재생성하면 구독도 초기화되지만 다른 입력 상태까지 사라집니다.
이번 요구는 화면 수명을 유지하면서 의존 객체 하나만 바꾸는 것입니다.

InheritedWidget을 통해 의존성을 얻는 경우에는 didChangeDependencies도 검토해야 합니다.
Stream 구독은 cancellation이 Future를 반환할 수 있으므로 이 동기 notifier 예제를 그대로 복제하지 말고
취소 중 도착하는 이벤트와 자원 정리 순서를 별도로 설계해야 합니다.

## 연습과 검증

1. 객체 교체 후 이전 객체를 변경했을 때 화면이 갱신되지 않는지 확인합니다.
2. 새 객체의 알림은 화면에 도착하는지, 같은 객체로 부모만 rebuild해도 리스너가 중복되지 않는지 확인합니다.
3. 자식을 제거한 뒤 부모가 가진 notifier에 알림을 보내도 예외가 없는지 확인합니다.
4. ValueListenableBuilder로 바꾸고 소유자의 dispose 책임이 어떻게 남는지 설명합니다.

독립 프로젝트에서 정적 분석과 widget 테스트로 구독 교체·같은 입력 재전달·화면 제거 후 알림을 확인했습니다.
실제 Android/iOS 기기, Stream 취소 경합, 성능 측정은 이번 검증 범위에 포함하지 않았습니다.
