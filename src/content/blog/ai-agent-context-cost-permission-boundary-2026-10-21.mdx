> Mistral Managed Deployments는 10월 9일 **Public Preview**여서 stable 비교표에는 넣지 않았습니다.

## 결론부터 말하면

이번 주 agent 운영의 핵심은 더 큰 모델 하나를 고르는 일이 아니라, **오래 들고 갈 문맥**, **빨리 끝낼 하위 작업**,
**실행을 허용할 권한**을 서로 다른 계약으로 분리하는 일입니다.

Spring Boot 팀이 요청 처리, 비동기 worker, privileged admin job을 한 transaction으로 섞지 않듯이 agent도 같은 대화에
모든 코드베이스·비밀·브라우저 권한을 넣어서는 안 됩니다. context는 재사용 단위, worker는 비용·지연 단위, sandbox는
권한·감사 단위로 나누어야 운영 가능한 시스템이 됩니다.

## 1. 긴 문맥은 cache가 아니라 제품 계약이다

10월 20일 OpenAI changelog는 shared instructions, tools, context를 더 오래 재사용하는 12시간 prompt cache를
추가했습니다. 이것은 모든 프롬프트를 길게 만들라는 뜻이 아닙니다. cache write 비용과 문맥 오염 비용을 같이 계산해야 합니다.

재사용 가치가 높은 것은 다음처럼 비교적 안정적인 입력입니다.

- repo 규칙, 코드 스타일, 승인 정책
- tool schema와 오류 복구 규칙
- 충분히 검토된 도메인 용어집

반대로 incident 세부 정보, 일회성 접근 토큰, 고객 식별 데이터, 현재 배포 상태는 cache에 오래 둘 기본값이 아닙니다.
Spring의 application configuration과 request-scoped data를 나누듯, **변경 주기와 민감도**로 context를 나눕니다.

## 2. 빠른 worker에는 좁은 입력과 측정값을 준다

Anthropic은 Haiku 5.5를 고볼륨·비용 민감 작업과 coding subagent 용도로 설명했습니다. 여기서 얻을 교훈은
"저렴한 모델로 전부 바꾸기"가 아닙니다. 주 agent가 문제를 분해하고, worker가 명확한 입력·출력 계약으로
분류, 로그 요약, 파일 후보 추출, 제한된 test triage를 처리하게 만드는 것입니다.

```text
주 agent: 변경 계획 + 위험 등급 + 필요한 증거를 결정
worker: diff에서 migration 파일 여부와 테스트 실패 범주만 JSON으로 반환
주 agent: JSON과 원문 증거를 대조한 뒤 승인 요청 또는 다음 도구 호출
```

worker 평가에는 정답률만 두지 마세요. timeout 비율, 입력 token, 재시도, 잘못된 "안전" 판정, 사람 검토가 뒤집은 비율을
같이 남겨야 routing이 가격표가 아니라 운영 선택이 됩니다.

## 3. sandbox는 모델 품질과 별개의 보안 경계다

OpenAI는 Agents API hosted sandbox에 Artifact SDK와 spreadsheet·presentation·document skills를 포함했고,
ultrafast mode도 지원 모델에 제공한다고 발표했습니다. 빠르게 결과가 나온다는 사실은 외부 쓰기를 자동 승인할 근거가 아닙니다.

실무에서는 sandbox마다 다음을 고정합니다.

| 구분 | 읽기 작업 | 준비 작업 | 외부 쓰기 |
|---|---|---|---|
| 권한 | 최소 repo/data read | 임시 파일·test 실행 | 별도 capability |
| 네트워크 | allowlist 또는 차단 | 목적지 제한 | 대상·payload 확인 |
| 결과 | 인용·근거 링크 | diff·artifact·test log | 승인자·감사 이벤트 |
| rollback | 해당 없음 | workspace 삭제 가능 | 재시도/취소 절차 |

권한 token을 prompt 안에 넣지 말고 실행 환경의 scoped credential로 전달합니다. agent가 도구를 호출할 수 있다는 것과
그 결과를 외부로 반영해도 된다는 것을 분리하는 것이 핵심입니다.

## 4. persistent context에는 만료와 가시성이 필요하다

Google의 Gemini agent 발표은 skills, connectors, persistent execution, authorization controls, spend caps를 함께
제시했습니다. 장기 실행 agent일수록 편리하지만, 기억이 자동으로 신뢰 가능한 사실 저장소가 되는 것은 아닙니다.

따라서 memory에는 source, 작성자 역할, 생성 시각, TTL, sensitivity를 둡니다. 배포 상태나 가격처럼 빨리 변하는 값은
매 작업에서 원본을 재조회합니다. 사용자가 "왜 이 권한이 필요한가"와 "무엇이 아직 기억되는가"를 확인하고 철회할 경로도
제공합니다.

## Spring Boot 팀의 최소 운영 템플릿

```yaml
agentRun:
  objective: "release note draft"
  context:
    sources: ["docs/release-policy.md"]
    ttl: "24h"
    sensitive: false
  workers:
    - name: "diff-classifier"
      input: "git diff --name-status only"
      budget: { timeoutSeconds: 30, maxAttempts: 1 }
  sandbox:
    network: "deny-by-default"
    writablePaths: ["/workspace/out"]
  approval:
    requiredFor: ["push", "publish", "production-write"]
  observability:
    record: ["model", "route", "tokens", "toolCalls", "approvalId"]
```

이 YAML은 특정 vendor API가 아니라 team contract의 예시입니다. 실제 schema는 tool provider에 맞춰 바꾸되,
**객체별 권한·비용·만료·승인**이 리뷰 가능한 설정으로 남는다는 원칙은 유지합니다.
