## 이번 주 개념

목록 안에 항목이 생기는 것과 화면에 변경 알림이 전달되는 것은 별개입니다. 이번에는 작은 화면 상태를
`ValueNotifier`에 담고 **새 목록 대입 → 알림 → 필요한 화면 갱신**의 경계를 실습합니다.
[지난 학습](/blog/posts/flutter-futurebuilder-parameter-lifecycle-2026-11-04/)은 조회 Future의 수명을 다뤘습니다.
이번 예제는 서버 조회 없이 메모리 안의 목록만 바꾸므로 비동기 요청 순서 문제와도 구분합니다.

## Java와 Spring에서는 어떻게 다뤘는가

Java에서 `ArrayList.add()`를 호출하면 객체 내부는 달라집니다. 그렇다고 그 객체를 읽던 모든 소비자에게
이벤트가 자동 발행되지는 않습니다. Spring의 이벤트 발행도 명시적인 호출과 수신 경로가 필요합니다.
JPA dirty checking은 영속성 컨텍스트가 관리하는 별도 메커니즘이므로 Flutter 화면 갱신에 그대로 대응하지 않습니다.

| 익숙한 개념 | 이번 화면의 경계 |
|---|---|
| 컬렉션의 내부 수정 | Dart List의 add |
| 변경을 소비자에게 전달 | notifier의 알림 |
| 응답을 다시 구성 | builder의 Widget 생성 |

## Flutter에서는 무엇이 다른가

[공식 ValueNotifier 문서](https://api.flutter.dev/flutter/foundation/ValueNotifier-class.html)는
새 값과 이전 값을 `==`로 비교해 다를 때 알린다고 설명합니다. 일반 Dart List의 기본 비교는 원소별 비교가
아니므로 같은 인스턴스를 수정해 다시 대입해도 알림이 없습니다. 반대로 원소가 같은 새 List는 알릴 수 있습니다.
커스텀 값 타입에서 `==`를 재정의했다면 그 타입의 동등성 정책을 따라갑니다.

변경 전에는 `items.value.add('a')`로 값만 바꾸고 알림을 기대했습니다. 변경 후에는 이전 값을 펼쳐 새 목록을
만들어 대입합니다. 이 예제의 `List.unmodifiable`은 바깥 목록 수정을 막습니다. 목록 원소가 가변 객체라면
그 내부까지 깊게 불변으로 바꾸는 기능은 아닙니다.

## 최소 실행 예제

빈 Flutter 앱의 `lib/main.dart`에 넣습니다. 별도 패키지나 서버는 없습니다.
직접 정의한 함수와 변수는 스네이크케이스를 사용하며 프레임워크 override 이름은 유지합니다.

```dart
import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: ItemsPage()));

class ItemsPage extends StatefulWidget {
  const ItemsPage({super.key});
  @override
  State<ItemsPage> createState() => _ItemsPageState();
}

class _ItemsPageState extends State<ItemsPage> {
  final _items = ValueNotifier<List<String>>(const []);

  void _add_item() {
    _items.value = List.unmodifiable([
      ..._items.value,
      '항목 ${_items.value.length + 1}',
    ]);
  }

  @override
  void dispose() {
    _items.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(title: const Text('목록 알림 실습')),
    body: Column(children: [
      ElevatedButton(onPressed: _add_item, child: const Text('추가')),
      ValueListenableBuilder<List<String>>(
        valueListenable: _items,
        child: const Text('선택한 목록'),
        builder: (context, items, child) => Column(children: [
          child!,
          Text('개수 ${items.length}'),
          for (final item in items) Text(item),
        ]),
      ),
    ]),
  );
}
```

State가 notifier를 생성하고 해제합니다. 자식 builder가 외부에서 받은 notifier를 임의로 dispose하지 않습니다.
실제 앱에서 공유 소유자가 따로 있다면 소유자의 수명에 맞춰 해제해야 합니다.
[ValueListenableBuilder](https://api.flutter.dev/flutter/widgets/ValueListenableBuilder-class.html)는
리스너 등록을 관리하고 현재 값을 builder에 전달합니다. 값과 무관한 `child`를 전달하면 같은 하위 위젯을
재사용할 수 있지만, 이것만으로 앱 전체 성능이 빨라졌다고 주장할 수는 없습니다. 실제 병목은 프로파일링해야 합니다.

## 동작 예시와 오해

| 대입 또는 조작 | 알림 수 | 주의할 점 |
|---|---|---|
| 기존 목록에 add | 0 | 값은 바뀌어도 화면 알림 없음 |
| 같은 목록 재대입 | 0 | 내부 변경 감지 기능이 아님 |
| 새 목록 대입 | 1 | 내용이 같아도 알림 가능 |

처음 화면은 `개수 0`입니다. 추가 버튼 뒤에는 `개수 1`과 `항목 1`이 보입니다.
이것은 공개용 독립 샘플이며 API 요청·응답·상태 코드·시간 형식·DB 저장값 변경은 없습니다.

알림이 없던 내부 수정도 다른 이유로 화면이 다시 빌드되면 드러날 수 있습니다. 따라서 “나중에 화면에 보였다”는
관찰만으로 알림이 정상이라고 결론 내리면 안 됩니다. 알림 횟수와 화면 결과를 나눠 확인해야 합니다.
또 notifier를 build 안에서 매번 만들면 소유 수명이 불명확해집니다. 공유 전역 변수로 바꾸는 것도 해제 책임을
해결하지는 않습니다. 목록 상태가 작다는 이유만으로 화면 전체의 도메인 상태를 하나에 몰아넣지 않습니다.

## 연습과 검증 범위

1. 새 목록 대입을 기존 목록의 add로 바꾸고 화면이 언제 바뀌는지 관찰합니다.
2. 같은 원소를 가진 새 목록을 대입하고 알림 횟수를 셉니다.
3. 삭제 동작도 새 목록을 만드는 방식으로 구현합니다.
4. 목록 원소를 가변 객체로 바꾸고 바깥 목록 불변성과 원소 불변성의 차이를 설명합니다.

독립 임시 프로젝트에서 정적 분석은 진단 없이 통과했고 테스트 3개를 통과했습니다.
내부 수정·동일 참조 재대입의 무알림, 새 목록 대입의 알림과 수정 금지, 같은 내용의 새 목록 알림,
버튼 뒤 화면 변경 및 화면 해제를 확인했습니다. 기준 안정판 3.47.9 자체와 실제 모바일 기기 성능은 실행 검증하지 않았습니다.
