## 결론부터 말하면

Next.js App Router에서 URL은 설정 파일보다 `app` 디렉터리의 폴더 구조로 결정됩니다.
Spring Boot 개발자에게는 `@GetMapping("/admin/users/{id}")`로 경로를 선언하던 습관과
가장 크게 다른 지점입니다.

다만 폴더가 보인다고 모두 공개 URL이 되는 것은 아닙니다. `page.tsx`가 있어야 화면
라우트가 공개되고, `route.ts`가 있어야 API 엔드포인트가 공개됩니다. `layout.tsx`는
URL을 만들지 않고 같은 세그먼트 아래의 화면을 감싸는 공통 UI를 담당합니다.

이번 글에서는 작은 관리자 화면을 예로 들어 정적 경로, 동적 세그먼트, 중첩 layout을
Spring MVC와 비교해 보겠습니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring MVC에서는 URL과 실행 코드를 어노테이션으로 연결합니다.

```java
@Controller
@RequestMapping("/admin/users")
class AdminUserController {

    @GetMapping
    String list(Model model) {
        model.addAttribute("users", userService.findUsers());
        return "admin/users/list";
    }

    @GetMapping("/{userId}")
    String detail(@PathVariable Long userId, Model model) {
        model.addAttribute("user", userService.findUser(userId));
        return "admin/users/detail";
    }
}
```

여기서는 패키지 구조가 URL을 만들지 않습니다. `com.example.admin.user` 같은 패키지는
정리 방식일 뿐이고, 실제 라우팅 계약은 `@RequestMapping`, `@GetMapping`,
`@PathVariable`에 있습니다.

반대로 Next.js App Router에서는 폴더와 예약 파일 이름이 라우팅 계약입니다.

```text
app/
├── layout.tsx
└── admin/
    ├── layout.tsx
    └── users/
        ├── page.tsx
        └── [userId]/
            └── page.tsx
```

이 구조에서 만들어지는 공개 화면은 `/admin/users`와 `/admin/users/123`입니다.
`app/admin/layout.tsx`는 URL을 추가하지 않고 두 화면의 공통 골격을 감쌉니다.

## App Router에서 무엇이 다른가

App Router의 핵심은 폴더를 URL 세그먼트로 읽는다는 점입니다.

| App Router 파일 | 공개 URL | Spring MVC에서 가까운 개념 |
|---|---|---|
| `app/page.tsx` | `/` | `@GetMapping("/")`로 반환하는 화면 |
| `app/admin/users/page.tsx` | `/admin/users` | `@GetMapping("/admin/users")` |
| `app/admin/users/[userId]/page.tsx` | `/admin/users/{userId}` | `@PathVariable userId` |
| `app/admin/layout.tsx` | 없음 | 관리자 화면 공통 레이아웃 |
| `app/api/health/route.ts` | `/api/health` | `@RestController`의 작은 API |

중요한 차이는 `layout.tsx`입니다. Spring MVC에서 공통 네비게이션은 보통 Thymeleaf
fragment, JSP include, React SPA layout, 또는 별도 템플릿 계층에서 처리했습니다.
Next.js App Router에서는 공통 UI가 라우트 트리 안에 들어가고, 하위 페이지를
`children`으로 감쌉니다.

## 최소 실행 예제

새 App Router 프로젝트에서 아래처럼 폴더를 만듭니다.

```text
app/
├── layout.tsx
└── admin/
    ├── layout.tsx
    └── users/
        ├── page.tsx
        └── [userId]/
            └── page.tsx
```

루트 layout은 필수입니다. 공식 문서 기준으로 `app` 디렉터리의 최상위 root layout은
`html`과 `body` 태그를 포함해야 합니다.

```tsx
// app/layout.tsx
export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="ko">
      <body>{children}</body>
    </html>
  )
}
```

관리자 영역 layout은 URL을 만들지 않고 하위 화면을 감쌉니다.

```tsx
// app/admin/layout.tsx
export default function AdminLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <section>
      <nav>
        <a href="/admin/users">사용자</a>
        <a href="/admin/audit-logs">감사 로그</a>
      </nav>
      <main>{children}</main>
    </section>
  )
}
```

목록 페이지는 `/admin/users`에 대응합니다.

```tsx
// app/admin/users/page.tsx
type UserSummary = {
  id: string
  name: string
  role: string
}

async function getUsers(): Promise<UserSummary[]> {
  const response = await fetch(`${process.env.API_BASE_URL}/api/users`, {
    cache: 'no-store',
  })

  if (!response.ok) {
    throw new Error(`사용자 목록 조회 실패: ${response.status}`)
  }

  return response.json()
}

export default async function UsersPage() {
  const users = await getUsers()

  return (
    <>
      <h1>사용자</h1>
      <ul>
        {users.map((user) => (
          <li key={user.id}>
            <a href={`/admin/users/${user.id}`}>
              {user.name} · {user.role}
            </a>
          </li>
        ))}
      </ul>
    </>
  )
}
```

상세 페이지는 `[userId]` 폴더로 동적 세그먼트를 받습니다.

```tsx
// app/admin/users/[userId]/page.tsx
type UserDetail = {
  id: string
  name: string
  role: string
  lastLoginAt: string | null
}

async function getUser(userId: string): Promise<UserDetail> {
  const response = await fetch(
    `${process.env.API_BASE_URL}/api/users/${userId}`,
    { cache: 'no-store' },
  )

  if (!response.ok) {
    throw new Error(`사용자 상세 조회 실패: ${response.status}`)
  }

  return response.json()
}

export default async function UserDetailPage({
  params,
}: {
  params: Promise<{ userId: string }>
}) {
  const { userId } = await params
  const user = await getUser(userId)

  return (
    <article>
      <h1>{user.name}</h1>
      <dl>
        <dt>권한</dt>
        <dd>{user.role}</dd>
        <dt>최근 로그인</dt>
        <dd>{user.lastLoginAt ?? '기록 없음'}</dd>
      </dl>
    </article>
  )
}
```

Next.js 16 기준으로 `params`는 Promise로 전달됩니다. Spring의 `@PathVariable Long userId`
처럼 이미 원하는 타입으로 변환된 값이라고 생각하면 안 됩니다. URL에서 온 값이므로 먼저
문자열로 받고, 필요하면 런타임 검증을 거쳐 도메인 타입으로 좁히는 편이 안전합니다.

## 대응 개념 비교

| 질문 | Spring MVC | Next.js App Router |
|---|---|---|
| URL은 어디서 정의되는가 | 어노테이션 | `app` 폴더와 `page.tsx` |
| 경로 변수는 어떻게 받는가 | `@PathVariable` | `[segment]`와 `params` |
| 공통 화면 골격은 어디에 두는가 | 템플릿, fragment, SPA layout | `layout.tsx` |
| 라우트가 공개되는 조건은 무엇인가 | Controller handler 등록 | `page.tsx` 또는 `route.ts` 존재 |
| 공통 layout은 매 이동마다 다시 그려지는가 | 템플릿 렌더링 방식에 따라 다름 | 같은 layout 경계 안에서는 상태를 보존하고 재사용 |

`layout.tsx`는 Spring의 Filter나 Interceptor와 다릅니다. 요청을 가로채서 권한을 판정하는
계층이 아니라, 하위 페이지를 감싸는 UI 계층입니다. 인증이나 권한의 최종 판단은 Spring
Security와 API에서 유지하고, Next.js에서는 화면 접근 흐름과 사용자 경험을 보조하는
식으로 책임을 나누는 편이 명확합니다.

## route group은 URL 정리가 아니라 코드 정리입니다

폴더명을 괄호로 감싸면 route group이 됩니다.

```text
app/
├── (public)/
│   └── login/
│       └── page.tsx        # /login
└── (admin)/
    ├── layout.tsx
    └── admin/
        └── users/
            └── page.tsx    # /admin/users
```

`(public)`과 `(admin)`은 URL에 포함되지 않습니다. 팀, 관심사, layout 경계를 정리하기
위한 폴더입니다. 공식 문서의 주의점처럼 서로 다른 route group 안의 파일이 같은 URL로
해석되면 충돌이 납니다. 예를 들어 `(public)/about/page.tsx`와
`(admin)/about/page.tsx`는 둘 다 `/about`이므로 함께 둘 수 없습니다.

여러 root layout을 만들 수도 있지만, 서로 다른 root layout 사이로 이동하면 클라이언트
사이드 전환이 아니라 전체 페이지 로드가 발생합니다. 관리자 화면처럼 완전히 다른 UI
경험을 분리할 때만 의식적으로 선택하는 편이 좋습니다.

## Java 개발자가 자주 하는 오해

### 폴더를 만들면 바로 URL이 열린다

`app/admin/users/_components/UserRow.tsx` 같은 파일은 공개 URL이 아닙니다. App Router에서
라우트가 공개되려면 해당 세그먼트에 `page.tsx`나 `route.ts`가 있어야 합니다. 컴포넌트와
유틸 파일을 같은 세그먼트 근처에 둘 수 있지만, 팀 규칙을 위해 `_components`,
`_lib`처럼 private folder를 쓰면 의도가 더 분명해집니다.

### layout에 현재 URL과 query를 직접 넣으면 된다

공식 문서 기준으로 layout은 내비게이션 중 재사용될 수 있어 최신 pathname이나 query
param을 직접 읽는 장소로 적합하지 않습니다. 현재 URL에 따라 바뀌는 breadcrumb나 검색어는
page의 `searchParams` 또는 Client Component의 `usePathname`, `useSearchParams`로 처리하는
편이 맞습니다.

### `[userId]`는 숫자 타입이다

URL 세그먼트는 문자열입니다. 숫자 ID라면 `Number(userId)` 후 `Number.isInteger` 같은
검증을 거쳐야 합니다. Spring MVC의 converter와 validation이 해 주던 부분을 Next.js
화면 코드에서도 명시해야 합니다.

### Next.js route handler가 Spring API를 대체한다

`route.ts`로 API를 만들 수는 있지만, 기존 Spring Boot가 도메인 규칙과 트랜잭션의
소유자라면 화면용 BFF나 가벼운 프록시 정도로만 제한하는 것이 단순합니다. 업무 규칙을
두 군데로 나누면 권한, 검증, 감사 로그가 어긋나기 쉽습니다.

## 직접 해볼 연습

1. `create-next-app@latest`로 App Router 프로젝트를 만듭니다.
2. `/admin/users` 목록 페이지와 `/admin/users/[userId]` 상세 페이지를 추가합니다.
3. `app/admin/layout.tsx`에 공통 navigation을 넣고 두 페이지에서 재사용되는지 확인합니다.
4. `[userId]` 값이 숫자가 아니면 `notFound()`를 호출하도록 런타임 검증을 추가합니다.
5. `app/(admin)/admin/users/page.tsx`로 route group을 적용해 URL이 그대로인지 확인합니다.
6. 같은 `/about`을 만드는 route group 두 개를 일부러 만들어 충돌 에러가 나는지 확인합니다.
