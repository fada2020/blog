## 이번 주에는 변경을 실행하고 확인하는 기반을 봅니다

에이전트에 전달할 작업 절차가 표준으로 이동하고, 런타임의 DNS·TLS 경계는 보안 패치 대상이 됐습니다.
브라우저에서는 화면의 근거를 더 세밀하게 확인할 수 있게 됐고, 데이터베이스 패키지에서는 설치 가능 여부와
계속 업데이트되는지가 갈라졌습니다. Spring Boot 팀도 JVM만 확인해서는 이 변화가 보이지 않습니다.
CI 스크립트, 프런트엔드 빌드, 운영 이미지와 브라우저 확인 도구까지 함께 보는 편이 유용합니다.

## 1. Agent Skills가 AAIF로 이동했습니다

Anthropic은 10월 22일 [Agent Skills를 Agentic AI Foundation으로 기부한다고 발표](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation)했습니다.
이는 새 모델의 정식 출시가 아니라 작업 절차를 담는 공개 표준의 거버넌스 변경입니다. 스킬은 `SKILL.md`와
필요한 스크립트·참고자료를 담는 폴더 형태입니다. 발표는 여러 에이전트 플랫폼의 채택도 설명합니다.

실무에서는 반복되는 리뷰나 릴리스 절차를 특정 채팅의 긴 지시문에만 두지 않고 버전 관리할 수 있다는 점이
유용합니다. 다만 문서 형식이 같아졌다고 플랫폼별 도구, 권한, 실행 결과까지 같아지는 것은 아닙니다.

Spring의 인터페이스를 공유해도 구현체와 트랜잭션 경계가 저절로 같아지지 않는 것과 비슷합니다. 팀 스킬에는
입력, 완료 조건, 실패 시 멈출 지점과 외부 쓰기 권한을 구분해 적겠습니다. 다른 환경으로 옮길 때는 실제 도구 호출과
결과를 작은 샘플로 확인하는 편이 안전합니다. 이것은 표준 이관 발표에서 도출한 운영상의 판단입니다.

## 2. Node.js 보안 패치는 CI의 런타임까지 확인해야 합니다

[10월 21일 공식 보안 공지](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)는
26.x·24.x·22.x 라인의 패치를 안내합니다. DNS의 NUL 처리, 비정규 IP 표현의 TLS 인증서 검증,
Brotli 처리 등을 포함합니다. 각 취약점의 영향 범위가 다르므로 공지의 해당 라인을 확인해야 합니다.

[26.12.1 릴리스 노트](https://nodejs.org/en/blog/release/v26.12.1/)는 이를 **Current 보안 릴리스**로 명시합니다.
Current를 LTS로 바꿔 부르거나, 기존 LTS 사용자가 무조건 26으로 올려야 한다고 해석하지 않겠습니다.
선택한 지원 라인의 수정 버전을 적용하고 아래 위치의 실제 바이너리를 확인하는 것이 먼저입니다.

```bash
node --version
node -p 'process.execPath'
node -p 'JSON.stringify(process.versions)'
```

Spring Boot API가 직접 Node.js로 실행되지 않더라도 프런트엔드 빌드, 문서 생성, CI action 또는 보조 도구에는
별도 런타임이 있을 수 있습니다. 패키지 잠금 파일만 바꿔서는 실행 이미지가 바뀌었다는 증거가 되지 않습니다.
점검표에는 의존성 파일과 함께 로컬·CI·컨테이너의 런타임 버전을 각각 기록하겠습니다.

## 3. Chrome DevTools는 화면 검증 근거를 더 세밀하게 제공합니다

Google은 10월 20일 [New in DevTools - November 2026](https://developer.chrome.com/blog/new-in-devtools-november-2026/)을 공개했습니다.
문서 제목의 월과 게시일이 다르므로 게시일을 기준으로 선정했습니다. 공식 글은 Chrome 155·156의 stable 배포를
설명하며, agent용 CSS 스타일 조회, anchor positioning 편집, Network와 Memory 진단 개선을 소개합니다.

특히 CSS를 고친 에이전트가 계산된 스타일과 적용 규칙을 확인할 수 있다는 점이 눈에 띕니다. 사람이 DevTools에서
보던 화면의 근거를 자동 작업에도 연결할 수 있기 때문입니다. 다만 도구 기능 소개만으로 모든 브라우저의 CSS 지원을
보장하지는 않습니다. 사용 중인 Chrome과 agent 도구의 버전도 각각 확인해야 합니다.

Spring Boot 팀이 관리 콘솔의 겹친 버튼을 수정한다면, 코드 diff에 더해 좁은 화면의 스크린샷, 실제 크기와 초점 이동을
함께 확인하는 식으로 활용할 수 있습니다. 네트워크 응답 성공과 사용자가 버튼을 누를 수 있다는 사실도 구분하겠습니다.
이 활용 예시는 공식 발표의 기능을 바탕으로 구성한 독립적인 예입니다.

## 4. PostgreSQL RPM 저장소 종료는 DB 엔진 종료와 다릅니다

PGDG는 10월 20일 [RHEL 10.0·9.6용 저장소를 archive로 이동한다고 공지](https://www.postgresql.org/about/news/rhel-100-and-96-repositories-are-being-retired-3411/)했습니다.
해당 minor 버전용 패키지 경로의 변경이며 PostgreSQL 전체의 지원 종료가 아닙니다. 공식 공지는 rolling EL-10·EL-9
저장소 RPM은 영향받지 않고, 옮겨진 저장소에는 더 이상 업데이트가 제공되지 않는다고 구분합니다.

RHEL 계열 운영 이미지라면 OS 이름만 적지 말고 minor 버전과 활성 repo를 함께 확인하겠습니다. 지금 설치가 성공해도
다음 보안 업데이트를 받을 수 있는지는 다른 질문입니다. archive 경로를 고정하면 설치 재현에는 도움이 될 수 있지만,
계속 관리되는 경로로 옮길 계획을 대신하지는 못합니다.

```bash
cat /etc/os-release
dnf repolist --enabled
```

이 명령은 상태 확인용입니다. 운영 서버에서 즉시 OS나 DB를 변경하는 절차가 아닙니다. 실제 전환에는 확장 모듈,
백업 복구와 재시작 검증이 필요합니다. PostgreSQL 19의 RC 표시는 stable로 취급하지 않았으며, 이 발표를 최신 DB
메이저 버전으로의 즉시 이전 근거로 사용하지도 않았습니다.

실제 배포도 나누어 보겠습니다. 제외는 중요하지 않다는 뜻이 아니라 이번 글의 기간·검증·편집 범위에 따른 선택입니다.

## 이번 주 실행 순서

1. Node.js를 쓰는 위치와 선택한 지원 라인의 보안 패치를 확인합니다.
2. RHEL 계열 PostgreSQL 서버의 minor 버전과 repo 경로를 조사합니다.
3. 반복 작업 하나를 스킬로 정리하되 완료 조건과 실행 권한을 명시합니다.
4. 화면 수정 하나에 실제 브라우저 근거를 남기는 실험을 합니다.

새 도구 도입과 기존 환경의 보안 유지가 함께 필요했던 한 주였습니다. 모든 것을 한꺼번에 교체하기보다,
현재 실행되는 버전과 확인 가능한 결과를 먼저 기록하겠습니다.
