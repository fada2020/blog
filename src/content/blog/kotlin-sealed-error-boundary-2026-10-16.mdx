## 결론부터 말하면

오류의 **의미**는 domain 안에서 `sealed interface`로 작고 닫힌 집합으로 표현하고, HTTP 상태 코드와
문제 응답은 controller advice 같은 **바깥 경계**에서 결정하는 편이 안전합니다. 그러면 새 오류 종류를
추가했을 때 `when`이 빠진 분기를 컴파일 단계에 드러내고, JPA·HTTP 클라이언트·프레임워크 예외가
비즈니스 규칙을 오염시키는 일을 줄일 수 있습니다.

다만 모든 예외를 sealed 값으로 바꾸라는 뜻은 아닙니다. 프로그래밍 오류, 손상된 불변식, 취소 신호는
억지로 `Result`나 `ApiError`로 포장하지 않습니다. 특히 coroutine의 `CancellationException`은 요청이
사라졌다는 lifecycle 신호이므로 다시 전파해야 합니다.

- domain 오류는 호출자가 처리 가능한 사실로 모델링합니다.
- HTTP `404`, `409`, `422`, `503`은 web adapter가 정합니다.
- 예상하지 못한 오류는 관측 가능한 `500`으로 남기고 원인을 숨기지 않습니다.
- 취소는 오류 응답으로 바꾸지 않고 coroutine 구조에 맡깁니다.

## Java/Spring의 예외 계층과 무엇이 다른가

Java/Spring에서는 checked exception, `RuntimeException` 하위 클래스, `@ControllerAdvice`를 조합하는 일이
많습니다. 이 방식은 널리 쓰이지만, 어떤 예외가 정상적인 업무 분기인지 호출부에서 즉시 알기 어렵고,
새 하위 예외가 생겨도 `catch` 누락을 컴파일러가 모두 알려 주지는 않습니다.

Kotlin의 sealed 계층은 **이 서비스가 반환할 수 있는 업무 실패 종류**를 한 파일 또는 패키지 경계에
명시하는 데 알맞습니다. `when`을 식으로 쓰면 분기 누락을 숨길 `else`가 필요 없습니다.

```kotlin
sealed interface PaymentFailure {
    data class InvalidAmount(val reason: String) : PaymentFailure
    data object CustomerNotFound : PaymentFailure
    data object ProviderUnavailable : PaymentFailure
}

sealed interface PaymentResult {
    data class Accepted(val id: String) : PaymentResult
    data class Rejected(val failure: PaymentFailure) : PaymentResult
}
```

여기서 `InvalidAmount`는 검증 가능한 입력 문제이고, `CustomerNotFound`는 조회 결과이며,
`ProviderUnavailable`은 호출자가 재시도 정책을 가질 수 있는 일시 문제입니다. 반면 `NullPointerException`이나
잘못된 DB mapping은 이 목록에 넣지 않습니다. 그런 문제를 정상 응답처럼 반환하면 경보와 수정의 우선순위를 낮춥니다.

## HTTP는 adapter에서만 번역하기

service가 `ResponseEntity`를 직접 반환하기 시작하면 domain 규칙이 HTTP에 묶입니다. Spring MVC와 WebFlux,
메시지 소비자, 배치 작업이 같은 service를 재사용하기도 어려워집니다. web 계층에서만 번역하면 경계가 선명합니다.

```kotlin
fun PaymentResult.toResponse(): ResponseEntity<Any> = when (this) {
    is PaymentResult.Accepted -> ResponseEntity.accepted().body(mapOf("id" to id))
    is PaymentResult.Rejected -> when (val failure = failure) {
        is PaymentFailure.InvalidAmount -> ResponseEntity.unprocessableEntity()
            .body(mapOf("code" to "INVALID_AMOUNT", "message" to failure.reason))
        PaymentFailure.CustomerNotFound -> ResponseEntity.notFound().build()
        PaymentFailure.ProviderUnavailable -> ResponseEntity.status(503)
            .body(mapOf("code" to "PROVIDER_UNAVAILABLE"))
    }
}
```

이 예시는 응답 **형식의 원칙**을 보여 줄 뿐입니다. 실제 서비스는 기존 problem-detail schema, 오류 코드,
상태 코드 계약을 그대로 지켜야 합니다. 새 글을 위해 기존 endpoint의 필드나 상태 코드를 바꾸면 안 됩니다.

| 상황 | domain 표현 | web 경계의 예 | 운영 처리 |
| --- | --- | --- | --- |
| 입력 규칙 위반 | `InvalidAmount` | `422` | 사용자 수정 경로 제공 |
| 리소스 없음 | `CustomerNotFound` | `404` | 요청 ID와 조회 조건 확인 |
| 일시적인 외부 장애 | `ProviderUnavailable` | `503` | timeout·재시도·circuit breaker 관측 |
| 불변식 위반 | 예상 밖 예외 | `500` | 오류 보고와 원인 수정 |
| 요청 취소 | `CancellationException` | 응답으로 재포장하지 않음 | 취소 전파 확인 |

## coroutine에서는 취소를 별도 취급하기

지난 글의 `finally` 정리 원칙은 여기에도 그대로 적용됩니다. 아래처럼 광범위한 `catch`에서 모든 예외를
`ProviderUnavailable`로 바꾸면, 취소된 요청이 정상적인 503처럼 기록될 수 있습니다.

```kotlin
suspend fun charge(command: ChargeCommand): PaymentResult = try {
    gateway.charge(command)
} catch (cancelled: CancellationException) {
    throw cancelled
} catch (timeout: TimeoutCancellationException) {
    PaymentResult.Rejected(PaymentFailure.ProviderUnavailable)
}
```

timeout을 업무 결과로 처리할지, 호출자에게 예외로 올릴지는 계약의 선택입니다. 중요한 것은 **실제 취소를
삼키지 않고**, timeout·재시도·idempotency key·외부 side effect를 함께 설계하는 것입니다. 결제가 실제로
완료됐는지 모르는 timeout을 단순 재시도로 해결해서도 안 됩니다.

## 최소 연습: 새 실패를 추가해 보기

1. `PaymentFailure`에 `data object DailyLimitExceeded`를 추가합니다.
2. `toResponse()`의 `when`에서 컴파일 오류가 나는지 확인합니다.
3. 서비스 단위 테스트는 이 실패를 반환하는 조건만 검증합니다.
4. web adapter 테스트는 기존 response schema 안에서 선택한 상태 코드와 오류 코드를 검증합니다.
5. `CancellationException`이 실패 응답으로 변환되지 않는 테스트를 한 개 추가합니다.

이 순서는 Java의 광범위한 `catch (Exception)`보다 변경 지점을 작게 보여 줍니다. 단, sealed 계층이
너무 커지면 모든 하위 시스템 오류를 한 타입에 몰아넣었다는 신호일 수 있습니다. adapter별 오류는 adapter에,
업무 규칙은 domain에 남기는 편이 낫습니다.

## 점검표

- 이 실패가 호출자가 처리 가능한 업무 사실인가?
- HTTP 상태·본문·로그 포맷을 domain에서 결정하고 있지 않은가?
- 새 sealed 하위 타입이 생기면 `when` 분기가 반드시 검토되는가?
- 기존 API의 필드·상태 코드·시간 값 의미를 임의로 바꾸지 않았는가?
- timeout과 실제 요청 취소를 구별하고, 취소를 다시 던지는가?
- 예상 밖 예외가 요청 ID·trace와 함께 관측되는가?
