## 결론부터 말하면

운영 초기화 기능에서 가장 위험한 코드는 길고 복잡한 로직이 아니라 **이전 관계 구조를 기억하는 짧은
삭제 조건**이었습니다. 예전에는 자식 테이블이 사용자를 직접 참조했지만, 현재 구조에서는 원본 측정 행을
통해 사용자를 따라가야 했습니다. 그런데 삭제 SQL에는 여전히 `WHERE user_id = ?` 같은 직접 소유 조건이
남아 있었고, 실제 초기화 요청은 존재하지 않는 컬럼을 삭제 조건으로 사용하다 실패했습니다.

이번 회고의 핵심은 세 가지였습니다.

- 삭제 SQL은 화면 요구사항이 아니라 현재 FK 방향과 소유 관계를 기준으로 작성합니다.
- 부모 행을 지우기 전에 자식 행을 먼저 지워야 고아 데이터와 FK 부작용을 피할 수 있습니다.
- 운영성 삭제 기능은 성공 응답보다 "실패했을 때 어디까지 롤백되는가"를 테스트해야 합니다.

Spring Boot 개발자에게 익숙한 말로 바꾸면, `@Transactional` 서비스 안에 있다고 해서 삭제 흐름이
자동으로 안전해지는 것은 아닙니다. 트랜잭션은 경계를 제공하지만, 어떤 행을 어떤 순서로 지울지는
저장소 계약과 SQL이 직접 말해야 합니다.

> 검증일: 2026-08-26. Spring 공식 프로젝트 페이지 기준 Spring Boot 안정 버전 `4.1.1`, Spring Data JPA
> 안정 버전 `4.1.1`을 확인했습니다. Spring Framework 트랜잭션 문서는 `7.0.9` Reference를 기준으로,
> PostgreSQL 삭제 문법은 PostgreSQL `18` 공식 문서를 기준으로 작성했습니다. `4.2.0-M1` 같은 milestone은
> 안정 버전으로 보지 않았습니다.

## 문제가 된 모양

운영 도구에는 특정 사용자와 연결된 업무 데이터를 강하게 초기화하는 기능이 있었습니다. 이런 기능은 일반
삭제보다 책임이 큽니다. 여러 테이블을 순서대로 정리하고, 중간에 하나라도 실패하면 전체 작업이 되돌아가야
하기 때문입니다.

문제는 데이터 모델이 바뀐 뒤에 생겼습니다. 예전 구조에서는 예측 데이터가 사용자를 직접 참조했습니다.
현재 구조에서는 예측 데이터가 원본 측정 데이터를 참조하고, 사용자 소유 관계는 원본 측정 데이터에서
판단합니다.

| 구분 | 예전 구조 | 현재 구조 |
|---|---|---|
| 예측 데이터 소유자 | 예측 테이블의 `user_id` | 원본 측정 테이블의 `user_id` |
| 삭제 조건 | 예측 행에서 사용자 ID 직접 비교 | 원본 측정 행을 조인하거나 하위 쿼리로 추적 |
| 삭제 순서 | 예측 행과 원본 행을 각각 삭제 | 예측 행을 먼저 삭제한 뒤 원본 행 삭제 |
| 실패 위험 | 조건 누락이나 과삭제 | 오래된 컬럼 참조, 고아 예측 행, 부분 초기화 |

장애 자체는 단순했습니다. 운영자가 초기화를 실행하면 예측 데이터 삭제 단계에서 SQL 오류가 발생했습니다.
하지만 이 오류가 중요한 이유는 "컬럼명이 틀렸다"에 그치지 않습니다. 저장소 코드가 현재 도메인 관계를
따라가지 못했고, 초기화 기능의 회귀 테스트도 그 관계 변화를 잡지 못했습니다.

<Mermaid title="관계 기반 삭제 순서">

  Reset["운영 초기화 요청"] --> Tx["@Transactional 경계"]

  FindParents --> DeleteChildren["예측/파생 행 먼저 삭제"]
  DeleteChildren --> DeleteParents["원본 측정 행 삭제"]
  DeleteParents --> DeleteRest["나머지 관련 데이터 삭제"]
  DeleteRest --> Commit["전체 커밋"]

  DeleteChildren -->|오래된 컬럼 참조| Failure["삭제 실패"]

`}

## 삭제 조건은 관계 방향을 따라야 합니다

이런 버그는 보통 코드 리뷰에서 잘 보이지 않습니다. 삭제 SQL이 한 줄이면 더 그렇습니다.

```sql
delete from prediction_records
where user_id = :userId;
```

예전 모델에서는 맞는 코드였을 수 있습니다. 하지만 현재 모델에서 예측 행이 원본 측정 행을 바라본다면,
소유자 조건은 예측 테이블에 없습니다. 삭제 조건도 관계를 따라 이동해야 합니다.

```sql
delete from prediction_records p
using source_measurements m
where p.source_measurement_id = m.id
  and m.user_id = :userId;
```

또는 데이터베이스와 저장소 스타일에 따라 하위 쿼리로 표현할 수도 있습니다.

```sql
delete from prediction_records
where source_measurement_id in (
  select id
  from source_measurements
  where user_id = :userId
);
```

중요한 것은 SQL 모양이 아니라 기준입니다. "이 사용자의 예측 데이터"라는 업무 문장은 현재 스키마에서는
"이 사용자의 원본 측정 행을 참조하는 예측 데이터"로 번역되어야 합니다. 이 번역이 저장소 메서드 이름과
테스트 이름에 드러나야 다음 스키마 변경 때도 놓치지 않습니다.

```java
interface PredictionCleanupRepository {
    int deletePredictionsOwnedThroughSourceMeasurements(long userId);
}
```

메서드 이름은 조금 길어도 됩니다. 운영 삭제 코드에서는 짧은 이름보다 오해가 적은 이름이 더 낫습니다.

## 부모보다 자식을 먼저 지웁니다

삭제 순서도 관계 구조를 따라야 합니다. 원본 측정 행을 먼저 지우면 자식 예측 행은 FK 정책에 따라 같이
삭제되거나, 참조가 `null`로 바뀌거나, 삭제 자체가 실패합니다. 어느 쪽이든 운영 초기화 코드가 기대한
결과와 다를 수 있습니다.

특히 `ON DELETE SET NULL` 같은 정책이 있으면 원본 행을 먼저 삭제했을 때 예측 행은 남지만 소유자를 추적할
연결이 사라질 수 있습니다. 그러면 이후 정리 배치나 감사 조회에서 "누구의 데이터였는지 모르는 파생 행"이
됩니다.

그래서 삭제 순서는 아래처럼 명시하는 편이 안전했습니다.

| 순서 | 작업 | 확인할 것 |
|---|---|---|
| 1 | 대상 부모 행 ID를 현재 조건으로 식별 | 사용자 소유, 기간, 상태 조건 |
| 2 | 부모 행을 참조하는 파생·예측 행 삭제 | 삭제 건수와 조인 조건 |
| 3 | 부모 원본 행 삭제 | FK 정책에 기대지 않는 명시 삭제 |
| 4 | 나머지 관련 도메인 행 삭제 | 독립 소유 조건과 감사 대상 |
| 5 | 결과 검증 | 남은 자식 행, 원본 행, 롤백 여부 |

JPA 엔티티의 cascade 설정만 믿는 것도 조심해야 합니다. 운영 초기화는 대량 삭제에 가깝고, 성능과 범위
때문에 JPQL 또는 native SQL을 쓰는 경우가 많습니다. 이때 cascade, orphan removal, DB FK 동작, 직접 SQL이
서로 다른 규칙을 가질 수 있습니다. 한 기능 안에서는 삭제 책임을 한곳에 모아 순서를 코드로 읽을 수 있게
두는 편이 낫습니다.

## 트랜잭션은 실패 범위를 증명해야 합니다

이번 사례에서 다행이었던 점은 초기화 서비스가 하나의 트랜잭션 경계 안에 있었다는 것입니다. 예측 데이터
삭제 단계에서 오류가 나면 앞서 실행된 다른 DB 변경도 함께 롤백되어야 했습니다.

하지만 "서비스에 `@Transactional`이 있다"는 사실만으로 충분하지 않습니다. 다음 질문에 답할 수 있어야
합니다.

| 질문 | 이유 |
|---|---|
| 삭제 메서드들이 같은 트랜잭션에 참여하는가 | 별도 커밋이 있으면 부분 초기화가 남을 수 있음 |
| 중간 실패가 rollback 대상 예외로 전파되는가 | 예외를 잡아 삼키면 커밋될 수 있음 |
| 외부 이벤트나 파일 삭제가 섞이는가 | DB 롤백으로 되돌릴 수 없는 부작용 |
| 테스트가 실패 지점을 강제로 만들 수 있는가 | 정상 경로 테스트만으로는 롤백 보장 불가 |

Spring Framework의 선언적 트랜잭션은 메서드 단위로 트랜잭션 의미를 코드 가까이에 둘 수 있게 해 줍니다.
다만 롤백 규칙, 전파 방식, 별도 스레드나 외부 부작용은 따로 봐야 합니다. 운영 삭제 기능에서 가장 먼저
확인할 것은 "성공하면 몇 건 지워지는가"보다 "실패하면 정말 아무것도 남기지 않는가"였습니다.

```java
@Transactional
public ResetResult strongReset(long userId) {
    cleanupRepository.deletePredictionsOwnedThroughSourceMeasurements(userId);
    cleanupRepository.deleteSourceMeasurements(userId);
    cleanupRepository.deleteOtherOwnedRows(userId);
    return ResetResult.completed(userId);
}
```

이 코드는 단순하지만 두 가지 조건을 전제로 합니다. 모든 저장소 호출이 같은 트랜잭션에 참여해야 하고,
실패를 성공 응답으로 바꾸면 안 됩니다. 운영 화면에 친절한 오류 메시지를 보여 주더라도 서비스 내부에서는
롤백 가능한 예외가 트랜잭션 관리자까지 전달되어야 합니다.

## 회귀 테스트는 SQL의 현재성을 확인합니다

이 유형의 버그는 컴파일이 잡아 주지 않습니다. native SQL 문자열 안의 오래된 컬럼명은 애플리케이션 시작
또는 실제 실행 시점이 되어야 드러납니다. 그래서 운영 삭제 기능에는 실제 테스트 데이터로 관계를 만들고,
삭제 후 남은 행을 확인하는 회귀 테스트가 필요했습니다.

```java
@Test
void strongResetDeletesPredictionsThroughCurrentSourceRelationship() {
    User user = saveUser();
    SourceMeasurement source = saveSourceMeasurement(user.id());
    PredictionRecord prediction = savePrediction(source.id());

    resetService.strongReset(user.id());

    assertThat(predictionRepository.existsById(prediction.id())).isFalse();
    assertThat(sourceRepository.existsById(source.id())).isFalse();
}
```

여기서 테스트 이름은 의도적으로 관계를 말합니다. "예측 데이터를 삭제한다"보다 "현재 원본 관계를 통해
예측 데이터를 삭제한다"가 더 정확합니다. 다음에 예측 데이터의 소유 관계가 또 바뀌면 테스트 이름부터
수정 대상이 됩니다.

롤백 테스트도 별도로 둡니다.

```java
@Test
void strongResetRollsBackPreviousDeletesWhenLaterCleanupFails() {
    User user = saveUserWithRelatedRows();
    cleanupRepository.failOnPurposeAfterFirstDelete();

    assertThatThrownBy(() -> resetService.strongReset(user.id()))
        .isInstanceOf(ResetFailedException.class);

    assertThat(firstRepository.countByUserId(user.id())).isEqualTo(1);
    assertThat(secondRepository.countByUserId(user.id())).isEqualTo(1);
}
```

실제 구현에서는 실패 주입 방식을 테스트 더블, 제약 조건 위반, 별도 테스트용 저장소 등으로 선택할 수
있습니다. 핵심은 삭제가 일부 진행된 뒤 실패하는 상황을 한 번은 만들어 본다는 점입니다. 운영 삭제 기능은
실패 경로가 곧 안전장치입니다.

## 저장소 코드에 스키마 변경 알림을 남깁니다

스키마 변경이 일어날 때마다 모든 native SQL을 사람이 기억해서 고치기는 어렵습니다. 그렇다고 추상화를
먼저 크게 만들 필요는 없습니다. 최소한 아래 세 가지는 비용 대비 효과가 컸습니다.

| 점검 항목 | 방법 |
|---|---|
| 직접 컬럼 참조 | `rg "user_id|source_measurement_id|delete from"`로 native SQL 검색 |
| 관계 기반 삭제 | 저장소 메서드 이름에 `Through...`, `BySource...`처럼 경로 명시 |
| 스키마 변경 PR | 변경 테이블을 참조하는 운영 삭제·초기화 테스트 실행 |

Spring Data JPA의 repository abstraction은 일반 조회와 저장에는 많은 반복을 줄여 줍니다. 하지만 운영성
대량 삭제는 도메인별 SQL을 직접 쓰는 편이 더 명확할 때가 있습니다. 그 경우에는 "직접 SQL을 썼다"는
사실 자체를 위험 신호로 보고, 스키마 변경 때 검색 가능한 이름과 테스트를 남겨야 합니다.

## 작은 실습: 초기화 기능 점검표

비슷한 강한 삭제나 초기화 기능이 있다면 아래 표를 먼저 채워 볼 수 있습니다.

| 질문 | 확인할 것 |
|---|---|
| 삭제 대상의 소유자는 어느 테이블에서 판단하는가 | 직접 컬럼인지, 부모 행을 통한 관계인지 |
| 자식 행과 부모 행 중 무엇을 먼저 지우는가 | FK 정책, `ON DELETE` 동작, 고아 데이터 위험 |
| native SQL이 현재 스키마와 맞는가 | 실제 컬럼명, 조인 조건, 삭제 건수 |
| 중간 실패가 전체 롤백되는가 | `@Transactional`, 전파 방식, 예외 처리 |
| 롤백 밖 부작용이 있는가 | 이벤트, 파일, 캐시, 외부 API |
| 테스트가 남은 행을 직접 확인하는가 | 응답 코드보다 DB 상태 검증 |
| 운영 로그가 민감 값을 남기지 않는가 | 대상 식별자 일반화, 토큰·원문 제외 |

이 표가 비어 있으면 초기화 기능은 "큰 삭제 버튼"에 가까워집니다. 반대로 관계, 순서, 롤백, 감사 범위를
먼저 적으면 구현은 단순해지고 장애 분석도 빨라집니다.

## 오늘의 결론

관계 구조가 바뀌면 삭제 SQL도 같이 바뀌어야 합니다. 특히 운영 초기화처럼 여러 테이블을 건드리는 기능은
예전 컬럼 하나가 남아 있어도 전체 흐름을 막거나, 더 나쁘게는 일부 데이터만 지운 상태를 만들 수 있습니다.

이번 정리의 방향은 단순했습니다. 삭제 조건은 현재 FK 방향을 따라 작성합니다. 파생 행을 먼저 지우고
원본 행을 지웁니다. 트랜잭션은 선언에 그치지 않고 실패 시 롤백되는지 테스트합니다. 운영 삭제 기능에서
가장 중요한 계약은 "성공하면 지워진다"가 아니라 "실패하면 어중간하게 남지 않는다"였습니다.
