## 결론부터 말하면

Flutter 두 번째 단계에서 가장 먼저 익혀야 할 감각은 **부모가 제약을 내려보내고, 자식이 크기를 고른 뒤,
부모가 위치를 정한다**는 layout 흐름입니다.

Spring Boot 개발자는 보통 책임 방향을 위에서 아래로 읽습니다. Controller가 요청을 받고, Service가 규칙을
적용하고, Repository가 저장소와 통신합니다. Flutter layout도 비슷하게 위에서 아래로 읽을 수 있지만,
여기서 내려가는 것은 요청 DTO가 아니라 `constraints`입니다.

이번 글에서는 Flutter 첫걸음에서 본 Widget tree를 한 단계 더 밀고 갑니다.

- Row와 Column은 자식을 어떻게 배치하는가
- constraints는 왜 "부모가 내려주는 계약"인가
- `setState()`는 서버 저장이 아니라 화면 재계산 신호인 이유
- state는 어느 위젯이 소유해야 하는가

## 이번 주 개념

Flutter layout은 제약과 크기 선택의 협상으로 볼 수 있습니다. 공식 문서는 이 흐름을 간단히 정리합니다.
부모 위젯이 자식에게 최소/최대 너비와 높이를 전달하고, 자식은 그 범위 안에서 크기를 고릅니다. 그다음
부모가 자식의 위치를 정합니다.

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const LearningApp());
}

class LearningApp extends StatelessWidget {
  const LearningApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      home: DashboardScreen(),
    );
  }
}

class DashboardScreen extends StatelessWidget {
  const DashboardScreen({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Layout first')),
      body: Padding(
        padding: const EdgeInsets.all(16),
        child: Column(
          crossAxisAlignment: CrossAxisAlignment.stretch,
          children: const [
            SummaryHeader(title: '오늘 처리할 작업'),
            SizedBox(height: 12),
            TaskCounter(),
          ],
        ),
      ),
    );
  }
}
```

여기서 `Scaffold`, `Padding`, `Column`, `SummaryHeader`, `TaskCounter`는 각각 다른 책임을 가집니다.

| 코드 | 역할 |
|---|---|
| `Scaffold` | Material 앱 화면의 기본 구조를 제공합니다. |
| `Padding` | 자식에게 더 좁은 layout 영역을 넘깁니다. |
| `Column` | 자식들을 세로 방향으로 배치합니다. |
| `crossAxisAlignment.stretch` | 가로축으로 자식을 가능한 폭까지 늘립니다. |
| `SizedBox(height: 12)` | 두 위젯 사이의 고정 간격을 만듭니다. |

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 객체가 어느 책임을 가져야 하는지 계속 판단합니다.

```java
@Service
class TaskService {

    TaskSummary summarize(List<Task> tasks) {
        long completed = tasks.stream().filter(Task::completed).count();
        return new TaskSummary(tasks.size(), completed);
    }
}
```

이 코드는 화면 배치를 모릅니다. Service는 비즈니스 값을 만들고, Controller나 프론트엔드가 그 값을
표현합니다. 책임이 섞이면 테스트가 어려워집니다.

Flutter도 비슷합니다. layout 위젯은 배치 책임을 갖고, 상태 위젯은 변하는 값을 갖고, 작은 표시 위젯은
받은 값을 그립니다. 모든 값을 가장 아래 위젯에 몰아넣거나, 반대로 모든 위젯을 화면 루트에서 직접 제어하면
금방 복잡해집니다.

## Flutter에서는 무엇이 다른가

Flutter에서 layout은 부모와 자식 사이의 단방향 협상입니다. 자식이 "나는 무조건 500px을 쓰겠다"고 말해도
부모가 내려준 제약을 벗어날 수 없습니다.

<Mermaid title="Flutter constraints와 state 흐름">
{`flowchart TD
  Parent["부모 위젯"] -->|constraints 전달| Child["자식 위젯"]
  Child -->|size 선택| Parent
  Parent -->|position 결정| Screen["화면 배치"]

  Event["사용자 입력"] --> Handler["이벤트 핸들러"]
  Handler --> SetState["setState()"]
  SetState --> Rebuild["build() 재호출"]
  Rebuild --> Parent
`}
</Mermaid>

Spring Boot 개발자 관점에서 가까운 비교는 아래와 같습니다.

| Spring Boot에서 익숙한 것 | Flutter에서 가까운 개념 | 주의할 점 |
|---|---|---|
| Controller가 요청 범위 결정 | 부모 위젯이 constraints 전달 | 자식이 부모 제약을 무시할 수 없습니다. |
| Service가 필요한 값 계산 | State가 화면에 필요한 값 보관 | 서버 진실 공급원과 UI state를 섞지 않습니다. |
| DTO를 View에 전달 | props처럼 생성자 인자를 전달 | Widget은 mutable 객체처럼 수정하지 않습니다. |
| transaction commit | `setState()` | 저장 보장이 아니라 rebuild 예약입니다. |
| 책임 경계 분리 | state lifting | 여러 자식이 쓰는 state는 공통 부모로 올립니다. |

## Row와 Column은 방향만 다른 것이 아닙니다

`Row`와 `Column`은 자식들을 한 축으로 배치합니다. 처음에는 "가로냐 세로냐"만 보면 되지만, 실제로는
main axis와 cross axis를 함께 읽어야 합니다.

```dart
class SummaryHeader extends StatelessWidget {
  const SummaryHeader({
    required this.title,
    super.key,
  });

  final String title;

  @override
  Widget build(BuildContext context) {
    return Row(
      mainAxisAlignment: MainAxisAlignment.spaceBetween,
      children: [
        Text(
          title,
          style: Theme.of(context).textTheme.titleLarge,
        ),
        const Icon(Icons.check_circle_outline),
      ],
    );
  }
}
```

`Row`에서 main axis는 가로 방향입니다. `mainAxisAlignment.spaceBetween`은 첫 자식과 마지막 자식을 양끝에
두고 사이 공간을 나눕니다. `Column`에서 같은 옵션을 쓰면 세로 방향으로 적용됩니다.

레이아웃 버그가 생겼을 때는 아래 순서로 확인하면 덜 헤맵니다.

1. 부모가 어느 크기 제약을 내려주는가
2. 현재 위젯의 main axis는 어느 방향인가
3. 자식이 남은 공간을 얼마나 차지해야 하는가
4. 스크롤이 필요한 화면인데 `Column`만 쓰고 있지는 않은가

## setState는 작은 화면 상태에만 먼저 씁니다

Flutter 공식 문서는 상호작용 튜토리얼에서 `StatefulWidget`과 `setState()`로 탭에 반응하는 UI를 만듭니다.
처음에는 이 정도 범위가 적당합니다.

```dart
class TaskCounter extends StatefulWidget {
  const TaskCounter({super.key});

  @override
  State<TaskCounter> createState() => _TaskCounterState();
}

class _TaskCounterState extends State<TaskCounter> {
  int completedCount = 0;

  void completeOne() {
    setState(() {
      completedCount += 1;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Column(
      crossAxisAlignment: CrossAxisAlignment.start,
      children: [
        Text('완료한 작업: $completedCount'),
        const SizedBox(height: 8),
        FilledButton(
          onPressed: completeOne,
          child: const Text('완료 처리'),
        ),
      ],
    );
  }
}
```

`setState()`는 이 `State` 객체가 관리하는 UI를 다시 계산하라고 알려 줍니다. 데이터베이스에 저장하거나,
서버와 동기화하거나, 실패 시 재시도를 보장하지 않습니다.

서버 저장이 필요한 값이라면 함수 이름부터 분리하는 편이 좋습니다.

```dart
Future<void> submitCompletion() async {
  setState(() {
    isSubmitting = true;
  });

  try {
    await taskApi.completeOne();
  } finally {
    setState(() {
      isSubmitting = false;
    });
  }
}
```

이 코드는 여전히 예제 수준입니다. 핵심은 UI 상태(`isSubmitting`)와 서버 상태(`completeOne`)를 같은 것으로
착각하지 않는 것입니다.

## state lifting으로 소유자를 정합니다

공식 state management 문서는 여러 위젯이 같은 값을 써야 한다면 그 값을 공통 부모나 그보다 위에 두는
방식을 설명합니다. Flutter에서는 아래 자식 위젯을 외부에서 명령형으로 고치는 방식보다, 새 값을 가진
위젯을 다시 구성하는 흐름이 자연스럽습니다.

```dart
class TaskBoard extends StatefulWidget {
  const TaskBoard({super.key});

  @override
  State<TaskBoard> createState() => _TaskBoardState();
}

class _TaskBoardState extends State<TaskBoard> {
  int completedCount = 0;

  void completeOne() {
    setState(() {
      completedCount += 1;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Column(
      crossAxisAlignment: CrossAxisAlignment.start,
      children: [
        TaskSummary(count: completedCount),
        const SizedBox(height: 12),
        TaskAction(onComplete: completeOne),
      ],
    );
  }
}
```

`TaskSummary`와 `TaskAction`이 같은 값을 기준으로 움직여야 하므로 `completedCount`를 공통 부모인
`TaskBoard`에 둡니다. Spring에서 여러 Service가 같은 transaction 안의 값을 공유해야 할 때 경계를
위로 올리는 감각과 비슷합니다. 다만 Flutter의 state lifting은 UI 조립 책임에 관한 이야기입니다.

## 최소 실행 예제

Flutter 3.47.1 stable SDK가 준비되어 있다면 아래처럼 작은 앱을 만들 수 있습니다.

```bash
flutter create flutter_layout_state
cd flutter_layout_state
flutter run
```

`lib/main.dart`에서 다음 실습을 해 보세요.

1. `Column`의 `crossAxisAlignment`를 바꿔 자식 폭이 어떻게 달라지는지 확인합니다.
2. `Row`의 `mainAxisAlignment`를 `start`, `center`, `spaceBetween`으로 바꿔 봅니다.
3. `TaskCounter`의 state를 `TaskBoard`로 올리고, 표시 위젯과 버튼 위젯을 분리합니다.
4. 버튼을 빠르게 여러 번 눌렀을 때 UI state와 서버 저장 state를 어떻게 나눌지 함수 이름으로 먼저 표현해
   봅니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 `setState()`를 transaction commit처럼 보는 것입니다. `setState()`는 화면 갱신 신호입니다.
서버 저장, 권한 검사, 중복 방지, 실패 보상은 별도 API와 서버 설계가 맡아야 합니다.

두 번째 오해는 layout 문제를 자식 위젯 안에서만 고치려는 것입니다. Flutter layout은 부모가 제약을
내려보내는 구조입니다. 자식이 넘치거나 눌린다면 부모가 어떤 constraints를 전달하는지 먼저 봐야 합니다.

세 번째 오해는 모든 state를 가장 가까운 버튼 위젯에 넣는 것입니다. 혼자 쓰는 작은 상태라면 괜찮지만,
형제 위젯이 함께 읽거나 바꿔야 하는 값은 공통 부모로 올리는 편이 단순합니다.

네 번째 오해는 `Row`와 `Column`만으로 모든 화면을 해결하려는 것입니다. 항목이 많아지거나 화면보다 길어질
가능성이 있으면 스크롤 위젯과 목록 위젯을 함께 고려해야 합니다.

## 마무리

Flutter를 Spring Boot 감각으로 배울 때 중요한 연결점은 "책임 경계"입니다. Spring에서 Controller,
Service, Repository 책임을 섞지 않으려 하듯이, Flutter에서도 layout, 표시, 상호작용, 서버 동기화 책임을
분리해야 합니다.

오늘은 그중 layout constraints와 state 소유 위치를 봤습니다. 이 기준이 잡히면 다음 단계에서 목록,
스크롤, 폼 입력, 서버 API 호출을 다룰 때도 어떤 위젯이 무엇을 알아야 하는지 더 선명하게 판단할 수 있습니다.
