## 1. Gemini Enterprise 개발 도구 GA는 AI 코딩을 관리자 정책으로 끌어옵니다

Google Cloud release notes는 2026년 8월 21일 Gemini Enterprise의 AI developer tools 관련
변화를 공지했습니다. 공식 release notes 기준 AI developer tools는 Gemini Enterprise Standard,
Plus, Pay-as-you-go edition에서 GA로 제공되며, Antigravity 2.0, Antigravity CLI, Android Studio
접근을 포함합니다. 관리자는 Google Cloud Console에서 개발 도구 사용 여부, 파일 접근, terminal
command 실행, model availability 같은 보안 정책을 설정하고 Cloud Monitoring과 logging으로
사용량을 볼 수 있습니다.

이 발표는 "AI assistant를 쓸 수 있다"보다 "AI assistant를 조직 정책으로 다룰 수 있다"에 가깝습니다.
Spring Boot 팀에서도 IDE plugin이나 cloud agent를 개인 설정으로만 두면 운영 기준을 맞추기
어렵습니다. 어떤 repository에서 어떤 명령을 실행할 수 있는지, 어떤 파일을 읽을 수 있는지, 사용량과
비용을 어디에서 볼지부터 정해야 합니다.

| 검토 항목 | 이유 |
|---|---|
| 파일 접근 정책 | agent가 `.env`, key, 운영 dump를 읽지 못하게 해야 합니다. |
| terminal command 정책 | build와 test는 허용하더라도 배포와 삭제 명령은 분리해야 합니다. |
| IAM role | 개인 계정보다 조직 role로 기능 접근을 추적하는 편이 감사에 유리합니다. |
| 사용량 관측 | token, API call, 활성 사용자 지표가 비용과 도입 범위를 설명합니다. |

Java 개발자가 익숙한 관점으로 보면, 이것은 Spring Security의 method authorization과 비슷합니다.
기능을 켜는 것보다 누가 어떤 action을 어떤 context에서 실행할 수 있는지가 먼저입니다.

## 2. Amazon EKS CA rotation은 오래된 클러스터의 신뢰 경계를 교체하는 작업입니다

AWS는 2026년 8월 20일 Amazon EKS에서 certificate authority rotation을 지원한다고 공지했습니다.
공식 공지 기준 Amazon EKS는 rotation lifecycle과 AWS-managed component의 successor CA 신뢰
업데이트를 관리합니다. 다만 고객은 worker node 교체와 external client의 successor CA trust
업데이트를 successor CA가 활성화되기 전에 끝내야 합니다.

중요한 배경은 클러스터 수명입니다. AWS 공지는 2018년부터 생성된 EKS 클러스터 CA가 10년 유효
기간을 갖고 있고, 초기 클러스터가 rotation 활동을 시작해야 하는 시점에 가까워지고 있다고 설명합니다.
인증서는 애플리케이션 배포처럼 자주 바꾸는 리소스가 아니기 때문에, 막상 바꾸려면 누가 client인지부터
찾기 어렵습니다.

Spring Boot 서비스를 EKS에서 운영한다면 다음 순서로 보는 편이 안전합니다.

```text
클러스터별 CA 만료 시점 확인
-> kubectl, CI runner, Argo CD, monitoring agent 같은 외부 client 목록화
-> managed node group과 self-managed node 교체 계획 분리
-> staging cluster에서 successor CA trust 검증
-> 운영 cluster maintenance window와 rollback 기준 확정
```

CA rotation은 단순 control plane 설정 변경이 아닙니다. API server를 호출하는 모든 client의
trust store와 node lifecycle이 엮입니다. Spring Boot 애플리케이션 자체가 바뀌지 않아도 readiness
probe, deployment controller, log collector, secret synchronizer가 API server에 접근하지 못하면
배포와 장애 대응이 멈출 수 있습니다.

## 3. Docker ELS의 MinIO 지원은 EOL을 운영 위험으로 다룹니다

Docker는 2026년 8월 24일 MinIO end of life와 Docker Extended Lifecycle Support를 설명했습니다.
공식 Docker 글은 MinIO open-source project가 2026년 2월 13일 upstream에서 archived 되었고,
Docker ELS가 upstream 지원이 끝난 소프트웨어를 최대 5년까지 패치, compliance, audit-ready
상태로 유지하는 모델이라고 설명합니다. MinIO는 Docker Hardened Images catalog에서 유지되는
ELS 사례로 제시됐습니다.

EOL은 "언젠가 바꾸면 된다"가 아니라 "새 CVE가 나왔을 때 누가 patch를 만들고 증적을 남기는가"의
문제입니다. 객체 저장소나 오래된 runtime은 migration 비용이 크기 때문에 예외 문서만 쌓이기 쉽습니다.
Docker ELS의 핵심 메시지는 migration 일정을 늦추자는 것이 아니라, migration이 끝날 때까지
patch SLA와 SBOM, VEX, provenance 같은 감사 증적을 붙여 운영 위험을 낮추자는 쪽입니다.

Spring Boot 팀에서 확인할 항목은 다음과 같습니다.

| 항목 | 확인 방법 |
|---|---|
| EOL dependency | container image, sidecar, batch image, local dev image까지 inventory를 만든다. |
| upstream support | 공식 support policy와 release history로 실제 지원 종료 여부를 확인한다. |
| patch 책임 | vendor, 내부 fork, migration 중 어느 쪽이 CVE 대응을 맡는지 정한다. |
| 감사 증적 | SBOM, signature, provenance, exception 승인 문서를 한곳에 모은다. |

MinIO를 쓰지 않더라도 이 발표는 Node 18, Python 3.8, 오래된 Nginx, 오래된 database image 같은
자산을 다시 보게 만듭니다. Java 애플리케이션은 최신이어도 주변 이미지가 EOL이면 운영 감사에서
같은 배포 단위의 위험으로 묶입니다.

## 4. Visual Studio 2026 18.9.1은 AI 명령 승인과 Test Agent 안정화를 고쳤습니다

Microsoft는 Visual Studio 2026 release notes에서 18.9.1 stable 릴리스를 2026년 8월 18일에
공개했다고 안내했습니다. 공식 release notes 기준 18.9.1의 주요 수정은 Copilot Command preview
dialog가 scroll되지 않아 allow 또는 deny action을 막던 문제와 18.9.0의 Test Agent 수정입니다.

큰 기능 발표는 8월 11일 18.9.0에 더 많았지만, 이번 글의 7일 범위에서는 18.9.1을 운영 기준으로
봅니다. AI 명령 승인 UI가 막히거나 Test Agent가 불안정하면 팀 표준 IDE에서 "AI를 써도 되는
작업"과 "테스트로 검증된 작업"의 경계가 흐려집니다.

Visual Studio를 주 IDE로 쓰지 않는 Java 팀에도 참고할 점이 있습니다. AI coding agent가 IDE,
CLI, CI로 들어오면 command approval UX와 test agent 안정성은 생산성 기능이 아니라 변경 승인
절차의 일부가 됩니다. IntelliJ, VS Code, CLI agent를 쓰는 팀도 다음 기준을 갖춰야 합니다.

- agent가 제안한 command를 승인하기 전에 command 전체를 볼 수 있는가
- test 실행 결과가 어느 runner와 어느 dependency 버전에서 나온 것인지 남는가
- agent가 만든 PR은 추가 human approval을 요구하는가
- IDE update를 개인 선택에 맡기지 않고 최소 patch version을 공지하는가

## preview와 beta 발표는 운영 기준에서 분리했습니다

이번 주에는 Kubernetes v1.37 예정 안내, Chrome과 여러 AI 도구의 preview 성격 업데이트도
확인했습니다. 방향성은 중요하지만, 이 글은 최근 7일 안에 공식 발표된 안정 기능, GA, stable
릴리스, 명확한 lifecycle 대응만 다뤘습니다.

실무에서는 다음처럼 분리하는 편이 안전합니다.

- preview와 beta는 PoC, 비용 추정, 호환성 조사에 둡니다.
- 운영 점검표에는 GA, stable, security advisory, support policy만 넣습니다.
- agent와 IDE 기능은 "써도 되는가"보다 "어떤 권한과 증적으로 쓰는가"를 먼저 정합니다.

## 실무 체크리스트

- [ ] AI coding tool을 조직 IAM, 파일 접근, terminal command 정책으로 관리할 수 있는지 확인한다.
- [ ] agent 사용량, token, API call, 실행 command audit log를 남기는 위치를 정한다.
- [ ] EKS cluster별 CA 만료 시점과 rotation 대상 external client를 목록화한다.
- [ ] EKS node 교체, CI runner trust store, GitOps controller trust store를 별도 작업으로 나눈다.
- [ ] production image 중 upstream EOL component가 있는지 SBOM과 release policy로 확인한다.
- [ ] EOL component는 migration 계획과 patch 책임, 감사 증적을 함께 기록한다.
- [ ] 표준 IDE와 AI agent 도구의 최소 patch version을 정하고 test agent 결과를 PR 증적으로 남긴다.
