## 결론부터 말하면

Kotlin의 `let`, `run`, `apply`, `also`, `with`는 새로운 능력을 주는 문법이 아닙니다. 같은 코드를 지역 변수와
일반 함수 호출로도 쓸 수 있습니다. 그런데 서버 코드에서는 이 작은 함수들이 **값을 정규화하는 경계, 객체를
설정하는 경계, 부수 효과를 남기는 경계**를 짧게 드러내는 데 도움이 됩니다.

문제는 남용입니다. scope function을 길게 중첩하면 `this`와 `it`이 어떤 객체인지 흐려지고, Java/Spring Boot에
익숙한 개발자에게는 오히려 디버깅하기 어려운 코드가 됩니다.

이번 글의 기준은 단순합니다.

- nullable 값을 non-null command로 바꿀 때는 `?.let`과 `takeIf`를 좁게 씁니다.
- 객체 설정에는 `apply`를 쓰되, JPA entity 변경 감지를 숨기는 용도로 쓰지 않습니다.
- 로깅, metric, 감사 기록 같은 부수 효과에는 `also`를 씁니다.
- 여러 줄 계산 결과가 필요할 때만 `run`이나 `with`를 씁니다.
- service 핵심 흐름에서는 중첩 chain보다 명시적인 지역 변수가 더 나을 때가 많습니다.

## 이번 주 개념

Kotlin 공식 문서 기준 scope function은 다섯 가지입니다.

| 함수 | 객체 참조 | 반환값 | 서버 코드에서 읽는 의도 |
|---|---|---|---|
| `let` | `it` | lambda 결과 | nullable 처리, 값 변환 |
| `run` | `this` | lambda 결과 | 설정과 계산을 한 블록으로 묶음 |
| `with` | `this` | lambda 결과 | 이미 있는 객체에서 여러 값을 읽어 계산 |
| `apply` | `this` | 원래 객체 | 객체 설정 |
| `also` | `it` | 원래 객체 | 로깅, 검증 기록, metric 같은 side effect |

핵심 차이는 두 가지입니다. 첫째, 블록 안에서 객체를 `this`로 볼지 `it`으로 볼지입니다. 둘째, 블록의 결과를
돌려줄지 원래 객체를 그대로 돌려줄지입니다.

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 보통 지역 변수와 builder로 같은 의도를 표현했습니다.

```java
String email = request.email();
if (email == null || email.isBlank()) {
    throw new BadRequestException("email is required");
}

RegisterCommand command = RegisterCommand.builder()
    .email(email.trim().toLowerCase(Locale.ROOT))
    .displayName(request.displayName().trim())
    .build();

log.info("register command created: {}", command.email());
return userService.register(command);
```

이 코드는 길지만 흐름이 명시적입니다. Kotlin으로 옮길 때 무조건 한 줄 chain으로 줄이면 가독성이 좋아지는 것이
아닙니다.

```kotlin
return request.email?.trim()?.lowercase()?.takeIf { it.isNotBlank() }?.let {
    userService.register(RegisterCommand(it, request.displayName!!.trim()))
} ?: throw BadRequestException("email is required")
```

짧지만 좋지 않은 코드입니다. email 검증, displayName 강제 unwrap, command 생성, service 호출, 예외 처리가 한
문장에 섞였습니다. Spring Boot service 코드는 줄 수보다 실패 경계가 더 중요합니다.

## Kotlin에서는 무엇이 다른가

Kotlin에서는 nullable type과 safe call 덕분에 외부 입력을 작은 변환 단계로 좁힐 수 있습니다.

```kotlin
data class RegisterRequest(
    val email: String?,
    val displayName: String?,
)

data class RegisterCommand(
    val email: String,
    val displayName: String,
)

fun RegisterRequest.toCommand(): RegisterCommand {
    val normalizedEmail = email
        ?.trim()
        ?.lowercase()
        ?.takeIf { it.isNotBlank() }
        ?: throw BadRequestException("email is required")

    val normalizedName = displayName
        ?.trim()
        ?.takeIf { it.isNotBlank() }
        ?: throw BadRequestException("displayName is required")

    return RegisterCommand(
        email = normalizedEmail,
        displayName = normalizedName,
    )
}
```

여기서 `takeIf`는 단일 객체 필터처럼 씁니다. 조건을 만족하면 그 값을 돌려주고, 아니면 `null`이 됩니다. 그 뒤
Elvis 연산자 `?:`로 실패를 명시합니다. `let`을 꼭 써야 하는 상황은 아닙니다. 값이 이미 충분히 분명하면 지역
변수가 더 읽기 쉽습니다.

`let`은 다음처럼 nullable 값 하나를 좁힐 때 좋습니다.

```kotlin
fun RegisterRequest.toOptionalReferral(): ReferralCode? =
    referralCode
        ?.trim()
        ?.takeIf { it.isNotBlank() }
        ?.let(::ReferralCode)
```

## `apply`는 설정에만 둡니다

`apply`는 원래 객체를 반환합니다. 그래서 builder나 test fixture 설정에 잘 맞습니다.

```kotlin
val objectMapper = ObjectMapper().apply {
    findAndRegisterModules()
    disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
}
```

테스트 fixture에서도 의도가 분명합니다.

```kotlin
val request = MockMvcRequestBuilders.post("/users").apply {
    contentType(MediaType.APPLICATION_JSON)
    content("""{"email":"user@example.com","displayName":"Kim"}""")
}
```

다만 entity 변경을 숨기는 데 쓰면 조심해야 합니다.

```kotlin
order.apply {
    status = OrderStatus.CANCELLED
    cancelledAt = clock.instant()
    cancellationReason = reason
}
```

이 코드가 틀렸다는 뜻은 아닙니다. 하지만 transaction 안의 핵심 상태 전이라면 명시적인 메서드가 더 낫습니다.

```kotlin
order.cancel(reason, clock.instant())
```

상태 변경에는 도메인 언어가 필요합니다. `apply`는 "여러 setter를 불렀다"만 말해 줍니다.

## `also`는 부수 효과를 감춥니다

`also`는 원래 값을 그대로 돌려주면서 중간에 일을 하나 더 합니다. 그래서 로깅이나 metric에 맞습니다.

```kotlin
fun create(command: RegisterCommand): User =
    userRepository.save(User.from(command))
        .also { saved ->
            auditLog.record("USER_CREATED", saved.id)
        }
```

이 패턴은 부수 효과가 작고 실패해도 전체 흐름을 어떻게 할지 분명할 때만 씁니다. 감사 로그 실패가 회원 생성
실패로 이어져야 한다면 `also` 안에 숨기지 말고 별도 단계로 꺼내야 합니다.

```kotlin
val saved = userRepository.save(User.from(command))
auditLog.recordUserCreated(saved.id)
return saved
```

읽는 사람이 "이 줄에서 저장만 하나?"라고 기대하는 위치에 중요한 외부 호출을 넣으면 안 됩니다.

## `run`과 `with`는 계산 결과가 필요할 때만 씁니다

`run`과 `with`는 lambda 결과를 반환합니다. 여러 값을 읽어 하나의 결과를 만들 때 적당합니다.

```kotlin
fun User.toResponse(): UserResponse =
    with(this) {
        UserResponse(
            id = id,
            email = email,
            displayName = profile.displayName,
        )
    }
```

하지만 단순 mapping에서는 일반 함수가 더 낫습니다.

```kotlin
fun User.toResponse(): UserResponse =
    UserResponse(
        id = id,
        email = email,
        displayName = profile.displayName,
    )
```

`with`가 줄 수를 크게 줄이지 못한다면 쓰지 않아도 됩니다. scope function은 표현력을 높이는 선택지이지,
Kotlin답게 보이기 위한 장식이 아닙니다.

## Java interop까지 보면 extension과 package도 보입니다

scope function은 대부분 Kotlin 안에서 읽는 문제지만, 서버 프로젝트에는 Java 코드가 남아 있을 수 있습니다.
Kotlin 공식 Java interop 문서 기준 package-level function과 extension function은 JVM에서 파일명 기반 class의
static method로 컴파일됩니다. 필요하면 `@file:JvmName`으로 Java에서 보이는 이름을 조정할 수 있습니다.

그래서 Java에서도 호출해야 하는 public helper라면 파일명과 package를 신중하게 정해야 합니다.

```kotlin
@file:JvmName("UserMappers")

package example.user

fun User.toResponse(): UserResponse =
    UserResponse(id = id, email = email)
```

Kotlin에서는 `user.toResponse()`로 읽히지만, Java에서는 생성된 utility method처럼 보입니다. 혼합 코드베이스라면
이 차이를 알고 공개 API 경계를 정해야 합니다.

## 실무 체크리스트

| 상황 | 먼저 선택할 표현 | 피할 표현 |
|---|---|---|
| nullable request field 정규화 | 지역 변수, `takeIf`, Elvis | 긴 `?.let { ... } ?: ...` chain |
| DTO 또는 test fixture 설정 | `apply` | 핵심 도메인 상태 전이를 `apply`에 숨기기 |
| 저장 뒤 작은 로그 남기기 | `also` | 실패 정책이 중요한 외부 호출을 `also`에 숨기기 |
| 여러 줄 계산 결과 만들기 | `run`, `with` | 중첩된 `this`와 `it` |
| Java 호출이 필요한 helper | package와 `@JvmName` 검토 | 파일명에 맡긴 public JVM 이름 |

## 연습 문제

1. 기존 Java builder 코드를 Kotlin `data class`와 `apply` 없이 바꿔 보세요. 값 객체에는 생성자만으로 충분한지
   먼저 확인합니다.
2. nullable request field를 `takeIf`와 Elvis 연산자로 정규화해 보세요. `!!`가 남아 있으면 실패 경계를 다시
   분리합니다.
3. service 메서드에 있는 `also`를 찾아 보세요. 그 안의 부수 효과가 실패해도 되는 일인지, 실패하면 transaction을
   중단해야 하는 일인지 분류합니다.
4. `apply`로 entity 필드를 여러 개 바꾸는 코드를 도메인 메서드로 바꿔 보세요. 테스트 이름이 더 자연스러워지는지
   확인합니다.
