> **검증 범위**
>
> 2026년 9월 13일 KST에 OpenTelemetry의 2026년 9월 11일 환경 변수 context propagation 글,
> OpenTelemetry context propagation 개념 문서, W3C Trace Context, W3C Baggage 문서를 확인했습니다.
> 환경 변수 carrier는 OpenTelemetry Specification의 **Release Candidate** 상태입니다. 따라서 이 글은 안정 기능으로
> 단정하지 않고, CI/CD와 batch 환경에서 무엇을 실험하고 어떤 보안 경계를 둬야 하는지에 초점을 둡니다.

## 이번 주에 이 기술이 중요했던 이유

HTTP API끼리 호출할 때 trace가 이어지는 것은 이제 익숙합니다. Spring Boot 서비스에서 `traceparent` header를 받고,
다음 service로 넘기고, collector가 spans를 모아 하나의 trace로 보여 주는 흐름입니다.

그런데 실제 장애 분석은 HTTP 경계 밖에서 끊어집니다.

- GitHub Actions job이 shell script를 실행합니다.
- shell script가 Gradle, Maven, Playwright, Docker build를 다시 실행합니다.
- Jenkins pipeline이 batch step, PowerShell step, container step을 이어 붙입니다.
- Argo Workflows가 Kubernetes Pod 여러 개를 순서대로 띄웁니다.
- Spring Batch job이 child process나 외부 command를 호출합니다.

이런 흐름은 네트워크 요청이 아니라 **process 생성**으로 이어집니다. header를 붙일 곳이 없습니다. 그래서 각 단계가
별도 trace로 쪼개지고, "테스트가 느렸는지, docker build가 느렸는지, 배치 내부 쿼리가 느렸는지"를 한 화면에서
따라가기 어렵습니다.

OpenTelemetry가 2026년 9월 11일 공개한 환경 변수 carrier RC는 이 빈틈을 다룹니다.

**프로세스가 자식 프로세스를 만들 때 trace context를 환경 변수로 주입하고, 자식이 그 값을 읽어 같은 trace에 붙게 하자는 제안입니다.**

## 핵심 개념

OpenTelemetry의 propagation은 context를 다음 실행 단위로 넘기는 일입니다. HTTP에서는 carrier가 header입니다.
message queue에서는 message attribute가 carrier가 됩니다. 이번 RC에서 다루는 carrier는 환경 변수입니다.

| 개념 | HTTP API에서의 감각 | CI/CD와 batch에서의 감각 |
|---|---|---|
| carrier | HTTP header | process environment |
| parent span | 요청을 받은 controller span | workflow job 또는 pipeline step span |
| child span | 다른 service 호출 | shell, test runner, build tool, container step |
| propagation field | `traceparent`, `tracestate`, baggage | `TRACEPARENT`, `TRACESTATE`, `BAGGAGE` |
| 위험 | header spoofing, baggage 과다 전달 | 환경 변수 노출, secret 오해, trust boundary 혼동 |

중요한 구분이 하나 있습니다. `TRACEPARENT`와 `TRACESTATE`는 trace를 이어 주는 값입니다. `OTEL_EXPORTER_OTLP_ENDPOINT`
같은 `OTEL_*` 변수는 SDK가 telemetry를 어디로 보낼지 정하는 설정입니다. 둘을 섞으면 안 됩니다.

trace context는 "이 작업이 어느 parent 작업에서 시작됐는가"를 말합니다. exporter 설정은 "이 telemetry를 어디로 보낼 것인가"를
말합니다. 전자는 흐름의 관계이고, 후자는 수집 파이프라인 설정입니다.

## 내부 동작 원리

Spring Boot 개발자에게 가장 가까운 비유는 servlet filter입니다. filter가 incoming request에서 context를 추출하고,
outgoing client가 context를 inject합니다. 환경 변수 carrier에서도 같은 일이 벌어지지만, 추출과 주입 지점이 HTTP가 아니라
process boundary입니다.

<Mermaid title="환경 변수 carrier로 이어지는 CI trace">
{`flowchart LR
  Job["CI job span"] --> Inject["환경 변수 주입"]
  Inject --> Shell["shell step"]
  Shell --> Build["Gradle 또는 Maven"]
  Build --> Test["test runner"]
  Test --> App["Spring Boot test context"]
  Job --> Collector["OpenTelemetry Collector"]
  Shell --> Collector
  Build --> Collector
  Test --> Collector
  App --> Collector
`}
</Mermaid>

흐름은 단순합니다.

1. workflow integration이 현재 span context를 읽습니다.
2. 자식 command를 실행하기 전에 `TRACEPARENT`, `TRACESTATE`, 필요한 경우 `BAGGAGE`를 환경 변수로 넣습니다.
3. 자식 process의 OpenTelemetry instrumentation이나 wrapper가 환경 변수에서 context를 추출합니다.
4. 자식 process가 만든 span은 부모 job span 아래에 붙습니다.

이 방식은 HTTP propagation을 대체하지 않습니다. 컨테이너 A에서 컨테이너 B로 자동 전파되는 것도 아닙니다. Kubernetes Pod는
서로의 process environment를 상속하지 않으므로 각 container step마다 별도 injection이 필요합니다.

## 어디에 쓰면 좋은가

첫 후보는 test pipeline입니다. 테스트가 12분 걸렸다는 사실보다 더 중요한 것은 12분이 어디에서 생겼는가입니다.

| 작업 | trace로 보고 싶은 질문 | 적용 후보 |
|---|---|---|
| unit test | 느린 test class가 build span 아래에 보이는가 | Gradle, Maven, JUnit |
| E2E test | browser setup, server boot, assertion 대기가 분리되는가 | Playwright, Cypress |
| image build | dependency download와 layer build가 분리되는가 | Docker, BuildKit |
| migration check | schema diff와 검증 쿼리가 분리되는가 | Flyway, Liquibase |
| batch job | 파일 다운로드, chunk 처리, 업로드가 이어지는가 | Spring Batch, shell wrapper |

두 번째 후보는 운영성 batch입니다. 예를 들어 정산 batch가 shell에서 시작되고, Java process를 띄우고, 다시 외부 command를
호출한다면 HTTP trace만으로는 전체 시간을 보기 어렵습니다. 환경 변수 carrier를 쓰면 "스케줄러가 시작한 한 번의 실행" 아래에
각 단계의 span을 묶어 볼 수 있습니다.

세 번째 후보는 agentic build workflow입니다. 코드 생성, 테스트, lint, browser check, commit 준비처럼 여러 tool을
순서대로 실행하는 workflow는 process tree가 길어집니다. trace context가 이어지면 실패한 마지막 step만 보는 대신,
어떤 도구가 반복적으로 시간을 쓰는지 볼 수 있습니다.

## Spring Boot 팀의 설계 기준

Spring Boot 서비스 코드에 바로 환경 변수 propagation을 넣기 전에 세 계층을 나누는 것이 좋습니다.

| 계층 | 책임 | 주의점 |
|---|---|---|
| pipeline wrapper | parent span 생성, 환경 변수 주입 | secret과 baggage를 섞지 않음 |
| build/test tool | 환경 변수에서 context 추출, child span 생성 | trace 미지원 도구는 wrapper로 감쌈 |
| application instrumentation | 기존 HTTP, JDBC, messaging span 생성 | HTTP header propagation과 역할을 분리 |

애플리케이션에서 할 일은 "모든 환경 변수를 읽어서 span에 붙이기"가 아닙니다. 오히려 반대입니다. trace context 필드만
정해진 propagator로 읽고, baggage는 최소화해야 합니다.

```text
허용:
TRACEPARENT=00-...-...-01
TRACESTATE=vendor=value
BAGGAGE=build.id=123,workflow.name=nightly

금지:
DATABASE_PASSWORD=...
ACCESS_TOKEN=...
PRIVATE_URL=...
```

환경 변수는 process 내부 모든 코드가 볼 수 있습니다. 운영 체제와 권한 구성에 따라 다른 process나 사용자에게 노출될 수도 있습니다.
따라서 propagation 변수는 secret 저장소가 아닙니다. baggage는 특히 조심해야 합니다. 사용자 식별자, 계정, 내부 URL, token,
원문 prompt 같은 값을 넣지 않는 것이 기본입니다.

## 자주 하는 오해

첫 번째 오해는 "환경 변수 carrier를 켜면 자동으로 span이 생긴다"입니다. carrier는 context를 운반할 뿐입니다.
span을 만들려면 wrapper, SDK, auto-instrumentation, test reporter 같은 실행 주체가 있어야 합니다.

두 번째 오해는 "CI job 하나에 trace 하나만 있으면 충분하다"입니다. 전체 job duration만 있으면 느린 원인을 알 수 없습니다.
download, compile, test, image build, deploy dry-run을 child span으로 나누어야 의미가 생깁니다.

세 번째 오해는 "`BAGGAGE`에 디버깅 정보를 많이 넣어도 된다"입니다. baggage는 downstream으로 전달되는 값입니다.
고카디널리티 값과 민감정보를 넣으면 비용, 보안, 저장 정책이 모두 흔들립니다.

네 번째 오해는 "RC니까 production에서 바로 표준으로 쓰면 된다"입니다. RC는 feedback을 받는 단계입니다. vendor와 language별
구현 상태, SDK version, collector 설정, 보안 정책을 좁은 pipeline에서 먼저 확인해야 합니다.

## 따라 해 볼 실험

작게 시작하려면 nightly test workflow 하나만 고릅니다.

```bash
# parent span을 만드는 wrapper가 있다고 가정한 예시
export TRACEPARENT="00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
export TRACESTATE="ci=nightly"
export BAGGAGE="workflow.name=nightly-test"

./gradlew test
npm run test:e2e
```

실제 적용에서는 위 값을 손으로 만들지 않습니다. pipeline integration이나 wrapper가 parent span을 만들고 자식 command에 주입해야
합니다. 손으로 값을 넣는 것은 propagation 흐름을 이해하기 위한 최소 실험일 뿐입니다.

검증표는 이렇게 둡니다.

```text
실험 범위: nightly test workflow
성공 기준:
  - workflow span 아래에 Gradle test span이 붙는다
  - E2E test span이 별도 trace로 갈라지지 않는다
  - baggage에 민감정보가 없다
  - exporter endpoint와 trace context 변수를 구분한다
  - context가 없어도 build는 실패하지 않는다
```

## 리스크와 적용 순서

적용 순서는 보수적으로 잡습니다.

1. OpenTelemetry collector와 backend가 CI telemetry를 받을 별도 dataset 또는 service name을 준비합니다.
2. nightly workflow 하나에서 wrapper 기반 parent span을 만듭니다.
3. `TRACEPARENT`, `TRACESTATE`만 먼저 전달하고, baggage는 비워 둡니다.
4. build/test 도구별 child span이 실제 parent 아래에 붙는지 확인합니다.
5. baggage가 필요하면 허용 key 목록을 만들고, 값 길이와 cardinality를 제한합니다.
6. Jenkins, GitHub Actions, Argo처럼 실행기가 달라지는 지점마다 별도 injection 여부를 확인합니다.

가장 중요한 원칙은 실패 방식입니다. propagation이 깨져도 build가 깨지면 안 됩니다. trace가 빠진 것은 관측성 저하이지,
업무 로직 실패가 아닙니다. 반대로 secret이 baggage로 흘러간 것은 즉시 차단해야 하는 보안 사고입니다.

## 다음에 확인할 지표

- CI job duration이 아니라 step별 duration이 분리되어 보이는지
- test runner span이 별도 trace로 갈라지는 비율
- `TRACEPARENT`가 없는 실행에서도 workflow가 정상 종료되는지
- baggage key 개수와 cardinality가 증가하지 않는지
- collector에서 CI telemetry와 production service telemetry가 섞이지 않는지
- RC가 stable로 승격될 때 변수 이름, validation rule, language support matrix가 바뀌는지

이번 주의 결론은 명확합니다. CI/CD와 batch 관측성의 빈칸은 "로그를 더 찍자"만으로 채워지지 않습니다.
프로세스 경계를 trace 경계로 인식하고, 환경 변수 carrier를 보안적으로 제한해 실험하면 build, test, batch의 느린 구간을
한 흐름으로 볼 수 있습니다. 단, 지금은 RC입니다. production 표준으로 박기보다 작은 pipeline에서 실패 방식과 보안 경계를
먼저 검증하는 것이 맞습니다.
