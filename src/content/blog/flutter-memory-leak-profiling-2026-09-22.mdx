## 결론부터 말하면

Flutter 메모리 문제는 "앱이 오래 켜져 있으면 무거워진다"는 말만으로는 원인을 찾기 어렵습니다. Spring Boot에서
`OutOfMemoryError`를 만나면 heap dump, allocation profile, GC log를 나눠 보듯이 Flutter에서도 **누수인지,
메모리 팽창인지, 정상적인 cache 증가인지**를 먼저 분리해야 합니다.

Flutter DevTools Memory view는 memory chart, Profile Memory, Diff Snapshots, Trace Instances를 제공합니다.
성능 글에서 frame jank를 UI thread와 raster thread로 나눴다면, 이번 글에서는 memory graph를 보고 retained object와
allocation path를 좁히는 흐름을 다룹니다.

## 이번 주 개념

공식 Memory view 문서는 Dart VM의 heap과 외부 메모리, raster cache, RSS를 구분해서 봐야 한다고 설명합니다.
Garbage collector가 unreachable object는 회수하지만, root에서 계속 참조되는 object는 앱이 더 이상 필요로 하지 않아도
살아남습니다. 그래서 `dispose()`가 필요한 객체, 오래 사는 static/global reference, closure가 잡고 있는 context가
문제가 됩니다.

| Flutter Memory view | 보는 것 | Spring Boot에 비유하면 |
|---|---|---|
| Memory chart | heap, RSS, raster cache 흐름 | heap usage, native memory, GC trend |
| Profile Memory | 현재 class별 allocation | heap histogram |
| Diff Snapshots | 동작 전후 object 증가 | heap dump diff |
| Trace Instances | 특정 class allocation stack | allocation profiler |
| Retaining path | object를 살려 두는 참조 경로 | GC root path |

## Java/Spring에서는 어떻게 다뤘는가

서버에서 메모리 문제가 생기면 먼저 증상을 나눕니다.

```java
class ReportCache {
    private static final Map<String, Report> reports = new ConcurrentHashMap<>();

    void remember(String id, Report report) {
        reports.put(id, report);
    }
}
```

위 코드는 요청마다 report를 저장하지만 삭제하지 않으면 누수가 됩니다. 반대로 큰 CSV를 한 번에 읽어 `List<Row>`로
올리는 코드는 누수라기보다 메모리 팽창입니다. 둘 다 RSS를 올릴 수 있지만 대응은 다릅니다. 누수는 참조를 끊어야 하고,
팽창은 처리 단위와 자료구조를 바꿔야 합니다.

Flutter도 같습니다. `TextEditingController`, `AnimationController`, `ScrollController`, stream subscription,
listener는 생명주기가 있습니다. 화면이 사라졌는데도 참조가 남으면 GC가 회수하지 못합니다.

## Flutter에서는 무엇이 다른가

Flutter 앱은 UI object, image, animation, platform resource가 같은 사용자 행동 안에서 같이 움직입니다. 화면 전환,
목록 스크롤, 사진 미리보기, route stack이 메모리 그래프에 동시에 나타납니다. 그래서 서버처럼 "요청 하나"만 보지 말고
"사용자 시나리오 하나"를 고정해야 합니다.

예를 들어 다음 시나리오를 세 번 반복합니다.

1. 목록 화면을 연다.
2. 상세 화면을 연다.
3. 이미지를 크게 본다.
4. 뒤로 돌아온다.

반복할 때마다 heap이 계속 올라가고 내려오지 않으면 누수 후보입니다. 한 번 크게 올라갔다가 안정되면 cache나 정상적인
warm-up일 수 있습니다. Memory view의 Diff Snapshots는 반복 전후에 어떤 class가 늘었는지 보여 줍니다.

## 대응 개념 비교

| Spring Boot 감각 | Flutter에서의 대응 | 질문 |
|---|---|---|
| heap dump diff | Diff Snapshots | 같은 행동 뒤 어떤 class가 계속 늘었나 |
| GC root path | retaining path | 누가 object를 계속 잡고 있나 |
| listener 해제 누락 | controller/listener/subscription dispose 누락 | 화면 종료 때 정리되는가 |
| 큰 collection | 큰 List, Map, decoded image | 정말 한 번에 들고 있어야 하나 |
| native memory | image/raster cache, platform resource | Dart heap 밖 메모리도 같이 늘었나 |

Flutter에서 특히 조심할 점은 `BuildContext`입니다. 공식 문서는 State가 widget보다 오래 살 수 있으므로 State field가
짧은 생명주기의 context를 붙잡는 상황을 경계하라고 설명합니다. callback이 widget보다 오래 살면 context 대신 필요한
작은 값만 저장하는 편이 안전합니다.

## 최소 실행 예제: listener는 붙인 곳에서 떼어냅니다

아래 코드는 검색 입력의 변화를 view model에 전달합니다.

```dart
class SearchPageState extends State<SearchPage> {
  final controller = TextEditingController();

  @override
  void initState() {
    super.initState();
    controller.addListener(_onQueryChanged);
  }

  void _onQueryChanged() {
    widget.viewModel.search(controller.text);
  }

  @override
  Widget build(BuildContext context) {
    return TextField(controller: controller);
  }
}
```

문제는 화면이 사라질 때 listener와 controller가 정리되지 않는다는 점입니다.

```dart
class SearchPageState extends State<SearchPage> {
  final controller = TextEditingController();

  @override
  void initState() {
    super.initState();
    controller.addListener(_onQueryChanged);
  }

  void _onQueryChanged() {
    widget.viewModel.search(controller.text);
  }

  @override
  void dispose() {
    controller.removeListener(_onQueryChanged);
    controller.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return TextField(controller: controller);
  }
}
```

Spring Boot에서 `@PreDestroy`나 connection close를 빼먹으면 resource가 남듯, Flutter에서도 생명주기가 있는 객체는
`dispose()`에서 정리해야 합니다. 단, 모든 객체에 dispose가 필요한 것은 아닙니다. disposable object인지 먼저 확인하고,
정리 책임이 어느 widget/state/view model에 있는지 정합니다.

## Memory view에서 보는 순서

먼저 profile mode로 앱을 실행합니다. 디버그 빌드는 개발 편의 기능 때문에 메모리와 성능 판단이 흐려질 수 있습니다.

```bash
flutter run --profile
```

그다음 DevTools Memory view에서 다음 순서로 봅니다.

| 단계 | 볼 곳 | 판단 |
|---|---|---|
| 1 | Memory chart | 반복 시나리오 뒤 heap/RSS가 회복되는지 봅니다. |
| 2 | Profile Memory | 어떤 class가 큰 비중을 차지하는지 확인합니다. |
| 3 | Diff Snapshots | 동작 전후 증가한 class를 찾습니다. |
| 4 | Trace Instances | 의심 class가 어디에서 생성되는지 봅니다. |
| 5 | Retaining path | 누가 object를 계속 붙잡고 있는지 확인합니다. |

Memory chart에서 RSS만 늘고 Dart heap은 안정적이면 native memory, image, raster cache 쪽도 봐야 합니다. 반대로 특정
Dart class instance가 반복마다 계속 늘면 listener, controller, stream, route, cache map을 먼저 확인합니다.

## 누수와 팽창을 구분합니다

메모리 누수는 "필요 없어졌는데도 참조가 남아 회수되지 않는 object"입니다. 메모리 팽창은 "필요하긴 하지만 너무 많이
들고 있는 상태"입니다. 둘은 그래프가 다르게 보입니다.

| 증상 | 흔한 원인 | 첫 대응 |
|---|---|---|
| 반복할수록 계단식 증가 | listener/subscription 해제 누락 | dispose와 retaining path 확인 |
| 한 번 크게 증가 후 유지 | 큰 목록, image preload, cache | page size, thumbnail, cache 정책 확인 |
| 화면 전환 후 route 관련 object 유지 | Navigator stack 또는 callback 참조 | route 생명주기와 closure 확인 |
| raster cache가 크게 증가 | 큰 image, clip/shadow, layer cache | 이미지 해상도와 rendering 효과 점검 |

Spring Boot에서 모든 메모리 증가를 "leak"이라고 부르면 원인 분석이 흐려집니다. Flutter도 마찬가지입니다. 먼저
증가가 반복 누적인지, 정상 cache인지, 큰 데이터 모델 때문인지 분리해야 수정이 작아집니다.

## 실무 체크리스트

- [ ] 같은 사용자 시나리오를 profile mode에서 세 번 반복한다.
- [ ] Memory chart에서 heap, RSS, raster cache를 따로 본다.
- [ ] 반복 전후 Diff Snapshot을 찍고 계속 늘어나는 class를 찾는다.
- [ ] disposable object는 `dispose()`에서 정리되는지 확인한다.
- [ ] callback이 State보다 오래 살 수 있다면 `BuildContext`나 큰 object를 잡지 않는지 본다.
- [ ] 큰 이미지와 긴 목록은 누수보다 메모리 팽창 문제일 수 있음을 분리한다.
- [ ] 수정 후 같은 시나리오로 다시 측정하고 snapshot을 보관한다.

## 연습 문제

1. 기존 화면 하나에서 `TextEditingController`, `AnimationController`, `ScrollController`, stream subscription을 찾습니다.
2. 각 객체의 생성 위치와 정리 위치를 한 줄로 적습니다.
3. Memory view에서 화면 진입과 이탈 전후 snapshot을 찍습니다.
4. Diff Snapshots에서 해당 화면 관련 class가 남는지 확인합니다.
5. 남는 class가 있다면 retaining path를 보고 참조를 끊을 최소 수정만 적용합니다.
