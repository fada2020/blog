## 결론부터 말하면

Flutter 앱 생명주기는 "화면이 보인다/안 보인다" 정도의 이벤트가 아닙니다. 인증 세션 재검증, 위치 권한 재확인, 임시 입력 저장,
타이머 중지, socket 재연결처럼 **앱 밖에서 시간이 흐른 뒤 다시 들어오는 경계**를 다루는 장치입니다.

Spring Boot 개발자에게 비유하면 request 하나의 lifecycle보다는 application lifecycle과 graceful shutdown, scheduled job resume,
health check 재검증을 섞어 놓은 감각에 가깝습니다. 사용자가 앱 전환기, 권한 설정, 전화, 잠금 화면, 브라우저 결제 화면을 거쳐
돌아오면 앱은 같은 프로세스처럼 보이지만, 외부 조건은 이미 바뀌었을 수 있습니다.

## 이번 주 개념

Flutter의 `AppLifecycleState`는 앱이 실행 중일 때의 상태를 나타냅니다. 공식 API 문서는 모든 플랫폼이 같은 상태를 그대로 제공하지
않기 때문에 Flutter가 일부 상태를 합성해 공통 state machine을 맞춘다고 설명합니다. 또한 앱이 갑자기 종료되면 모든 알림을 받을 수
있다고 가정해서는 안 됩니다.

핵심 상태는 이렇게 나눠서 기억하면 편합니다.

- `resumed`: 보이고 입력을 받을 수 있는 상태입니다. Spring Boot로 치면 serving 상태의 application입니다.
- `inactive`: 보일 수 있지만 입력 focus가 없는 상태입니다. traffic은 있지만 잠시 gate가 내려간 상태에 가깝습니다.
- `hidden`: 모든 view가 숨겨진 상태입니다. 외부 load balancer에서 빠지기 직전의 drain 신호처럼 다룹니다.
- `paused`: 모바일에서 보이지 않고 frame callback도 멈춘 상태입니다. background로 내려간 worker처럼 생각합니다.
- `detached`: engine은 있으나 host view와 떨어진 상태입니다. runtime은 있으나 endpoint가 붙지 않은 상태입니다.
- `AppLifecycleListener`: 상태 전환 callback을 등록하는 객체입니다. application lifecycle event listener 역할을 합니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 요청이 들어오고 응답이 나가는 경계가 명확합니다. 요청이 끝나면 transaction을 닫고, connection을 반환하고,
MDC를 정리합니다. 애플리케이션 자체가 내려갈 때는 `SmartLifecycle`, shutdown hook, readiness probe로 새 traffic을 막고
진행 중인 작업을 마무리합니다.

```java
@Component
class ShutdownState implements SmartLifecycle {
    private volatile boolean running;

    @Override
    public void start() {
        running = true;
    }

    @Override
    public void stop() {
        running = false;
        // 새 작업을 막고, 진행 중인 작업을 정리한다.
    }

    @Override
    public boolean isRunning() {
        return running;
    }
}
```

Flutter에는 사용자의 앱 전환이 이보다 자주 일어납니다. 앱은 종료되지 않았지만 화면이 숨겨지고, 몇 초 뒤 다시 돌아오고, 권한이나
네트워크가 바뀐 채 계속됩니다. 따라서 lifecycle event를 "종료 준비"로만 보면 부족합니다.

## Flutter에서는 무엇이 다른가

공식 API는 현재 lifecycle state를 `SchedulerBinding`에서 읽을 수 있고, 변경은 `AppLifecycleListener`나
`WidgetsBindingObserver`의 lifecycle callback으로 관찰하라고 설명합니다. 새 코드에서는 callback 단위가 분명한
`AppLifecycleListener`가 읽기 좋습니다.

```dart
import 'package:flutter/widgets.dart';

class SessionLifecycleController {
  SessionLifecycleController({
    required this.refreshSession,
    required this.saveDraft,
    required this.pauseRealtime,
  }) {
    _listener = AppLifecycleListener(
      onResume: refreshSession,
      onHide: pauseRealtime,
      onPause: saveDraft,
      onDetach: saveDraft,
      onStateChange: (state) {
        debugPrint('app lifecycle changed: $state');
      },
    );
  }

  final Future<void> Function() refreshSession;
  final VoidCallback saveDraft;
  final VoidCallback pauseRealtime;

  late final AppLifecycleListener _listener;

  void dispose() {
    _listener.dispose();
  }
}
```

핵심은 callback 안에서 너무 많은 일을 직접 하지 않는 것입니다. 생명주기 callback은 "무슨 일이 필요하다"는 신호로 보고, 실제
네트워크 재검증, 저장, stream 재연결은 작은 service method로 분리합니다.

## `resumed`에서 무엇을 다시 확인할까

사용자가 앱 밖으로 나갔다 돌아오면 다음 값이 바뀌었을 수 있습니다.

재개 시점에는 다음 항목을 작게 다시 확인합니다.

- 인증 token: 서버 session이 만료되었거나 refresh가 실패했을 수 있으므로 `/me` 또는 session status를 다시 조회합니다.
- 권한: 설정 앱에서 알림, 위치, 사진 권한이 바뀌었을 수 있으므로 permission plugin으로 현재 상태를 다시 읽습니다.
- 원격 설정: feature flag나 maintenance banner가 바뀔 수 있으므로 짧은 TTL cache를 재검증합니다.
- 결제와 외부 인증 결과: 브라우저나 외부 앱을 거쳐 돌아온 뒤 pending transaction 상태를 조회합니다.
- 실시간 연결: socket, stream, subscription이 끊겼을 수 있으므로 foreground에서 재연결합니다.

Spring에서 request마다 security context를 새로 확인하듯, Flutter도 foreground 복귀 시점에 "이전 화면 state가 아직 유효한가"를
묻는 습관이 필요합니다.

```dart
Future<void> refreshOnResume() async {
  final session = await authRepository.fetchSessionStatus();

  if (!session.isValid) {
    router.go('/login');
    return;
  }

  await inboxRepository.refreshIfStale(maxAge: const Duration(minutes: 5));
}
```

단, `resumed`가 올 때마다 무조건 무거운 API를 호출하면 앱 전환이 잦은 사용자에게 비용과 지연을 만듭니다. TTL, debounce,
현재 route를 함께 보세요.

## `hidden`과 `paused`에서 무엇을 저장할까

`AppLifecycleState.hidden`은 모든 view가 사용자에게 보이지 않는 상태를 나타냅니다. migration guide에 따르면 이 값은 stable
3.13.0부터 들어왔고, exhaustive switch를 쓰는 코드는 `hidden` case를 추가해야 합니다. 모바일에서는 `inactive`와 `paused` 사이를
지날 때 합성될 수 있습니다.

저장 전략은 짧고 보수적으로 잡습니다. 앱이 갑자기 종료되면 알림을 못 받을 수 있으므로, 중요한 데이터는 lifecycle callback 하나에만
의존하지 않습니다.

저장 전략은 데이터 성격별로 나눕니다.

- form draft: 입력 중 debounce와 `hidden`에서 저장하되, callback에서 큰 직렬화를 하지 않습니다.
- scroll position: route state 또는 restoration으로 다루고 business data와 분리합니다.
- upload queue: enqueue 시점에 저장하고 background 전환 때 처음 만들지 않습니다.
- analytics event: 짧은 buffer flush만 시도하고 실패해도 사용자 흐름을 막지 않습니다.

```dart
void handleLifecycleState(AppLifecycleState state) {
  switch (state) {
    case AppLifecycleState.resumed:
      unawaited(refreshOnResume());
    case AppLifecycleState.inactive:
      saveDraftLightly();
    case AppLifecycleState.hidden:
    case AppLifecycleState.paused:
      pauseRealtimeAndFlushDraft();
    case AppLifecycleState.detached:
      disposeNativeHandles();
  }
}
```

`switch`를 쓸 때는 새 enum 값이 추가될 수 있다는 사실도 고려해야 합니다. 안정 버전 기준으로 모든 case를 다루되, 값의 의미를
주석 대신 함수 이름으로 드러내는 편이 유지보수에 좋습니다.

## `WidgetsBindingObserver`를 직접 쓰는 경우

기존 코드나 widget 단위 관찰에는 `WidgetsBindingObserver`가 여전히 자주 쓰입니다. 이 방식은 observer 등록과 해제를 직접 관리해야
합니다.

```dart
class LifecycleAwarePageState extends State<LifecycleAwarePage>
    with WidgetsBindingObserver {
  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addObserver(this);
  }

  @override
  void dispose() {
    WidgetsBinding.instance.removeObserver(this);
    super.dispose();
  }

  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    handleLifecycleState(state);
  }
}
```

Spring에서 listener를 등록하고 해제하지 않아 memory leak을 만드는 것처럼, Flutter에서도 observer를 추가했다면 `dispose`에서
반드시 제거합니다. 앱 전체 정책이면 controller/service에 `AppLifecycleListener`를 두고, 화면 한정 정책이면 widget의 생명주기에
맞춰 observer를 둡니다.

## Java 개발자가 자주 하는 오해

1. **"`paused`에서 반드시 저장하면 안전하다."**  
   공식 API는 갑작스러운 종료나 일부 상태 skip을 경고합니다. 중요한 값은 입력 시점이나 queue 등록 시점에 이미 저장해야 합니다.

2. **"`resumed`는 앱이 처음 켜질 때만 온다."**  
   앱 전환, 권한 설정, 외부 인증, 전화 interrupt 뒤에도 올 수 있습니다. 재검증 로직은 idempotent해야 합니다.

3. **"`inactive`는 background와 같다."**  
   플랫폼마다 의미가 다릅니다. Android의 focus loss, iOS의 foreground inactive처럼 보이지만 입력만 막힌 상태도 있습니다.

4. **"lifecycle callback에서 route 이동과 API 호출을 마음껏 해도 된다."**  
   callback은 짧게 유지하고, mounted 여부, 현재 route, 중복 호출 방지를 확인해야 합니다.

## 연습 문제

1. 앱이 foreground로 돌아올 때 `/me` API를 다시 조회하되, 마지막 조회 후 3분이 지나지 않았으면 생략하는 함수를 만들어 보세요.
2. 사용자가 알림 권한 설정 화면을 다녀온 뒤 `resumed`에서 권한 상태를 다시 읽고 UI badge를 갱신하는 흐름을 설계해 보세요.
3. `AppLifecycleState.hidden`과 `paused`에서 같은 저장 함수를 호출할 때, 어떤 저장은 입력 즉시 처리해야 하는지 따로 표시해 보세요.
