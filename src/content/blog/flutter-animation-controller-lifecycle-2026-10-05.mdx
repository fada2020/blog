## 결론부터 말하면

Flutter animation은 "예쁘게 움직이기"보다 먼저 **누가 시간을 소유하고, 언제 멈추고, 언제 해제하는가**의 문제입니다.
작은 색상 변화나 크기 변화는 `AnimatedContainer` 같은 implicit animation으로 충분합니다. 하지만 재생, 역재생,
연쇄 실행, drag progress 같은 제어가 필요하면 `AnimationController`가 필요합니다.

Spring Boot 개발자에게 비유하면, implicit animation은 framework가 알아서 실행하는 짧은 transition이고,
`AnimationController`는 `TaskScheduler`나 `ExecutorService`처럼 직접 소유권과 종료 시점을 관리해야 하는 자원에 가깝습니다.

## 이번 주 개념

Flutter 공식 animation 문서는 implicit animation과 explicit animation을 나누어 설명합니다. 핵심 기준은 단순합니다.
값이 바뀔 때 framework가 알아서 보간해도 되면 implicit animation, 시작과 정지와 진행률을 직접 제어해야 하면 explicit
animation입니다.

| Flutter 개념 | 역할 | Spring Boot에 비유하면 |
|---|---|---|
| `AnimatedContainer` | 속성 변경을 자동 보간 | framework가 처리하는 기본 transition |
| `AnimationController` | animation 시간을 직접 제어 | scheduler handle 또는 실행 중 job |
| `TickerProvider` | frame tick을 공급 | 실행 주기와 lifecycle을 연결하는 owner |
| `TickerMode` | subtree 비활성 시 tick 억제 | 비활성 profile의 scheduler pause |
| `dispose()` | controller 자원 해제 | executor shutdown 또는 listener 해제 |

## Java/Spring에서는 어떻게 다뤘는가

Spring에서는 짧은 요청 처리와 오래 살아 있는 실행 자원을 구분합니다. Controller method 안에서 `ExecutorService`를 새로 만들고
버리지 않으면 thread가 남습니다. 반대로 application lifecycle에 묶인 scheduler는 시작과 종료를 명확히 둡니다.

```java
@Component
class ReportWarmupJob {
    private final TaskScheduler scheduler;

    ReportWarmupJob(TaskScheduler scheduler) {
        this.scheduler = scheduler;
    }

    void schedule() {
        scheduler.schedule(this::warmup, Instant.now().plusSeconds(1));
    }

    private void warmup() {
        // 짧은 background work
    }
}
```

Flutter에서도 같은 감각이 필요합니다. `build()`는 여러 번 호출될 수 있습니다. 매번 controller를 만들면 같은 화면에 여러 clock이
생기는 셈입니다. 그래서 controller는 `State.initState()`에서 만들고, `State.dispose()`에서 해제합니다.

## Flutter에서는 무엇이 다른가

Flutter animation은 화면 frame과 직접 연결됩니다. 공식 `AnimationController` 문서는 controller가 주어진 duration 동안
기본적으로 0.0에서 1.0까지 값을 만들며, animation 중에는 기기가 새 frame을 표시할 준비가 될 때마다 새 값을 만든다고 설명합니다.

여기서 `vsync`가 중요합니다. `AnimationController` 생성자에는 `TickerProvider`가 필요합니다. 보통 해당 `State`가
`SingleTickerProviderStateMixin`이나 `TickerProviderStateMixin`을 적용해 ticker provider가 됩니다.

```dart
class SaveButtonState extends State<SaveButton>
    with SingleTickerProviderStateMixin {
  late final AnimationController _controller;

  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
      vsync: this,
      duration: const Duration(milliseconds: 220),
    );
  }

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }
}
```

`vsync`는 배터리와 성능을 위해 필요합니다. 현재 subtree가 비활성화되어 tick을 낼 필요가 없을 때 불필요한 frame update를 줄일 수
있습니다. Spring에서 사용하지 않는 polling job을 계속 돌리지 않는 것과 같은 운영 감각입니다.

## implicit animation부터 시작하기

상태가 바뀔 때 색상, 크기, padding 정도만 부드럽게 바꾸고 싶다면 `AnimationController`를 직접 들지 않아도 됩니다.

```dart
class SaveStatusBadge extends StatelessWidget {
  const SaveStatusBadge({super.key, required this.saved});

  final bool saved;

  @override
  Widget build(BuildContext context) {
    return AnimatedContainer(
      duration: const Duration(milliseconds: 180),
      curve: Curves.easeOut,
      padding: const EdgeInsets.symmetric(horizontal: 12, vertical: 8),
      decoration: BoxDecoration(
        color: saved ? Colors.green.shade100 : Colors.orange.shade100,
        borderRadius: BorderRadius.circular(8),
      ),
      child: Text(saved ? 'Saved' : 'Saving'),
    );
  }
}
```

이 구조는 Spring MVC에서 기본 validation message를 view에 다시 그리는 느낌과 비슷합니다. "어떻게 움직일지"를 framework에
맡기고, widget은 목표 상태만 선언합니다.

## explicit animation이 필요한 순간

다음 중 하나가 필요하면 controller를 직접 소유하는 편이 낫습니다.

| 요구사항 | implicit으로 충분한가 | 이유 |
|---|---|---|
| 저장 상태에 따라 색상만 변경 | 충분 | 목표 값만 바꾸면 됨 |
| 사용자가 누르면 progress를 처음부터 재생 | controller 권장 | `forward(from: 0)` 필요 |
| 실패 시 역재생 | controller 필요 | `reverse()` 제어 필요 |
| 여러 animation을 순서대로 실행 | controller 필요 | `TickerFuture`와 취소 처리 필요 |
| drag 위치와 animation progress 동기화 | controller 필요 | value를 직접 조정 |

예를 들어 저장 버튼을 누르면 아이콘이 살짝 확장됐다가 돌아오는 micro interaction을 만들 수 있습니다.

```dart
class PulseSaveButtonState extends State<PulseSaveButton>
    with SingleTickerProviderStateMixin {
  late final AnimationController _controller;
  late final Animation<double> _scale;

  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
      vsync: this,
      duration: const Duration(milliseconds: 180),
    );
    _scale = Tween<double>(begin: 1, end: 1.08).animate(
      CurvedAnimation(parent: _controller, curve: Curves.easeOut),
    );
  }

  Future<void> playPulse() async {
    await _controller.forward(from: 0);
    await _controller.reverse();
  }

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return ScaleTransition(
      scale: _scale,
      child: IconButton(
        icon: const Icon(Icons.save),
        onPressed: playPulse,
      ),
    );
  }
}
```

## `TickerFuture`와 취소를 가볍게 보지 않기

`AnimationController.forward()` 같은 method는 `TickerFuture`를 반환합니다. 공식 문서는 animation이 취소되면 일반 future가
완료되지 않을 수 있고, `orCancel`은 취소 시 error로 완료된다고 설명합니다.

화면이 사라졌는데 animation 완료 후 `setState()`를 호출하면 흔한 lifecycle bug가 됩니다. controller를 `dispose()`하면 진행 중인
animation은 취소됩니다. 그래서 연쇄 animation을 기다릴 때는 취소 가능성을 코드에 드러내는 편이 안전합니다.

```dart
Future<void> closeThenSubmit() async {
  try {
    await _controller.reverse().orCancel;
    if (!mounted) return;
    widget.onSubmit();
  } on TickerCanceled {
    // 화면이 사라져 animation이 취소된 상황은 정상 lifecycle로 본다.
  }
}
```

Spring에서 client가 연결을 끊었는데도 긴 작업 결과를 response에 쓰려 하면 의미가 없어지는 것과 비슷합니다. UI lifecycle에서는
취소가 실패가 아니라 정상 경로일 수 있습니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 animation을 `build()` 안에서 시작해도 된다는 생각입니다. `build()`는 상태 변경, 부모 rebuild, theme 변경으로
반복 호출됩니다. animation 시작은 event handler, `initState()`, 명확한 lifecycle callback에서 다룹니다.

두 번째 오해는 controller를 많이 만들수록 정교하다는 생각입니다. 여러 값이 같은 시간축을 공유한다면 controller 하나에 여러
`Tween`을 붙이는 편이 단순합니다.

세 번째 오해는 animation이 business state를 대신할 수 있다는 생각입니다. 저장 성공 여부, 결제 상태, 권한 상태는 animation 값이
아니라 domain state입니다. animation은 그 state를 사용자에게 이해하기 쉽게 보여 주는 layer입니다.

## 연습 문제

1. 현재 Flutter 화면에서 `AnimatedContainer`, `AnimatedOpacity`, `AnimatedSwitcher`로 충분한 상호작용을 하나 찾습니다.
2. 같은 화면에서 시작, 정지, 역재생이 필요한 animation을 하나 고릅니다.
3. controller를 `initState()`에서 만들고 `dispose()`에서 해제하는지 확인합니다.
4. 완료 callback에서 `setState()`를 호출한다면 화면 dispose 시나리오를 적어 봅니다.
5. business state와 animation state가 섞인 변수명을 분리합니다.
