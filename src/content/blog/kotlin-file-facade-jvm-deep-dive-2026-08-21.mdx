## 결론부터 말하면

Kotlin의 top-level 함수는 "클래스 없이 실행되는 마법"이 아닙니다. 소스 코드에서는 파일과 패키지에
직접 속하지만, JVM으로 컴파일될 때는 Java가 호출할 수 있는 정적 메서드 형태로 노출됩니다.

그래서 Spring Boot 개발자가 Kotlin을 팀 코드에 섞기 시작할 때는 두 가지 관점을 동시에 가져야 합니다.

- Kotlin을 읽는 사람에게는 파일, 패키지, 함수 이름이 설계 경계입니다.
- Java와 JVM 도구에게는 컴파일러가 만든 file facade 클래스와 정적 메서드 이름이 계약입니다.

top-level 선언은 작은 순수 함수, 변환기, 테스트 헬퍼를 간결하게 만들 때 좋습니다. 반대로 Java에서
호출되는 공개 API, Spring bean 생명주기, 상태를 가진 도메인 동작까지 top-level로 밀어 넣으면 경계가
흐려집니다. 이번 글은 전날 Kotlin 첫걸음 글에서 다룬 top-level 감각을 JVM 상호운용 관점으로 한 단계
더 깊게 봅니다.

## 이번 주에 이 기술이 중요했던 이유

이번 주 Kotlin 입문 글에서는 Java 클래스 중심 사고를 잠시 내려놓고 top-level 함수로 프로그램을 시작하는
감각을 잡았습니다. 그 다음 질문은 자연스럽습니다.

**클래스 밖에 쓴 함수가 JVM에서는 어디에 생기며, Java 코드에서는 어떻게 부를 수 있을까요?**

이 질문은 단순한 내부 구현 호기심이 아닙니다. Kotlin을 Spring Boot 프로젝트에 도입하면 한동안 Java와
Kotlin 코드가 함께 존재합니다. 테스트, 공통 모듈, Gradle task, 사내 라이브러리, 기존 Java 서비스가
Kotlin 함수를 직접 호출할 수도 있습니다. 이때 top-level 선언의 컴파일 결과를 모르면 다음 문제가 생깁니다.

| 상황 | 모르면 생기는 문제 |
|---|---|
| Java 코드가 Kotlin top-level 함수를 호출함 | `SomeFileKt.someFunction()` 같은 이름이 갑자기 공개 API처럼 굳어집니다. |
| 파일 이름을 바꿈 | Java 호출 코드나 리플렉션 기반 설정이 깨질 수 있습니다. |
| 같은 패키지에 같은 파일 이름을 둠 | JVM class 이름 충돌로 컴파일이 실패할 수 있습니다. |
| 모든 유틸을 top-level로 둠 | Spring bean, 도메인 객체, 순수 함수의 경계가 흐려집니다. |

Kotlin 소스의 간결함은 장점입니다. 다만 JVM 위에서 운영되는 서비스라면 컴파일 뒤의 이름과 호출 경계까지
같이 설계해야 합니다.

## 핵심 개념: 패키지가 소스 경계이고 파일 이름이 JVM 이름에 영향을 줍니다

Kotlin 파일은 `package` 헤더로 패키지에 연결됩니다. 파일 안에 선언한 클래스, 함수, 프로퍼티는 모두 그
패키지에 속합니다. 공식 문서 기준 top-level 함수와 프로퍼티는 클래스뿐 아니라 패키지 안의 직접 선언으로
import할 수 있습니다.

```kotlin
package com.example.billing

const val DEFAULT_CURRENCY = "KRW"

fun formatAmount(amount: Long): String {
    return "%,d %s".format(amount, DEFAULT_CURRENCY)
}

class Invoice(
    val id: Long,
    val amount: Long,
)
```

Kotlin 코드에서는 아래처럼 함수와 프로퍼티를 직접 가져올 수 있습니다.

```kotlin
package com.example.order

import com.example.billing.DEFAULT_CURRENCY
import com.example.billing.formatAmount

fun renderOrderTotal(total: Long): String {
    return "결제 금액: ${formatAmount(total)} / 통화: $DEFAULT_CURRENCY"
}
```

Java에 익숙한 눈에는 클래스 이름 없이 함수가 import되는 점이 낯설 수 있습니다. 하지만 Kotlin에서는
패키지와 파일이 소스 조직의 중요한 단위입니다. 작은 변환 함수 하나를 억지로 `BillingUtils` 같은 클래스로
감쌀 필요가 없습니다.

다만 JVM은 top-level 멤버를 직접 담을 수 없습니다. Kotlin/JVM 컴파일러는 이를 감싸는 클래스를 만듭니다.
공식 coding conventions 문서는 이 wrapper class를 file facade라고 설명합니다. 기본 이름은 파일 이름에서
나옵니다.

## 내부 동작 원리: Java에서는 정적 메서드처럼 보입니다

예를 들어 파일 이름이 `Amounts.kt`라면 Kotlin/JVM은 top-level 선언을 담는 `AmountsKt` 형태의 클래스를
만들 수 있습니다.

```text
src/main/kotlin/com/example/billing/Amounts.kt
```

```kotlin
package com.example.billing

fun formatAmount(amount: Long): String {
    return "%,d KRW".format(amount)
}
```

Java 호출 코드는 대략 아래처럼 보입니다.

```java
package com.example.order;

import com.example.billing.AmountsKt;

class OrderMessage {
    String render(long total) {
        return AmountsKt.formatAmount(total);
    }
}
```

중요한 점은 `AmountsKt`라는 이름이 Kotlin 소스에 직접 존재하지 않는다는 것입니다. Java와 일부 JVM 도구가
보는 컴파일 결과 이름입니다. Kotlin 쪽에서는 여전히 `formatAmount()`라는 top-level 함수로 읽습니다.

<Mermaid title="Kotlin top-level 선언과 JVM 노출 흐름">
{`flowchart LR
  Source["Amounts.kt<br/>package com.example.billing"] --> TopLevel["top-level function<br/>formatAmount"]
  TopLevel --> Compiler["Kotlin/JVM compiler"]
  Compiler --> Facade["file facade<br/>AmountsKt"]
  Facade --> JavaCall["Java call<br/>AmountsKt.formatAmount(total)"]
  TopLevel --> KotlinCall["Kotlin call<br/>formatAmount(total)"]
`}
</Mermaid>

이 구조를 알면 파일 이름 변경도 더 신중해집니다. Kotlin 내부에서만 쓰는 함수라면 파일 이름 변경은 보통
IDE가 처리합니다. 하지만 Java 코드, public library consumer, 리플렉션, 문서화된 샘플이 `AmountsKt`를
직접 참조한다면 파일 이름이 API 이름처럼 동작합니다.

## 실무 설계 선택지: top-level, object, companion object를 구분합니다

Spring Boot 프로젝트에서 모든 것을 top-level로 둘 필요는 없습니다. 반대로 Java 때처럼 모든 것을
`final class XxxUtils`로 되돌릴 필요도 없습니다. 기준은 호출 경계와 상태입니다.

| 선택지 | 적합한 경우 | 주의할 점 |
|---|---|---|
| top-level 함수 | 상태 없는 변환, 검증, 작은 factory, 테스트 fixture | Java 호출 이름이 파일 이름에 묶일 수 있습니다. |
| top-level `const val` | 컴파일 타임 상수, annotation 값 | 환경값이나 변경 가능한 설정처럼 쓰면 안 됩니다. |
| `object` | 이름 있는 singleton, 전략 묶음, 명시적 namespace | 단순 namespace만 만들려고 남용하면 Java식 utility class로 돌아갑니다. |
| companion object | 클래스와 강하게 연결된 factory, Java static 호출 편의 | 도메인 객체 내부 책임과 생성 편의가 섞이지 않게 해야 합니다. |
| Spring bean class | 의존성 주입, transaction, 외부 리소스, 상태 경계 | 순수 계산만 있다면 bean이 과할 수 있습니다. |

예를 들어 금액 포맷팅처럼 입력만으로 결과가 정해지는 함수는 top-level이 충분할 수 있습니다.

```kotlin
package com.example.billing

fun formatAmount(amount: Long, currency: String): String {
    return "%,d %s".format(amount, currency)
}
```

반대로 repository, clock, message source, transaction 같은 외부 의존성이 필요하면 Spring bean이 맞습니다.

```kotlin
package com.example.billing

import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional

@Service
class BillingService(
    private val invoiceRepository: InvoiceRepository,
) {
    @Transactional(readOnly = true)
    fun findPrintableInvoice(id: Long): PrintableInvoice {
        val invoice = invoiceRepository.findByIdOrThrow(id)
        return PrintableInvoice(
            id = invoice.id,
            amountText = formatAmount(invoice.amount, invoice.currency),
        )
    }
}
```

여기서 `formatAmount()`는 top-level 순수 함수이고, `BillingService`는 Spring 생명주기와 transaction
경계를 가진 객체입니다. 두 역할을 분리하면 Kotlin의 간결함과 Spring의 운영 모델을 같이 살릴 수 있습니다.

## Java 상호운용을 공개 계약으로 볼 때의 기준

Kotlin만 소비하는 내부 모듈에서는 top-level 선언이 자연스럽습니다. 하지만 Java에서도 직접 호출해야 하는
라이브러리라면 이름을 더 보수적으로 다뤄야 합니다.

```kotlin
package com.example.billing

class BillingFormats private constructor() {
    companion object {
        @JvmStatic
        fun amount(amount: Long, currency: String): String {
            return formatAmount(amount, currency)
        }
    }
}

fun formatAmount(amount: Long, currency: String): String {
    return "%,d %s".format(amount, currency)
}
```

이렇게 하면 Java 호출부는 아래처럼 더 의도적인 이름을 사용할 수 있습니다.

```java
String text = BillingFormats.amount(12000L, "KRW");
```

항상 이렇게 해야 한다는 뜻은 아닙니다. 내부 서비스 코드에서 Java 호출자를 위해 모든 함수에 wrapper를
만들면 코드가 불필요하게 늘어납니다. 다만 이미 외부 팀이나 Java 모듈이 호출하는 API라면 "Kotlin에서
예쁘게 보이는 이름"과 "Java에서 안정적으로 유지할 이름"을 나눠 생각하는 편이 안전합니다.

## 흔한 실패 사례

### 1. 파일 이름을 가볍게 바꿨는데 Java 호출 코드가 깨집니다

`Amounts.kt`를 `MoneyFormatting.kt`로 바꾸면 Kotlin 호출부는 IDE가 대부분 따라갑니다. 하지만 Java 코드가
`AmountsKt.formatAmount()`를 직접 호출하고 있었다면 호출 이름이 달라질 수 있습니다.

대응 기준은 간단합니다.

| 함수 소비자 | 파일 이름 변경 위험 |
|---|---|
| Kotlin 내부에서만 호출 | 낮음 |
| 같은 저장소의 Java 코드가 호출 | 중간 |
| 외부 모듈이나 문서가 호출 | 높음 |

외부 계약이 된 함수라면 파일 이름을 사실상 API 이름처럼 취급하거나, Java용 wrapper를 별도로 둡니다.

### 2. 같은 패키지에 같은 파일 이름을 둬서 file facade가 충돌합니다

Kotlin coding conventions 문서는 JVM이 같은 fully qualified class name을 여러 개 허용하지 않는다는 점을
주의시킵니다. 특히 multiplatform이나 source set이 나뉜 프로젝트에서 같은 패키지와 같은 파일 이름을 쓰면
컴파일러가 같은 facade 이름을 만들 수 있습니다.

```text
commonMain/kotlin/com/example/Platform.kt
jvmMain/kotlin/com/example/Platform.kt
```

둘 다 top-level 선언을 가지고 JVM 대상으로 컴파일되면 facade 이름이 충돌할 수 있습니다. 그래서 플랫폼별
source set에는 `Platform.jvm.kt`, `Platform.android.kt`처럼 suffix를 두라는 공식 convention이 있습니다.

Spring Boot 단일 JVM 프로젝트에서도 원리는 같습니다. 파일 이름은 단순 정리용 메모가 아니라 JVM class
이름 후보가 됩니다.

### 3. Spring bean으로 관리되어야 할 코드를 top-level로 빼냅니다

top-level 함수는 의존성이 없는 계산에 좋습니다. 하지만 다음 코드처럼 repository 접근과 transaction 경계가
필요한 로직을 top-level 함수로 두면 Spring이 관리해야 할 책임이 흩어집니다.

```kotlin
fun closeInvoice(invoiceRepository: InvoiceRepository, id: Long) {
    val invoice = invoiceRepository.findByIdOrThrow(id)
    invoice.close()
}
```

이 함수는 입력으로 repository를 받으니 테스트하기 쉬워 보일 수 있습니다. 하지만 실제 업무 코드에서는
transaction, 권한, 이벤트 발행, 감사 로그 같은 경계가 함께 붙을 가능성이 큽니다. 이런 경우에는 service
class 안에 두고, top-level 함수는 순수 계산만 맡기는 편이 리뷰하기 쉽습니다.

## 독립 실행 실습

아래 실습은 Spring Boot 프로젝트가 없어도 Kotlin/JVM의 top-level 선언 노출 방식을 확인하는 용도입니다.
JDK와 Kotlin compiler 또는 Kotlin Gradle 프로젝트가 준비되어 있다면 같은 원리를 확인할 수 있습니다.

### 1. Kotlin 파일을 만듭니다

```kotlin
// src/main/kotlin/com/example/billing/Amounts.kt
package com.example.billing

fun formatAmount(amount: Long): String {
    return "%,d KRW".format(amount)
}
```

### 2. Java 호출 코드를 만듭니다

```java
// src/main/java/com/example/order/OrderMessage.java
package com.example.order;

import com.example.billing.AmountsKt;

public class OrderMessage {
    public String render(long total) {
        return AmountsKt.formatAmount(total);
    }
}
```

### 3. 파일 이름을 바꾸기 전에 호출 이름을 확인합니다

Kotlin Gradle Plugin `2.4.10` 기준으로 JVM 프로젝트를 구성했다면 `build/classes` 아래에서 컴파일 결과를
확인할 수 있습니다.

```bash
./gradlew clean compileKotlin compileJava
find build/classes -name '*Amounts*'
```

예상 관찰 포인트는 다음과 같습니다.

```text
Kotlin source: com/example/billing/Amounts.kt
JVM facade:   com/example/billing/AmountsKt.class
Java call:    AmountsKt.formatAmount(total)
```

### 4. 이름 변경의 영향을 확인합니다

`Amounts.kt`를 `MoneyFormatting.kt`로 바꾸고 다시 컴파일합니다. Java 코드가 여전히 `AmountsKt`를 import하고
있다면 실패할 수 있습니다. 이 실패는 Kotlin 함수가 사라졌다는 뜻이 아니라 Java에서 보던 facade 이름이
달라졌다는 신호입니다.

실무에서는 이 실습을 통해 다음 결정을 내릴 수 있습니다.

- Java 호출자가 없는 내부 함수라면 top-level을 편하게 씁니다.
- Java 호출자가 있는 함수라면 파일 이름을 API처럼 관리합니다.
- 외부 공개 API라면 Java용 wrapper나 명시적인 객체 이름을 둡니다.

## 정리

Kotlin top-level 선언은 Java의 utility class를 짧게 쓰는 문법만은 아닙니다. Kotlin 코드에서는 패키지와
파일을 중심으로 작은 함수를 자연스럽게 배치하게 해 주고, JVM에서는 file facade를 통해 Java가 호출 가능한
정적 멤버로 노출합니다.

Spring Boot 팀에서 Kotlin을 도입한다면 기준은 이렇게 잡는 편이 좋습니다.

| 질문 | 선택 |
|---|---|
| 입력만으로 결과가 정해지는 작은 함수인가 | top-level 함수 |
| Spring transaction이나 의존성 주입이 필요한가 | service 또는 component class |
| Java 호출자가 안정적인 이름을 기대하는가 | wrapper 또는 명시적 JVM API |
| 파일 이름 변경이 외부 계약을 바꿀 수 있는가 | API 변경으로 취급 |

소스가 간결해졌다고 설계 경계까지 사라지는 것은 아닙니다. Kotlin에서는 클래스 대신 파일과 패키지가 더
자주 경계를 드러냅니다. 그 경계가 JVM과 Java 호출 코드에서 어떻게 보이는지까지 확인하면, Kotlin을
Spring Boot 코드베이스에 더 차분하게 섞을 수 있습니다.
