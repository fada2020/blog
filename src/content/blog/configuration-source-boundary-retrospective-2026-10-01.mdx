> **검증 범위**
>
> 2026년 10월 1일에 AWS Systems Manager Parameter Store, Jenkins Credentials와 Credentials Binding,
> Terraform validate, OWASP Secrets Management 문서를 확인했습니다. 실제 업무일지의 조직명, 저장소명,
> 작업명, 계정, 운영 URL, 내부 경로와 식별 가능한 관리자 정보는 공개 글에서 일반화했습니다. 이 글은 설정 관리
> 기능을 설계하고 검증한 회고이며, 특정 운영 환경의 현재 연결 상태를 증명하는 글이 아닙니다.

## 결론부터 말하면

설정 관리 화면을 만들 때 가장 헷갈리는 지점은 "값을 저장했다"와 "서비스가 그 값을 사용한다"를 같은 상태로 보는 것입니다.
DB에 설정을 저장해도 런타임이 읽지 않으면 적용된 것이 아닙니다. SSM Parameter를 수정해도 배포 job이 그 경로를 보지 않으면
효과가 없습니다. Jenkins Credential을 갱신해도 Pipeline이 credential ID를 참조하지 않으면 실행 경로는 그대로입니다.

이번 회고의 핵심은 네 가지였습니다.

- 저장 위치별로 권한과 적용 범위를 다르게 표시했습니다.
- 비밀값은 원문 반환, 감사 로그 기록, 화면 재노출을 막았습니다.
- Jenkins 작업 파라미터는 허용된 job과 key만 바꾸도록 제한했습니다.
- Terraform 검증과 모의 화면 검증을 실제 클라우드 변경으로 과장하지 않았습니다.

## 문제가 된 모양

운영 설정은 한 종류가 아니었습니다.

| 설정 위치 | 예시 | 위험 |
|---|---|---|
| 애플리케이션 DB | 기능 토글, 공개 설정, 암호화된 비밀값 | 앱이 읽는 시점과 캐시 정책을 착각함 |
| SSM Parameter | 환경별 설정, SecureString | IAM scope와 KMS 권한이 넓어질 수 있음 |
| Jenkins job parameter | 배포 기본값, 대상 revision | Jenkinsfile이 다시 덮어쓸 수 있음 |
| Jenkins Credentials | 토큰, 사용자명/비밀번호, SSH 키 | 원문 노출과 감사 로그 오염 위험 |

처음에는 한 화면에서 "설정 관리"를 제공하면 충분해 보였습니다. 실제로는 각 저장소가 가진 보안 모델, 변경 전파 방식,
검증 방법이 달랐습니다. 하나의 저장 버튼으로 모두를 같은 의미처럼 보이게 만들면 운영자가 잘못된 확신을 갖게 됩니다.

## 선택한 설계

화면은 네 탭으로 나누되, 공통 원칙은 하나로 묶었습니다. "어디에 저장했는가", "누가 바꿀 수 있는가",
"무엇이 실제로 적용됐는가"를 같은 줄에서 추적할 수 있어야 합니다.

<Mermaid title="설정 저장소와 적용 경계">
{`flowchart TD
  Admin["Admin configuration UI"] --> Permission["Environment permission check"]
  Permission --> Db["Encrypted DB setting"]
  Permission --> Ssm["SSM Parameter"]
  Permission --> JenkinsParam["Jenkins job parameter"]
  Permission --> JenkinsCredential["Jenkins Credential"]
  Db --> Audit["Masked audit log"]
  Ssm --> Audit
  JenkinsParam --> Audit
  JenkinsCredential --> Audit
  Audit --> Verify["Validation and mock browser checks"]
  Verify --> Apply{"Runtime actually reads it?"}
  Apply -->|yes| Effective["Applied configuration"]
  Apply -->|no| StoredOnly["Stored, not effective yet"]
`}
</Mermaid>

DB 설정은 앱 내부 설정에 가깝습니다. SSM Parameter는 AWS IAM과 KMS 권한까지 포함합니다. Jenkins 파라미터는 job XML의
나머지 구조를 보존해야 합니다. Jenkins Credential은 secret 원문을 다시 보여 주지 않는 것을 기본값으로 잡아야 합니다.

## DB 설정은 암호화보다 키 경계가 먼저입니다

비밀값을 DB에 넣을 수 있게 만들더라도 DB만으로 보안이 끝나지 않습니다. 암호화 키가 같은 DB 안에 있으면 공격자가 DB를
읽었을 때 함께 읽힐 수 있습니다. 그래서 비밀값은 DB에 암호문으로 저장하되, 마스터 키는 DB 밖의 서버 설정이나 secret store에
있어야 합니다.

실무에서 기록해야 할 상태는 이것입니다.

```text
값이 DB에 저장됨
값이 암호화되어 저장됨
마스터 키가 DB 밖에서 주입됨
런타임이 해당 설정을 읽음
변경 후 사용자 시나리오가 통과함
```

이 다섯 문장은 서로 다릅니다. "DB에 저장했다"만으로 나머지를 완료 처리하면 안 됩니다.

## SSM Parameter는 경로와 IAM을 함께 좁힙니다

AWS Systems Manager Parameter Store 문서는 `SecureString`이 AWS KMS로 암호화된다고 설명합니다. 이것은 좋은 기본값이지만,
권한 설계를 대신하지는 않습니다. 환경별 prefix, 허용된 parameter name, 읽기/쓰기 권한, decryption 권한을 따로 봐야 합니다.

관리 화면에서는 다음을 분리했습니다.

- 조회 가능한 경로
- 변경 가능한 경로
- SecureString 여부
- 변경 감사 로그에 남길 metadata
- 원문 값을 다시 표시하지 않는 masking 상태

SSM을 바꾸는 것은 인프라 변경에 가깝습니다. 화면에서 저장 성공이 떠도, 서비스가 그 parameter를 언제 읽는지와 배포가 필요한지는
별도 검증 항목으로 남겨야 합니다.

## Jenkins는 파라미터와 Credential의 위험이 다릅니다

Jenkins Credentials 문서는 credential을 encrypted form으로 저장하고, Pipeline에서는 credential ID를 통해 사용한다고 설명합니다.
Credentials Binding 문서는 secret을 명령 문자열에 직접 넣는 방식보다 환경 변수 확장을 선호하라고 안내합니다.

여기서 파라미터 수정과 credential 수정은 다른 작업입니다.

| 작업 | 안전장치 |
|---|---|
| job parameter 기본값 수정 | 허용 job, 허용 key, 오래된 revision 차단 |
| credential metadata 수정 | 기존 type과 id 보존 |
| secret text 교체 | 화면과 로그에 원문 미반환 |
| SSH private key 수정 | passphrase가 필요한 키는 지원 범위 밖으로 차단 |

특히 Jenkinsfile이 job parameter 기본값을 다시 정의한다면 화면 저장값은 다음 재구성에서 사라질 수 있습니다. 그래서 UI에는
"저장 위치"와 "Pipeline 적용 방식"을 같이 보여 줘야 합니다.

## Terraform 검증은 실제 적용이 아닙니다

Terraform validate 문서는 configuration의 속성명과 값 타입 같은 일반 검증에 유용하지만, 특정 workspace와 입력 변수,
원격 API 상태를 포함한 검증은 plan이 담당한다고 설명합니다.

따라서 결과 보고는 이렇게 나눠야 합니다.

```text
terraform fmt 통과
terraform validate 통과
mock backend 브라우저 검증 통과
실제 AWS/SSM/Jenkins CRUD 미실행
승인된 환경에서 종단 검증 필요
```

이 구분은 소심한 표현이 아닙니다. 운영 회고에서는 진짜로 검증한 것만 완료로 적어야 다음 사람이 남은 위험을 볼 수 있습니다.

## 비밀값은 감사 가능해야 하지만 공개되면 안 됩니다

OWASP Secrets Management Cheat Sheet는 secret의 중앙 저장, 접근 통제, 감사, 회전, 폐기를 함께 다룹니다. 설정 관리 화면에서도
같은 균형이 필요했습니다. 누가 언제 어떤 설정을 바꿨는지는 남겨야 하지만, secret 원문은 로그에 남기면 안 됩니다.

그래서 감사 로그에는 다음만 남기는 방향이 안전합니다.

- 환경
- 설정 이름 또는 credential ID
- 변경 주체
- 변경 시각
- secret 값 변경 여부
- 이전/이후 값의 원문이 아닌 masking 또는 hash metadata

반대로 API 응답, 브라우저 상태, 테스트 screenshot, CI 로그에 원문 secret이 남으면 설정 관리 기능 자체가 노출 경로가 됩니다.

## 배운 점

첫째, 설정 관리의 첫 화면은 저장소 목록이 아니라 적용 상태 목록이어야 합니다. 운영자가 궁금한 것은 "값이 어디 있나"와
"지금 서비스가 그 값을 쓰나"입니다.

둘째, secret을 수정할 수 있다는 것은 secret을 읽을 수 있다는 뜻이 아니어야 합니다. 기존 값을 유지하려면 metadata 보존과
마스킹 표현이 필요합니다.

셋째, Jenkins와 SSM을 한 UI에서 다룰수록 허용 목록이 중요합니다. 범용 관리자 API처럼 만들면 편하지만, 작은 실수가 전체
배포 권한으로 번집니다.

넷째, 테스트와 배포 증거는 나눠 적어야 합니다. 로컬 테스트, mock 브라우저 검증, Terraform validate, 실제 AWS 변경,
Jenkins 실행, 사용자 화면 확인은 모두 별도 상태입니다.

## 점검표

- 설정별 저장 위치와 실제 소비자가 문서화되어 있는가
- secret 원문을 API 응답과 감사 로그에 반환하지 않는가
- 환경별 읽기/쓰기 권한이 분리되어 있는가
- Jenkins job과 credential ID가 허용 목록으로 제한되어 있는가
- validate와 plan/apply 결과를 같은 성공으로 쓰지 않는가
- 변경 후 사용자 시나리오 검증을 별도 상태로 남기는가
