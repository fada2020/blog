## 수집이 돌아왔다고 알림까지 검증된 것은 아닙니다

운영 관측 작업에서 수집 신호가 도착하고 수집 공백 경보가 정상으로 돌아온 것을 확인했습니다. 하지만 알림 액션은 꺼 둔 상태였고 실제 장애를 주입하지 않았습니다. 이때 완료라고 말할 수 있는 범위는 수집 경로의 복구입니다. 장애 탐지와 수신함 도착까지 성공했다고 확장하면 근거가 사라집니다.

이 글은 실제 운영 경험에서 조직·서비스·계정·시각·식별자를 제거한 회고입니다. 아래 JSON과 절차는 설명용 합성 예시입니다. 검증일은 2026년 11월 19일입니다.

## 세 가지 질문을 따로 물었습니다

| 질문 | 필요한 증거 | 증거가 없는 경우 |
|---|---|---|
| 수집기가 살아 있는가 | 주기 신호와 수신 시각 | 공백 원인 조사 |
| 장애를 탐지하는가 | 실패 지표와 경보 전환 | 탐지 미검증 |
| 담당자가 받았는가 | 발송과 수신 증거 | 전달 미검증 |

주기 신호는 로그 전송 경로가 동작한다는 증거입니다. 실제 저장 실패를 분류하는 코드가 실행됐다는 증거는 아닙니다. 경보 상태가 OK로 바뀌어도 알림 액션이 비활성이라면 수신 여부를 판단할 수 없습니다.

[CloudWatch 경보 공식 문서](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AlarmThatSendsEmail.html)는 경보 평가와 액션을 구분합니다. [누락 데이터 처리 문서](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html)에는 missing, ignore, breaching, notBreaching의 선택이 있습니다. 데이터가 없다는 이유만으로 정상이라고 해석하지 않도록 지표의 의미에 맞춰 정해야 합니다.

## 실패 건수 0과 신호 없음

실패 이벤트가 있을 때만 지표를 내보내는 구조에서는 로그가 없다는 사실이 정상인지 전송 중단인지 모호합니다. 실패 건수와 별도로 주기 신호를 두면 이 모호함을 줄일 수 있습니다. 그렇다고 모든 지표의 누락을 장애로 처리하면 정상적인 무이벤트 구간에도 경보가 발생합니다.

Spring Boot 개발자라면 애플리케이션 health 응답과 업무 처리 성공을 구분하듯 생각할 수 있습니다. HTTP 200은 프로세스의 응답을 보여 주지만 비동기 전송의 종단 성공을 증명하지는 않습니다. 요청 흐름 밖으로 옮긴 진단 전송은 지연을 줄이는 대신 유실·재시도·적체 관측을 따로 설계해야 합니다.

## 완료 기록의 저장값을 바꿨습니다

다음은 제품 응답이 아니라 회고에서 제안하는 검증 기록 형식입니다.

```json
{
  "collection_signal": "verified",
  "alarm_recovery": "verified",
  "failure_detection": "not_tested",
  "notification_action": "disabled",
  "recipient_delivery": "not_tested"
}
```

`not_tested`를 성공이나 실패로 집계하지 않습니다. 기록을 이렇게 나누면 다음 담당자가 어느 단계부터 이어야 하는지 알 수 있습니다. 배포 성공 여부와도 별도 필드로 관리할 수 있습니다.

## 안전한 후속 시험을 설계합니다

격리 환경에서 합성 실패를 발생시키고 고정된 분류 코드가 생성되는지 확인합니다. 다음으로 수집 신호를 멈춰 공백 경보를 시험하고, 승인된 테스트 수신처로 알림을 보내 발송과 수신을 각각 확인합니다. 운영에 시험 로그를 주입하거나 경보 액션을 켜는 것은 이 글에서 실행한 작업이 아닙니다.

검증 기록에는 지표 시각과 실제 확인 시각, 평가 구간을 함께 둡니다. 늦게 도착한 데이터와 현재 복구를 혼동하지 않기 위해서입니다. 단일 HTTP 요청의 성공만으로 비동기 경로 전체를 통과했다고 표시하지 않습니다.

## 진단에 남길 정보도 좁혔습니다

진단에는 처리 단계, 고정 사유 코드, 예외 종류와 임의의 진단 ID처럼 조사에 필요한 최소 항목을 남깁니다. 요청 원문, SQL, 인증 정보와 개인 정보는 남기지 않습니다. 스택과 예외 메시지에도 원문이 섞일 수 있어 필드 이름만 안전하다고 가정해서는 안 됩니다.

[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)는 로그의 민감정보 제외와 로그 실패 자체의 시험을 다룹니다. 보관 기간, 접근 권한과 디스크 고갈도 전송 성공과 별도로 관리할 항목입니다.

이번 회고에서 확인한 것은 수집 신호 수신과 경보 복구였습니다. 실제 실패 경보 전환과 수신처 전달은 남은 검증입니다. 완료 기록에서 이 경계를 보존하는 것이 다음 장애 대응의 출발점이 됩니다.
