## 이번 주 개념: 대기 예약과 진행 중 응답을 따로 관리합니다

검색어를 입력할 때마다 요청하면 `f`, `fl`, `flu`가 모두 서버에 도착합니다.
마지막 입력 후 300ms 동안 추가 입력이 없을 때만 검색하는 trailing debounce를 넣으면 불필요한 조회를 줄일 수 있습니다.

그런데 타이머만 취소하면 충분하지 않습니다. 이전 검색이 이미 시작됐다면 새 입력의 300ms 대기 중에도
이전 응답이 도착할 수 있습니다. **입력 즉시 이전 응답의 반영 권한을 없애고, 타이머는 새 요청의 시작만 늦춥니다.**
어제 학습한 요청 번호를 타이머 callback 안이 아니라 입력 callback에서 증가시키는 이유입니다.

## Java와 Spring에서는 어떻게 다뤘는가

Java의 예약 실행과 취소를 떠올리면 이해하기 좋습니다. 아직 실행되지 않은 예약을 취소하는 일과 이미 시작한
HTTP 호출을 중단하는 일은 다릅니다. Spring 서버의 rate limit은 서버 전체 부하를 제한하고, 화면의 debounce는
사용자가 입력 중인 중간 상태를 묶습니다. 하나가 다른 하나의 보안·용량 정책을 대신하지 않습니다.

| 익숙한 개념 | Flutter에서 맡길 책임 |
|---|---|
| 예약 실행 | `Timer`로 조회 시작 지연 |
| 예약 취소 | `cancel()`로 이전 callback 방지 |
| 응답 유효성 | 요청 번호로 현재 입력과 비교 |
| 자원 정리 | `dispose()`에서 타이머 해제 |

Dart 타이머는 정확한 실시간 스케줄러가 아닙니다. 300ms는 UX를 위한 대기 기준이며 네트워크 응답 시간의 보장이 아닙니다.

## Flutter에서는 무엇이 다른가

`State`가 타이머를 소유하면 화면이 사라질 때 함께 정리할 수 있습니다. `build()`에서 타이머를 만들면
재빌드마다 예약이 늘어나므로 입력 callback에서만 예약합니다. 공식 `Timer.cancel()`은 여러 번 호출해도 허용되며,
취소한 타이머는 callback을 호출하지 않습니다. 이미 시작한 Future의 취소까지 보장하는 API는 아닙니다.

## 최소 실행 예제

새 Flutter 프로젝트의 `lib/main.dart`에 넣어 실행합니다. 외부 패키지와 실제 HTTP 서버는 필요하지 않습니다.
직접 정의한 함수와 변수는 스네이크케이스로 작성하고 프레임워크 메서드는 원래 이름을 유지했습니다.

```dart
import 'dart:async';
import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: SearchPage()));

Future<List<String>> search_items(String query) async {
  await Future<void>.delayed(const Duration(milliseconds: 500));
  if (query == 'error') throw StateError('조회 실패');
  return ['$query 결과'];
}

class SearchPage extends StatefulWidget {
  const SearchPage({super.key});

  @override
  State<SearchPage> createState() => _SearchPageState();
}

class _SearchPageState extends State<SearchPage> {
  Timer? _debounce_timer;
  int _request_id = 0;
  String _phase = '검색어를 입력하세요';
  List<String> _items = [];

  void _on_input(String input_value) {
    final current_id = ++_request_id;
    _debounce_timer?.cancel();
    final query = input_value.trim();
    setState(() {
      _items = [];
      _phase = query.isEmpty ? '검색어를 입력하세요' : '입력 대기';
    });
    if (query.isEmpty) return;
    _debounce_timer = Timer(const Duration(milliseconds: 300), () {
      _search(query, current_id);
    });
  }

  Future<void> _search(String query, int current_id) async {
    if (!mounted || current_id != _request_id) return;
    setState(() => _phase = '조회 중');
    try {
      final items = await search_items(query);
      if (!mounted || current_id != _request_id) return;
      setState(() {
        _items = items;
        _phase = '조회 완료';
      });
    } catch (_) {
      if (!mounted || current_id != _request_id) return;
      setState(() => _phase = '다시 입력해 주세요');
    }
  }

  @override
  void dispose() {
    _request_id++;
    _debounce_timer?.cancel();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(title: const Text('Debounce 실습')),
    body: Padding(
      padding: const EdgeInsets.all(24),
      child: Column(
        crossAxisAlignment: CrossAxisAlignment.stretch,
        children: [
          TextField(onChanged: _on_input),
          Text(_phase),
          for (final item in _items) Text(item),
        ],
      ),
    ),
  );
}
```

## 입력·요청·화면의 실제 예시

| 입력과 시간 | 조회 호출 | 화면 결과 |
|---|---|---|
| 0ms `f`, 100ms `fl` | 400ms에 `fl` 한 번 | 900ms부터 `fl 결과` |
| `a` 조회 중 `ab` 입력 | `ab`는 300ms 뒤 시작 | `a` 응답은 즉시 무효 |
| 대기 중 입력 삭제 | 새 조회 없음 | 빈 목록과 입력 안내 |
| 대기 중 화면 종료 | 예약 callback 취소 | 종료 후 화면 갱신 없음 |
| `error` 입력 후 대기 | 가짜 조회 실패 | 재입력 안내 |

위 시간은 이벤트 처리가 지연되지 않는 실습의 논리 시간입니다. 실제 실행은 프레임과 이벤트 루프의 영향을 받습니다.
실제 API가 `GET /items?q=fl`에 `{"items":["fl 결과"]}`를 반환한다면 그 필드나 상태 코드를 바꾸지 않고
클라이언트의 호출 시점과 응답 반영 여부만 조정합니다. 예제에는 저장값 변경이 없습니다.

## Java 개발자가 자주 하는 오해

타이머를 취소했으니 이전 HTTP 요청도 취소됐다고 생각하기 쉽습니다. 이 예제에서 이전 Future는 끝까지 실행되며
결과만 무시됩니다. 또 요청 번호를 조회 시작 때 증가시키면 새 입력 후 대기 중인 틈에 이전 결과가 살아 있습니다.
번호 증가는 입력 즉시 수행해야 합니다.

모든 입력 이벤트를 서버에 남겨야 하는 감사 로그나 결제 명령에 debounce를 무조건 적용해서도 안 됩니다.
중간 검색 상태를 버려도 되는지 먼저 결정해야 합니다. 한글 조합 중 조회를 막을지는 별도 입력 정책이며,
이 예제는 `onChanged`에 전달된 문자열을 그대로 처리합니다.

## 연습과 검증 범위

1. `f`, `fl`을 100ms 간격으로 입력하고 조회가 한 번만 시작되는지 확인합니다.
2. `a` 조회가 시작된 후 `ab`를 입력하고, 새 대기 시간 중 도착한 `a`가 표시되지 않는지 확인합니다.
3. 대기 중 입력 삭제와 화면 종료를 각각 재현합니다.
4. debounce 시간을 0으로 바꾸어도 요청 번호 검사가 필요한 이유를 설명합니다.

예제는 별도 임시 프로젝트에서 Flutter 3.47.4 / Dart 3.13.3으로 정적 분석(문제 없음)과 위젯 테스트 5개를 통과했습니다.
연속 입력, 새 대기 중 이전 응답, 입력 삭제, 화면 종료(예약 중·조회 중), 현재 실패를 확인했습니다.
기준 안정판 3.47.9에서 직접 실행한 것으로 해석하지 않습니다.
실제 HTTP 취소, Android/iOS 키보드와 실기기 네트워크 지연을 검증한 예제는 아닙니다.
