같은 이벤트 다섯 건에서도 실패 건수는 3, 실패 이력이 있는 주문은 2, 현재 실패 상태인 주문은 1이 될 수 있습니다. 집계 함수를 바꾸기 전에 ‘무엇 한 개를 세는지’를 정해야 했습니다. 이번 주 [분류와 건수 집계](/blog/posts/kotlin-grouping-counts-2026-11-07/)에서 남긴 중복 주문 문제를 더 깊게 살펴봅니다.

검증 기준일은 2026년 11월 8일이며 Kotlin/JVM 최신 안정 버전 2.4.21을 사용했습니다. 2.5 계열 사전 공개판은 기준에 넣지 않았습니다. [공식 릴리스](https://kotlinlang.org/docs/releases.html)

## 집계 단위부터 정하기

| 질문 | 단위 | 중복 처리 |
| --- | --- | --- |
| 실패 알림이 몇 번 왔나 | 이벤트 | 재전송 포함 |
| 실패를 겪은 주문이 몇 개인가 | 주문 ID | 같은 주문 통합 |
| 지금 실패 상태인 주문은 몇 개인가 | 주문별 최신 상태 | 순서를 결정한 뒤 집계 |

첫 번째 값은 전송 부하를, 두 번째는 영향 범위를, 세 번째는 현재 상태를 설명합니다. 서로 대체할 수 없습니다. 아래 실습에서 중복 전송을 식별할 event ID는 생략했습니다. 실제 처리량과 원래 사건 수를 나누려면 event ID의 유일성 정책도 별도로 필요합니다.

## Grouping은 결과를 저장하는 캐시가 아닙니다

`groupingBy`는 원본과 키 선택 방법을 연결합니다. `eachCount` 같은 종단 연산이 순회를 수행합니다. 같은 `Grouping`에 종단 연산을 두 번 호출하면 다시 읽는다는 점을 실습으로 확인합니다. [groupingBy API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.collections/grouping-by.html)

`groupBy`는 키별 목록을 돌려주므로 원본 행을 다시 보여 줄 때 편합니다. `eachCount`는 키별 정수를 돌려주므로 건수만 필요한 결과에 맞습니다. [그룹화 가이드](https://kotlinlang.org/docs/collection-grouping.html), [eachCount API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.collections/each-count.html)

입력 N개와 키 K개를 생각하면, 일반적인 해시 연산을 가정할 때 두 방식의 순회 시간은 대체로 N에 비례합니다. 추가 결과 공간은 목록을 보관하면 N개 참조와 키 구조가 필요하고, 건수만 보관하면 K개 누적값이 중심이 됩니다. 이미 존재하는 입력 목록의 메모리는 두 경우 모두 별도입니다. 이것은 구조에 대한 분석이며 성능 벤치마크 결과가 아닙니다.

## 독립 실행 실습

`event_order`는 예제에서 정한 전체 순서입니다. 시각이 같을 수 있는 실제 시스템에서는 시퀀스나 동률 해소 규칙까지 정의해야 합니다.

```kotlin
data class OrderEvent(
    val order_id: Int,
    val status: String,
    val event_order: Int,
)

fun main() {
    val events = mutableListOf(
        OrderEvent(101, "FAILED", 1),
        OrderEvent(101, "FAILED", 2),
        OrderEvent(101, "PAID", 3),
        OrderEvent(102, "FAILED", 4),
        OrderEvent(103, "PAID", 5),
    )
    val failed_events = events.count { it.status == "FAILED" }
    val ever_failed_orders = events.filter { it.status == "FAILED" }
        .map { it.order_id }.toSet().size

    val latest_by_order = events.groupingBy { it.order_id }
        .reduce { _, previous, current ->
            if (current.event_order > previous.event_order) current else previous
        }
    val current_failed_orders = latest_by_order.values.count { it.status == "FAILED" }
    check(failed_events == 3)
    check(ever_failed_orders == 2)
    check(current_failed_orders == 1)

    var visits = 0
    val grouping = events.groupingBy {
        visits += 1
        it.status
    }
    check(visits == 0)
    check(grouping.eachCount() == mapOf("FAILED" to 3, "PAID" to 2))
    check(visits == 5)
    events.add(OrderEvent(104, "PAID", 6))
    check(grouping.eachCount() == mapOf("FAILED" to 3, "PAID" to 3))
    check(visits == 11)
    check(emptyList<OrderEvent>().groupingBy { it.status }.eachCount().isEmpty())
    println("9 checks passed")
}
```

`Main.kt`로 저장한 뒤 안정 버전 컴파일러로 실행합니다.

```sh
kotlinc Main.kt -include-runtime -d grouping.jar
java -jar grouping.jar
```

원본을 바꾼 다음 다시 집계하면 새 원소도 읽습니다. 이 관찰은 단일 스레드 실습입니다. 순회 중 다른 스레드가 목록을 수정해도 안전하다는 뜻은 아닙니다. [reduce API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.collections/reduce.html)

## Spring 서비스에서 선택할 경계

Java Streams에서는 `groupingBy(classifier, counting())`가 키별 `Long`을 돌려줍니다. Kotlin `eachCount()`의 `Int`와 응답 필드 타입을 혼동하지 않아야 합니다. 큰 누적값에는 `Long` 누적을 별도로 설계하고 기존 API의 숫자 범위를 검토합니다. [Java Collectors](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/stream/Collectors.html)

조회가 큰 테이블에 걸치면 DB에서 집계할지부터 결정합니다. ‘조회 기간에 실패한 주문’과 ‘현재 실패인 주문’은 필터를 적용하는 순서도 다릅니다. 예를 들어 기간 밖의 성공 이벤트를 제외하고 최신 상태를 고르면 이미 복구된 주문을 실패로 남길 수 있습니다. 먼저 업무 질문과 기준 시점을 고정한 뒤 쿼리와 애플리케이션 집계가 같은 모집단을 읽는지 확인합니다.

고유 주문 집계는 ID 집합을 보관해야 해서 단순 건수보다 메모리를 더 쓸 수 있습니다. 최신 상태 집계도 주문별 후보를 유지해야 합니다. `groupingBy`로 바꿨다는 사실만으로 모든 집계가 일정 메모리가 되지는 않습니다.

## 흔한 실패와 검증

- 재전송을 주문 수로 세었습니다. 같은 주문의 실패 두 건과 복구 한 건을 넣어 세 단위를 각각 검증합니다.
- `Grouping`을 스냅샷으로 생각했습니다. 반복 순회 사이에 원본을 바꾸는 실습으로 재평가를 확인합니다.
- 빈 입력의 키가 자동으로 생길 것으로 예상했습니다. 응답에 모든 상태가 필요하면 집계 후 상태 목록을 기준으로 0을 채웁니다.
- 최신 시각만 정렬했습니다. 동률, 역순 도착, 기간 밖 복구 이벤트를 별도 사례로 추가합니다.

이번 실습의 9개 검사는 컬렉션 의미를 확인합니다. DB 격리 수준, 동시 수정, 대용량 처리량은 검증 범위에 포함하지 않았습니다.
