## 신모델보다 먼저 비교 단위를 정했습니다

> **공식 자료 검증일: 2026년 11월 18일 KST.** GPT-6.2 Astra·Sol, MAI Code 2·Flash,
> Claude Fable 5.2, Muse Ember와 최신 배포 채널을 확인했습니다. 이 글은 문서 비교와 실험 설계입니다.
> 동일 저장소에서 이 모델들을 실행한 성능 순위나 실측 비용을 제시하지 않습니다.

11월 17일 새 모델 발표를 읽으며 먼저 바꾼 질문은 “어느 모델이 가장 싸나”에서 “검토를 통과한 변경 한 건에
얼마가 드나”였습니다. 낮은 토큰 단가라도 재시도와 사람의 수정 시간이 늘면 총비용이 커집니다.
[지난주 sandbox 범위](/blog/posts/ai-agent-sandbox-scope-2026-11-11/)에서 실행 경계를 비교했다면,
이번에는 그 경계를 고정한 뒤 결과와 비용을 측정하는 방법을 정리했습니다.

## 이번 주 발표를 같은 의미로 읽지 않습니다

| 후보 | 공식 확인 내용 | 비교할 때 고정할 것 |
|---|---|---|
| GPT-6.2 Astra·Sol | 11월 17일 API 제공 | 모델 ID·도구 API |
| MAI Code 2·Flash | 11월 17일 모델 발표 | 제공 채널·평가 설정 |
| Claude Fable 5.2 | 11월 9일 기술 작업용 모델 | 모드·접근 조건 |
| Muse Ember | 11월 9일 효율 지향 모델 | harness·reasoning 설정 |

[OpenAI 변경 이력](https://developers.openai.com/api/docs/changelog)은 GPT-6.2 두 모델의 Responses와
Chat Completions 제공을 구분하며 **도구 호출에는 Responses API가 필요하다**고 명시합니다.
기존 agent에서 모델 이름만 바꾸고 API 경로·도구 계약을 그대로 두어도 된다는 뜻이 아닙니다.
같은 날 공지한 2시간·8시간 background completion window는 **public beta**이므로 정식 모델 제공과 분리합니다.
할인만 보고 실시간 작업의 기본 경로로 선택하지 않습니다.

[Microsoft의 공식 모델 페이지](https://microsoft.ai/models/mai-code-2/)와
[11월 17일 발표](https://microsoft.ai/news/microsoft-ignite-2026/)는 MAI Code 2의 비용 대비 성능을 강조합니다.
발표에 실린 경쟁 모델 대비 수치는 공급사 평가입니다. 그 비율을 우리 저장소의 결함 수정 성공률로 옮길 근거는 없습니다.
[모델 카드](https://microsoft.ai/pdf/MAI-Code-2-And-MAI-Code-2-Flash-Model-Card.pdf?v=2)는 Code 2와 Flash의
대상 작업을 나누고 서비스별 이용 약관을 연결합니다. 모델 발표와 우리 계정·리전·채널의 실제 사용 가능 여부는 별도 확인합니다.

[Anthropic 발표](https://www.anthropic.com/claude-fable-and-mythos-5-2)는 Fable과 Mythos의 접근 조건을
구분합니다. 기능이 닮았다고 같은 사용자에게 같은 경로로 제공되는 것은 아닙니다. 이번 실험의 후보는 접근 가능한
Fable을 기준으로 정하고, 접근 승인에 의존하는 후보는 동일 조건 실험에 섞지 않습니다.

## 벤치마크는 모델과 실행 도구의 조합입니다

[Meta의 Muse Ember 평가 방법](https://research.meta.ai/static/muse-ember-evaluation-report)은 내부 비교에서
공통 harness를 쓰는 경우와 외부 결과가 원래 agent 제품의 harness를 유지하는 경우를 구별합니다.
여기서 harness는 프롬프트, 파일 탐색, 명령 실행, 테스트, 재시도와 종료 판정의 묶음입니다.
같은 모델도 도구와 예산이 바뀌면 다른 결과를 낼 수 있습니다.

Java 팀의 비유로는 같은 SQL을 비교하면서 한쪽에만 캐시와 인덱스를 제공하면 JDBC 드라이버의 차이로
해석할 수 없는 것과 비슷합니다. 따라서 두 실험을 나눕니다.

- **모델 교체 실험:** 동일 입력, 도구, 시간·토큰 상한, 테스트와 초기 커밋에서 모델만 바꿉니다.
- **제품 선택 실험:** Codex·Claude Code·Vibe 등 실제 제품의 기본 workflow를 비교하되, 결과를 제품 조합의 성능으로 기록합니다.

독립 평가를 찾을 때도 이름이 같은 지표만 모으지 않습니다. 버전, task set, 실행 agent, reasoning 설정이
다르면 하나의 순위표로 합치지 않습니다. 이번 신모델의 동등 조건 독립 실측을 확보하지 못해 순위 주장을 보류했습니다.

## Spring Boot 팀의 최소 실험

공개 가능한 합성 저장소에 입력 검증, 경계값 버그, 테스트 누락 같은 독립 과제 10개를 준비합니다.
각 과제에는 시작 커밋과 사람만 볼 수 있는 판정 기준을 둡니다. 정상 입력뿐 아니라 오류 상태 코드와 JSON 필드,
시간 형식까지 고정합니다. agent가 테스트 기대값을 바꿔 성공을 만들면 실패로 판정합니다.

각 후보는 과제별로 깨끗한 작업 트리에서 세 번 실행합니다. 총 30회는 출발점일 뿐 통계적 우월성을 보장하지 않습니다.
순서를 섞고 실패·시간 초과·도구 오류도 분모에 포함합니다. 같은 환경을 쓸 수 없는 후보는 별도 군으로 남깁니다.

다음 JSON은 벤더 API 응답이 아닌 **제안하는 실험 저장값**입니다. 실제 실행 전 상태를 그대로 표현했습니다.

```json
{
  "task_id": "validation_01",
  "model_id": "candidate_a",
  "harness_version": "fixed_01",
  "attempt": 1,
  "result": "not_run",
  "model_cost_usd": null,
  "tool_cost_usd": null,
  "elapsed_seconds": null,
  "review_minutes": null
}
```

null을 비용 0으로 집계하지 않습니다. 실제 실행 후 청구 가능한 사용량, 캐시 할인, reasoning 사용량,
재시도, 외부 도구 요금과 검토 시간을 기록합니다. 구독 요금제는 API 토큰 단가와 직접 섞지 않고 월 비용을
관측한 작업량에 배분한 시나리오를 따로 제시합니다.

## 계산 예시는 관측값이 아닙니다

성공 한 건의 실행 비용은 **모든 시도의 모델·도구 비용 합계 / 검토 통과 건수**로 계산합니다.
성공이 0이면 나눗셈 결과를 만들지 말고 실패로 표시합니다. 사람 비용을 포함할 때는 검토 분에 합의한 시간 단가를 적용합니다.

가령 합성 실험 A가 10회에 2달러를 쓰고 8건 통과했다면 실행 비용은 0.25달러입니다.
B가 10회에 1달러를 쓰고 4건 통과해도 0.25달러입니다. B의 단순 청구액이 절반이라는 이유만으로 선택하면
완료율 차이를 숨깁니다. 검토 시간과 p95 지연도 같은 표에서 확인해야 합니다.

쉬운 과제는 빠른 모델로, 실패 과제는 상위 모델로 보내는 routing도 후보입니다. 다만 이 전략은 실패 감지의 정확도와
전환 비용을 포함한 별도 실험입니다. 숨은 오류를 감지하지 못하면 싼 모델의 답을 그대로 승인할 수 있습니다.
우선 단일 후보의 기준선을 확보한 뒤, 동일 과제로 routing을 검증합니다.

## 넓게 스캔한 후보와 제외 이유

오늘은 새로 발표된 Microsoft 모델을 최소 확인 목록에 추가했습니다. 이전 주 Google 실행 인프라 중심 주제에서
모델·제품 평가 방법으로 옮겼습니다. 다음 제외는 품질 판정이 아니라 이번 실험의 범위를 정한 기록입니다.

- **Google:** [Gemini Decisions API](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/)는
  닫힌 선택지 결정용으로 확인했습니다. 자유로운 코드 수정 agent와 과제가 달라 순위 비교에서 제외했습니다. 어제 소개한 발표이기도 합니다.
- **xAI/Grok:** [11월 11일 Grok Bot 1.0](https://x.ai/news/grok-bot-1-0)과
  [공식 뉴스](https://x.ai/news)의 11월 16일 회계 업무 사례를 확인했습니다. 협업 workflow 확대는 후보이지만
  같은 Java 수정 harness와 비용 자료를 확보하지 못해 수치 비교를 제외했습니다.
- **Meta:** [Muse Ember 발표](https://research.meta.ai/blog/muse-ember)는 효율 후보로 포함했고,
  성능 수치 재인용보다 평가 방법의 차이를 본문에서 사용했습니다.
- **Mistral:** [11월 17일 Vibe Desktop 정식 출시](https://docs.mistral.ai/resources/release-notes)를 확인했습니다.
  로컬·클라우드 coding과 Work가 결합된 제품이며 단일 모델과 평가 단위가 달라 제품 실험 후보로 남겼습니다.
- **Qwen:** [11월 16일 Token Plan 업데이트](https://docs.modelstudio.console.alibabacloud.com/en/model-studio/token-plan-product-updates)는
  Qwen4-Max 제공을 명시합니다. [preview 문서](https://help.aliyun.com/en/model-studio/qwen4-max-preview)는
  별도 preview ID와 종료 조건을 안내합니다. 미리보기 할인과 정식 모델 비용을 섞지 않고,
  선택 채널의 실제 모델 ID·과금 검증 전에는 수치 비교에서 제외했습니다.
- **DeepSeek:** [공식 API 시작 문서](https://api-docs.deepseek.com/news)의 Flash alias와 통합 경로를 확인했습니다.
  alias가 가리키는 모델을 실행 때 기록해야 하므로 고정 ID·동등한 실험을 확보하기 전 순위 비교를 제외했습니다.

새 제품을 즉시 운영 기본값으로 만드는 대신, 작은 과제에서 완료율·비용·지연·검토 부담을 함께 남기는 것이
이번 주의 실천 과제입니다. 공개 벤치마크는 후보를 줄이는 자료이고 최종 선택의 증거는 우리 과제의 재현 가능한 결과입니다.
