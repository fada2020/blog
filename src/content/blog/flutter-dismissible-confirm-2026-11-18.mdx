> [공식 릴리스 목록](https://docs.flutter.dev/release/release-notes)과 Dismissible API를 확인했습니다.
> 예제는 로컬 Flutter 3.47.4 / Dart 3.13.3에서 분석 오류 없이 위젯 테스트 1개를 통과했습니다.
> 취소 시 유지, 확인 시 선택 ID만 제거되는 것을 검사했습니다. 최신 안정판 SDK나 실제 기기에서는 실행하지 않았습니다.

## 삭제 제스처와 데이터 삭제를 나눕니다

[37강](/blog/posts/flutter-reorderable-list-index-2026-11-17/)에서는 항목 ID와 목록 위치를 구분했습니다.
이번에는 같은 목록에 밀어서 삭제하는 동작을 붙입니다. 카드가 화면 밖으로 움직였다는 사실과 서버가
데이터를 삭제했다는 사실은 다릅니다. 먼저 로컬 목록에서 확인과 제거를 정확하게 연결했습니다.

Spring MVC에서 삭제 확인 화면은 DELETE 요청의 성공 응답이 아닙니다. Flutter의 `confirmDismiss`도
사용자의 결정을 기다리는 단계입니다. `onDismissed`는 애니메이션이 진행된 뒤 목록에서 항목을 제거할 시점입니다.
이 예제에는 HTTP 요청과 영구 저장이 없으며, 앱을 재실행하면 초기 목록으로 돌아갑니다.

## 두 콜백의 계약

[confirmDismiss 공식 문서](https://api.flutter.dev/flutter/widgets/Dismissible/confirmDismiss.html)에 따르면
반환한 Future가 끝날 때까지 같은 위젯을 다시 드래그할 수 없습니다. true면 제거를 진행하고 false나 null이면
되돌립니다. false와 null일 때는 `onDismissed`가 호출되지 않습니다.

[Dismissible API](https://api.flutter.dev/flutter/widgets/Dismissible-class.html)는 목록 항목마다 구별되는 key를
주고, 완료 콜백에서 해당 항목을 목록에서 제거하도록 요구합니다. 위젯을 그대로 두면 이미 제거된 Dismissible이
다시 트리에 남는 오류가 생길 수 있습니다.

| 단계 | 담당하는 일 | 담당하지 않는 일 |
|---|---|---|
| 확인 | 사용자의 허용·취소 | 서버 성공 보장 |
| 애니메이션 완료 | 로컬 목록에서 ID 제거 | 데이터베이스 커밋 |
| 저장 계층 | 실제 삭제·실패 처리 | 이 예제에서는 변경 없음 |

## 실행 가능한 최소 예제

새 Flutter 프로젝트의 `lib/main.dart`를 다음으로 바꿉니다. 직접 정의한 변수는 snake_case를 사용하고,
Flutter가 정한 메서드·이름 있는 매개변수는 API 그대로 사용했습니다.

```dart
import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: DeletePage()));

class DeletePage extends StatefulWidget {
  const DeletePage({super.key});

  @override
  State<DeletePage> createState() => _DeletePageState();
}

class _DeletePageState extends State<DeletePage> {
  final task_ids = <String>['a', 'b', 'c'];

  Future<bool?> confirm_delete(String task_id) {
    return showDialog<bool>(
      context: context,
      builder: (dialog_context) => AlertDialog(
        title: Text('$task_id 삭제'),
        content: const Text('목록에서 제거할까요?'),
        actions: [
          TextButton(
            onPressed: () => Navigator.pop(dialog_context, false),
            child: const Text('취소'),
          ),
          TextButton(
            onPressed: () => Navigator.pop(dialog_context, true),
            child: const Text('삭제'),
          ),
        ],
      ),
    );
  }

  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(title: const Text('삭제 확인')),
    body: ListView(
      children: [
        for (final task_id in task_ids)
          Dismissible(
            key: ValueKey(task_id),
            direction: DismissDirection.endToStart,
            background: Container(color: Colors.red),
            confirmDismiss: (_) => confirm_delete(task_id),
            onDismissed: (_) => setState(() {
              task_ids.remove(task_id);
            }),
            child: ListTile(title: Text('할 일 $task_id')),
          ),
      ],
    ),
  );
}
```

`removeAt(index)` 대신 `remove(task_id)`를 썼습니다. 비동기 확인이 열린 동안 다른 이벤트가 목록 순서를
바꿀 수 있기 때문입니다. 실제 서비스에서는 ID의 유일성을 입력 단계에서 보장해야 합니다. 이 샘플은 a·b·c를
상수로 만들었으며 중복 ID나 외부 목록 변경을 지원하는 저장 계층은 포함하지 않았습니다.

`endToStart`는 방향성에 따라 해석됩니다. 한국어처럼 왼쪽에서 오른쪽으로 쓰는 화면에서는 오른쪽에서 왼쪽으로
밉니다. 모든 언어에서 물리적으로 같은 방향이라고 가정하면 안 됩니다.

## 서버 삭제를 붙일 때 결정할 것

서버 성공 후 화면을 없애려면 확인 단계에서 요청을 기다리고 성공일 때만 true를 반환하는 방식을 검토할 수 있습니다.
다만 요청 중 표시, 시간 초과, 취소, 화면 종료, 이미 삭제된 항목의 처리는 따로 설계해야 합니다.
서버 실패를 성공으로 바꾸거나 예외를 숨기고 true를 반환하지 않습니다.

반대로 먼저 숨기는 낙관적 갱신을 선택했다면 실패 시 복구할 ID·원래 순서·내용을 보관해야 합니다.
SnackBar의 실행 취소는 서버 삭제를 자동으로 되돌리지 않습니다. 복원 API나 지연 삭제 같은 별도 계약이 필요합니다.
어떤 방식이든 화면 콜백만으로 정확히 한 번의 원격 삭제를 보장할 수는 없습니다.

## 검증과 연습

로컬 Flutter 3.47.4 / Dart 3.13.3에서 이 코드를 분석하고 위젯 테스트로 취소·확인 흐름을 검사했습니다.
취소 후 a가 남고, 확인 후 a만 사라지며 b·c는 유지되는 것을 검증했습니다. 공식 기준인 3.50.0과 설치 SDK는
다릅니다. 실제 Android·iOS 기기의 제스처와 접근성 입력은 이번 로컬 테스트 범위에 포함하지 않았습니다.

1. 확인 창의 바깥을 눌러 닫고 항목이 남는지 확인합니다.
2. b를 삭제한 뒤 c의 ID와 표시가 유지되는지 확인합니다.
3. 서버 실패를 합성한 저장 계층을 붙이고 실패 시 목록을 보존하도록 확장합니다.
4. 밀기 어려운 사용자를 위해 명시적 삭제 버튼을 제공하는 화면도 비교합니다.

다음 단계에서는 제스처의 성공 여부보다 사용자 결정, 로컬 목록, 서버 저장 결과를 서로 다른 상태로 기록하는 것이 중요합니다.
