## 결론부터 말하면

Spring Boot 서버에서 Kotlin `data class`를 쓰기 시작하면 `@NotBlank`, `@JsonProperty`, `@Id`, `@Autowired` 같은
annotation이 "분명히 붙어 있는데도" 프레임워크가 못 보는 일이 생깁니다. 이유는 Kotlin의 property 하나가 JVM에서는
constructor parameter, field, getter, setter parameter 같은 여러 Java 요소로 나뉘기 때문입니다.

기본 원칙은 단순합니다.

- Bean Validation이 field를 읽어야 하면 `@field:NotBlank`처럼 씁니다.
- 생성자 parameter를 읽는 프레임워크라면 `@param:`을 씁니다.
- getter 기반 JavaBean 규칙을 읽는 도구라면 `@get:`을 씁니다.
- Java에서 보이지 않아도 되는 Kotlin 전용 metadata라면 `@property:`를 씁니다.
- 팀 규약이 잡히기 전에는 target 없는 annotation보다 명시 target을 선호합니다.

Kotlin 2.4.20 문서의 기본 target 선택 규칙은 예전보다 똑똑합니다. 그래도 Spring, Jackson, Hibernate, Bean Validation처럼
Java reflection을 오래 써 온 도구와 만날 때는 "어디에 붙는가"를 코드에 드러내는 편이 디버깅 비용을 줄입니다.

## 이번 주 개념

Kotlin 문서에서 annotation은 코드 요소에 metadata를 붙이고, compiler나 runtime tool이 그 metadata를 처리하는 장치입니다.
Java 개발자에게는 익숙한 개념입니다. 차이는 property입니다.

```kotlin
data class CreateUserRequest(
    @field:NotBlank
    val email: String,
)
```

Kotlin에서 `email`은 하나의 property처럼 보입니다. 하지만 JVM에는 대략 다음 조각들이 생깁니다.

- primary constructor parameter
- private backing field
- public getter
- component function과 copy 관련 메서드

따라서 annotation을 그냥 붙이면 도구가 기대한 위치와 실제 위치가 엇갈릴 수 있습니다.

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 field와 getter가 코드에 따로 보입니다.

```java
public class CreateUserRequest {
    @NotBlank
    private final String email;

    public CreateUserRequest(String email) {
        this.email = email;
    }

    public String getEmail() {
        return email;
    }
}
```

어떤 annotation이 field에 붙었는지, getter에 붙었는지 눈으로 확인하기 쉽습니다. Spring MVC의 request body validation,
Jackson의 JSON property mapping, JPA의 access strategy도 이 구조를 전제로 설명되는 경우가 많습니다.

Kotlin으로 오면 코드가 짧아집니다.

```kotlin
data class CreateUserRequest(
    @NotBlank
    val email: String,
)
```

짧아진 만큼 질문이 숨어듭니다. `@NotBlank`는 constructor parameter에 붙었을까요, field에 붙었을까요, getter에 붙었을까요?
Kotlin 문서는 annotation의 `@Target`과 Kotlin compiler의 기본 선택 규칙에 따라 target이 정해진다고 설명합니다. 실무에서는
이 규칙을 외우기보다 프레임워크가 보는 위치를 명시하는 편이 안전합니다.

## Kotlin에서는 무엇이 다른가

Kotlin은 use-site target 문법으로 annotation 위치를 지정합니다.

```kotlin
data class CreateUserRequest(
    @field:NotBlank
    @field:Email
    val email: String,

    @param:JsonProperty("display_name")
    val displayName: String?,
)
```

`@field:`는 backing field에 붙입니다. Bean Validation을 field access로 쓰는 request DTO에서 자주 고르는 target입니다.
`@param:`은 constructor parameter에 붙입니다. 생성자 binding이나 parameter 이름 기반 도구와 만날 때 의미가 있습니다.
`@get:`은 getter에 붙입니다. JavaBean getter를 읽는 라이브러리나 API 문서화 도구와 맞출 때 씁니다.

Spring Framework 7.0.9 문서는 Kotlin null safety와 JSpecify annotation을 설명합니다. Kotlin 2.1부터 JSpecify
nullability annotation을 더 엄격하게 다룬다는 점도 확인해야 합니다. 즉 Kotlin 타입의 `String`과 `String?` 자체가
계약이고, Java annotation은 그 계약을 Java API와 tooling에 전달하는 보조 수단입니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin 표현 | 판단 기준 |
|---|---|---|
| field에 validation annotation | `@field:NotBlank` | request DTO에서 field validation을 기대할 때 |
| constructor parameter annotation | `@param:JsonProperty` | 생성자 parameter를 직접 읽는 도구와 맞출 때 |
| getter annotation | `@get:Schema` | JavaBean getter 기반 문서화나 serialization 규칙이 필요할 때 |
| class-level annotation | `@Entity`, `@ConfigurationProperties` | Java와 거의 동일하게 class에 붙일 때 |
| nullability annotation | `String` / `String?` 우선 | Kotlin 타입으로 계약을 먼저 표현할 때 |
| Java reflection 확인 | decompile 또는 bytecode view | 프레임워크가 못 읽을 때 최종 확인용 |

## 최소 실행 예제

Bean Validation이 request DTO의 field를 보도록 명시해 봅니다.

```kotlin
import jakarta.validation.Valid
import jakarta.validation.constraints.Email
import jakarta.validation.constraints.NotBlank
import org.springframework.web.bind.annotation.PostMapping
import org.springframework.web.bind.annotation.RequestBody
import org.springframework.web.bind.annotation.RestController

data class CreateUserRequest(
    @field:NotBlank
    @field:Email
    val email: String,

    @field:NotBlank
    val name: String,
)

@RestController
class UserController {
    @PostMapping("/users")
    fun create(@Valid @RequestBody request: CreateUserRequest): String {
        return "created:${request.email}"
    }
}
```

여기서 핵심은 `@Valid`가 controller parameter에 붙고, `@field:NotBlank`가 DTO field에 붙는다는 점입니다.
두 위치가 다릅니다.

Jackson 이름을 생성자 parameter 쪽에 맞추고 싶다면 별도로 씁니다.

```kotlin
import com.fasterxml.jackson.annotation.JsonProperty

data class CreateProfileRequest(
    @param:JsonProperty("display_name")
    val displayName: String,
)
```

한 property에 여러 프레임워크 계약이 들어가면 줄 수가 늘어납니다. 그래도 이 중복은 의미 있는 중복입니다.

```kotlin
data class RegisterRequest(
    @param:JsonProperty("email")
    @field:NotBlank
    @field:Email
    val email: String,
)
```

JSON 이름은 constructor binding 경계, validation은 field validation 경계입니다. 같은 `email`이라도 읽는 도구가 다릅니다.

## Java 개발자가 자주 하는 오해

첫째, Kotlin property가 Java field와 같다는 오해입니다. Kotlin property는 field일 수도 있고, getter만 있을 수도 있으며,
custom getter가 있으면 backing field가 없을 수도 있습니다.

둘째, annotation을 하나만 붙이면 모든 프레임워크가 알아서 같은 의미로 읽는다는 오해입니다. Spring, Jackson, Hibernate,
Bean Validation은 각자 보는 위치와 lifecycle이 다릅니다.

셋째, `String?`에 `@Nullable`을 또 붙여야 안전하다는 오해입니다. Kotlin 안에서는 타입 자체가 주 계약입니다. Java API로
노출되거나 Spring API의 nullness annotation을 해석해야 하는 경계에서만 추가 annotation의 의미를 따집니다.

넷째, `@property:`가 Java reflection에서도 잘 보일 것이라는 오해입니다. Kotlin 문서는 `property` target이 Java에는
보이지 않는다고 설명합니다. Java 기반 프레임워크가 읽어야 한다면 `field`, `get`, `param` 중 하나를 검토해야 합니다.

## 연습 문제

1. 현재 프로젝트의 request DTO 하나를 골라 validation annotation이 target 없이 붙어 있는지 찾습니다.
2. 그 DTO를 Spring MVC validation, Jackson 생성자 binding, OpenAPI 문서화 중 어떤 도구가 읽는지 나눠 적습니다.
3. `@field:`, `@param:`, `@get:` 중 필요한 target만 남기고, 이유를 코드 리뷰 설명처럼 한 문장으로 써 봅니다.
4. nullable field에 `String?`와 validation annotation이 같이 있을 때 "없어도 되는 값"인지 "있으면 형식을 검사할 값"인지 구분합니다.

오늘의 결론은 가시성입니다. Kotlin은 Spring Boot 코드를 짧게 만들지만, Java reflection 기반 프레임워크와 만나는 경계에서는
짧은 코드보다 보이는 계약이 더 중요합니다. annotation target을 명시하면 DTO, validation, serialization의 책임이 한 줄씩
분리되어 디버깅하기 쉬워집니다.
