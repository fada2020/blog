> **검증 정보**
>
> 2026년 9월 12일에 Kotlin 2.4.20 릴리스 노트, Kotlin 2.4.0 변경 사항, context parameters 문서,
> Kotlin language features and proposals 문서를 확인했습니다. 기준 안정 버전은 `Kotlin 2.4.20`입니다.
> JetBrains는 2026년 9월 7일 Kotlin 2.4.20 정식 릴리스를 공지했고, context parameters는 Kotlin 2.4.0에서
> 안정 기능이 됐습니다. 단, explicit context arguments는 아직 Experimental이므로 이 글의 기본 예제에서는 안정 기능처럼 쓰지 않습니다.

## 결론부터 말하면

Kotlin의 `context parameters`는 함수가 필요로 하는 값을 호출 문맥에서 암묵적으로 공급받게 해 주는 기능입니다.
Spring Boot 개발자에게는 DI처럼 보일 수 있지만, 역할은 다릅니다.

Spring DI는 애플리케이션 객체를 만들고 연결합니다. `context parameters`는 이미 존재하는 값을 특정 호출 범위에 놓고,
그 범위 안의 함수가 그 값을 쓰도록 합니다.

그래서 첫 판단 기준은 단순합니다.

- `Repository`, `Client`, `Service` 같은 장기 생명주기 의존성은 Spring Bean으로 둡니다.
- request id, tenant, 권한 스코프, validation collector, DSL builder처럼 짧은 호출 문맥은 context parameter 후보입니다.
- 여러 구현체가 같은 타입으로 동시에 있을 수 있으면 이름 있는 wrapper type을 둡니다.
- Controller 바깥으로 숨겨진 의존성을 너무 많이 흘리면 읽기 어려워지므로, service public API에는 신중하게 씁니다.
- 명시성이 더 중요한 팀 코드에서는 평범한 파라미터가 여전히 더 좋은 선택입니다.

## 이번 주 개념

Kotlin 문서는 context parameters를 "주변 context에서 암묵적으로 사용할 수 있는 dependency를 선언하는 방법"으로 설명합니다.
문법은 함수나 property 앞에 `context(name: Type)`을 붙이는 방식입니다.

```kotlin
interface AuditContext {
    val requestId: String
    fun record(message: String)
}

context(audit: AuditContext)
fun approveOrder(orderId: Long) {
    audit.record("approve order $orderId in ${audit.requestId}")
}
```

호출하는 쪽은 `context(value) { ... }` 블록 안에서 함수를 호출합니다.

```kotlin
fun main() {
    val audit = object : AuditContext {
        override val requestId: String = "REQ-123"
        override fun record(message: String) = println(message)
    }

    context(audit) {
        approveOrder(10)
    }
}
```

`approveOrder()`의 인자는 `orderId` 하나처럼 보이지만, 함수 선언을 보면 `AuditContext`가 필요하다는 사실이 드러납니다.
숨겨진 전역 상태가 아니라 호출 범위에 놓인 값입니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 보통 생성자 주입으로 service가 필요한 객체를 받습니다.

```java
@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final AuditLogger auditLogger;

    public OrderService(OrderRepository orderRepository, AuditLogger auditLogger) {
        this.orderRepository = orderRepository;
        this.auditLogger = auditLogger;
    }

    public void approve(long orderId, String requestId) {
        orderRepository.approve(orderId);
        auditLogger.record(requestId, "approve order " + orderId);
    }
}
```

이 구조는 좋습니다. `OrderRepository`와 `AuditLogger`는 애플리케이션이 관리하는 장기 의존성이기 때문입니다.
문제는 모든 호출에 반복해서 따라다니는 짧은 문맥입니다.

```java
orderService.approve(orderId, requestId, tenantId, operatorId, locale, clock);
```

파라미터가 늘어나면 실제 비즈니스 입력과 실행 문맥이 한 줄에 섞입니다. Java에서는 보통 `RequestContext` 객체를 만들어
명시적으로 넘깁니다.

```java
orderService.approve(command, requestContext);
```

Kotlin에서도 이 방식은 여전히 좋은 기본값입니다. `context parameters`는 여기서 한 번 더 나아가,
특정 호출 범위 전체에 같은 문맥을 깔아 두고 작은 helper들이 그 문맥을 공유하게 합니다.

## Kotlin에서는 무엇이 다른가

Kotlin 코드에서 가장 먼저 피해야 할 오해는 `context parameters`를 Spring Bean 주입의 대체품으로 보는 것입니다.

아래처럼 repository를 context parameter로 숨기면 service의 실제 의존성이 멀리 흩어집니다.

```kotlin
interface OrderRepository {
    fun approve(orderId: Long)
}

context(repository: OrderRepository)
fun approveOrder(orderId: Long) {
    repository.approve(orderId)
}
```

작은 예제에서는 깔끔해 보입니다. 하지만 실제 Spring Boot 애플리케이션에서는 어떤 repository 구현이 쓰이는지,
transaction boundary가 어디인지, 테스트 double을 어디서 바꿔 끼우는지 읽기 어려워질 수 있습니다.

더 좋은 첫 사용처는 장기 의존성이 아니라 짧은 호출 문맥입니다.

```kotlin
data class OrderCommand(
    val orderId: Long,
    val operatorId: Long,
)

interface AuditScope {
    val requestId: String
    fun record(event: String)
}

class OrderService(
    private val orderRepository: OrderRepository,
) {
    context(audit: AuditScope)
    fun approve(command: OrderCommand) {
        orderRepository.approve(command.orderId)
        audit.record("operator=${command.operatorId} approved order=${command.orderId}")
    }
}
```

여기서 repository는 생성자 주입으로 남아 있습니다. audit scope만 호출 문맥으로 들어갑니다.
이렇게 나누면 Spring의 객체 생명주기와 Kotlin의 호출 문맥이 서로 싸우지 않습니다.

## 대응 개념 비교

| Spring Boot 습관 | Kotlin context parameters | 판단 기준 |
|---|---|---|
| 생성자 주입 | 그대로 유지 | Bean 생명주기는 Spring이 관리 |
| `RequestContext` 파라미터 | `context(scope: RequestScope)` | 여러 helper가 같은 짧은 문맥을 공유할 때 |
| ThreadLocal request holder | context parameter | 숨겨진 전역 상태보다 호출 범위가 명확할 때 |
| method argument 6개 이상 | command + context 분리 | 비즈니스 입력과 실행 문맥을 나눌 때 |
| test fixture setup | `context(fakeScope) { ... }` | 테스트에서 문맥을 작게 공급할 때 |

## 최소 실행 예제

아래 코드는 Spring 없이 실행할 수 있는 작은 예제입니다.

```kotlin
data class Order(
    val id: Long,
    val status: String,
)

interface AuditScope {
    val requestId: String
    fun record(message: String)
}

class InMemoryOrders {
    private val orders = mutableMapOf<Long, Order>()

    fun save(order: Order) {
        orders[order.id] = order
    }

    fun approve(orderId: Long): Order {
        val approved = Order(orderId, "APPROVED")
        save(approved)
        return approved
    }
}

context(audit: AuditScope)
fun InMemoryOrders.approveWithAudit(orderId: Long): Order {
    val order = approve(orderId)
    audit.record("request=${audit.requestId} approved=${order.id}")
    return order
}

fun main() {
    val orders = InMemoryOrders()
    val audit = object : AuditScope {
        override val requestId: String = "REQ-2026-09-12"
        override fun record(message: String) = println(message)
    }

    context(audit) {
        orders.approveWithAudit(100)
    }
}
```

이 예제에서 `InMemoryOrders`는 명시적인 receiver입니다. `AuditScope`는 context parameter입니다.
호출부에서는 "어떤 저장소에 대해 어떤 주문을 승인하는지"가 보이고, audit 문맥은 블록으로 묶여 있습니다.

## 이름 충돌과 ambiguity

Kotlin은 context parameter를 타입으로 찾습니다. 같은 scope level에 호환되는 값이 둘 이상 있으면 compiler가 ambiguity를 보고합니다.

```kotlin
interface Logger {
    fun info(message: String)
}

context(logger: Logger)
fun writeLog() {
    logger.info("done")
}

fun main() {
    val apiLogger = object : Logger {
        override fun info(message: String) = println("api: $message")
    }
    val batchLogger = object : Logger {
        override fun info(message: String) = println("batch: $message")
    }

    context(apiLogger, batchLogger) {
        // writeLog() // Logger가 둘이라 모호합니다.
    }
}
```

이 경우에는 "둘 다 Logger"로 두지 말고 의미가 있는 타입을 따로 둡니다.

```kotlin
interface ApiLogger : Logger
interface BatchLogger : Logger

context(logger: ApiLogger)
fun writeApiLog() {
    logger.info("done")
}
```

Spring에서도 `@Qualifier`를 남발하면 코드가 읽기 어려워집니다. Kotlin context parameter도 마찬가지입니다.
타입만으로 문맥을 찾으므로, 타입 이름이 곧 설계 문서가 됩니다.

## Java 개발자가 자주 하는 오해

첫째, "이제 DI framework가 필요 없다"는 오해입니다. 아닙니다. Spring은 객체 생성, lifecycle, proxy, transaction,
configuration binding, conditional bean 같은 일을 합니다. context parameter는 그런 일을 하지 않습니다.

둘째, "암묵적이면 전역 상태와 같다"는 오해입니다. 전역 상태는 어디서 바뀌었는지 추적하기 어렵습니다.
context parameter는 선언부와 호출 scope에 필요 값이 드러납니다. 다만 남용하면 읽기 어려워지는 것은 맞습니다.

셋째, "service public method에 전부 붙이면 깔끔하다"는 오해입니다. 공개 API는 호출자가 한눈에 이해해야 합니다.
팀원이 Kotlin에 익숙하지 않거나 Java caller가 많은 경계라면 command object와 명시 파라미터가 더 낫습니다.

넷째, "Experimental 예제를 그대로 써도 된다"는 오해입니다. Kotlin 2.4.0에서 context parameters 자체는 안정화됐지만,
explicit context arguments는 별도 compiler option이 필요한 Experimental 기능입니다. 글이나 팀 규칙에서는 이 둘을 분리해서 말해야 합니다.

## 어디에 먼저 써 볼까

Spring Boot 팀이라면 production service에 바로 넓게 적용하기보다 test helper나 작은 DSL에서 먼저 써 보는 편이 좋습니다.

```kotlin
interface ValidationScope {
    fun error(field: String, message: String)
}

context(errors: ValidationScope)
fun validateQuantity(quantity: Int?) {
    if (quantity == null) {
        errors.error("quantity", "required")
    } else if (quantity !in 1..99) {
        errors.error("quantity", "must be between 1 and 99")
    }
}
```

이런 helper는 입력값 자체보다 "오류를 어디에 모을 것인가"가 문맥입니다. 명시 파라미터로 넘겨도 되지만,
여러 validation 함수가 같은 collector를 공유한다면 context parameter가 읽기 좋은 선택이 될 수 있습니다.

반대로 아래 경우에는 보류합니다.

- transaction boundary가 context 뒤에 숨어야 하는 경우
- 같은 타입의 context가 여러 개 섞일 가능성이 높은 경우
- Java 호출자가 직접 불러야 하는 public API인 경우
- 단순 함수 하나에만 쓰이는 값인 경우
- 팀 코드 리뷰에서 암묵성이 비용으로 느껴지는 경우

## 연습 문제

1. 기존 service method 중 `requestId`, `operatorId`, `locale`, `clock`처럼 비즈니스 입력과 실행 문맥이 섞인 예를 하나 찾습니다.
2. 그 method의 진짜 command 값과 호출 문맥 값을 두 그룹으로 나눕니다.
3. Spring Bean 의존성은 생성자에 남기고, 짧은 호출 문맥만 `context` 후보로 표시합니다.
4. 같은 타입이 둘 이상 들어올 수 있는 문맥이 있는지 확인합니다.
5. 테스트 코드에서 `context(fakeScope) { ... }`로 읽기 쉬워지는지, 오히려 숨겨지는지 비교합니다.

오늘의 결론은 무리하지 않는 쪽입니다. `context parameters`는 멋진 기능이지만, 좋은 Kotlin 코드는 Spring DI를 버리는 코드가 아닙니다.
Bean 생명주기는 Spring에 맡기고, 짧은 호출 문맥만 작게 감싸면 Java/Spring 개발자도 납득할 수 있는 경계가 생깁니다.
