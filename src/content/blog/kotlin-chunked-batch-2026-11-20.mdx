## 이번 주 개념

`chunked(2)`는 입력을 최대 두 원소씩 나눕니다. 다섯 원소라면 묶음 크기는 `[2, 2, 1]`입니다. 마지막 한 원소를 버리지 않습니다. 다만 묶음을 만드는 일과 DB 트랜잭션을 나누는 일은 별개입니다.

> 검증일: 2026년 11월 20일 KST. 최신 안정판 Kotlin 2.4.21 기준입니다. Gradle 플러그인 목록의 2.5.0 Beta는 제외했습니다.

[공식 릴리스 이력](https://kotlinlang.org/docs/releases.html)과 [Gradle 플러그인 목록](https://plugins.gradle.org/plugin/org.jetbrains.kotlin.jvm)에서 안정 버전을 확인했습니다.

## Java와 Spring에서는 어떻게 다뤘는가

Java에서는 인덱스를 일정 간격으로 증가시키고 마지막 인덱스를 목록 크기로 제한하는 반복문을 작성하곤 합니다. Kotlin에서는 목록 분할을 표준 라이브러리로 표현할 수 있습니다. Spring Batch의 청크 지향 처리에서 말하는 커밋 경계는 프레임워크가 관리하는 별도 개념입니다. 이름이 비슷해도 Kotlin 컬렉션 함수가 트랜잭션 매니저를 호출하지는 않습니다.

| 질문 | chunked가 정하는 것 | 호출자가 정하는 것 |
| --- | --- | --- |
| 한 묶음의 최대 크기 | 양수 size | 외부 API 제한에 맞는 값 |
| 마지막 묶음 | 남은 원소 포함 | 작은 묶음도 받는 API인지 |
| 실패 후 재시도 | 제공하지 않음 | 중복 방지 키와 재시도 단위 |
| 저장 원자성 | 제공하지 않음 | 전체 또는 묶음별 트랜잭션 |

## 최소 실행 예제

다음은 DB나 HTTP를 호출하지 않는 독립 Kotlin/JVM 예제입니다. 외부 전송을 기록 목록으로 대체했습니다.

```kotlin
fun main() {
    val ids = listOf(1, 2, 3, 4, 5)
    val batches = ids.chunked(2)
    check(batches == listOf(listOf(1, 2), listOf(3, 4), listOf(5)))
    check(batches.flatten() == ids)
    check(emptyList<Int>().chunked(2).isEmpty())
    check(runCatching { ids.chunked(0) }.isFailure)

    val sums = ids.chunked(2) { batch -> batch.sum() }
    check(sums == listOf(3, 7, 5))
    val snapshots = ids.chunked(2) { batch -> batch.toList() }
    check(snapshots == batches)

    val sent_batches = mutableListOf<List<Int>>()
    val result = runCatching {
        for (batch in batches) {
            if (batch.contains(3)) error("simulated failure")
            sent_batches.add(batch)
        }
    }
    check(result.isFailure)
    check(sent_batches == listOf(listOf(1, 2)))
    println("8 checks passed")
}
```

일반 `chunked(size)`는 목록의 목록을 반환합니다. 변환 함수를 받는 오버로드에는 별도 주의점이 있습니다.

## transform에 전달된 목록은 보관하지 않습니다

`chunked(size) { batch -> ... }`의 `batch`는 변환 함수 안에서만 유효한 임시 목록입니다. 함수 밖에서 나중에 읽어야 한다면 예제처럼 `toList()`로 스냅샷을 만듭니다. 합계로 즉시 변환하면 목록 자체를 보관할 필요가 없습니다. 요소가 가변 객체라면 목록 복사는 요소의 깊은 복사가 아닙니다.

## 요청과 저장 경계를 구분합니다

학습용 입력 `{"ids":[1,2,3,4,5],"batch_size":2}`는 `[[1,2],[3,4],[5]]`로 나뉩니다. 이 JSON은 설명용이며 실제 서비스 API가 아닙니다. 위 실패 실험에서 기록된 값은 `[[1,2]]`뿐입니다. 전체를 처음부터 재시도하면 첫 묶음이 중복 처리될 수 있습니다. 외부 호출이 성공한 뒤 응답만 유실되는 경우도 있으므로, 재시도 가능성은 묶음 크기만으로 해결되지 않습니다.

전체 입력을 검증한 뒤 저장해야 한다면 앞선 [누락 값 다루기](/blog/posts/kotlin-map-not-null-2026-11-19/)처럼 입력 실패를 먼저 보존합니다. `mapNotNull`로 잘못된 입력을 버린 뒤 묶으면 원래 요청의 위치와 개수가 달라집니다.

예제는 Kotlin/JVM 2.4.21에서 실행해 8개 check를 확인했습니다. 실제 DB 롤백이나 네트워크 재시도는 검증하지 않았습니다. 일반 Iterable의 `chunked`는 결과를 목록으로 만들므로, 무한 스트림을 처리하는 함수로 생각해서도 안 됩니다.

## 자주 하는 오해와 연습

한 묶음이 작다고 전체 메모리 사용량이 자동으로 제한되지는 않습니다. 이미 전체 입력과 모든 묶음을 메모리에 올렸는지 확인해야 합니다. 또한 분할은 병렬 실행을 뜻하지 않습니다.

1. 입력 개수를 0, 1, 4, 5로 바꾸고 마지막 묶음 크기를 비교합니다.
2. 실패한 두 번째 묶음부터 재개하는 가짜 전송 함수를 만들고 중복 기록 여부를 확인합니다.
3. 변환 람다에서 목록 자체 대신 합계와 개수를 반환해 봅니다.

[chunked 공식 API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.collections/chunked.html)의 양수 크기 조건, 마지막 묶음과 임시 목록 계약을 기준으로 작성했습니다.
