## 결론부터 말하면

Flutter에서 화면 이동을 배울 때 처음부터 복잡한 app shell을 만들 필요는 없습니다. 다만 **작은 화면 이동은
`Navigator.push()`로 익히고, URL과 인증 상태가 얽히는 순간부터 route table을 한곳에 모으는 습관**을
가져야 합니다.

Spring Boot 개발자는 URL을 Controller mapping으로 읽는 데 익숙합니다. `/orders/{orderId}`가 어떤
handler로 가는지, 인증이 필요한지, 없는 리소스는 어떤 응답이 되는지 서버 쪽에서 정합니다. Flutter도
화면이 늘어나면 비슷한 질문을 하게 됩니다.

- 홈에서 상세 화면으로 어떻게 이동하는가
- 상세 화면은 어떤 parameter를 받아야 하는가
- 로그인 전에는 어떤 화면으로 돌려보내야 하는가
- 브라우저 뒤로 가기와 모바일 back button은 같은 의미인가

## 이번 주 개념

Flutter 공식 navigation 문서는 `Router`와 `Navigator`가 함께 쓰이도록 설계되어 있다고 설명합니다.
선언형 routing package로 Router API를 쓸 수도 있고, `Navigator.push()`와 `Navigator.pop()`처럼 명령형
API를 직접 호출할 수도 있습니다.

가장 작은 예제는 `Navigator` stack을 이해하는 코드입니다.

```dart
class OrderListScreen extends StatelessWidget {
  const OrderListScreen({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Orders')),
      body: ListView(
        children: [
          ListTile(
            title: const Text('Order #42'),
            onTap: () {
              Navigator.of(context).push(
                MaterialPageRoute<void>(
                  builder: (_) => const OrderDetailScreen(orderId: 42),
                ),
              );
            },
          ),
        ],
      ),
    );
  }
}

class OrderDetailScreen extends StatelessWidget {
  const OrderDetailScreen({
    required this.orderId,
    super.key,
  });

  final int orderId;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('Order #$orderId')),
      body: Center(
        child: FilledButton(
          onPressed: () => Navigator.of(context).pop(),
          child: const Text('Back'),
        ),
      ),
    );
  }
}
```

이 코드는 list screen 위에 detail screen을 하나 더 올립니다. `pop()`은 마지막 화면을 제거합니다.
처음에는 이것만으로도 화면 이동의 감각을 잡을 수 있습니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 route가 서버의 진입점입니다.

```java
@RestController
class OrderController {

    @GetMapping("/orders/{orderId}")
    OrderResponse findOrder(@PathVariable long orderId) {
        return orderService.findOrder(orderId);
    }
}
```

이 코드에는 세 가지 계약이 들어 있습니다.

| 계약 | Spring Boot | Flutter |
|---|---|---|
| 주소 | `/orders/{orderId}` | `/orders/:orderId` 또는 screen 생성자 |
| 진입점 | Controller method | route builder 또는 widget |
| 인증/인가 | Filter, Interceptor, Method Security | redirect, route guard, 화면 조건 분기 |
| 없는 대상 | 404 또는 error response | error screen, redirect, empty state |
| 뒤로 가기 | 새 HTTP 요청 또는 브라우저 history | Navigator stack, browser history, system back |

Spring에서는 URL이 서버 리소스를 가리킵니다. Flutter에서는 URL이 항상 서버 리소스와 1:1로 맞지는
않습니다. 모바일 앱에서는 현재 stack이 더 중요할 수 있고, Flutter web에서는 browser history와 deep link가
중요해집니다. 그래서 화면 이동 규칙을 어디에 둘지 초기에 정해야 합니다.

## Flutter에서는 무엇이 다른가

`Navigator`는 화면 stack을 다룹니다. `push`는 새 route를 위에 올리고, `pop`은 현재 route를 제거합니다.
반면 `Router` 기반 접근은 앱 상태와 URL을 route table로 연결합니다.

<Mermaid title="Navigator와 Router의 역할">
{`flowchart TD
  Tap["사용자 탭"] --> Imperative["Navigator.push()"]
  Imperative --> Stack["화면 stack 변경"]
  Stack --> Detail["상세 화면 표시"]

  Url["/orders/42 deep link"] --> Router["Router 또는 go_router"]
  Auth["로그인 상태"] --> Router
  Router --> Builder["route builder"]
  Router --> Redirect["redirect"]
  Builder --> Page["page-backed route"]
`}
</Mermaid>

공식 문서는 Router나 선언형 routing package를 통해 이동하면 page-backed route가 만들어지고, 이런 route는
deep link와 browser history에 더 잘 맞는다고 설명합니다. 반대로 `showDialog()`나 직접 `push()`로 만든
route는 현재 화면 위에 잠깐 올리는 흐름에 잘 맞습니다.

## 작은 앱은 Navigator로 충분합니다

두세 화면짜리 내부 도구라면 `Navigator.push()`가 가장 읽기 쉽습니다.

```dart
onTap: () async {
  final changed = await Navigator.of(context).push<bool>(
    MaterialPageRoute(
      builder: (_) => const EditProfileScreen(),
    ),
  );

  if (changed == true) {
    // 목록을 다시 읽거나 화면 상태를 갱신합니다.
  }
}
```

이 패턴은 Spring MVC에서 form submit 후 redirect 결과를 보고 목록을 다시 읽는 흐름과 비슷합니다.
다만 Flutter에서는 `push()`가 `Future<T?>`를 반환하므로, 다음 화면에서 `pop(result)`로 값을 되돌려줄 수
있습니다.

```dart
Navigator.of(context).pop(true);
```

이 정도는 route table보다 명령형 코드가 더 단순합니다.

## URL과 인증이 생기면 go_router를 봅니다

앱에 deep link, web URL, bottom navigation, 로그인 redirect가 들어오면 route 정의를 한곳에 모으는 편이
낫습니다. Flutter 팀이 publish하는 `go_router`는 Router API 위에 URL 기반 navigation API를 제공합니다.

```dart
final router = GoRouter(
  initialLocation: '/orders',
  redirect: (context, state) {
    final signedIn = authRepository.isSignedIn;
    final goingToSignIn = state.matchedLocation == '/sign-in';

    if (!signedIn && !goingToSignIn) {
      return '/sign-in';
    }

    if (signedIn && goingToSignIn) {
      return '/orders';
    }

    return null;
  },
  routes: [
    GoRoute(
      path: '/orders',
      builder: (context, state) => const OrderListScreen(),
      routes: [
        GoRoute(
          path: ':orderId',
          builder: (context, state) {
            final orderId = int.parse(state.pathParameters['orderId']!);
            return OrderDetailScreen(orderId: orderId);
          },
        ),
      ],
    ),
    GoRoute(
      path: '/sign-in',
      builder: (context, state) => const SignInScreen(),
    ),
  ],
);

class LearningApp extends StatelessWidget {
  const LearningApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp.router(routerConfig: router);
  }
}
```

여기서 route table은 Spring의 Controller mapping 목록과 비슷한 역할을 합니다. 차이는 이 mapping이 서버
요청이 아니라 앱 화면 상태를 만든다는 점입니다.

## 화면 parameter는 문자열에서 domain 값으로 바꿉니다

URL parameter는 문자열입니다. Spring Boot에서도 `@PathVariable long orderId`처럼 변환 경계가 있습니다.
Flutter에서도 route builder 안에서 문자열을 그대로 화면 전체에 흘리지 말고, 필요한 타입으로 바꿉니다.

```dart
GoRoute(
  path: '/orders/:orderId',
  builder: (context, state) {
    final rawOrderId = state.pathParameters['orderId'];
    final orderId = int.tryParse(rawOrderId ?? '');

    if (orderId == null) {
      return const InvalidOrderScreen();
    }

    return OrderDetailScreen(orderId: orderId);
  },
);
```

서버라면 400이나 404를 고를 수 있습니다. 앱에서는 잘못된 deep link를 받았을 때 오류 화면을 보여줄지,
목록으로 보낼지, 로그인 화면으로 보낼지 정해야 합니다. 중요한 것은 이 결정을 각 screen의 `build()` 안에
흩뿌리지 않는 것입니다.

## redirect는 인증만 넣고 업무 규칙은 과하게 넣지 않습니다

`redirect`는 강력하지만 모든 업무 규칙을 넣는 장소는 아닙니다. 예를 들어 로그인 여부, onboarding 완료
여부처럼 route 진입 자체를 막는 조건은 적합합니다. 반대로 주문이 취소되었는지, 결제가 가능한 상태인지
같은 domain rule은 상세 화면이나 service layer에서 읽는 편이 낫습니다.

| 조건 | route redirect에 적합한가 | 이유 |
|---|---|---|
| 로그인하지 않은 사용자가 보호 화면 접근 | 적합 | 화면 진입 전 공통 정책입니다. |
| 약관 동의가 끝나지 않음 | 대체로 적합 | 앱 전체 onboarding 흐름입니다. |
| 주문이 취소 상태라 수정 불가 | 부적합 | domain data를 읽은 뒤 화면에서 처리할 규칙입니다. |
| 네트워크 오류로 주문 조회 실패 | 부적합 | loading/error/data 상태로 표시해야 합니다. |

Spring Security filter에 모든 Service rule을 넣지 않는 것과 같은 감각입니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 URL이 항상 서버 API와 같아야 한다는 생각입니다. Flutter 화면 URL은 사용자가 돌아올 수
있는 위치를 표현할 뿐입니다. `/orders/42` 화면이 내부적으로 `/api/v2/order-summaries/42`를 호출해도
문제 없습니다.

두 번째 오해는 모든 이동을 global helper로 감싸는 것입니다. 작은 앱에서 `context.goOrderDetail(id)`
같은 helper를 남발하면 route table을 봐도 실제 이동 경로가 잘 보이지 않습니다. 먼저 명확한 route 이름과
path를 유지하는 편이 낫습니다.

세 번째 오해는 `build()`에서 인증 상태를 매번 읽고 임의로 다른 화면을 반환하는 방식입니다. 잠깐은
동작하지만 deep link, browser back, splash, token refresh가 들어오면 흐름이 흔들립니다. 진입 정책은
route layer에 두고, 화면 안에서는 현재 화면의 loading/error/data 상태를 다루는 편이 읽기 쉽습니다.

## 연습 문제

1. `OrderListScreen`에서 `Navigator.push()`로 상세 화면을 열고, 상세 화면에서 `pop(true)`를 반환해
   목록이 새로고침되었다는 메시지를 표시해 보세요.
2. 같은 흐름을 `go_router`의 `/orders/:orderId` path로 바꿔 보세요.
3. 로그인하지 않은 상태에서 `/orders/42` deep link가 들어오면 `/sign-in`으로 보내고, 로그인 후 다시
   원래 화면으로 돌아가는 정책을 설계해 보세요.
4. `orderId`가 숫자가 아닐 때 목록으로 redirect할지 오류 화면을 보여줄지 정하고, 그 이유를 적어 보세요.

## 다음 단계

화면 이동을 익히면 다음 병목은 상태의 범위입니다. 목록, 상세, form, 인증 상태가 서로 영향을 주기 시작하면
`setState()`만으로는 흐름을 설명하기 어려워집니다. 다음 Flutter 학습 글에서는 작은 앱에서 provider나
상태 관리 도구를 도입하기 전에, 어떤 state를 local로 두고 어떤 state를 app-level로 올릴지 먼저
나눠보겠습니다.
