## 결론부터 말하면

Kotlin의 extension function은 클래스를 몰래 바꾸는 문법이 아닙니다. 기존 타입의 바깥에 함수를 선언하되,
호출할 때는 그 타입의 멤버처럼 읽히게 만드는 **정적 함수 호출 표기법**에 가깝습니다.

receiver lambda는 한 단계 더 나아가 "이 블록 안에서는 어떤 객체를 기준으로 함수를 호출할 것인가"를 정합니다.
그래서 Kotlin DSL, Gradle Kotlin DSL, Ktor routing, 테스트 fixture builder 같은 코드가 Java builder보다
문장처럼 보입니다.

Spring Boot 개발자가 잡을 기준은 단순합니다.

- extension은 도메인 핵심 동작보다 변환, 표시, 테스트 helper처럼 경계 밖 보조 동작에 먼저 씁니다.
- receiver lambda는 설정 대상이 분명한 builder에 씁니다.
- 멤버 함수와 같은 이름의 extension으로 핵심 동작을 덮어쓰려 하지 않습니다.
- 여러 receiver가 겹치는 DSL에서는 `@DslMarker` 같은 제한을 둡니다.
- Java 호출자가 많은 API라면 extension의 JVM 이름과 위치를 의식합니다.

## 이번 주 개념

Kotlin 공식 문서는 extension이 class나 interface에 새 기능을 "추가한 것처럼" 호출하게 해 주지만, 실제로 그 타입에
새 member를 넣는 것은 아니라고 설명합니다. receiver type을 함수 이름 앞에 붙이면 됩니다.

```kotlin
fun String.normalizedEmail(): String =
    trim().lowercase()
```

호출하는 쪽에서는 멤버 함수처럼 보입니다.

```kotlin
val email = " USER@EXAMPLE.COM ".normalizedEmail()
```

receiver lambda는 함수 타입에 receiver를 붙입니다. Kotlin 문서의 표기법으로는 `A.(B) -> C`입니다. 즉 `A`라는
객체를 receiver로 두고, `B`를 인자로 받아, `C`를 돌려주는 함수입니다.

```kotlin
class RouteBuilder {
    fun get(path: String, handler: () -> Unit) {
        println("GET $path")
        handler()
    }
}

fun routes(init: RouteBuilder.() -> Unit): RouteBuilder {
    val builder = RouteBuilder()
    builder.init()
    return builder
}
```

이제 호출부는 아래처럼 됩니다.

```kotlin
routes {
    get("/orders") {
        println("load orders")
    }
}
```

`routes { ... }` 블록 안에서는 `RouteBuilder`가 암묵적인 기준 객체가 됩니다. Java builder의 `.get(...).post(...)`
chain과 비슷하지만, Kotlin은 블록 안의 `this`를 타입으로 제한할 수 있습니다.

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 보통 static utility, builder, fluent API로 같은 문제를 풀었습니다.

```java
public final class EmailNormalizer {
    private EmailNormalizer() {
    }

    public static String normalize(String value) {
        return value.trim().toLowerCase(Locale.ROOT);
    }
}
```

호출부는 명시적입니다.

```java
String email = EmailNormalizer.normalize(request.email());
```

장점은 출처가 분명하다는 것입니다. 단점은 작은 변환 함수가 늘어날수록 도메인 흐름보다 helper class 이름이 먼저
보인다는 것입니다.

Builder도 마찬가지입니다.

```java
RouteConfig config = RouteConfig.builder()
    .get("/orders", orderHandler)
    .post("/orders", createOrderHandler)
    .build();
```

Java에서 이 형태는 자연스럽습니다. Kotlin으로 옮긴다고 해서 모두 DSL로 바꿀 필요는 없습니다. receiver lambda는
계층 구조나 설정 대상이 분명할 때만 값이 있습니다.

## Kotlin에서는 무엇이 다른가

Kotlin extension의 가장 좋은 첫 사용처는 request DTO, entity, external response 사이의 변환 경계입니다.

```kotlin
data class OrderRequest(
    val productId: String?,
    val quantity: Int?,
)

data class CreateOrderCommand(
    val productId: String,
    val quantity: Int,
)

fun OrderRequest.toCommand(): CreateOrderCommand {
    val productId = productId
        ?.trim()
        ?.takeIf { it.isNotBlank() }
        ?: throw BadRequestException("productId is required")

    val quantity = quantity
        ?.takeIf { it > 0 }
        ?: throw BadRequestException("quantity must be positive")

    return CreateOrderCommand(
        productId = productId,
        quantity = quantity,
    )
}
```

이 함수가 `OrderRequest`의 멤버는 아닙니다. 그래서 request class를 순수 데이터 모양으로 유지하면서도 변환 로직을
가까운 파일에 둘 수 있습니다.

다만 extension은 남용하기 쉽습니다. 아래처럼 repository 조회, 권한 확인, 외부 API 호출까지 extension에 넣으면
호출부는 예뻐 보이지만 의존성이 숨어 버립니다.

```kotlin
// 피하는 편이 좋습니다.
suspend fun OrderRequest.createOrder(
    repository: OrderRepository,
    auth: AuthContext,
): Order = repository.save(toCommand().ownedBy(auth.userId))
```

도메인 행위와 I/O는 service에 둡니다. extension은 값을 다른 값으로 바꾸는 좁은 경계에 둘 때 읽기 쉽습니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin 표현 | 주의할 점 |
|---|---|---|
| static utility | top-level function 또는 extension function | 출처가 숨지 않도록 파일과 package를 명확히 둡니다. |
| DTO mapper class | `Request.toCommand()` | DB 조회나 권한 판단은 넣지 않습니다. |
| fluent builder | receiver lambda builder | 계층 구조가 있을 때만 씁니다. |
| Spring Java config lambda | Kotlin DSL-style config | 암묵적 `this`가 많아지면 제한합니다. |
| test fixture factory | receiver lambda fixture | 테스트 의도만 남기고 production 규칙을 숨기지 않습니다. |

Extension은 "짧게 쓰는 상속"이 아닙니다. Kotlin 문서 기준 extension dispatch는 정적입니다. 변수의 선언 타입이
무엇인지에 따라 어떤 extension이 호출될지 컴파일 시점에 정해집니다. 실제 runtime subtype을 보고 override되는
멤버 함수처럼 동작하지 않습니다.

## 최소 실행 예제

아래 예제는 Spring 없이 실행할 수 있는 작은 route builder입니다. 핵심은 `ApiRoutes.() -> Unit`입니다.

```kotlin
data class Endpoint(
    val method: String,
    val path: String,
    val permission: String,
)

class ApiRoutes {
    private val endpoints = mutableListOf<Endpoint>()

    fun get(path: String, permission: String) {
        endpoints += Endpoint("GET", path, permission)
    }

    fun post(path: String, permission: String) {
        endpoints += Endpoint("POST", path, permission)
    }

    fun build(): List<Endpoint> = endpoints.toList()
}

fun api(init: ApiRoutes.() -> Unit): List<Endpoint> {
    val routes = ApiRoutes()
    routes.init()
    return routes.build()
}

fun Endpoint.isWriteOperation(): Boolean =
    method in setOf("POST", "PUT", "PATCH", "DELETE")

fun main() {
    val endpoints = api {
        get("/orders", permission = "ORDER_READ")
        post("/orders", permission = "ORDER_WRITE")
    }

    println(endpoints)
    println(endpoints.filter(Endpoint::isWriteOperation))
}
```

`api { ... }` 안에서는 `get`, `post`를 바로 호출합니다. 블록의 receiver가 `ApiRoutes`이기 때문입니다.
그리고 `Endpoint.isWriteOperation()`은 I/O 없이 값을 판정하는 보조 동작이므로 extension으로 두기 좋습니다.

## receiver가 많아질 때는 경계를 닫습니다

DSL을 중첩하면 암묵적인 receiver가 여러 개 생깁니다. 처음에는 편하지만, 바깥 builder의 함수를 안쪽에서 실수로
호출할 수 있습니다.

```kotlin
class ApiRoutes {
    fun group(path: String, init: RouteGroup.() -> Unit) {
        RouteGroup(path).init()
    }

    fun get(path: String, permission: String) {
        println("GET $path $permission")
    }
}

class RouteGroup(private val prefix: String) {
    fun get(path: String, permission: String) {
        println("GET $prefix$path $permission")
    }
}
```

이 구조에서 안쪽 `group` 블록은 `RouteGroup`을 기준으로 읽혀야 합니다. DSL이 커질수록 어떤 `get`을 호출하는지
헷갈릴 수 있습니다. Kotlin의 type-safe builders 문서는 이런 builder 조합에서 `@DslMarker`를 사용해 receiver
범위를 제한하는 방식을 보여줍니다.

```kotlin
@DslMarker
annotation class ApiDsl

@ApiDsl
class ApiRoutes {
    fun group(path: String, init: RouteGroup.() -> Unit) {
        RouteGroup(path).init()
    }
}

@ApiDsl
class RouteGroup(private val prefix: String) {
    fun get(path: String, permission: String) {
        println("GET $prefix$path $permission")
    }
}
```

이제 DSL 안의 실수는 더 빨리 드러납니다. Spring Boot 설정 코드처럼 한번 만들면 오래 읽히는 API일수록 이런
제약이 중요합니다.

## Java 호출자를 고려합니다

Kotlin extension은 JVM에서 실제 member method가 아닙니다. Java에서 호출하면 top-level 함수가 들어 있는 파일의
facade class를 통해 static method처럼 보입니다. 예를 들어 `OrderMappings.kt`에 `fun OrderRequest.toCommand()`를
두면 Java 호출자는 대략 `OrderMappingsKt.toCommand(request)` 같은 모양을 보게 됩니다.

Kotlin 안에서만 쓰는 변환 함수라면 문제 없습니다. 하지만 Java module이나 Spring bean에서 직접 호출해야 한다면
다음 중 하나를 선택하는 편이 낫습니다.

- Java 호출부도 자연스럽게 읽혀야 하면 일반 mapper class나 Spring component를 둡니다.
- Kotlin 내부 표현만 정리하려면 extension을 둡니다.
- public library라면 `@file:JvmName` 같은 JVM 노출 이름을 따로 설계합니다.

Extension을 public API로 내보내는 순간 호출 문법뿐 아니라 binary compatibility와 package 이동 비용도 API의
일부가 됩니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 extension이 private member에 접근할 수 있다고 생각하는 것입니다. 접근 권한은 일반 함수와 같습니다.
receiver의 public API로 보이는 것만 사용할 수 있습니다.

두 번째 오해는 extension이 override처럼 동작한다고 생각하는 것입니다. extension은 정적으로 해석됩니다. 다형성이
필요하면 interface member나 sealed hierarchy를 먼저 고려합니다.

세 번째 오해는 DSL이 항상 좋은 API라는 생각입니다. DSL은 호출부를 짧게 만들지만, 구현자가 만든 작은 언어를 팀원이
새로 배워야 합니다. 설정 대상이 단순하면 named argument와 data class가 더 낫습니다.

네 번째 오해는 모든 mapper를 extension으로 옮기는 것입니다. 변환이 순수하고 가까운 문맥에서만 쓰이면 좋지만,
repository, 외부 API, transaction이 들어오면 service method가 더 솔직합니다.

## 연습 문제

아래 Java helper를 Kotlin extension으로 옮겨 보세요.

```java
public static boolean isBlankOrSystem(String value) {
    return value == null || value.isBlank() || value.equals("system");
}
```

조건은 세 가지입니다.

1. nullable receiver를 사용합니다.
2. `null`, blank, `"system"`이면 `true`를 반환합니다.
3. `" user "`는 `false`를 반환합니다.

다음으로 작은 builder를 만들어 보세요.

```kotlin
val policy = accessPolicy {
    allow("ORDER_READ")
    allow("ORDER_WRITE")
}
```

`accessPolicy`의 parameter type은 `AccessPolicyBuilder.() -> Unit`이어야 합니다. 완성한 뒤 Java builder보다
읽기 좋아진 부분과 오히려 숨겨진 부분을 한 줄씩 적어 보세요.
