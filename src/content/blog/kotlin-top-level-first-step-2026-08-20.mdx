## 결론부터 말하면

Kotlin을 처음 볼 때 가장 먼저 바꿔야 하는 습관은 **모든 코드를 클래스 안에 넣어야 한다는 Java식
반사 동작**입니다. Kotlin은 JVM 위에서 실행될 수 있지만, 소스 코드의 모양은 Java보다 더 작게 시작합니다.

Spring Boot 개발자는 보통 아래 구조에 익숙합니다.

```java
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

Kotlin에서는 같은 진입점을 파일의 top-level 함수로 둘 수 있습니다.

```kotlin
fun main() {
    println("Hello Kotlin")
}
```

처음에는 이 차이가 사소해 보입니다. 하지만 Kotlin의 파일, 함수, 클래스, 값 선언을 이해하는 출발점입니다.
이번 글에서는 Spring Boot/Java 개발자가 Kotlin을 시작할 때 가장 먼저 잡아야 할 네 가지를 정리합니다.

- top-level 선언은 어떤 의미인가
- `val`과 `var`는 Java 변수와 어떻게 다른가
- Kotlin class 선언은 왜 짧은가
- `data class`는 언제 DTO처럼 쓸 수 있는가

## 이번 주 개념

Kotlin 파일은 클래스 선언 없이도 함수와 값을 가질 수 있습니다. 공식 문서도 함수는 파일 top-level에
선언할 수 있다고 설명합니다. 그래서 작은 프로그램은 아래처럼 시작합니다.

```kotlin
fun main() {
    val user = User(id = 1L, name = "Kim")
    println(user.displayName())
}

class User(
    val id: Long,
    private val name: String,
) {
    fun displayName(): String = "user-$id:$name"
}
```

여기에는 Kotlin 첫 학습에서 중요한 규칙이 들어 있습니다.

| 코드 | 역할 |
|---|---|
| `fun main()` | 파일 top-level에 선언한 프로그램 진입점입니다. |
| `val user` | 한 번 참조가 정해지면 다시 대입하지 않는 읽기 전용 지역 변수입니다. |
| `class User(...)` | 주 생성자와 property 선언을 클래스 헤더에 함께 둡니다. |
| `private val name` | 생성자 인자이면서 클래스 내부 property입니다. |
| `fun displayName()` | 클래스 member function입니다. |

Kotlin을 Java의 축약 문법으로만 보면 `public static`, getter, 생성자 boilerplate가 줄었다는 점만 보입니다.
하지만 더 중요한 차이는 "파일에 가까운 작은 선언"과 "불변에 가까운 값 흐름"을 기본 감각으로 삼는다는
점입니다.

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 실행 가능한 함수가 클래스 밖에 있을 수 없습니다. 작은 유틸리티 함수도 보통 클래스와
`static` 메서드 안에 둡니다.

```java
public final class UserNames {
    private UserNames() {
    }

    public static String displayName(long id, String name) {
        return "user-" + id + ":" + name;
    }
}
```

Spring Boot 프로젝트에서도 비슷합니다. `@Service`, `@Component`, `@Configuration` 같은 클래스가
애플리케이션 구조의 기본 단위가 됩니다. 그래서 Kotlin을 시작할 때도 모든 함수를 객체나 companion object
안에 넣고 싶어집니다.

Kotlin에서는 그럴 필요가 없습니다.

```kotlin
fun displayName(id: Long, name: String): String {
    return "user-$id:$name"
}
```

이 함수는 어떤 클래스의 member도 아닙니다. 파일의 top-level 선언입니다. 테스트 fixture, 작은 변환 함수,
도메인 값 포맷터처럼 상태가 없는 함수는 굳이 클래스로 감싸지 않아도 됩니다.

## Kotlin에서는 무엇이 다른가

Kotlin 소스 파일은 JVM 바이트코드로 컴파일될 때 필요한 클래스 형태로 변환됩니다. 하지만 개발자가 읽고
관리하는 소스의 단위는 더 자유롭습니다. 공식 coding conventions도 서로 밀접한 여러 선언을 같은 파일에
둘 수 있다고 안내합니다.

<Mermaid title="Java 클래스 중심과 Kotlin 파일 중심 선언 비교">
{`flowchart LR
  JavaFile["Java source file"] --> JavaClass["class required"]
  JavaClass --> StaticMethod["static utility method"]
  JavaClass --> InstanceMethod["instance method"]

  KotlinFile["Kotlin source file"] --> TopLevel["top-level function"]
  KotlinFile --> KotlinClass["class"]
  KotlinClass --> MemberFunction["member function"]

  TopLevel --> SimpleLogic["상태 없는 변환과 검증"]
  MemberFunction --> DomainBehavior["객체 상태와 함께 쓰는 동작"]
`}
</Mermaid>

Spring Boot 개발자 관점에서 가까운 비교는 아래와 같습니다.

| Java/Spring에서 익숙한 것 | Kotlin에서 먼저 볼 개념 | 주의할 점 |
|---|---|---|
| `public static void main` | `fun main()` | 클래스 안에 둘 필요가 없습니다. |
| utility class | top-level function | 상태가 없다면 객체로 감싸지 않아도 됩니다. |
| `final` 지역 변수 | `val` | 참조 재대입을 막는 기본 선택지입니다. |
| mutable 지역 변수 | `var` | 꼭 값이 바뀌는 경우에만 씁니다. |
| constructor와 field | 주 생성자 property | 생성자 인자와 property 선언이 합쳐질 수 있습니다. |
| DTO record | `data class` | 값 전달 모델에 적합하지만 도메인 행위까지 대신하지 않습니다. |

## `val`을 기본으로 시작합니다

Kotlin에는 지역 변수 선언에 `val`과 `var`가 있습니다.

```kotlin
val createdAt = Instant.now()
var retryCount = 0

retryCount += 1
```

`val`은 다시 대입할 수 없습니다. Java의 `final` 지역 변수와 비슷하게 읽을 수 있습니다. 반면 `var`는
재대입이 가능합니다. 그래서 Kotlin 코드를 처음 쓸 때는 `val`로 시작하고, 정말 값이 바뀌어야 할 때만
`var`로 바꾸는 편이 좋습니다.

이 습관은 Spring Boot 서비스 코드에서도 도움이 됩니다.

```kotlin
fun register(command: RegisterUserCommand): UserResponse {
    val normalizedEmail = command.email.trim().lowercase()
    val user = User(email = normalizedEmail, name = command.name)
    val saved = userRepository.save(user)

    return UserResponse.from(saved)
}
```

여기서 중간 값은 모두 `val`입니다. 요청을 정규화하고, 엔티티를 만들고, 저장 결과를 응답으로 바꾸는 흐름이
한 방향으로 읽힙니다. Java에서도 같은 코드를 작성할 수 있지만, Kotlin은 `val`을 짧게 쓸 수 있어 기본값으로
삼기 쉽습니다.

## 클래스 선언은 생성자부터 읽습니다

Kotlin class는 주 생성자를 클래스 헤더에 둘 수 있습니다.

```kotlin
class Money(
    val amount: Long,
    val currency: String,
) {
    fun format(): String = "$amount $currency"
}
```

이 코드는 아래 Java 코드의 생성자, field, getter 일부를 한곳에 모은 느낌입니다.

```java
public final class Money {
    private final long amount;
    private final String currency;

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public String format() {
        return amount + " " + currency;
    }
}
```

처음에는 Kotlin class 헤더가 낯설지만, 읽는 순서는 단순합니다.

1. 클래스 이름을 봅니다.
2. 괄호 안의 값이 생성자 인자인지 property인지 봅니다.
3. 본문 안의 함수가 이 property를 어떻게 사용하는지 봅니다.

`val amount: Long`처럼 `val`이나 `var`가 붙으면 생성자 인자이면서 property입니다. 단순히 `amount: Long`
처럼 쓰면 생성자 안에서만 받는 인자이고 property로 남지 않습니다.

## `data class`는 값 전달 모델에 잘 맞습니다

Spring Boot에서 request/response DTO나 projection을 만들 때 Java record를 쓰는 팀이 많습니다.
Kotlin에서는 `data class`가 비슷한 역할을 자주 합니다.

```kotlin
data class UserResponse(
    val id: Long,
    val email: String,
    val name: String,
)
```

`data class`는 값 비교, 문자열 표현, `copy()` 같은 기능을 자동으로 제공합니다.

```kotlin
val original = UserResponse(1L, "a@example.com", "Kim")
val changed = original.copy(name = "Lee")
```

다만 모든 클래스를 `data class`로 만들 필요는 없습니다. 값 전달이 목적이면 잘 맞지만, 도메인 규칙과
상태 전이를 캡슐화해야 한다면 일반 class가 더 분명할 수 있습니다.

```kotlin
class Order(
    val id: Long,
    private var status: OrderStatus,
) {
    fun cancel() {
        check(status == OrderStatus.CREATED)
        status = OrderStatus.CANCELED
    }
}
```

이 코드는 값 묶음이라기보다 행위를 가진 도메인 객체입니다. 이런 객체까지 DTO처럼 `copy()`로 바꾸기
시작하면 상태 전이 규칙이 흩어질 수 있습니다.

## 최소 실행 예제

Kotlin command-line compiler를 설치했거나 IntelliJ IDEA에서 Kotlin/JVM 프로젝트를 만들었다면 아래 파일
하나로 시작할 수 있습니다.

```kotlin
// src/main/kotlin/learning/FirstStep.kt
package learning

fun main() {
    val request = CreateProductRequest(
        name = "Keyboard",
        price = 120_000,
    )

    val product = request.toProduct(id = 1L)
    println(product.label())
}

data class CreateProductRequest(
    val name: String,
    val price: Long,
)

class Product(
    val id: Long,
    private val name: String,
    private val price: Long,
) {
    fun label(): String = "[$id] $name - $price"
}

fun CreateProductRequest.toProduct(id: Long): Product {
    return Product(
        id = id,
        name = name.trim(),
        price = price,
    )
}
```

이 예제에서 볼 포인트는 세 가지입니다.

- `main()`은 클래스 밖 top-level 함수입니다.
- `CreateProductRequest`는 값 전달에 집중하는 `data class`입니다.
- `Product`는 행위를 가진 일반 class입니다.
- `toProduct()`는 특정 변환을 표현하는 top-level extension function입니다.

Spring Boot 프로젝트에 바로 넣는다면 controller, service, repository부터 만들고 싶을 수 있습니다. 하지만
Kotlin 첫 단계에서는 프레임워크를 잠시 빼고 언어의 선언 단위를 먼저 보는 편이 좋습니다.

## Java 개발자가 자주 하는 오해

| 오해 | 실제로는 |
|---|---|
| Kotlin은 Java boilerplate를 줄이는 문법이다 | JVM을 잘 쓰지만 선언 단위와 null, 값 흐름 감각이 다릅니다. |
| top-level 함수는 전역 함수라서 무조건 피해야 한다 | 상태 없는 작은 함수에는 자연스러운 선택입니다. |
| 모든 값 모델은 `data class`면 된다 | DTO에는 좋지만 도메인 행위가 있으면 일반 class가 낫습니다. |
| `val`이면 객체가 완전히 불변이다 | 참조 재대입이 막힐 뿐, 참조 대상의 내부 가변성은 별도 문제입니다. |
| Kotlin class는 생성자가 생략된 것이다 | 주 생성자가 클래스 헤더로 올라온 것입니다. |

특히 `val`은 조심해서 이해해야 합니다.

```kotlin
val names = mutableListOf("Kim")
names.add("Lee")
```

`names`에 다른 리스트를 다시 대입할 수는 없지만, `MutableList` 자체는 바뀔 수 있습니다. 불변 컬렉션과
읽기 전용 참조를 구분해야 합니다.

## 연습 문제

1. Java의 간단한 DTO class 하나를 Kotlin `data class`로 바꿔 봅니다.
2. `static` utility method 하나를 Kotlin top-level function으로 옮겨 봅니다.
3. `var`로 작성한 지역 변수 중 `val`로 바꿀 수 있는 값을 찾아 봅니다.
4. 값 전달 모델과 도메인 행위 모델을 각각 `data class`, 일반 class로 나눠 봅니다.
5. extension function을 하나 만들고, member function으로 두는 경우와 이름을 비교해 봅니다.

## 오늘의 결론

Kotlin 첫 단계에서는 Spring Boot 애플리케이션을 바로 옮기기보다 파일 하나에서 시작하는 편이 좋습니다.
`fun main()`을 클래스 밖에 두고, `val`을 기본으로 쓰고, 값 전달은 `data class`, 행위가 있는 모델은 일반
class로 나눠 봅니다.

이 감각이 잡히면 Kotlin 코드는 Java의 짧은 버전이 아니라 다른 선언 단위를 가진 JVM 언어로 보이기
시작합니다. 그다음에 Spring Controller, Service, Repository를 Kotlin으로 옮겨도 코드가 덜 어색해집니다.
