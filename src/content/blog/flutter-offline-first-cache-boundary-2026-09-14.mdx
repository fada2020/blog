> 기준으로 한다고 표시합니다. 예제 기준 패키지는 `shared_preferences` 2.5.5입니다. beta, dev, main channel은
> 안정판처럼 다루지 않았습니다.

## 결론부터 말하면

Flutter에서 offline-first를 붙일 때 핵심은 "일단 저장해 두자"가 아닙니다. **어떤 데이터가 앱의 진짜
read model인지, 어떤 데이터는 단순 preference인지, 네트워크 실패 때 화면이 무엇을 약속할 수 있는지**를 먼저
정하는 것입니다.

Spring Boot 개발자에게 익숙한 말로 바꾸면 Controller가 DB, Redis, 외부 API를 직접 뒤지지 않는 것과 같습니다.
Flutter에서도 widget이 `SharedPreferences`나 SQLite를 직접 읽기 시작하면 캐시가 여러 군데로 흩어집니다.
repository가 local data source와 remote API를 묶고, 화면은 "현재 표시할 상태"만 받아야 합니다.

지난 글에서 네트워크 실패와 재시도 경계를 나눴다면, 이번 글은 실패해도 사용자가 볼 수 있는 마지막 데이터를
어디에 둘지 정리합니다.

## 이번 주 개념

Flutter 공식 offline-first guide는 repository를 single source of truth로 둡니다. repository가 local data와
remote data를 결합하고, 연결 상태와 관계없이 화면에 하나의 접근점을 제공하는 구조입니다.

이번 글의 최소 경계는 네 가지입니다.

| 경계 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| remote data source | API 호출, status code 수신 | 화면 상태 결정 |
| local data source | 마지막 성공 데이터 저장, 조회 | 서버 충돌 해결 정책 결정 |
| repository | local fallback, refresh, sync flag 관리 | `BuildContext` 접근 |
| widget/view model | loading, cached, fresh, error 표시 | 저장소 종류 선택 |

작은 설정값은 key-value 저장소로 충분할 수 있습니다. 하지만 목록, 상세, 동기화 대기열처럼 관계와 갱신 시간이
중요한 데이터는 별도 local database나 명시적인 cache repository를 둬야 합니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 캐시를 붙여도 Controller가 캐시 구현을 알 필요는 없습니다.

```java
@Service
class ArticleReadService {

    private final ArticleClient remote;
    private final ArticleCache cache;

    ArticleView getArticle(String id) {
        return remote.fetch(id)
            .map(cache::saveAndReturn)
            .orElseGet(() -> cache.getOrThrow(id));
    }
}
```

현실 코드는 `Optional`보다 더 섬세하겠지만, 경계는 같습니다. remote 실패를 화면까지 그대로 흘리지 않고,
서비스가 마지막으로 믿을 수 있는 데이터를 찾습니다. Flutter에서도 이 책임은 widget이 아니라 repository에
있어야 합니다.

## Flutter에서는 무엇이 다른가

Flutter 앱은 사용자의 기기 안에서 계속 실행됩니다. 지하철, 엘리베이터, 회사 Wi-Fi 전환, background 복귀처럼
네트워크가 흔들리는 상황이 일상입니다. 서버의 한 요청이 실패했다고 화면 전체를 비워 버리면 모바일 경험이
거칠어집니다.

<Mermaid title="Flutter offline-first 읽기 경계">
{`flowchart TD
  Widget["Widget<br/>cached badge, retry"] --> ViewModel["ViewModel<br/>Async state"]
  ViewModel --> Repo["Repository<br/>single access point"]
  Repo --> Local["Local data source<br/>last known data"]
  Repo --> Remote["Remote API<br/>fresh data"]
  Remote --> Repo
  Repo --> Sync["Sync state<br/>fresh, cached, stale, failed"]
  Sync --> ViewModel
  Local --> Repo
`}
</Mermaid>

공식 guide는 offline-first 읽기 방식으로 두 가지를 설명합니다. 첫째, 네트워크 호출에 실패하면 local database의
데이터를 fallback으로 반환합니다. 둘째, `Stream`으로 local 데이터를 먼저 내보내고, remote 호출이 성공하면
새 데이터를 저장한 뒤 다시 내보냅니다.

두 방식 모두 중요한 전제는 같습니다. 화면은 저장소를 직접 고르지 않습니다. repository가 "지금 보여줄 수 있는
가장 좋은 데이터"와 그 상태를 함께 돌려줍니다.

## 대응 개념 비교

| Spring Boot 관점 | Flutter 관점 | 주의할 점 |
|---|---|---|
| Service layer | repository | 화면에서 저장소를 직접 선택하지 않습니다. |
| Redis/cache aside | local data source | 만료 시간과 갱신 시점을 정합니다. |
| DB read model | local database/cache model | API DTO와 UI model을 그대로 섞지 않습니다. |
| `@Cacheable` hit/miss | cached/fresh state | 오래된 데이터 표시 여부를 사용자에게 알려야 합니다. |
| scheduler sync | background/manual refresh | 앱 생명주기와 배터리 제약을 고려합니다. |

Spring 서버에서는 Redis가 잠시 오래된 값을 줄 수 있어도 서버 로그와 모니터링으로 추적합니다. 모바일 앱에서는
사용자가 직접 오래된 값을 봅니다. 그래서 cached data에는 `fetchedAt`, `isStale`, `syncFailed` 같은 상태가
필요합니다.

## 최소 실행 예제

먼저 화면이 볼 상태를 명시합니다.

```dart
sealed class CachedResult<T> {
  const CachedResult();
}

class Fresh<T> extends CachedResult<T> {
  const Fresh(this.value);

  final T value;
}

class Cached<T> extends CachedResult<T> {
  const Cached(this.value, this.fetchedAt);

  final T value;
  final DateTime fetchedAt;
}

class EmptyWithError<T> extends CachedResult<T> {
  const EmptyWithError(this.error);

  final Object error;
}
```

remote와 local 저장소도 interface로 나눕니다.

```dart
abstract interface class ArticleRemoteDataSource {
  Future<ArticleDto> fetchArticle(String id);
}

abstract interface class ArticleLocalDataSource {
  Future<CachedArticle?> findArticle(String id);
  Future<void> saveArticle(CachedArticle article);
}
```

repository는 먼저 remote를 시도하고, 실패하면 local fallback을 반환합니다.

```dart
class ArticleRepository {
  ArticleRepository({
    required ArticleRemoteDataSource remote,
    required ArticleLocalDataSource local,
    required Clock clock,
  })  : _remote = remote,
        _local = local,
        _clock = clock;

  final ArticleRemoteDataSource _remote;
  final ArticleLocalDataSource _local;
  final Clock _clock;

  Future<CachedResult<Article>> getArticle(String id) async {
    try {
      final dto = await _remote.fetchArticle(id);
      final article = Article.fromDto(dto);

      await _local.saveArticle(
        CachedArticle(
          id: article.id,
          title: article.title,
          body: article.body,
          fetchedAt: _clock.now(),
        ),
      );

      return Fresh(article);
    } catch (error) {
      final cached = await _local.findArticle(id);

      if (cached == null) {
        return EmptyWithError(error);
      }

      return Cached(cached.toArticle(), cached.fetchedAt);
    }
  }
}
```

이 구조의 장점은 테스트가 쉽다는 점입니다. remote가 실패하도록 fake를 만들고, local에 기존 데이터가 있을 때
`Cached`가 반환되는지만 확인하면 됩니다.

## Stream으로 갱신 흐름 보여주기

사용자 경험을 조금 더 좋게 만들려면 local 데이터를 먼저 보여주고, remote 성공 후 fresh data를 다시 내보낼 수
있습니다.

```dart
Stream<CachedResult<Article>> watchArticle(String id) async* {
  final cached = await _local.findArticle(id);

  if (cached != null) {
    yield Cached(cached.toArticle(), cached.fetchedAt);
  }

  try {
    final dto = await _remote.fetchArticle(id);
    final article = Article.fromDto(dto);

    await _local.saveArticle(
      CachedArticle(
        id: article.id,
        title: article.title,
        body: article.body,
        fetchedAt: _clock.now(),
      ),
    );

    yield Fresh(article);
  } catch (error) {
    if (cached == null) {
      yield EmptyWithError(error);
    }
  }
}
```

이 방식은 Spring에서 stale cache를 먼저 읽고 background refresh를 거는 느낌과 비슷합니다. 다만 Flutter에서는
두 번째 값이 들어올 때 화면이 자연스럽게 갱신되어야 하므로 loading spinner만 계속 보여 주는 방식보다 상태가
하나 더 필요합니다.

## SharedPreferences는 어디까지 쓰나

`shared_preferences` 2.5.5 문서는 단순 key-value 저장용 Flutter plugin이라고 설명합니다. 동시에 쓰기가 disk에
반드시 즉시 보존된다고 보장하지 않으므로 critical data 저장에는 쓰지 말라고 안내합니다.

그래서 아래처럼 나누는 편이 안전합니다.

| 데이터 | 저장 후보 | 이유 |
|---|---|---|
| theme mode, last selected tab | `SharedPreferencesAsync` | 작고 복구 가능하며 key-value에 맞습니다. |
| access token | secure storage 계층 | 민감정보이므로 일반 preference와 분리합니다. |
| article list, user profile | local database/cache data source | 조회, 만료, 동기화 상태가 필요합니다. |
| pending write queue | local database | 재시도, 순서, 중복 방지가 필요합니다. |

`SharedPreferences`의 기존 API는 local cache를 사용합니다. 문서는 새 코드에서 `SharedPreferencesAsync`나
`SharedPreferencesWithCache` 사용을 권장합니다. 여러 isolate, background engine, native code와 함께 값을
만지는 앱이라면 최신 값을 보장하기 쉬운 async API부터 검토하는 편이 낫습니다.

```dart
class PreferencesStore {
  PreferencesStore(this._prefs);

  final SharedPreferencesAsync _prefs;

  Future<void> saveLastArticleId(String id) {
    return _prefs.setString("lastArticleId", id);
  }

  Future<String?> getLastArticleId() {
    return _prefs.getString("lastArticleId");
  }
}
```

이 코드는 "마지막으로 열어 본 글" 같은 힌트에는 맞습니다. 하지만 글 본문 캐시 전체를 이곳에 넣기 시작하면
만료, schema 변경, 부분 갱신이 곧바로 어려워집니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 "offline-first는 모든 기능을 offline에서 완벽히 처리한다"는 생각입니다. 공식 guide도 앱마다
요구사항이 다르다고 설명합니다. 어떤 앱은 cached data를 보여 주기만 하면 되고, 어떤 앱은 쓰기 작업까지
대기열에 넣어야 합니다.

두 번째 오해는 캐시 hit가 항상 성공이라는 생각입니다. 모바일에서는 cached data가 오래됐을 수 있습니다.
화면에 작은 "마지막 업데이트" 상태를 보여 주거나, stale이면 일부 action을 막아야 할 수 있습니다.

세 번째 오해는 key-value 저장소를 mini database처럼 쓰는 것입니다. preference는 preference답게 작고 복구 가능한
값에만 쓰는 편이 좋습니다. 데이터의 관계, 정렬, 만료, 충돌 해결이 필요해지는 순간 repository 뒤의 local
database로 옮겨야 합니다.

## 다음 단계

offline-first 읽기 경계를 잡으면 앱은 네트워크 실패에도 덜 흔들립니다. 하지만 쓰기 작업은 더 조심스럽습니다.
사용자가 offline에서 수정한 값이 서버의 최신 값과 충돌할 수 있기 때문입니다. 다음 Flutter 글에서는 optimistic
state와 저장 대기열을 어떻게 나눌지 이어서 다루겠습니다.
