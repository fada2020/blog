## 결론부터 말하면

API 검증을 강화할 때 가장 먼저 지켜야 할 대상은 새 기능이 아니라 **이미 배포된 클라이언트의 성공
경로**였습니다. 신규 버전에서는 식별자, 소유권, 발생 시각을 엄격하게 검증해야 했지만, 버전 정보가
없는 기존 요청까지 같은 규칙으로 다시 검증하면서 정상 저장이 `422` 입력 오류로 막힐 수 있었습니다.

이번 회고의 핵심은 세 가지였습니다.

- 버전이 없는 기존 요청은 기존 계약 그대로 처리합니다.
- 신규 버전 요청만 강화된 식별자 검증을 통과해야 합니다.
- 선택적 부가 데이터 매핑 실패는 핵심 저장 성공을 막지 않도록 계약을 나눕니다.

Spring Boot 개발자에게 익숙한 표현으로 말하면, 컨트롤러의 `@Valid`를 강하게 만드는 것만으로는
충분하지 않습니다. 어떤 클라이언트 계약에 적용되는 검증인지, 실패해도 본 요청을 막지 말아야 하는
부가 처리인지, 어떤 회귀 테스트가 기존 앱 경로를 보호하는지까지 같이 정해야 합니다.

> 검증일: 2026-08-06. Spring 공식 사이트 기준 Spring Boot 안정 버전 `4.1.0`, Spring Framework
> 안정 버전 `7.0.8`을 확인했습니다. API 버전 분기 설명은 Spring MVC API Versioning 문서를,
> 트랜잭션 경계 설명은 Spring Framework의 rollback과 propagation 공식 문서를 기준으로 작성했습니다.

## 문제가 된 모양

요청 하나에 핵심 이벤트와 부가 장비 정보가 함께 들어오는 API가 있었습니다. 기존 앱에서는 핵심
이벤트 저장이 우선이었고, 부가 장비 정보는 매핑할 수 있을 때만 상태 이력으로 연결했습니다. 매핑에
실패해도 핵심 이벤트 저장까지 실패시키지는 않는 계약이었습니다.

신규 버전에서는 이 계약을 더 엄격하게 만들 필요가 있었습니다. 명시적으로 전달된 장비 식별자와
사용 회차가 실제 사용자, 발생 시각, 활성 상태와 맞는지 검증해야 했습니다. 문제는 그 엄격한 검증이
버전이 없는 기존 요청에도 적용된 점이었습니다.

| 구분 | 기존 요청에서 기대한 동작 | 신규 검증이 만든 위험 |
|---|---|---|
| 핵심 이벤트 | 먼저 저장되어야 함 | 부가 매핑 실패 때문에 저장 자체가 막힘 |
| 부가 장비 정보 | 연결 가능할 때만 상태 이력에 반영 | 중첩 식별자 재검증이 전체 요청을 실패시킴 |
| 버전 헤더 | 없어도 기존 계약으로 처리 | 누락을 신규 엄격 규칙으로 오해 |
| 오류 분류 | 명시 입력 오류만 4xx | 선택적 매핑 실패도 4xx로 노출 |

이 문제는 "검증이 나쁘다"가 아닙니다. 검증이 어느 계약에 속하는지 분리하지 않은 것이 문제였습니다.
새 버전의 안정성을 높이려면 기존 버전의 느슨한 호환성도 함께 테스트해야 합니다.

## 계약을 두 개로 나눕니다

기존 앱과 신규 앱이 같은 URL을 쓰더라도 같은 계약이라고 보면 안 됩니다. 버전 정보가 없는 요청은
이미 배포된 앱이 보내는 모양을 그대로 받아야 합니다. 반대로 신규 버전 요청은 더 강한 검증을 요구할
수 있습니다.

정리하면 아래처럼 나누는 편이 안전했습니다.

| 계약 | 입력 기준 | 실패 처리 |
|---|---|---|
| 레거시 요청 | 버전 헤더 없음 | 핵심 이벤트 저장 우선, 부가 매핑 실패는 저장 실패로 보지 않음 |
| 신규 버전 요청 | 명시적 버전 헤더 있음 | 식별자, 소유권, 발생 시각 불일치 시 명확한 422 |
| 공통 서버 오류 | DB 장애, 예상 못 한 상태, 코드 결함 | 5xx와 오류 추적으로 분류 |

여기서 중요한 점은 레거시 요청을 "검증하지 않는다"가 아니라 "기존에 약속한 만큼만 검증한다"입니다.
필수 필드, 형식, 권한 같은 기본 검증은 유지합니다. 다만 새 버전에서 추가한 엄격한 연결 검증을
소급 적용하지 않습니다.

## 선택적 부가 처리는 핵심 저장과 분리합니다

하나의 HTTP 요청 안에 여러 의미가 섞이면 실패 경계가 흐려집니다. 핵심 이벤트 저장은 업무적으로
반드시 성공해야 하는 부분이고, 부가 장비 정보 매핑은 상태 이력을 풍부하게 만드는 보조 처리일 수
있습니다. 둘의 실패 정책이 같지 않다면 코드에서도 분리해야 합니다.

```java
public EventResponse createEvent(CreateEventRequest request) {
    ApiVersion version = versionResolver.resolve(request.headers());

    if (version.isStrict()) {
        DeviceRef ref = strictDeviceResolver.resolve(
            request.ownerId(),
            request.recordedAt(),
            request.deviceRef()
        );

        return eventService.saveWithDeviceRef(request, ref);
    }

    Event event = eventService.saveCoreEvent(request);
    optionalDeviceMapper.tryAttach(event, request.deviceSnapshot());
    return EventResponse.from(event);
}
```

실제 코드는 이보다 더 많은 예외 타입과 트랜잭션 경계를 가집니다. 그래도 방향은 단순합니다. 신규
버전은 저장 전에 엄격한 resolver를 통과하고, 레거시는 핵심 이벤트 저장을 먼저 지킨 뒤 가능한 부가
정보만 붙입니다.

Spring 트랜잭션을 쓴다면 이 경계를 더 명확히 봐야 합니다. 같은 `@Transactional` 안에서 부가 처리
예외가 롤백 전용 상태를 만들면, 예외를 잡았더라도 전체 커밋이 실패할 수 있습니다. 그래서 부가 처리
실패를 허용하는 계약이라면 저장 전 검증으로 실패를 미리 걸러내거나, 핵심 저장과 부가 처리를 별도
트랜잭션 또는 후속 작업으로 분리하는 선택지가 필요합니다.

## 4xx와 5xx도 계약의 일부입니다

신규 버전에서 명시 식별자가 틀렸다면 `422`는 자연스럽습니다. 클라이언트가 고쳐야 하는 입력 오류이기
때문입니다. 하지만 레거시 요청의 부가 매핑 실패는 다르게 봐야 했습니다. 기존 계약에서는 핵심 이벤트
저장이 우선이었으므로, 이 실패를 전체 요청의 `422`로 올리면 서버가 과거 계약을 바꾼 셈이 됩니다.

| 실패 | 레거시 요청 | 신규 버전 요청 |
|---|---|---|
| 필수 핵심 필드 누락 | 4xx | 4xx |
| 명시 식별자 소유권 불일치 | 기존 계약에 없으면 소급 적용하지 않음 | 422 |
| 부가 정보 자동 매핑 실패 | 핵심 저장 유지, 부가 이력만 생략 | 정책에 따라 422 또는 생략 |
| 예상 못 한 DB 제약 위반 | 5xx | 5xx |

오류 코드는 운영 관측성에도 영향을 줍니다. 입력 오류를 5xx처럼 수집하면 실제 장애 신호가 흐려지고,
호환성 회귀를 단순 사용자 오류로만 보면 배포 문제를 놓칠 수 있습니다. 그래서 회귀 테스트에는 HTTP
상태뿐 아니라 오류 추적 대상 여부까지 포함하는 편이 좋았습니다.

## 버전 분기는 작게 시작해도 됩니다

Spring Framework 7의 Spring MVC에는 API versioning 지원이 들어왔고, Spring Boot 4는 MVC/WebFlux
버전 설정을 자동 구성할 수 있습니다. 최신 스택에서는 이 기능을 검토할 수 있습니다. 다만 이미
운영 중인 Spring Boot 3.x나 다른 프레임워크라면 처음부터 큰 구조를 들일 필요는 없습니다.

작게는 요청 헤더 하나와 명시적인 resolver로도 충분합니다.

```java
enum ApiVersion {
    LEGACY,
    V1
}

class ApiVersionResolver {
    ApiVersion resolve(String rawVersion) {
        if (rawVersion == null || rawVersion.isBlank()) {
            return ApiVersion.LEGACY;
        }

        if (rawVersion.equals("1")) {
            return ApiVersion.V1;
        }

        throw new UnsupportedApiVersionException();
    }
}
```

중요한 것은 구현 방식보다 기본값입니다. 헤더가 없을 때 어떤 버전으로 볼지, 지원하지 않는 버전은
어떤 오류를 줄지, 신규 버전에서만 켜지는 검증이 무엇인지 문서와 테스트에 남겨야 합니다.

## 회귀 테스트는 오래된 클라이언트 모양으로 씁니다

이런 문제는 최신 요청 fixture만 테스트하면 놓칩니다. 실패를 재현한 요청은 대부분 "지금 보기에는
이상하지만 과거 앱이 실제로 보내던 모양"입니다. 따라서 테스트 이름과 fixture가 그 사실을 드러내야
합니다.

| 테스트 | 기대값 |
|---|---|
| 버전 헤더 없는 기존 요청에 부가 정보가 함께 온다 | 핵심 이벤트는 저장된다 |
| 부가 정보의 자동 매핑이 실패한다 | 전체 요청은 실패하지 않는다 |
| 신규 버전 요청에 잘못된 명시 식별자가 온다 | 422로 거부된다 |
| 신규 버전 요청에 발생 시각과 식별자가 맞는다 | 이벤트와 상태 이력이 함께 저장된다 |
| 지원하지 않는 버전 값이 온다 | 명확한 4xx로 거부된다 |
| 레거시 경로에서 서버 오류가 발생한다 | 입력 오류로 숨기지 않고 5xx로 드러난다 |

JUnit 예시로 줄이면 아래 정도의 테스트가 핵심을 지킵니다.

```java
@Test
void legacyRequestKeepsCoreEventWhenOptionalDeviceMappingFails() {
    CreateEventRequest request = legacyRequestWithUnmatchedDeviceSnapshot();

    EventResponse response = controller.createEvent(request);

    assertThat(response.status()).isEqualTo("saved");
    assertThat(eventRepository.existsByClientId(request.clientId())).isTrue();
    assertThat(deviceHistoryRepository.existsByClientId(request.clientId())).isFalse();
}
```

테스트가 조금 투박해 보여도 괜찮습니다. 이 테스트가 지키는 계약은 분명합니다. "부가 정보 매핑 실패가
기존 앱의 핵심 저장을 막지 않는다"입니다.

## 작은 실습: 검증을 추가하기 전에 표부터 만듭니다

API 검증을 강화하기 전에는 코드보다 아래 표를 먼저 채워 보는 편이 낫습니다.

| 질문 | 답해야 하는 내용 |
|---|---|
| 이 검증은 어떤 API 버전부터 적용되는가 | 레거시, v1, v2 중 어디인지 |
| 헤더가 없으면 어떤 계약인가 | 기존 앱을 위한 기본값 |
| 실패하면 핵심 저장을 막아야 하는가 | 필수 검증인지 선택적 부가 처리인지 |
| 클라이언트가 고칠 수 있는가 | 4xx인지 5xx인지 |
| 운영 알림 대상인가 | 사용자 입력 오류인지 배포 회귀인지 |
| 어떤 오래된 fixture가 필요한가 | 실제 기존 앱 요청 모양 |

이 표를 채우지 않고 검증 코드부터 넣으면 테스트는 새 규칙만 보호합니다. 반대로 표를 먼저 채우면
새 규칙과 기존 계약을 동시에 지키는 테스트가 자연스럽게 나옵니다.

## 오늘의 결론

API 호환성은 오래된 코드를 오래 살려 두는 일이 아니라, 이미 배포된 클라이언트의 성공 경로를 새
검증이 침범하지 않게 경계를 긋는 일에 가까웠습니다. 검증을 강화할수록 버전 분기, 선택적 부가 처리,
오류 분류, 오래된 요청 fixture가 함께 필요합니다. 그래야 새 계약은 더 엄격해지고, 기존 계약은 조용히
계속 동작합니다.
