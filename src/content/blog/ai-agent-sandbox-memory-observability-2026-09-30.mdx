## 결론부터 말하면

이번 주 AI agent 비교의 중심은 "어느 모델이 더 똑똑한가"가 아닙니다. 공식 발표들이 동시에 가리키는 방향은
**agent를 오래 실행하려면 sandbox, memory, observability, model routing을 제품 기능처럼 다뤄야 한다**는 것입니다.

Spring Boot 팀이라면 agent를 IDE 자동완성의 연장으로만 보지 않는 편이 좋습니다. 이제 agent는 파일을 고치고, 도구를 부르고,
subagent를 나누고, PR을 만들고, 비용과 trace를 남깁니다. 모델 선택은 그 다음 문제입니다.

## 라우팅은 모델 이름보다 실행 경계를 먼저 봅니다

OpenAI의 Agents API 발표는 long-running agent에 context management, tool use, subagent coordination, file/code 실행 환경이
필요하다고 설명합니다. 특히 harness와 sandbox를 분리해 선택할 수 있게 한 점이 중요합니다. GitHub Copilot도 local
sandboxing을 public preview로 내놓으며 agent의 file, network, credential 접근을 제한하는 방향을 강조했습니다.

<Mermaid title="AI agent 라우팅 기준">
{`flowchart TD
  Request["작업 요청"] --> Risk{"위험도와 증적"}
  Risk -->|작은 수정| Local["로컬 CLI agent"]
  Risk -->|독립 issue| PR["GitHub PR agent"]
  Risk -->|장기 실행| Managed["관리형 Agents API"]
  Risk -->|조사/초안| Research["빠른 모델 라우터"]

  Local --> Guard["sandbox와 승인"]
  PR --> Audit["PR, review, checks"]
  Managed --> Trace["session, memory, artifacts"]
  Research --> Verify["사람 검증"]
  Guard --> Result["diff와 테스트"]
  Audit --> Result
  Trace --> Result
  Verify --> Result
`}
</Mermaid>

간단한 test failure 수정은 local CLI agent가 빠릅니다. 이슈 하나를 비동기로 맡겨 PR을 받는 작업은 GitHub agent 흐름이
어울립니다. 며칠짜리 data cleanup, 문서 생성, 여러 도구 호출이 필요한 workflow는 관리형 session과 artifact 저장소가 더
중요합니다.

## 샌드박스는 보안만이 아니라 실패 비용의 경계입니다

Gemini CLI v0.61.0은 indirect prompt injection을 막고 filesystem boundary와 runtime state isolation을 강화했다고 공지했습니다.
v0.60.0에서도 environment 변경 consent, sandbox directory isolation, untrusted tool output provenance가 강조됐습니다.
Claude Code v2.1.285는 WebFetch tool을 끄는 환경변수를 추가했습니다.

이 흐름은 agent가 강해질수록 "무엇을 못 하게 할 것인가"가 제품의 핵심 기능이 된다는 뜻입니다.

| 작업 | 기본 허용 | 사람 승인 |
|---|---|---|
| test 실행, diff 읽기 | 허용 | 불필요 |
| source file 수정 | 허용 | 큰 변경이면 필요 |
| dependency 추가 | 제한 | 필요 |
| 외부 network, WebFetch | 제한 | 필요 |
| secret, production DB, 배포 | 금지 또는 제안만 | 반드시 필요 |

Spring Boot 팀의 기준은 단순해야 합니다. agent가 production credential에 닿지 않아도 충분히 많은 일을 할 수 있습니다.
먼저 sandbox를 좁게 잡고, 반복되는 안전 작업만 넓힙니다.

## 메모리와 관측성은 agent 운영의 두 번째 축입니다

OpenAI Agents API는 긴 session에서 context compaction을 제공하고, subagent가 각자 context를 유지한 뒤 main agent가 결과를
모으는 구조를 제시합니다. GitHub Copilot app은 OTel 설정을 통해 agent session의 모델 요청과 tool 사용 흐름을 기존 monitoring
도구에서 추적할 수 있다고 공지했습니다.

이 두 가지는 같이 봐야 합니다.

| 운영 요소 | 없을 때 생기는 문제 | 최소 대안 |
|---|---|---|
| session memory | agent가 이미 확인한 사실을 반복 확인 | 작업별 요약 파일 |
| context compaction | 긴 작업에서 앞선 결정 유실 | checkpoint와 evidence log |
| OTel/trace | 왜 이상한 tool call을 했는지 모름 | session id, command log, diff |
| PR 증적 | 채팅 결과만 남아 review가 어려움 | patch와 check 결과 |

agent를 "빨리 답하는 채팅"으로 쓰면 memory와 trace가 과해 보입니다. 하지만 agent에게 파일 수정과 긴 조사를 맡기면 둘은
과한 기능이 아니라 사고 복구 장치가 됩니다.

## 모델 라우팅은 가격표가 아니라 작업 단위로 봅니다

xAI의 Grok 4.7 release notes는 `grok-4.7`을 coding, agentic task, knowledge work용 frontier model로 공개하고, 500k context와
reasoning effort, token 가격을 함께 제시했습니다. GitHub Copilot은 같은 주에 Claude Opus 5.5, GPT-6 Sol, GPT-6 Luna, Grok 4.7
제공을 공지했습니다. Codex changelog도 GPT-6.1 Sol과 Sol/Luna 라우팅 흐름을 보여 줍니다.

그러면 질문은 "최고 모델 하나"가 아니라 다음처럼 바뀝니다.

| 작업 | 먼저 쓸 모델/agent | 바꿀 신호 |
|---|---|---|
| 반복적인 작은 수정 | 빠른/저비용 coding model | test가 2회 이상 실패 |
| 복잡한 설계 판단 | 강한 reasoning model | diff가 커져 review가 어려움 |
| 문서 조사와 요약 | 긴 context model | 출처 추적이 약함 |
| PR 자동 수정 | GitHub/Codex/Claude 계열 agent | check 실패가 반복 |
| 민감 작업 | agent 제안만 사용 | secret 또는 production 접근 필요 |

모델 라우터를 만들 필요는 없습니다. 처음에는 사람이 checklist로 라우팅해도 됩니다. 다만 작업마다 "왜 이 agent를 썼는가"와
"언제 더 강한 모델로 올릴 것인가"를 기록하면 비용과 품질을 비교할 수 있습니다.

## 이번 주 후보와 제외 이유

- Meta Muse 계열은 agentic coding과 API 후보로 계속 추적할 가치가 있지만, 이번 주 7일 안의 공식 coding-agent 운영 변경이
  충분하지 않아 본문 비교에서 제외했습니다.
- Mistral은 Vibe의 Chat/Work 통합 GA 개선을 확인했지만, 이번 글의 핵심인 sandbox와 observability 비교 축에서는 GitHub,
  OpenAI, Gemini CLI보다 직접적인 운영 자료가 적어 짧게만 다뤘습니다.
- Anthropic Claude 모델/Claude Code 커뮤니티 반응은 화제성이 컸지만, 단일 후기와 비공식 benchmark 캡처는 근거로 쓰지
  않았습니다. 공식 GitHub release와 플랫폼 release note만 사용했습니다.
- Grok 4.7의 자체 benchmark 수치는 제품 주장으로만 취급했습니다. 도입 판단은 가격, context, API 제공 상태, 별도 검증
  가능성으로 제한했습니다.

## Spring Boot 팀의 최소 운영 규칙

1. agent 작업을 `local-fix`, `cloud-pr`, `managed-long-run`, `research` 네 가지로만 분류합니다.
2. 각 분류에 허용 filesystem, network, secret 접근을 표로 정합니다.
3. agent 결과는 반드시 diff, test output, 남은 리스크, 사용한 모델을 남깁니다.
4. 긴 작업은 30분 단위 checkpoint나 memory file을 남기게 합니다.
5. public beta와 public preview 기능은 실험 lane에 두고, production 기본 workflow로 바로 승격하지 않습니다.
