> stable channel은 Flutter 3.47 계열이며, 이 글의 `gen-l10n`, `flutter_localizations`, ARB 구성은 stable API만 사용합니다.
> 문서에 언급된 향후 `material_ui`/`cupertino_ui` 권장 전환은 아직 기본 생성 흐름이 아니므로 현재 코드의 전제로 쓰지 않습니다.

## 결론부터 말하면

국제화는 `"저장"`을 `"Save"`로 바꾸는 번역 파일 작업이 아닙니다. **사용자가 선택한 언어와 지역에 따라
문장, 복수형, 날짜, 통화, 읽기 방향을 어떤 경계에서 결정할지** 정하는 설계입니다.

Spring Boot의 `MessageSource`를 controller 밖의 표현 계층으로 두는 것처럼, Flutter에서는 ARB를 원문 계약으로 두고
`gen-l10n`이 만든 타입 안전한 API만 widget이 호출하게 만듭니다. 서버 API가 이미 만든 날짜 문자열을 다시 번역하거나,
화면마다 locale을 제각각 해석하면 테스트하기 어려운 표시 버그가 생깁니다.

## 이번 주 개념

| Flutter 요소 | 책임 | Spring/웹에서 비유하면 |
|---|---|---|
| `supportedLocales` | 제품이 지원하는 locale 경계 | 지원 언어 목록 |
| `localizationsDelegates` | Material·Cupertino·앱 메시지 공급 | `MessageSource` 등록 |
| ARB | 원문, 번역, placeholder 메타데이터 | 메시지 번들과 파라미터 계약 |
| `AppLocalizations` | 생성된 타입 안전 접근점 | 메시지 facade |
| `Intl` | 날짜·숫자·통화의 지역 형식화 | `Locale` 기반 formatter |
| `Directionality` | LTR/RTL 배치 방향 | CSS logical property/`dir` |

## 먼저 locale을 앱의 계약으로 선언하기

`MaterialApp`에 delegate와 지원 locale을 모아 둡니다. 이 목록은 번역 품질을 보장한다는 뜻이 아니라,
**앱이 실제로 테스트하고 배포하는 locale만 허용한다**는 뜻입니다.

```dart
import 'package:flutter_localizations/flutter_localizations.dart';
import 'l10n/app_localizations.dart';

MaterialApp(
  localizationsDelegates: const [
    AppLocalizations.delegate,
    GlobalMaterialLocalizations.delegate,
    GlobalWidgetsLocalizations.delegate,
    GlobalCupertinoLocalizations.delegate,
  ],
  supportedLocales: AppLocalizations.supportedLocales,
  home: const OrderSummaryPage(),
);
```

기기의 정확한 locale이 목록에 없으면 Flutter는 같은 `languageCode`를 찾고, 그것도 없으면 첫 지원 locale로
fallback합니다. 특정 국가 코드를 무시하거나 별도 정책이 필요하다면 `localeResolutionCallback`에 이유와 테스트를
남깁니다. 무조건 기기 locale을 반환하는 callback은 지원하지 않는 번역으로 화면을 여는 실수가 될 수 있습니다.

## ARB를 화면 문구의 단일 원본으로 만들기

`pubspec.yaml`에는 생성 사용을 명시하고, 생성 결과를 앱 소스에서 import할 경로를 `l10n.yaml`으로 고정합니다.
`package:flutter_gen` 가상 패키지를 새 코드의 import 경로로 삼지 않는 것이 안전합니다. Flutter는 해당 synthetic
package에서 생성 소스 import로 옮기는 migration을 stable 3.32부터 안내하고 있습니다.

```yaml
# pubspec.yaml
flutter:
  generate: true
```

```yaml
# l10n.yaml
arb-dir: lib/l10n
output-dir: lib/l10n/generated
output-localization-file: app_localizations.dart
synthetic-package: false
```

```json
// lib/l10n/app_ko.arb
{
  "orderCount": "주문 {count}건",
  "@orderCount": {
    "placeholders": {
      "count": { "type": "int" }
    }
  }
}
```

widget은 raw key를 직접 조합하지 않고 생성 API를 사용합니다. placeholder 이름이 바뀌면 컴파일 단계에서
드러나므로, controller가 문자열 key를 손으로 입력하는 방식보다 회귀 범위가 작습니다.

```dart
Text(AppLocalizations.of(context)!.orderCount(orderCount));
```

## 서버 값과 표시 값을 섞지 않기

API는 의미가 보존된 값을 돌려주는 편이 좋습니다. 예를 들어 시각은 ISO-8601 instant, 금액은 통화 코드와 minor unit,
상태는 stable code로 전송합니다. Flutter가 사용자 locale로 표현합니다.

```dart
String visibleTotal(BuildContext context, int cents) {
  final locale = Localizations.localeOf(context).toString();
  return NumberFormat.currency(locale: locale, symbol: '₩')
      .format(cents / 100);
}
```

여기서 `₩`를 모든 통화의 기본으로 고정하는 것은 예시일 뿐 제품 정책은 아닙니다. 실제 서비스는 금액의 통화 코드와
소수 자릿수를 서버 계약에서 받거나, 통화별 formatter 규칙을 한 곳에 둡니다. locale은 **표현 방식**이고 통화는
**금전적 의미**라는 점을 분리해야 합니다.

## RTL은 문자열 문제가 아니라 레이아웃 문제

아랍어·히브리어처럼 RTL을 지원한다면 `left`, `right` 대신 `start`, `end` 계열을 먼저 선택합니다. `EdgeInsetsDirectional`,
`AlignmentDirectional`, `BorderRadiusDirectional`은 `Directionality`에 따라 올바르게 뒤집힙니다. 아이콘도 의미에 따라
결정합니다. 다음 단계라는 의미의 화살표는 방향에 맞춰야 하지만, 재생 버튼처럼 물리적 의미가 고정된 아이콘까지 뒤집지는
않습니다.

## Java 개발자가 자주 하는 오해

1. **번역 파일만 추가하면 i18n이 끝난다.** 날짜·숫자·복수형·RTL·접근성 label을 함께 검토해야 합니다.
2. **locale은 사용자 프로필 필드 하나다.** OS 설정, 앱 설정, 지원 목록, fallback 우선순위가 함께 작동합니다.
3. **서버가 한국어 문장을 주면 클라이언트가 편하다.** 같은 API를 여러 locale에서 재사용할 수 없고 표현 변경이 배포 계약이 됩니다.
4. **영어 화면이 정상이라 RTL도 정상이다.** 논리 방향 padding과 정렬을 쓰지 않으면 UI가 조용히 깨집니다.
