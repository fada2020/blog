> **검증 범위**
>
> 2026년 9월 10일에 Sentry Uptime Monitoring 문서, Spring Framework Filters 문서와 OpenAPI Specification
> 최신 발행본을 확인했습니다. Spring Framework 문서 기준 안정 버전은 `7.0.9`, OpenAPI Specification은
> `3.2.0`입니다. 실제 업무일지의 서비스명, 내부 화면명, 사용자 식별자, 저장소명, 운영 경로와 비공개 URL은
> 공개 글에서 제거하고 API 트래픽 모니터링 설계 원리만 일반화했습니다.

## 결론부터 말하면

API 트래픽 모니터링에서 모든 요청을 같은 로그로 보면 운영자가 봐야 할 신호가 금방 묻힙니다. 정상적인 uptime
확인 요청, 실제 사용자가 만든 조회 요청, 쓰기 요청, 오류 응답, 감사 로그와 연결되는 업무 이벤트는 서로 다른
질문에 답합니다.

이번 회고의 핵심은 두 가지였습니다.

- 외부 uptime 확인 요청은 장애 감지에는 필요하지만 사용자 API 이력 화면에서는 노이즈가 될 수 있습니다.
- `상세 payload가 저장됐는가`와 `업무 감사 로그와 연결됐는가`는 같은 값이 아닙니다.

처음에는 "상세 버튼이 왜 비활성화되지?"라는 화면 문제처럼 보였습니다. 실제로는 수집 제외 기준, 상세 저장 정책,
감사 로그 연결 조건, API 문서 설명이 서로 다르게 움직인 문제였습니다.

## 문제가 된 모양

운영 콘솔의 트래픽 목록에 사용자가 없는 정상 `GET /` 요청이 반복해서 보였습니다. path와 method만 보면 장애나
공격처럼 보일 수 있지만, User-Agent와 주기를 확인하니 uptime 모니터링 서비스가 가용성을 확인하는 요청이었습니다.

문제는 이 요청이 사용자 API 목록을 어지럽힌다는 점이었습니다. uptime probe는 서비스가 살아 있는지 확인하는 데는
필요합니다. 하지만 사용자별 API 이력이나 업무 처리 흐름을 보는 화면에 그대로 섞이면 운영자는 매번 같은 정상
요청을 제외하고 봐야 합니다.

두 번째 문제도 같이 보였습니다. 어떤 backend는 수집한 요청 전체의 HTTP 상세를 저장했고, 다른 backend는 쓰기 요청과
오류 응답에만 상세를 저장했습니다. 그래서 같은 운영 콘솔에서 어떤 소스는 정상 `GET`에도 상세 버튼이 보이고, 다른
소스는 보이지 않는 차이가 생겼습니다.

## 기존 설계의 한계

처음의 정책은 단순했습니다.

```text
요청 수집
-> 목록 row 저장
-> 필요하면 상세 저장
-> 감사 로그와 trace id 연결
-> 운영 콘솔 표시
```

그런데 "필요하면"이라는 말이 backend마다 다르게 해석됐습니다. 한쪽은 모든 수집 요청의 상세를 남겼고, 다른 쪽은
쓰기와 오류만 남겼습니다. 또한 uptime probe를 일반 사용자 요청과 같은 목록에 넣으면서, 운영 화면이 "가용성 확인"
목록인지 "사용자 API 이력" 목록인지 흐려졌습니다.

| 섞인 개념 | 실제로 나눠야 할 질문 |
|---|---|
| 요청이 수집됐는가 | 운영 콘솔 목록에 보여야 하는가 |
| HTTP 상세가 있는가 | body, header, query를 저장했는가 |
| 감사 로그와 연결됐는가 | 같은 trace로 업무 이벤트가 남았는가 |
| 정상 `GET`인가 | 상세가 없어도 되는 요청인가 |
| uptime 확인인가 | 사용자 흐름에서 제외할 요청인가 |

상세 버튼은 이 중 하나의 결과일 뿐입니다. 버튼 상태만 고치면 다음 backend나 다음 소스에서 같은 혼란이 반복됩니다.

## 선택한 설계

선택한 기준은 수집 단계에서 uptime probe를 분리하고, 수집된 요청은 상세 저장 여부와 감사 로그 연결 여부를 독립
필드로 설명하는 방식입니다.

<Mermaid title="API 트래픽 모니터링 수집 기준">
{`flowchart TD
  Request["HTTP request"] --> Filter["수집 filter"]
  Filter --> ProbeCheck["uptime probe 판정"]
  ProbeCheck -->|가용성 확인 요청| Uptime["uptime metric<br/>사용자 이력 제외"]
  ProbeCheck -->|업무 요청| Row["traffic log row"]
  Row --> DetailPolicy["HTTP 상세 저장 정책"]
  DetailPolicy --> DetailStore["detail storage"]
  Row --> AuditLink["trace 기반 감사 로그 연결"]
  DetailStore --> Console["운영 콘솔"]
  AuditLink --> Console
`}
</Mermaid>

Spring Framework 문서는 Servlet filter가 나머지 filter chain과 target servlet 앞뒤에 interception-style logic을
적용할 수 있다고 설명합니다. 이런 수집 filter는 요청을 가장 먼저 볼 수 있으므로, "이 요청을 사용자 트래픽으로
볼 것인가"를 정하기에 적절합니다.

다만 filter가 모든 운영 의미를 알아야 하는 것은 아닙니다. filter는 요청의 User-Agent, method, path, status처럼
수집에 필요한 최소 기준만 판단합니다. 업무 이벤트와 감사 로그 연결은 service나 별도 writer가 trace id 기준으로
처리합니다.

## 구현에서 조심한 점

Uptime probe 제외는 IP 대역보다 User-Agent 접두사를 기준으로 잡았습니다. 모니터링 서비스의 실행 IP는 바뀔 수 있고,
cloud 환경에서는 proxy나 NAT를 거치면서 주소 기준이 더 불안정해질 수 있습니다. 반대로 공식 문서와 실제 요청에서
확인한 User-Agent는 이 요청의 목적을 더 직접적으로 설명합니다.

물론 User-Agent는 위조할 수 있습니다. 그래서 이 기준을 보안 허용 목록으로 쓰면 안 됩니다. 여기서는 접근 허용이
아니라 **운영 콘솔의 사용자 이력 노이즈 제거**가 목적입니다. 같은 요청이 실제 API 권한을 우회하게 만들지 않습니다.

```kotlin
private fun isUptimeProbe(userAgent: String?): Boolean =
    userAgent?.startsWith("SentryUptimeBot/") == true

fun shouldCollect(request: HttpRequest): Boolean {
    if (isUptimeProbe(request.userAgent)) return false
    return request.path.startsWith("/api/")
}
```

이 예제는 공개용으로 단순화한 코드입니다. 실제 서비스에서는 proxy header 신뢰 경계, path allowlist, 민감 header
마스킹, body size 제한, storage 실패 처리까지 함께 봐야 합니다.

## 상세 저장과 감사 로그 연결을 분리합니다

운영 콘솔에서는 `hasDetail`과 `auditLogId`가 비슷하게 보일 수 있습니다. 둘 다 "더 볼 수 있는 정보"처럼 보이기
때문입니다. 하지만 두 값은 다른 질문에 답합니다.

| 필드 | 의미 | 버튼 동작 |
|---|---|---|
| `hasDetail` | HTTP request/response 상세가 별도 저장소에 있음 | HTTP 상세 버튼 활성화 |
| `auditLogId` | 같은 trace의 업무 감사 로그가 있음 | 감사 로그 이동 버튼 활성화 |
| `traceId` | 여러 관측성 기록을 묶는 상관관계 키 | 검색과 연결 기준 |

정상 `GET` 요청이어도 장애 분석에 필요하면 상세를 저장할 수 있습니다. 반대로 업무 감사 로그가 있어도 HTTP body를
저장하지 않는 정책일 수 있습니다. 예를 들어 민감한 payload를 다루는 요청은 감사 이벤트만 남기고 HTTP 상세는 저장하지
않는 편이 더 안전할 때가 있습니다.

이번에 택한 공개 원칙은 다음과 같습니다.

- 수집 대상으로 판정한 요청은 목록 row를 남깁니다.
- 상세 저장에 성공한 뒤에만 `hasDetail=true`로 표시합니다.
- 감사 로그 연결은 상세 저장 성공 여부와 독립적으로 trace id로 찾습니다.
- 과거에 상세를 저장하지 않은 row는 UI에서 상세가 없다고 보여 주고, 소급 생성했다고 꾸미지 않습니다.

## 문서가 UI 계약을 따라가야 합니다

이 문제는 코드만 고쳐서는 끝나지 않습니다. 운영자가 보는 API 문서와 화면 설명도 같은 언어를 써야 합니다.
OpenAPI Specification은 HTTP API를 사람이든 컴퓨터든 source code나 네트워크 트래픽을 직접 보지 않고 이해할 수
있게 해 주는 표준 인터페이스 설명입니다. 따라서 응답 필드 설명이 실제 UI 계약과 맞지 않으면 문서의 가치가
줄어듭니다.

운영 API 문서에는 아래 내용을 명시해야 했습니다.

- 목록 API의 `hasDetail`은 HTTP 상세 저장 여부입니다.
- `auditLogId`는 감사 로그 연결 여부이며 `hasDetail`과 독립입니다.
- 상세 API는 `hasDetail=true`인 row에서만 성공할 수 있습니다.
- 상세 저장소에 key가 없으면 404 계열로, 저장소 조회 자체가 실패하면 502 계열로 구분합니다.
- Uptime probe는 사용자 API 이력에서 제외될 수 있습니다.

이 설명이 없으면 화면에서 버튼이 비활성화됐을 때 운영자는 "권한 문제인가, 저장 실패인가, 정상 정책인가"를 다시
코드로 확인해야 합니다.

## 검증은 재현 경로부터 시작합니다

이번 유형의 버그는 snapshot 테스트보다 재현 경로가 중요했습니다. 목록 row가 생기는지, 상세 key가 생기는지, 버튼이
활성화되는지, 감사 로그 링크가 따로 살아 있는지를 나누어 확인해야 합니다.

```text
uptime probe 요청
-> 사용자 API 이력에 표시되지 않음

정상 GET 요청
-> 목록 row 생성
-> 상세 저장 성공 시 hasDetail true

쓰기 요청
-> 목록 row 생성
-> 상세 저장
-> 같은 trace의 감사 로그가 있으면 auditLogId 연결

저장소 오류
-> 목록 row와 상세 저장 상태를 거짓으로 꾸미지 않음
```

테스트도 이 순서를 따라가는 편이 좋습니다.

- Uptime User-Agent 요청은 수집 대상에서 제외되는지 확인합니다.
- 필터를 통과한 정상 `GET`도 상세 writer를 호출하는지 확인합니다.
- 상세 upload가 성공한 경우에만 key와 `hasDetail`이 채워지는지 확인합니다.
- `auditLogId`가 없어도 `hasDetail=true`일 수 있고, 반대도 가능하다는 응답 mapping을 확인합니다.
- Swagger/OpenAPI 설명에 버튼 비활성화 조건과 오류 응답을 남깁니다.

## 배운 점

관측성 기능은 데이터를 많이 저장하는 것보다 **무엇을 같은 축에서 비교할지**가 더 중요했습니다. Uptime monitoring은
서비스 신뢰성을 지키는 도구지만, 사용자 API 이력 화면에서는 반복 노이즈가 될 수 있습니다. 정상 `GET` 상세는 때로
장애 분석의 핵심 증거가 되지만, 감사 로그와 같은 의미는 아닙니다.

Spring Boot 관점에서는 익숙한 filter 문제입니다. filter는 request를 일찍 보고 수집 여부를 판단합니다. service는
업무 의미를 남깁니다. storage adapter는 상세 저장 성공 여부만 책임집니다. 운영 콘솔은 이 세 상태를 하나의 버튼
상태로 뭉개지 않고 각각 보여 줘야 합니다.

## 실무 체크리스트

- [ ] Uptime probe, load balancer health check, synthetic monitoring 요청을 사용자 API 이력에서 어떻게 다룰지 정했습니다.
- [ ] User-Agent 기준은 보안 허용이 아니라 노이즈 분류에만 사용합니다.
- [ ] 수집 row 생성, HTTP 상세 저장, 감사 로그 연결을 다른 상태로 저장합니다.
- [ ] 상세 저장에 실패했는데 `hasDetail=true`로 표시하지 않습니다.
- [ ] 과거 row의 상세가 없으면 소급 복구 가능 여부를 따로 판단하고 UI에서는 없다고 표시합니다.
- [ ] OpenAPI 설명에 `hasDetail`, `auditLogId`, 상세 API 404/502 조건을 분리해 적었습니다.
- [ ] 운영 콘솔에서 버튼 비활성화 이유를 문서와 같은 용어로 설명합니다.
