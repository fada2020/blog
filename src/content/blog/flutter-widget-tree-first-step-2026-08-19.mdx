## 결론부터 말하면

Flutter를 처음 볼 때 가장 먼저 잡아야 할 개념은 **화면이 Widget 객체의 트리로 선언되고,
Flutter engine이 그 트리를 실제 화면으로 그린다**는 점입니다.

Spring Boot 개발자는 보통 HTTP 요청이 Controller로 들어오고, Service와 Repository를 거쳐 응답
DTO가 만들어지는 흐름에 익숙합니다. Flutter에는 Controller가 화면을 반환하는 구조가 없습니다.
대신 `main()`에서 앱을 시작하고, `runApp()`에 넘긴 root widget 아래로 작은 widget들이 중첩되며
화면 구조가 만들어집니다.

이번 글에서는 Flutter 학습을 시작하기 위해 다음 세 가지를 구분합니다.

- Dart 코드는 어디서 시작하는가
- Widget은 Spring의 어떤 개념과도 완전히 같지 않은 이유
- `build()`는 언제 호출되고 무엇을 반환해야 하는가

## 이번 주 개념

Flutter 앱은 Dart의 `main()` 함수에서 시작합니다. 가장 작은 예제는 다음처럼 생겼습니다.

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const App());
}

class App extends StatelessWidget {
  const App({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      home: Scaffold(
        body: Center(
          child: Text('Hello Flutter'),
        ),
      ),
    );
  }
}
```

이 코드는 짧지만 Flutter의 핵심 규칙이 거의 들어 있습니다.

| 코드 | 역할 |
|---|---|
| `main()` | Dart 프로그램의 진입점입니다. |
| `runApp()` | Flutter에 root widget을 넘겨 앱 렌더링을 시작합니다. |
| `StatelessWidget` | 내부 mutable state 없이 입력값과 상위 context로 UI를 선언합니다. |
| `build()` | 현재 상태에서 어떤 widget tree가 필요한지 반환합니다. |
| `MaterialApp`, `Scaffold`, `Center`, `Text` | 작은 widget을 조합해 화면을 만듭니다. |

## Java/Spring에서는 어떻게 다뤘는가

Spring MVC에서는 요청 하나를 처리하는 흐름이 비교적 명확합니다.

```text
GET /users
-> UserController
-> UserService
-> UserRepository
-> users.html 또는 JSON 응답
```

Controller 메서드는 요청을 받고, 필요한 데이터를 모은 뒤, View 이름이나 Response DTO를 반환합니다.
상태 변경은 Service의 transaction 안에서 일어나고, 화면은 서버가 만든 HTML이거나 별도 프론트엔드가
API 응답을 받아 그립니다.

Flutter는 이 흐름과 다릅니다. 모바일 앱은 이미 기기 안에서 실행 중이고, 화면 갱신은 HTTP 요청을
새로 받는 방식이 아니라 앱 내부 상태가 바뀌면서 발생합니다.

```text
사용자 입력
-> state 변경
-> build() 재호출
-> 새 widget tree 계산
-> 필요한 부분만 화면 갱신
```

그래서 Flutter의 `build()`를 Spring Controller처럼 보면 헷갈립니다. `build()`는 네트워크 요청의
진입점이 아니라, 현재 상태를 UI 선언으로 바꾸는 함수에 가깝습니다.

## Flutter에서는 무엇이 다른가

Flutter의 Widget은 "화면에 보이는 컴포넌트"이면서 동시에 "화면을 어떻게 구성할지 설명하는
불변 설정 객체"에 가깝습니다. 실제 렌더링과 생명주기는 Flutter framework가 Widget 아래의 Element,
RenderObject 계층과 함께 관리합니다.

처음에는 내부 구현을 모두 외울 필요는 없습니다. 대신 아래 흐름만 구분하면 됩니다.

<Mermaid title="Flutter Widget tree와 렌더링 흐름">
{`flowchart TD
  Main["main()"] --> RunApp["runApp(root widget)"]
  RunApp --> WidgetTree["Widget tree 선언"]
  WidgetTree --> ElementTree["Element tree가 위치와 생명주기 관리"]
  ElementTree --> RenderTree["RenderObject tree가 layout과 paint 수행"]
  RenderTree --> Screen["기기 화면"]

  State["상태 변경"] --> Build["build() 재호출"]
  Build --> WidgetTree`}
</Mermaid>

Spring Boot 개발자 관점에서 가까운 비교를 해 보면 다음과 같습니다.

| Spring Boot에서 익숙한 것 | Flutter에서 가까운 개념 | 주의할 점 |
|---|---|---|
| `main()`의 `SpringApplication.run()` | Dart `main()`과 `runApp()` | 앱 부트스트랩이라는 점만 비슷합니다. |
| Controller가 응답 모델 구성 | `build()`가 widget tree 구성 | `build()`는 요청 핸들러가 아닙니다. |
| DTO | Widget 생성자 인자 | Widget은 화면 설정 객체이며 mutable DTO처럼 다루지 않습니다. |
| Service state | 앱 상태 객체 | 상태는 widget 밖 모델이나 `State` 객체에 둡니다. |
| Template fragment | 작은 widget 조합 | widget은 layout, style, gesture까지 모두 표현할 수 있습니다. |

## StatelessWidget부터 시작하는 이유

Flutter에는 `StatelessWidget`과 `StatefulWidget`이 자주 등장합니다. 이름 때문에
`StatelessWidget`은 단순하고 `StatefulWidget`은 고급이라고 생각하기 쉽지만, 더 중요한 기준은
**이 widget이 자체적으로 변하는 값을 소유해야 하는가**입니다.

아래 예제는 외부에서 받은 이름을 화면에 보여 주기만 합니다.

```dart
class GreetingCard extends StatelessWidget {
  const GreetingCard({
    required this.name,
    super.key,
  });

  final String name;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: Text('안녕하세요, $name님'),
      ),
    );
  }
}
```

이 widget은 `name`이 바뀌면 새 `GreetingCard` 인스턴스를 받아 다시 그려지면 됩니다. 내부에서 값을
수정하지 않습니다. Java record나 불변 DTO처럼 입력값을 받아 표현만 한다고 보면 이해가 쉽습니다.

반대로 버튼을 누를 때마다 숫자가 올라가는 화면은 자체 상태가 필요합니다.

```dart
class CounterPanel extends StatefulWidget {
  const CounterPanel({super.key});

  @override
  State<CounterPanel> createState() => _CounterPanelState();
}

class _CounterPanelState extends State<CounterPanel> {
  int count = 0;

  void increment() {
    setState(() {
      count += 1;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        Text('count: $count'),
        ElevatedButton(
          onPressed: increment,
          child: const Text('증가'),
        ),
      ],
    );
  }
}
```

`setState()`는 "값이 바뀌었으니 이 State 객체가 관리하는 UI를 다시 계산하라"는 신호입니다. Spring의
transaction commit과는 다릅니다. 데이터 저장을 보장하는 API가 아니라 UI 갱신 예약에 가깝습니다.

## 최소 실행 예제

Flutter SDK를 설치한 뒤 아래 명령으로 새 앱을 만들 수 있습니다.

```bash
flutter create flutter_first_step
cd flutter_first_step
flutter run
```

처음에는 `lib/main.dart`만 열어도 됩니다. 아래처럼 기본 카운터 예제를 더 작은 구조로 바꿔 보세요.

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const LearningApp());
}

class LearningApp extends StatelessWidget {
  const LearningApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      home: LearningHome(),
    );
  }
}

class LearningHome extends StatelessWidget {
  const LearningHome({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Flutter first step')),
      body: const Center(
        child: GreetingCard(name: 'Spring 개발자'),
      ),
    );
  }
}

class GreetingCard extends StatelessWidget {
  const GreetingCard({
    required this.name,
    super.key,
  });

  final String name;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: Text('안녕하세요, $name님'),
      ),
    );
  }
}
```

이 예제의 목표는 기능이 아니라 분리입니다. `LearningApp`은 앱 뼈대를 잡고, `LearningHome`은 한 화면을
담고, `GreetingCard`는 재사용 가능한 작은 UI 조각을 맡습니다. Spring Boot에서 Controller, Service,
Repository를 무조건 한 파일에 넣지 않는 것처럼, Flutter에서도 build 메서드 하나에 모든 widget을
계속 중첩하지 않는 습관이 중요합니다.

## Java 개발자가 자주 하는 오해

### build 메서드에 오래 걸리는 작업을 넣는다

`build()`는 자주 호출될 수 있습니다. HTTP 호출, 파일 읽기, 무거운 계산을 `build()` 안에 직접 넣으면
화면 갱신 때마다 같은 작업이 반복될 수 있습니다. Spring Controller에서 매 요청마다 실행돼도 되는
작업과 앱 화면이 다시 그려질 때마다 실행되면 안 되는 작업을 구분해야 합니다.

### Widget을 mutable 객체처럼 수정한다

Flutter Widget은 현재 UI 구성을 설명하는 객체로 보는 편이 안전합니다. 값을 바꾸고 싶다면 기존
Widget 인스턴스를 수정하기보다 상태를 바꾸고 새 widget tree를 계산하게 해야 합니다.

### StatefulWidget이 상태를 직접 가진다고 생각한다

상태는 `StatefulWidget` 자체가 아니라 `State<T>` 객체가 가집니다. `StatefulWidget`은 configuration,
`State`는 mutable state를 맡는다고 나누면 생명주기 혼란이 줄어듭니다.
