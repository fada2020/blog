> **범위** — 2026년 11월 5일 공식 Events API·서명 문서를 확인했습니다. 일반 알림 수신기의 작업 경험을 익명화했습니다. 실제로 확인한 합성 이벤트 결과와 아래의 권장 설계·독립 실습을 구분합니다. 조직·계정·내부 주소·업무 데이터는 포함하지 않습니다.

## 문제: 한 번의 발신으로 답글 하나를 보장할 수 있을까

요약 메시지 밑에 상세 답글을 자동으로 붙이는 작업이 있었습니다. 초기에는 카드 한 장의 발송을 확인했지만, 그것만으로 이벤트 수신부터 답글 연결까지 완성됐다고 볼 수 없었습니다. 수신 경로와 권한을 연결하고 합성 이벤트를 흘려 보낸 뒤에야 요약 하나에 답글 하나가 붙는 것을 확인했습니다.

여기서 핵심은 “성공”을 쪼개는 것이었습니다. 서명이 맞는 요청을 받았다는 사실, 발신 API가 성공했다는 사실, 수신 화면에 올바른 스레드가 보였다는 사실은 각각 다른 증거입니다. 한 환경의 성공으로 다른 환경도 완료됐다고 쓰면 남은 작업이 사라집니다.

## 기존 설계의 한계

이벤트를 요청 스레드에서 처리하고 외부 API 응답까지 기다리면 ACK가 늦어질 수 있습니다. Slack Events API는 빠른 2xx 응답을 요구하며 실패 시 재전송합니다. 재시도 헤더는 진단 단서이고, 이벤트 자체의 식별자를 대신하지 않습니다. 동일 이벤트를 다시 받더라도 이미 처리한 작업인지 판단할 저장 경계가 필요합니다.

작업 기록에는 중복 이벤트 처리와 합성 스레드 검증이 있었습니다. 다만 영속 inbox·outbox나 장애 지점 전체를 검증했다는 근거까지는 없었습니다. 아래는 그 경험을 바탕으로 정리한 권장 구조이며 실제 시스템에 모두 구현됐다는 설명은 아닙니다.

## 선택한 설계 원칙

Spring MVC controller에는 인증·입력 검증·수신 기록까지만 두고, 외부 답글 생성은 worker로 분리하는 구조를 권장합니다. 서명은 JSON을 파싱·재직렬화한 문자열이 아니라 원본 요청 바이트와 시각 헤더를 기준으로 검증합니다. 오래된 요청의 재사용을 막는 시각 검사와 상수 시간 비교도 함께 고려합니다.

<Mermaid title="인증된 이벤트 수신과 후속 처리의 경계">
{`flowchart TD
  Request["원본 요청"] --> Verify["서명과 시각 검증"]
  Verify --> Inbox["이벤트 키로 inbox 저장"]
  Inbox --> Ack["저장 성공 후 빠른 ACK"]
  Inbox --> Worker["worker 작업 가져오기"]
  Worker --> Reply["상세 답글 발신"]
  Reply --> Receipt["대상 스레드 실수신 확인"]
`}
</Mermaid>

동일 이벤트를 두 번 받는 가상 예시는 다음과 같습니다. 외부 이벤트 형식 전체가 아니라 중복 판단에 필요한 부분만 줄였습니다.

```json
{"event_id":"demo-event-001","type":"event_callback"}
```

| 상황 | 권장 내부 처리 | 응답·저장 예시 |
| --- | --- | --- |
| 최초 유효 이벤트 | inbox와 후속 작업을 원자적으로 기록 | `200`, `pending` 1건 |
| 같은 이벤트 재수신 | 기존 기록을 확인하고 추가 생성 생략 | `200`, 여전히 1건 |
| 서명 불일치 | 후속 처리 진입 차단 | `401`, 저장 0건 |
| 수신 기록 저장 실패 | 성공 ACK를 보내지 않음 | `5xx`, 재시도 대상으로 남김 |

이 상태 코드 표는 독립 예시의 설계 계약입니다. 외부 서비스의 모든 오류 응답을 규정하거나 기존 업무 API 계약을 변경한 결과가 아닙니다. `url_verification` challenge 요청은 일반 이벤트와 별도 경로로 처리합니다.

## 구현에서 놓치기 쉬운 원자성

단순히 메모리 Set에 이벤트 ID를 넣으면 한 프로세스에서는 중복을 막아도 재시작·다중 인스턴스에서 실패합니다. DB inbox라면 공급자·앱·이벤트 ID의 적절한 조합을 고유 키로 잡고, 같은 트랜잭션에 처리할 작업을 남기는 방법을 검토할 수 있습니다.

“중복 키를 먼저 저장하고 큐에 넣기”는 두 연산 사이에서 죽으면 작업을 잃습니다. “큐에 넣고 중복 키 저장”은 중간 실패 시 작업을 두 번 만듭니다. inbox를 worker가 직접 읽거나 트랜잭션 outbox를 사용하면 이 틈을 줄일 수 있습니다. 보관 기간·재처리·실패 상태도 운영 정책에 포함합니다.

외부 답글 API까지 정확히 한 번을 보장하는 것은 별도 문제입니다. 발신 성공 직후 완료 상태를 저장하기 전에 worker가 죽으면 재처리에서 중복 답글이 생길 수 있습니다. 목적지 API의 멱등성 지원을 확인하고, 지원이 충분하지 않으면 발신 결과 대조·운영 재처리 절차와 중복 가능성을 명시해야 합니다.

## 시행착오: 카드 전송과 자동 연결은 달랐습니다

초기 한 장짜리 카드 수신은 발신 경로만 확인한 결과였습니다. 이벤트 경로와 메시지 접근 권한이 준비된 뒤 합성 요약에서 상세 답글 하나로 이어지는 흐름을 확인했습니다. 화면 요구사항도 별개여서, 답글이 도착해도 요약·상세의 정보 배치가 맞지 않으면 다시 조정했습니다.

다른 환경에서는 정상 서명 challenge와 위조 서명 거부를 확인했지만, 비공개 채널 접근 조건이 충족되지 않아 자동 상세 답글 실수신은 미확인 상태였습니다. 앞선 환경의 성공을 가져와 이 단계를 완료 처리하지 않았습니다.

## 검증: 실패 지점별로 나눕니다

- 같은 이벤트를 순차·동시에 두 번 보내고 inbox·작업 수가 각각 한 건인지 확인합니다.
- 저장 직후 프로세스를 종료한 뒤 재시작해 pending 작업이 유실되지 않는지 확인합니다.
- 외부 발신 직후 완료 기록 전에 실패시켜 중복 가능성과 복구 절차를 확인합니다.
- 정상·위조 서명, 오래된 시각, 원본 본문 변경을 별도 검사합니다.
- 실제 대상 채널에서 요약 ID, 답글의 부모 연결, 답글 수와 화면 구성을 확인합니다.

이 목록 전체를 이미 실환경에서 통과했다는 의미는 아닙니다. 작업 기록으로 확인한 범위는 특정 환경의 합성 요약·답글 실수신, 다른 환경의 서명 검증까지입니다. 장애 주입·장시간 자연 이벤트·모든 환경의 수신은 별도 검증 대상으로 남습니다.

## 독립 실습: 메모리 중복 방지의 범위를 확인하기

다음 Node.js 코드는 **단일 프로세스의 순차 재수신**만 보여 줍니다. HTTP·서명·DB·외부 발신을 구현한 서버 예제는 아닙니다.

```javascript
import assert from 'node:assert/strict';
const accepted_events = new Set();
const pending_jobs = [];
function accept_event(event_id) {
  if (accepted_events.has(event_id)) return 'duplicate';
  accepted_events.add(event_id);
  pending_jobs.push({ event_id, state: 'pending' });
  return 'accepted';
}
assert.equal(accept_event('demo-event-001'), 'accepted');
assert.equal(accept_event('demo-event-001'), 'duplicate');
assert.equal(pending_jobs.length, 1);
console.log('3 dedup checks passed');
```

`dedup-demo.mjs`로 저장해 `node dedup-demo.mjs`로 실행합니다. 다음 과제는 저장을 DB 고유 제약과 트랜잭션으로 옮기고 동시 요청·재시작 검사를 추가하는 것입니다. Set 예제의 성공을 운영 멱등성의 증거로 사용하지 않습니다.

## 배운 점

수신기 구현의 완료 조건은 발신 API 응답 하나로 정할 수 없었습니다. 인증, 수신 기록, 재처리, 외부 발신과 실제 화면을 각각 확인해야 남은 문제의 위치가 보입니다. 중복 방지는 이벤트 식별자만 고르는 문제가 아니라, 실패했을 때 무엇이 저장돼 있고 어디서 다시 시작할지를 정하는 문제였습니다.
