하위 작업은 새 릴리스를 적용하고 성공으로 끝났습니다. 이어서 실행된 상위 작업은 최종 완료 기록을 만들다가 실패했습니다. 당시 작업일지를 바탕으로, 이미 적용된 릴리스를 재배포하지 않고 어느 단계의 실패인지 확인한 과정을 정리했습니다.

## 실패 지점을 먼저 확인하기

상위 작업의 마지막 단계는 실행 중인 릴리스를 조회해서 하위 작업의 성공 증거와 대조해야 했습니다. 그런데 이 경로가 배포 전에 쓰던 설정 변환 검사를 함께 호출했습니다. 실행 환경에는 외부 설정 저장소를 가리키는 참조가 있었고, 배포 전 검사는 변환할 설정 본문을 요구했습니다. 런타임 상태를 확인하는 도중에 배포 입력 규칙을 다시 적용하면서 완료 기록이 막혔습니다.

상위 실패만 보고 파이프라인 전체를 재실행하면 이미 성공한 배포까지 반복할 수 있습니다. 반대로 하위 성공만으로 완료를 찍으면 그 이후 다른 버전이 배포됐거나 설정이 바뀐 경우를 놓칩니다. 하위 작업의 결과와 현재 실행 상태를 둘 다 읽어서 결론을 내려야 했습니다. Jenkins의 하위 작업 실행과 결과 대기 옵션도 확인했습니다. [Jenkins Pipeline Build Step 공식 문서](https://www.jenkins.io/doc/pipeline/steps/pipeline-build-step/)

## 두 단계가 확인하는 정보

| 단계 | 읽는 정보 | 통과 조건 |
| --- | --- | --- |
| 배포 전 검사 | 배포 요청, 대상, 설정 입력 | 대상에 적용할 입력이 배포 규칙을 충족 |
| 배포 후 완료 기록 | 하위 성공 증거, 실행 리비전, 이미지와 설정 지문 | 동일한 릴리스가 현재 실행 중임을 확인 |

완료 기록 단계는 읽기 전용 조회로 바꿨습니다. 하위 작업에서 남긴 증거와 실제 실행 환경의 이미지 다이제스트, 소스 리비전, 설정 지문을 비교했습니다. 교체가 진행 중이거나 런타임 조회가 실패하면 완료 기록을 보류합니다. 비밀을 담을 수 있는 설정 본문 대신, 원인을 구분할 수 있는 고정 진단 코드를 사용했습니다.

예를 들어 아래는 설정 지문 비교가 실패했을 때 운영자가 볼 수 있는 **합성 예시**입니다. 실제 시스템의 필드와 값은 일반화했습니다.

```json
{
  "deployment": "succeeded",
  "completion_record": "blocked",
  "reason": "CONFIG_FINGERPRINT_MISMATCH"
}
```

이 결과를 받으면 하위 작업이 기록한 설정과 현재 실행 상태를 확인합니다. 상태를 비교하는 동안 구성 변경이 있었다면 어느 릴리스의 완료 기록을 만들고 있는지부터 다시 확인해야 합니다.

## 재배포 없이 검증한 범위

임시 검증 작업에서 실제 하위 성공 증거를 읽고 현재 런타임과 대조해 완료 기록을 생성했습니다. 이어서 조회 결과의 복사본에서 이미지 다이제스트, 소스 리비전, 설정 지문 등을 각각 바꾸고, 하위 성공 증거를 빼는 경우도 검증했습니다. 이 입력들은 모두 거부됐습니다. 서비스의 배포 식별자와 실행 작업 수는 검증 전후에 같았습니다.

과거에 실패한 상위 실행은 실패 이력으로 남겼습니다. 별도 검증 결과에 성공한 하위 릴리스와 대조 시점을 함께 기록하면, 당시 무엇이 적용됐고 나중에 무엇을 확인했는지 추적할 수 있습니다.
