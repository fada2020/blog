## 결론부터 말하면

이번 주 AI agent 운영의 핵심은 "어떤 모델이 제일 똑똑한가"보다 **agent가 무엇을 읽고, 어디에서 실행하고, 무엇을 기록하고,
어떤 빠른 경로로 판정하는가를 계약으로 고정하는 일**입니다.

Google은 Gemini 4 Argon을 coding과 agentic work 전면에 놓았고, GitHub는 Copilot agent의 local sandbox와 telemetry 통제를
강화했습니다. OpenAI는 Responses API의 ultrafast mode와 Decisions API beta로 agent workflow 안의 빠른 판정 경로를 열었습니다.
Mistral은 Workflow를 Mistral Cloud에서 운영하는 Managed Deployments를 공개 preview로 냈습니다.

Spring Boot 팀이라면 이 흐름을 모델 순위표로만 보면 아깝습니다. agent를 production workflow에 넣는 순간 필요한 것은
controller, service, transaction boundary처럼 반복 가능한 운영 계약입니다.

## agent 운영 계약은 네 칸으로 나눕니다

Agent를 도입할 때 prompt template부터 만지기 쉽지만, 운영 관점에서는 먼저 네 칸을 나눕니다.

<Mermaid title="AI agent 운영 계약">
{`flowchart TD
  Request["사용자 요청"] --> Route["routing / typed decision"]
  Route --> Model["model 또는 agent 선택"]
  Model --> Sandbox["tool sandbox policy"]
  Sandbox --> Work["코드 / 문서 / 브라우저 작업"]
  Work --> Telemetry["trace / telemetry / audit"]
  Telemetry --> Review["사람 검토"]
  Review --> Merge["저장 / 배포 / 보고"]

  Sandbox --> Deny["deny network / secrets / unsafe paths"]
  Telemetry --> Cost["cost와 attribution"]
`}
</Mermaid>

Java/Spring Boot에 빗대면 route는 controller mapping, sandbox는 security filter와 transaction boundary, telemetry는 audit log와
APM trace, review는 approval workflow입니다. 모델은 중요하지만, 모델만 바꿔서는 운영 사고가 줄지 않습니다.

## Gemini 4 Argon은 "깊은 작업" 후보로 보되 경로를 분리합니다

Google 공식 문서는 Gemini 4 Argon을 `gemini-4-argon` model code로 제시하고, code execution, function calling, file search,
search grounding, structured outputs, thinking을 지원한다고 설명합니다. Google Cloud 발표도 API, AI Studio, Gemini platform,
Google Antigravity에서 접근할 수 있다고 정리합니다. GitHub Copilot changelog는 Gemini 4 Argon이 Copilot의 여러 IDE와 agent
surface에 순차 rollout된다고 알렸습니다.

이런 모델은 "모든 일을 맡기는 기본값"보다 다음 작업에 먼저 붙이는 편이 낫습니다.

| 작업 | Argon 같은 deep-work 모델 후보 | 빠른 모델 후보 |
|---|---|---|
| 큰 코드베이스 성능 개선 | profiler 결과 해석, 수정 계획, edge case 검토 | 파일 분류, 단순 lint fix |
| 보안/정책 점검 | exploitability 추론, 위험 경로 설명 | severity label, allow/deny routing |
| 긴 PR 리뷰 | architecture drift와 test gap 분석 | changed-file summary |
| 운영 리서치 | 여러 공식 문서 비교와 migration plan | source 후보 수집 |

모델이 강해질수록 review gate는 더 중요해집니다. agent가 넓은 권한으로 더 오래 실행되기 때문입니다.

## local sandbox는 "agent가 똑똑해서 안전하다"를 대체합니다

GitHub Copilot local sandboxing GA는 이번 주 가장 실무적인 신호입니다. 공식 changelog는 Copilot이 시작한 tool과 command가
filesystem, network, credential, system capability 접근을 정책에 따라 제한받는다고 설명합니다. 또한 enterprise-managed settings로
sandbox를 요구하고 개발자가 약화할 수 없게 할 수 있습니다.

Spring Boot 팀의 감각으로 바꾸면 agent command는 `@Transactional` 밖에서 마음대로 side effect를 내는 코드가 아닙니다.
권한은 정책 파일과 관리 설정으로 제한되어야 합니다.

```yaml
agentPolicy:
  filesystem:
    read:
      - repo
      - docs
    write:
      - repo
    deny:
      - ~/.ssh
      - ~/.aws
  network:
    allow:
      - api.github.com
      - official-docs.example
    denyLocalNetwork: true
  credentials:
    githubCli: read-only
    git: push_requires_human_approval
```

실제 설정 문법은 각 도구 문서를 따라야 하지만, 팀 문서에는 이 정도 의사 계약을 먼저 적어야 합니다. "agent 사용 가능"보다
"어떤 경로와 credential은 절대 못 만진다"가 더 운영적인 기준입니다.

## telemetry는 내용 수집과 책임 소재를 분리합니다

GitHub의 10월 12일 changelog는 enterprise 관리자가 prompt, response, tool content를 수집하지 않고도 Copilot activity를 사용자에게
귀속할 수 있는 `telemetry.capture.identity`를 추가했다고 설명합니다. `user.name`, `process.user.name`, `host.name` 같은 속성과
prompt, response, toolArguments, toolOutput, policyDetail capture class는 별도이며 기본값은 꺼져 있습니다.

이 구분은 중요합니다. agent 운영 로그는 두 목적이 섞이면 금방 위험해집니다.

| 목적 | 남겨야 할 것 | 조심할 것 |
|---|---|---|
| 비용과 quota 관리 | user/team, model, duration, token, sandbox minutes | prompt 전문 저장 |
| 사고 조사 | run id, tool name, policy decision, changed files | secret이 들어간 tool output |
| 품질 개선 | eval dataset id, failed criterion, review result | 개인 폴더 경로, 내부 URL |
| 컴플라이언스 | 승인자, 승인 시각, 배포 artifact | 원문 source code 대량 export |

원칙은 단순합니다. 운영에 필요한 최소 metadata부터 켜고, content capture는 승인된 collector와 보존 정책이 있을 때만 켭니다.

## 빠른 판정 경로는 agent run을 짧게 만듭니다

OpenAI changelog의 두 변화는 agent workflow 설계에 직접 영향을 줍니다. `gpt-6.1-sol`의 Responses API ultrafast mode는 생성 token
간 지연을 줄이는 처리 tier이고, Decisions API beta는 `gpt-6-luna`로 text와 image를 typed answer로 빠르게 바꾸는 API입니다.

이 둘을 같은 "새 모델"로 보면 놓치는 점이 있습니다. agent workflow에는 deep reasoning이 필요한 단계와 빠른 판정만 필요한 단계가
섞입니다.

```text
incident-triage
  1. classify severity        -> Decisions API 후보
  2. collect logs             -> deterministic script
  3. compare hypotheses       -> deep model 후보
  4. write customer summary   -> standard response model
  5. approval to send         -> human checkpoint
```

빠른 경로를 분리하면 비용도 줄지만, 더 중요한 것은 실패 반경이 줄어든다는 점입니다. routing이나 policy check가 긴 free-form
agent 답변에 묻히지 않고 typed output으로 남습니다.

## Managed Deployment는 workflow 운영 책임을 새로 묻습니다

Mistral Managed Deployments는 Workflow worker를 직접 운영하지 않고 Mistral Cloud에서 build, scale, lifecycle을 맡기는 public
preview입니다. 공식 release note는 GitHub repository에서 workflow를 배포하고, service account 인증, egress 차단, UI logs 같은
기능을 설명합니다.

이런 managed runtime은 편하지만, 운영 계약은 더 분명해야 합니다.

| 결정 | self-hosted worker | managed deployment |
|---|---|---|
| secret 관리 | 내부 secret store와 배포 pipeline | vendor service account와 workspace policy |
| network 통제 | VPC, firewall, proxy | platform egress policy |
| log 접근 | 내부 log stack | vendor UI/API와 export |
| rollback | 직접 image/tag 관리 | deployment lifecycle API |

Public Preview라면 production critical path에 바로 넣기보다, 문서 생성, report draft, read-only 분석 같은 낮은 위험 workflow부터
검증하는 편이 좋습니다.

## 팀에서 바로 쓸 수 있는 최소 schema

agent run log는 길 필요가 없습니다. 다음 정도만 고정해도 다음 달 모델 교체와 비용 논의가 쉬워집니다.

```json
{
  "agent_run_id": "run_2026_10_14_001",
  "workflow": "release-check",
  "requested_by": "team-member-or-service-account",
  "model": "provider/model-or-agent",
  "decision_path": "fast|standard|deep",
  "sandbox_policy": "repo-write-no-secrets-v1",
  "telemetry_capture": ["identity", "policyDecision"],
  "tools_allowed": ["shell:read", "git:diff", "browser:official-docs"],
  "human_approval_required": ["write", "send", "push", "deploy"],
  "artifact": "pull-request-or-report-id",
  "result": "approved|needs-review|failed"
}
```

이 schema의 핵심은 모델 이름보다 `decision_path`, `sandbox_policy`, `human_approval_required`입니다. agent 운영은 결국
"누가 어떤 권한으로 무엇을 했고, 어디서 멈췄는가"를 설명해야 하기 때문입니다.

## 본문에 넣지 않은 후보와 제외 이유

- Anthropic Claude의 10월 release notes는 Claude Design, Slides, Docs와 Claude Code 안의 artifact 편집을 확인했지만,
  이번 글의 중심인 sandbox/telemetry/typed decision 운영 계약과는 거리가 있어 후보로만 남겼습니다.
- xAI는 10월 2일 voice transcription model EOL, 9월 `safety_identifier`, Grok 4.7 API 신호를 확인했지만 직전 수요일 글에서
  이미 운영 식별자와 model alias 관점으로 다뤘기 때문에 반복을 피했습니다.
- Meta는 10월 2일 capable model 책임 프레임워크 업데이트와 9월 말 enterprise platform/Muse 흐름을 확인했습니다. 다만 이번 주
  agent 실행 권한이나 telemetry 계약을 바꿀 만큼 구체적인 개발자 운영 API 변화가 적어 본문 축에서 제외했습니다.
- Mistral의 Vibe 통합과 Agentic Knowledge Base는 9월 22일 발표라 여전히 중요하지만, 이번 글에서는 10월 9일 Managed Deployments를
  더 최신 운영 신호로 우선했습니다.
- Reddit과 비공식 benchmark 글은 화제성 후보를 찾는 데만 참고하고, 본문 근거로 쓰지 않았습니다.

## 이번 주 실험 과제

1. 현재 팀의 agent 작업 하나를 골라 `fast`, `standard`, `deep` decision path로 나눠 보세요.
2. agent가 읽어도 되는 경로와 절대 읽으면 안 되는 credential 경로를 정책 문서로 적어 보세요.
3. prompt 전문 없이도 비용과 실행 주체를 추적할 수 있는 telemetry field를 5개만 고르세요.
4. PR review agent가 push나 deploy를 할 수 없도록 approval checkpoint를 명시하세요.
5. 새 모델을 도입하기 전, 같은 dataset 10개로 기존 모델과 결과 품질, 시간, 비용을 비교하세요.
