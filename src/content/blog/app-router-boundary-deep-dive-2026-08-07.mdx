## 이번 주에 이 기술이 중요했던 이유

이번 주 글에서는 Next.js App Router의 폴더 기반 라우팅, Next.js 16.3.0 안정 릴리스, 벌크
API의 응답 계약, 장애 알림의 상태 전이, 레거시 API 호환성을 다뤘습니다. 겉으로는 서로 다른
주제지만, 실제 설계 질문은 하나로 모입니다.

**어느 경계에서 판단하고, 어느 경계에서는 전달만 할 것인가**입니다.

Spring Boot에서는 이 질문을 Controller, Service, Repository, Transaction, Validation
경계로 나눠 왔습니다. Next.js App Router를 함께 쓰기 시작하면 같은 질문이 화면 계층에도
생깁니다. `page.tsx`가 서버에서 실행될 수 있고, Route Handler가 HTTP 요청을 받을 수 있으며,
Client Component가 브라우저 상태를 가질 수 있기 때문입니다.

문제는 기능이 많아서 어렵다기보다, 경계를 흐리기 쉽다는 데 있습니다. 데이터 조회를 모두 브라우저로
밀면 초기 렌더링과 권한 처리가 약해집니다. 반대로 모든 상호작용을 서버 쪽으로 끌고 오면 UI 상태와
사용자 피드백이 둔해집니다. Route Handler에 도메인 규칙을 넣기 시작하면 Spring Boot API와
Next.js BFF가 같은 책임을 두 번 갖게 됩니다.

## 핵심 개념

App Router에서 먼저 구분할 것은 파일 위치가 아니라 실행 환경입니다.

| 구성요소 | 적합한 책임 | 경계 기준 |
|---|---|---|
| Server Component | 서버 또는 빌드 시점의 데이터 조회, HTML 구성, 민감한 서버 의존성 접근 | 클릭 핸들러, 브라우저 상태, 대부분의 Hook은 두지 않습니다. |
| Client Component | 입력 상태, 이벤트, 드롭다운, 모달, 낙관적 UI | 서버 비밀값과 대량 데이터 조립 코드를 가져오지 않습니다. |
| Route Handler | 화면 전용 조합, 얇은 BFF, 외부 응답 모양 보정 | 핵심 도메인 검증과 트랜잭션을 소유하지 않습니다. |
| Spring Boot API | 권한, 도메인 규칙, 트랜잭션, 영속성 | 화면 컴포넌트 상태 관리는 맡기지 않습니다. |

Spring MVC에서는 `@GetMapping`과 `@PostMapping`이 URL과 메서드를 연결합니다. App Router에서는
폴더와 예약 파일이 라우팅 계약을 만듭니다. 하지만 이것만 보고 `route.ts`를 Spring Controller처럼
늘려 가면 위험합니다. Next.js의 서버 기능은 화면 서버에 가깝고, Spring Boot API는 도메인 서버에
가깝습니다.

따라서 첫 번째 원칙은 단순합니다.

**도메인 성공과 실패를 결정하는 규칙은 Spring Boot에 남기고, Next.js는 화면에 필요한 모양으로
조립합니다.**

## 내부 동작 원리

React Server Components에서 `'use client'`는 렌더 트리의 부모-자식 관계가 아니라 모듈 의존성
트리에 경계를 만듭니다. 어떤 파일 맨 위에 `'use client'`를 붙이면 그 파일과 그 파일이 직접
가져오는 하위 모듈들이 클라이언트 번들에 들어갈 수 있습니다.

이 차이가 중요합니다. Spring Boot 개발자는 보통 패키지나 클래스 계층으로 책임을 읽습니다.
Next.js에서는 import 방향이 실행 환경을 바꿉니다.

<Mermaid title="App Router 경계는 import 방향에서 커집니다">
{`flowchart LR
  Page["app/orders/page.tsx<br/>Server Component"] --> Summary["OrderSummary<br/>Server Component"]
  Page --> FilterShell["OrderFilterShell<br/>'use client'"]
  FilterShell --> FilterInput["FilterInput<br/>Client Component"]
  FilterShell --> BrowserStore["browser state<br/>Client bundle"]
  Page --> Api["Spring Boot API"]
  Api --> Domain["Domain rule and transaction"]
`}
</Mermaid>

위 흐름에서 `page.tsx`는 서버에서 API를 호출하고 초기 화면을 만듭니다. 필터 입력처럼 브라우저
상호작용이 필요한 작은 부분만 Client Component로 분리합니다. 이때 `OrderFilterShell` 아래로
가져온 모듈은 클라이언트 쪽으로 커질 수 있으므로, 서버 전용 SDK나 비밀값을 그 아래에 두면 안
됩니다.

Server Component의 장점은 서버에서 데이터에 가까운 위치로 이동한다는 점입니다. 브라우저에
불필요한 조립 코드를 보내지 않고, 첫 HTML을 만들 때 필요한 데이터를 바로 넣을 수 있습니다. 제한도
명확합니다. 클릭 이벤트, 로컬 상태, 브라우저 API, 대부분의 Hook은 Client Component에서 다뤄야
합니다.

## 실무 설계 선택지

작은 관리자 화면을 예로 보겠습니다. Spring Boot API가 주문 목록과 주문 상세를 제공하고,
Next.js가 관리자 UI를 담당한다고 가정합니다.

```text
GET /admin/orders
-> app/admin/orders/page.tsx
-> Spring Boot GET /api/admin/orders
-> Server Component가 목록 HTML 생성
-> 필터와 선택 상태만 Client Component로 분리
```

가장 보수적인 구조는 아래처럼 나눕니다.

```tsx
// app/admin/orders/page.tsx
import { OrderTable } from "./OrderTable";
import { OrderFilter } from "./OrderFilter";

export default async function OrdersPage() {
  const orders = await fetchOrdersFromSpring();

  return (
    <>
      <OrderFilter />
      <OrderTable orders={orders} />
    </>
  );
}
```

```tsx
// app/admin/orders/OrderFilter.tsx
"use client";

import { useState } from "react";

export function OrderFilter() {
  const [keyword, setKeyword] = useState("");

  return (
    <input
      value={keyword}
      onChange={(event) => setKeyword(event.target.value)}
      placeholder="주문 검색"
    />
  );
}
```

여기서 `OrderTable`은 서버에서 받은 데이터를 표시하는 역할만 합니다. `OrderFilter`는 입력 상태를
가지므로 Client Component입니다. 검색어를 서버 조회에 반영해야 한다면 URL search params나 form
submit으로 서버 경계를 다시 넘기는 방식을 먼저 검토합니다. 모든 필터를 브라우저 전역 상태로
밀어 넣는 것은 마지막 선택지에 가깝습니다.

Route Handler가 필요한 경우도 있습니다. 예를 들어 화면에서 여러 백엔드 응답을 묶어 하나의
프론트엔드 전용 응답으로 내려야 하거나, 외부 API 응답의 노출 필드를 줄여야 할 때입니다.

```ts
// app/api/order-dashboard/route.ts
export async function GET() {
  const [orders, summary] = await Promise.all([
    fetchSpring("/api/admin/orders"),
    fetchSpring("/api/admin/orders/summary"),
  ]);

  return Response.json({
    orders: orders.items,
    total: summary.totalCount,
  });
}
```

이 코드는 화면 전용 조합입니다. 주문을 저장할 수 있는지, 상태 전이가 가능한지, 권한이 충분한지는
여전히 Spring Boot가 결정해야 합니다. Route Handler가 도메인 검증을 복제하면 레거시 API
호환성 글에서 다룬 문제와 같은 종류의 회귀가 생깁니다. 어느 한쪽만 검증이 바뀌고 다른 쪽이
따라오지 못합니다.

## 흔한 실패 사례

첫 번째 실패는 `'use client'`를 페이지 최상단에 붙이는 것입니다. 당장은 Hook 오류가 사라져서
편해 보입니다. 하지만 페이지 전체가 클라이언트 쪽으로 커지면 서버에서 끝낼 수 있던 데이터 조립과
HTML 생성의 이점이 줄어듭니다. Spring Boot로 치면 Controller 하나의 문제를 해결하려고 Service와
Repository까지 같은 계층으로 올리는 것과 비슷합니다.

두 번째 실패는 Route Handler를 새 백엔드처럼 키우는 것입니다. BFF는 유용하지만, 도메인 규칙의
소유자가 되면 안 됩니다. 특히 결제, 권한, 재고, 상태 전이, 환불, 관리자 승인처럼 실패 의미가
중요한 로직은 Spring Boot API의 테스트와 트랜잭션 경계 안에 있어야 합니다.

세 번째 실패는 서버와 클라이언트 사이로 넘기는 값을 너무 풍부하게 만드는 것입니다. Server
Component에서 Client Component로 props를 넘길 때는 직렬화 가능한 값으로 좁히는 편이 안전합니다.
엔티티 전체, 서버 전용 객체, 함수, 비밀값을 넘기려 하면 실행 환경 경계가 흐려집니다.

네 번째 실패는 캐시와 권한을 한 묶음으로 생각하지 않는 것입니다. 사용자별 권한이 들어간 응답과
공개 정적 데이터를 같은 방식으로 다루면 안 됩니다. Spring Security에서 인증 사용자별 응답을
공유 캐시에 넣지 않는 것처럼, App Router에서도 어떤 데이터가 요청별인지, 공개 정적 데이터인지
먼저 표시해야 합니다.

## 독립 실행 실습

아래 실습은 실제 프로젝트에 붙이기 전에 경계 감각을 확인하기 위한 작은 연습입니다.

1. `app/products/page.tsx`를 Server Component로 둡니다.
2. `fetchProducts()`는 Spring Boot API를 호출한다고 가정하고 서버 파일에서만 import합니다.
3. 정렬 드롭다운만 `"use client"`가 붙은 `ProductSort.tsx`로 분리합니다.
4. 정렬 값은 URL search params로 표현하고, 목록 데이터 재조회는 서버 경계에서 다시 수행합니다.
5. 저장, 삭제, 권한 판단은 Next.js Route Handler가 아니라 Spring Boot API가 결정하게 둡니다.

점검 질문은 세 가지면 충분합니다.

| 질문 | 예라고 답해야 하는 상태 |
|---|---|
| 브라우저 상호작용이 필요한 컴포넌트만 Client Component인가 | 입력, 모달, 선택 상태만 클라이언트에 있습니다. |
| Route Handler가 도메인 성공/실패를 결정하지 않는가 | 화면 전용 조합과 응답 축소만 담당합니다. |
| Spring Boot API의 계약이 테스트로 보호되는가 | 권한, 검증, 트랜잭션 실패가 백엔드 테스트에 있습니다. |

## 정리하면

Next.js App Router를 Spring Boot와 함께 쓸 때 핵심은 새 파일 규칙을 외우는 것이 아닙니다.
서버에서 끝낼 일, 브라우저에서만 가능한 일, 화면 서버가 얇게 조합할 일, 백엔드가 반드시 소유해야
할 일을 나누는 것입니다.

처음에는 보수적으로 시작하는 편이 낫습니다. 페이지는 Server Component로 두고, 상호작용이 필요한
작은 섬만 Client Component로 분리합니다. Route Handler는 화면 전용 BFF로 제한합니다. 도메인
검증과 트랜잭션은 Spring Boot API에 남깁니다.

이 경계가 유지되면 App Router는 백엔드를 대체하는 서버가 아니라, Spring Boot API 위에서 화면에
맞는 렌더링과 조합을 담당하는 계층이 됩니다.
