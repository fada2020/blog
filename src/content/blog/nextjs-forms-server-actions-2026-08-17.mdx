## 결론부터 말하면

Next.js App Router에서 폼 처리는 `onSubmit` 이벤트를 먼저 떠올리기보다 **서버에서 수행할 변경 작업을
명확한 함수로 분리하는 것**에서 시작하는 편이 좋습니다.

Spring Boot 개발자는 보통 `@PostMapping`이 요청을 받고, DTO 검증을 거친 뒤, Service를 호출하고,
성공하면 상세 화면으로 리다이렉트하는 흐름에 익숙합니다. Next.js의 Server Actions도 비슷한 문제를
풀지만, 코드가 Controller 파일에 모이지 않습니다. 폼은 화면 컴포넌트에 있고, 변경 작업은 서버 함수로
분리되며, 저장 후 캐시 재검증과 리다이렉트까지 같은 흐름에서 처리합니다.

이번 글의 목표는 단순합니다.

**폼 제출을 화면 이벤트가 아니라 서버 변경 계약으로 바라보는 기준을 세웁니다.**

## 이번 주 개념

Next.js App Router에서는 `<form action={serverFunction}>` 형태로 폼 제출을 서버 함수에 연결할 수
있습니다. 이 서버 함수는 `FormData`를 받고, 서버에서 검증과 저장을 수행합니다.

```tsx
// app/products/actions.ts
"use server";

import { revalidatePath } from "next/cache";
import { redirect } from "next/navigation";

export async function createProduct(formData: FormData) {
  const name = String(formData.get("name") ?? "").trim();
  const price = Number(formData.get("price"));

  if (!name || !Number.isFinite(price) || price < 0) {
    throw new Error("상품 이름과 가격을 확인해야 합니다.");
  }

  await productRepository.create({ name, price });

  revalidatePath("/products");
  redirect("/products");
}
```

```tsx
// app/products/new/page.tsx
import { createProduct } from "../actions";

export default function NewProductPage() {
  return (
    <form action={createProduct}>
      <label>
        상품명
        <input name="name" required />
      </label>
      <label>
        가격
        <input name="price" type="number" min="0" required />
      </label>
      <button type="submit">등록</button>
    </form>
  );
}
```

중요한 점은 브라우저에서 JavaScript 상태를 먼저 만들지 않아도 기본 폼 제출 흐름을 사용할 수 있다는
것입니다. 사용자 경험을 더 다듬고 싶을 때 `useActionState`, `useFormStatus` 같은 React Hook을
붙입니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring MVC에서는 폼 제출이 대체로 Controller 메서드로 들어옵니다.

```java
@Controller
@RequestMapping("/products")
class ProductController {

    private final ProductService productService;

    @PostMapping
    String create(
        @Valid ProductCreateRequest request,
        BindingResult bindingResult,
        RedirectAttributes redirectAttributes
    ) {
        if (bindingResult.hasErrors()) {
            return "products/new";
        }

        Long productId = productService.create(request);
        redirectAttributes.addFlashAttribute("message", "상품을 등록했습니다.");
        return "redirect:/products/" + productId;
    }
}
```

이 구조에는 익숙한 장점이 있습니다.

| 책임 | Spring MVC에서 흔한 위치 |
|---|---|
| 요청 경로 | `@PostMapping` |
| 입력 검증 | `@Valid`, `BindingResult`, Service 검증 |
| 변경 작업 | Service 트랜잭션 |
| 후속 화면 | `redirect:` 또는 템플릿 반환 |
| 목록 최신화 | DB 재조회, HTTP 캐시 무효화, 애플리케이션 캐시 삭제 |

Next.js에서도 책임은 사라지지 않습니다. 다만 위치가 달라집니다. 폼 컴포넌트가 요청의 진입점을
보여주고, Server Action이 변경 계약과 후속 처리를 맡습니다.

## Next.js에서는 무엇이 다른가

가장 큰 차이는 서버 변경 함수가 UI 파일 가까이에 놓인다는 점입니다.

<Mermaid title="Next.js 폼 제출과 서버 변경 흐름">
{`flowchart LR
  A["form submit"] --> B["Server Action"]
  B --> C["입력 검증"]
  C --> D["저장 또는 외부 API 호출"]
  D --> E["revalidatePath / revalidateTag"]
  E --> F["redirect 또는 상태 반환"]`}
</Mermaid>

이 흐름은 Spring MVC의 POST Controller와 닮았지만, 두 가지를 특히 조심해야 합니다.

첫째, Server Action은 화면 코드 옆에 있어도 서버에서 실행되는 변경 경로입니다. 따라서 인증,
권한, 입력 검증을 클라이언트에 맡기면 안 됩니다. 버튼을 숨기거나 input을 `readonly`로 만드는 것은
보조 UX일 뿐입니다.

둘째, 저장 후 화면이 보는 데이터가 캐시되어 있다면 재검증을 명시해야 합니다. 이전 글에서 다룬
데이터 조회 캐시와 연결되는 부분입니다. 목록 페이지를 시간 기반으로 캐시했다면, 생성이나 수정 직후
`revalidatePath("/products")` 또는 더 세밀한 태그 재검증을 검토해야 합니다.

## 대응 개념 비교

Spring Boot 개발자가 Next.js 폼을 읽을 때는 아래처럼 대응시키면 이해가 빠릅니다.

| Spring MVC | Next.js App Router |
|---|---|
| `@PostMapping` | `<form action={serverAction}>` |
| request DTO | `FormData`를 파싱한 타입 |
| `@Valid` | 서버 함수 내부 검증 또는 검증 라이브러리 |
| Service 메서드 | Server Action에서 호출하는 서버 전용 함수 |
| `BindingResult` | `useActionState`로 반환하는 상태 |
| `redirect:` | `redirect()` |
| 캐시 삭제 | `revalidatePath()`, `revalidateTag()` |

여기서 Server Action을 Service처럼 크게 만들면 금방 읽기 어려워집니다. Action은 HTTP와 화면 흐름에
가까운 얇은 계층으로 두고, 도메인 규칙이나 외부 API 호출은 별도 서버 함수로 분리하는 편이 유지보수에
좋습니다.

```tsx
"use server";

export async function createProductAction(
  _previousState: ProductFormState,
  formData: FormData,
): Promise<ProductFormState> {
  const input = parseProductForm(formData);

  if (!input.ok) {
    return { status: "invalid", errors: input.errors };
  }

  const result = await createProduct(input.value);

  if (!result.ok) {
    return { status: "failed", errors: result.errors };
  }

  revalidatePath("/products");
  return { status: "created", id: result.id };
}
```

## 최소 실행 예제

폼 오류를 화면에 남겨야 한다면 `useActionState`를 붙입니다. 이 Hook은 Action의 반환 값을 컴포넌트
상태처럼 읽게 해 줍니다.

```tsx
// app/products/new/ProductForm.tsx
"use client";

import { useActionState } from "react";
import { createProductAction } from "../actions";

const initialState = {
  status: "idle",
  errors: {},
};

export function ProductForm() {
  const [state, formAction, isPending] = useActionState(
    createProductAction,
    initialState,
  );

  return (
    <form action={formAction}>
      <label>
        상품명
        <input name="name" aria-invalid={Boolean(state.errors.name)} />
      </label>
      {state.errors.name && <p role="alert">{state.errors.name}</p>}

      <label>
        가격
        <input name="price" type="number" min="0" />
      </label>
      {state.errors.price && <p role="alert">{state.errors.price}</p>}

      <button type="submit" disabled={isPending}>
        {isPending ? "등록 중" : "등록"}
      </button>
    </form>
  );
}
```

버튼만 별도 컴포넌트로 분리한다면 `useFormStatus`도 유용합니다. 이 Hook은 부모 `<form>`의 제출 상태를
읽습니다.

```tsx
"use client";

import { useFormStatus } from "react-dom";

export function SubmitButton() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "저장 중" : "저장"}
    </button>
  );
}
```

이때 `useFormStatus`는 같은 컴포넌트 안에서 만든 `<form>`이 아니라, 부모 폼의 상태를 읽는 Hook이라는
점을 기억해야 합니다. 버튼 컴포넌트를 폼 내부에 넣어야 의도대로 동작합니다.

## Java 개발자가 자주 하는 오해

### Server Action은 Controller를 완전히 대체한다

부분적으로만 맞습니다. 폼 제출과 화면 전환을 처리한다는 점에서는 Controller와 닮았습니다. 하지만
공개 API가 필요한 경우, 외부 클라이언트가 호출해야 하는 경우, 웹훅처럼 명시적인 HTTP 계약이 필요한
경우에는 Route Handler나 별도 백엔드 API가 더 적합합니다.

### 클라이언트 검증이 있으면 서버 검증을 줄여도 된다

아닙니다. Spring MVC에서 JavaScript 검증이 있어도 `@Valid`와 Service 검증을 없애지 않는 것과
같습니다. Next.js에서도 Server Action 내부에서 권한과 입력을 다시 확인해야 합니다.

```tsx
"use server";

export async function updateProductAction(formData: FormData) {
  const session = await requireSession();
  const productId = String(formData.get("productId") ?? "");

  await assertCanEditProduct(session.userId, productId);

  const input = parseProductForm(formData);
  if (!input.ok) {
    return { status: "invalid", errors: input.errors };
  }

  await updateProduct(productId, input.value);
  revalidatePath(`/products/${productId}`);
}
```

### 저장 후 목록이 자동으로 최신이 된다

항상 그렇지 않습니다. 목록 조회가 캐시되어 있으면 저장이 성공해도 사용자가 이전 목록을 볼 수
있습니다. 변경 Action 안에서 어떤 화면이나 태그를 다시 검증할지 같이 정해야 합니다.

### 모든 폼을 Client Component로 시작해야 한다

기본 폼은 Server Component에서도 만들 수 있습니다. 입력 중 실시간 미리보기, 복잡한 위저드, 브라우저
전용 API가 필요할 때 Client Component를 추가하면 됩니다. 처음부터 모든 필드를 `useState`로 관리할
필요는 없습니다.

## 실무 체크리스트

폼을 만들 때는 구현보다 먼저 아래 네 가지를 정합니다.

| 질문 | 선택 기준 |
|---|---|
| 이 변경은 누가 할 수 있는가 | Action 내부에서 세션과 권한을 확인합니다. |
| 실패를 어디에 보여줄 것인가 | 같은 화면에 남기면 `useActionState`, 성공 이동이면 `redirect()`를 검토합니다. |
| 저장 후 어떤 데이터가 낡아지는가 | 목록, 상세, 대시보드 중 재검증 대상을 고릅니다. |
| 외부 시스템과 연결되는가 | 재시도, 멱등성, 중복 제출 방지를 서버 쪽에서 처리합니다. |

성공 경로와 실패 경로도 미리 갈라 두는 편이 좋습니다. 생성이 끝나면 바로 상세 화면으로 보내는 폼은
`redirect()`가 단순하고, 같은 화면에 필드 오류를 남겨야 하는 폼은 Action 반환 타입을 먼저 설계해야
합니다. 이 기준이 흐리면 한 함수 안에서 리다이렉트, 상태 반환, 예외 처리가 섞여 Controller보다 읽기
어려운 코드가 됩니다.

Spring Boot의 POST 흐름을 Next.js로 옮긴다고 생각하면, 핵심은 문법이 아니라 책임 배치입니다.
폼은 사용자 입력의 입구이고, Server Action은 변경 계약이며, 캐시 재검증은 저장 성공 후의 후처리입니다.
