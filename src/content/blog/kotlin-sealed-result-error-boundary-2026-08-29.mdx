## 결론부터 말하면

Kotlin의 `sealed class`는 "상속을 조금 제한하는 클래스" 정도로 보면 아깝습니다. 서버 코드에서는 **성공과
실패의 가능한 모양을 타입으로 고정하고, 호출자가 그 경우를 빠뜨리지 않게 만드는 도구**로 쓸 수 있습니다.

Java/Spring Boot 프로젝트에서는 실패를 보통 예외로 표현했습니다.

- `IllegalArgumentException`, `EntityNotFoundException` 같은 예외를 던진다.
- `@ControllerAdvice`에서 예외를 HTTP 상태 코드와 JSON body로 바꾼다.
- validation 실패는 `MethodArgumentNotValidException`처럼 Spring MVC 예외 흐름에 맡긴다.
- 예상 가능한 업무 실패와 진짜 시스템 장애가 같은 `throw` 경로를 타기 쉽다.

Kotlin에서도 예외는 필요합니다. DB 연결 실패, JSON 파싱 실패, 외부 API timeout처럼 호출을 중단해야 하는
상황은 예외가 자연스럽습니다. 다만 "재고가 부족하다", "이미 처리된 요청이다", "권한이 없다"처럼 도메인에서
예상 가능한 실패는 `sealed class`로 모델링하면 service와 controller 사이의 계약이 더 분명해집니다.

## 이번 주 개념

`sealed class`와 `sealed interface`는 직접 하위 타입의 범위를 제한합니다. Kotlin 공식 문서 기준으로 direct
subclass는 같은 package와 module 안에서만 선언할 수 있고, 컴파일러는 가능한 하위 타입을 알고 있습니다.

```kotlin
sealed interface CreateOrderResult {
    data class Created(val orderId: Long) : CreateOrderResult
    data class OutOfStock(val sku: String, val available: Int) : CreateOrderResult
    data class DuplicateRequest(val requestId: String) : CreateOrderResult
}
```

이 타입을 반환하면 호출자는 성공뿐 아니라 실패의 모양도 같이 보게 됩니다.

```kotlin
fun createOrder(command: CreateOrderCommand): CreateOrderResult {
    if (isDuplicate(command.requestId)) {
        return CreateOrderResult.DuplicateRequest(command.requestId)
    }

    val available = inventory(command.sku)
    if (available < command.quantity) {
        return CreateOrderResult.OutOfStock(command.sku, available)
    }

    val order = saveOrder(command)
    return CreateOrderResult.Created(order.id)
}
```

핵심은 "실패를 숨기지 않는다"입니다. 함수 이름이나 문서만 읽고 추측하는 대신 반환 타입 자체가 가능한 결과를
말해 줍니다.

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 보통 업무 실패도 예외로 올렸습니다.

```java
Order createOrder(CreateOrderCommand command) {
    if (isDuplicate(command.requestId())) {
        throw new DuplicateRequestException(command.requestId());
    }

    int available = inventory(command.sku());
    if (available < command.quantity()) {
        throw new OutOfStockException(command.sku(), available);
    }

    return saveOrder(command);
}
```

그리고 controller 밖의 `@ControllerAdvice`에서 응답을 만듭니다.

```java
@ExceptionHandler(OutOfStockException.class)
ProblemDetail handleOutOfStock(OutOfStockException exception) {
    ProblemDetail problem = ProblemDetail.forStatus(409);
    problem.setTitle("Out of stock");
    problem.setProperty("sku", exception.sku());
    problem.setProperty("available", exception.available());
    return problem;
}
```

이 구조는 Spring MVC와 잘 맞습니다. 특히 framework 예외를 RFC 9457 Problem Details로 바꾸는 일은 Spring이
이미 좋은 도구를 제공합니다. 문제는 service 메서드의 시그니처만 봐서는 어떤 업무 실패가 정상적으로 예상되는지
잘 보이지 않는다는 점입니다.

Kotlin sealed result는 이 지점을 보완합니다. framework 경계에서는 예외와 `ProblemDetail`을 쓰고, 도메인
경계에서는 가능한 결과를 타입으로 드러낼 수 있습니다.

## Kotlin에서는 무엇이 다른가

Kotlin의 `when`은 sealed 계층과 함께 쓸 때 강해집니다. 모든 하위 타입을 처리하면 `else` 없이도 값 하나로
접을 수 있습니다.

```kotlin
fun CreateOrderResult.toHttpResponse(): ResponseEntity<Any> =
    when (this) {
        is CreateOrderResult.Created ->
            ResponseEntity.status(201).body(mapOf("orderId" to orderId))

        is CreateOrderResult.OutOfStock ->
            ResponseEntity.status(409).body(
                problemDetail(
                    title = "Out of stock",
                    detail = "$sku has only $available items",
                ),
            )

        is CreateOrderResult.DuplicateRequest ->
            ResponseEntity.status(409).body(
                problemDetail(
                    title = "Duplicate request",
                    detail = "requestId=$requestId was already processed",
                ),
            )
    }
```

새 실패 타입을 추가하면 이 변환 함수가 함께 바뀌어야 합니다. 이 강제성이 sealed type의 장점입니다.

Java 예외 방식은 흐름을 끊습니다. sealed result 방식은 흐름을 값으로 둡니다. 둘 중 하나만 쓰라는 뜻은
아닙니다. 기준은 실패가 **업무적으로 예상되는 결과인가, 아니면 실행을 중단해야 하는 장애인가**입니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin 선택지 | 언제 좋은가 |
|---|---|---|
| checked exception | Kotlin에는 강제 checked exception이 없음 | Java 호출 계약이 필요하면 `@Throws`를 검토합니다. |
| unchecked business exception | `sealed class` result | 예상 가능한 업무 실패를 호출자가 반드시 보게 하고 싶을 때 |
| `Optional<T>` | nullable 또는 `Result<T>` | 값 없음만 중요하면 nullable, 실패 원인이 필요하면 result |
| `@ControllerAdvice` | 계속 사용 | HTTP 오류 포맷 통일, framework 예외 처리 |
| enum status code | sealed subtype | 각 실패가 서로 다른 데이터를 들고 있을 때 |
| generic response wrapper | 좁은 sealed result | 한 use case의 가능한 결과를 좁게 고정할 때 |

`Result<T>`도 선택지입니다. Kotlin 표준 라이브러리의 `runCatching`은 block이 성공하면 값을 담고, 실패하면
던져진 `Throwable`을 failure로 감쌉니다.

```kotlin
fun parseQuantity(raw: String): Result<Int> =
    runCatching { raw.toInt() }
```

다만 `Result<T>`는 실패 원인이 `Throwable`입니다. "재고 부족", "중복 요청", "승인 대기"처럼 업무 실패의
필드가 각각 다르면 domain-specific sealed type이 더 읽기 쉽습니다.

## 최소 실행 예제

아래 예제는 주문 생성 use case에서 업무 실패는 sealed result로, 예상 밖 장애는 예외로 남깁니다.

```kotlin
data class CreateOrderCommand(
    val requestId: String,
    val sku: String,
    val quantity: Int,
)

sealed interface CreateOrderResult {
    data class Created(val orderId: Long) : CreateOrderResult
    data class OutOfStock(val sku: String, val available: Int) : CreateOrderResult
    data class InvalidQuantity(val quantity: Int) : CreateOrderResult
}

class OrderService(
    private val inventoryRepository: InventoryRepository,
    private val orderRepository: OrderRepository,
) {
    fun create(command: CreateOrderCommand): CreateOrderResult {
        if (command.quantity <= 0) {
            return CreateOrderResult.InvalidQuantity(command.quantity)
        }

        val available = inventoryRepository.findAvailable(command.sku)
        if (available < command.quantity) {
            return CreateOrderResult.OutOfStock(command.sku, available)
        }

        val order = orderRepository.save(command)
        return CreateOrderResult.Created(order.id)
    }
}
```

controller에서는 이 result를 HTTP 응답으로 바꿉니다.

```kotlin
@PostMapping("/orders")
fun create(@RequestBody request: CreateOrderRequest): ResponseEntity<Any> {
    val command = request.toCommand()

    return when (val result = orderService.create(command)) {
        is CreateOrderResult.Created ->
            ResponseEntity.status(201).body(OrderResponse(result.orderId))

        is CreateOrderResult.OutOfStock ->
            ResponseEntity.status(409).body(
                ProblemDetail.forStatus(409).apply {
                    title = "Out of stock"
                    detail = "Not enough inventory for ${result.sku}"
                    setProperty("available", result.available)
                },
            )

        is CreateOrderResult.InvalidQuantity ->
            ResponseEntity.badRequest().body(
                ProblemDetail.forStatus(400).apply {
                    title = "Invalid quantity"
                    detail = "quantity must be positive"
                    setProperty("quantity", result.quantity)
                },
            )
    }
}
```

이 코드는 짧지 않을 수 있습니다. 대신 실패 경계가 숨지 않습니다. 테스트도 더 단순해집니다.

```kotlin
@Test
fun `재고가 부족하면 OutOfStock을 반환한다`() {
    val service = OrderService(
        inventoryRepository = FakeInventoryRepository(available = 2),
        orderRepository = FakeOrderRepository(),
    )

    val result = service.create(
        CreateOrderCommand(
            requestId = "req-1",
            sku = "coffee",
            quantity = 3,
        ),
    )

    assertEquals(
        CreateOrderResult.OutOfStock(sku = "coffee", available = 2),
        result,
    )
}
```

## Java 개발자가 자주 하는 오해

첫 번째 오해는 "예외를 전부 sealed class로 바꾸면 좋은가"입니다. 그렇지 않습니다. DB 장애, 네트워크 장애,
serialization 실패, 프로그래밍 오류는 예외가 더 자연스럽습니다. controller advice, retry, transaction rollback,
observability 도구와도 잘 맞습니다.

두 번째 오해는 "공통 `ApiResult<T>` 하나를 만들면 끝나는가"입니다. 모든 use case가 같은 `Success`, `Fail`을
공유하면 오히려 타입 정보가 빈약해집니다. 주문 생성의 실패와 결제 승인 실패는 다른 데이터를 가집니다. 공통
wrapper보다 좁은 sealed result가 더 나을 때가 많습니다.

세 번째 오해는 "`runCatching`으로 try-catch를 모두 대체해도 되는가"입니다. `runCatching`은 편하지만 block에서
던진 `Throwable`을 failure로 감쌉니다. 특정 예외만 잡아야 하는 흐름, coroutine cancellation처럼 다시 던져야
하는 흐름, transaction rollback 정책과 얽힌 흐름에서는 명시적인 `try-catch`가 더 낫습니다.

네 번째 오해는 "controller까지 sealed type을 그대로 노출해도 되는가"입니다. 내부 result와 공개 HTTP 오류
body는 다릅니다. 공개 API에는 Spring의 `ProblemDetail` 같은 표준 형태로 변환하고, 내부 타입 이름이나 구현
세부사항은 숨기는 편이 안전합니다.

## 실무 적용 순서

처음부터 프로젝트 전체의 예외 체계를 바꾸지 않습니다. 한 use case에서 시작합니다.

| 단계 | 할 일 | 검증 |
|---|---|---|
| 1 | 예상 가능한 업무 실패를 2~3개만 고른다 | 실패가 문서가 아니라 타입에 보이는가 |
| 2 | service 반환 타입을 sealed result로 만든다 | 성공/실패 unit test가 모두 있는가 |
| 3 | controller에서 `when`으로 HTTP 응답을 만든다 | 새 subtype 추가 시 변환 코드가 함께 깨지는가 |
| 4 | 예상 밖 장애는 기존 exception handler로 둔다 | 5xx와 4xx가 섞이지 않는가 |
| 5 | 공개 body는 `ProblemDetail`로 통일한다 | 내부 class name, stack trace, ID가 노출되지 않는가 |

작은 기준도 정해 두면 좋습니다.

- 조회 결과가 없을 뿐이면 nullable이나 `findByIdOrNull()`이 충분할 수 있습니다.
- 업무 규칙 위반이 여러 갈래이고 각각 다른 데이터를 들고 있으면 sealed result를 씁니다.
- 외부 시스템 장애처럼 호출자가 복구하기 어려운 실패는 예외로 둡니다.
- HTTP status와 error code는 controller/advice 경계에서 결정합니다.

## 오늘 가져갈 기준

Kotlin sealed class는 예외를 없애는 도구가 아닙니다. **업무적으로 가능한 결과를 타입으로 고정해서 빠뜨리지
않게 만드는 도구**입니다.

Spring Boot 프로젝트에서는 예외, controller advice, ProblemDetail을 계속 씁니다. 다만 service 내부의 예상
가능한 실패까지 모두 예외에 숨기지 말고, 좁은 sealed result로 드러낼 수 있는지 먼저 봅니다. 이 기준만 잡아도
Kotlin 코드는 "짧아진 Java"가 아니라 실패 경계가 더 분명한 서버 코드가 됩니다.
