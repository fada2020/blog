## 결론부터 말하면

Flutter에서 상태 관리를 배울 때 처음부터 모든 값을 전역 store로 밀어 넣으면 오히려 화면이 불안정해집니다.
먼저 **한 위젯 안에서만 쓰는 상태는 `setState()`에 남기고, 여러 화면이 함께 읽는 값만 provider로 올리는 기준**을
세워야 합니다.

Spring Boot 개발자는 상태를 대체로 세 위치에서 봅니다.

- request마다 새로 만들어지는 값
- singleton Bean이 들고 있는 협업 객체
- database나 cache처럼 프로세스 밖에 있는 영속 상태

Flutter도 비슷한 구분이 필요합니다. 다만 서버 요청이 아니라 화면 rebuild가 기준입니다. 어떤 값이 바뀌면 어떤
위젯이 다시 그려져야 하는지부터 정해야 합니다.

## 이번 주 개념

Flutter 공식 문서는 상태를 크게 ephemeral state와 app state로 나눕니다. ephemeral state는 특정 위젯 안에
깔끔하게 갇히는 값입니다. 예를 들어 현재 탭 index, animation 진행률, 열려 있는 accordion 항목처럼 한 화면의
표현에 가까운 값입니다.

반대로 app state는 여러 화면이 함께 읽거나, 로그인 정보처럼 앱 전체 흐름을 바꾸거나, 세션 간 유지하고 싶은
값입니다. 장바구니, 사용자 설정, 인증 상태, 읽은 알림 목록이 여기에 가깝습니다.

| 질문 | `setState()`에 남길 값 | Riverpod provider로 올릴 값 |
|---|---|---|
| 누가 읽는가 | 한 위젯 또는 아주 가까운 자식 | 여러 화면, route, service |
| 사라져도 되는가 | 화면을 닫으면 사라져도 됨 | 화면 이동 후에도 의미가 있음 |
| 테스트 단위 | widget interaction | 상태 전이, repository 연결 |
| Spring 비유 | request handler 안의 local 변수 | 여러 controller가 의존하는 service facade |

공식 문서도 절대 규칙은 없다고 설명합니다. 작은 앱은 `StatefulWidget`과 `setState()`만으로도 충분할 수 있습니다.
중요한 것은 불편해지는 순간을 알아차리는 것입니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서 장바구니를 만든다고 생각해 보겠습니다. Controller가 HTTP 요청을 받고, Service가 장바구니
규칙을 처리하고, Repository가 저장소를 다룹니다.

```java
@Service
class CartService {

    private final CartRepository cartRepository;

    CartService(CartRepository cartRepository) {
        this.cartRepository = cartRepository;
    }

    Cart addItem(long userId, long itemId) {
        Cart cart = cartRepository.findByUserId(userId);
        cart.add(itemId);
        return cartRepository.save(cart);
    }
}
```

Spring에서는 service Bean이 화면을 다시 그리지 않습니다. 변경 결과를 HTTP response로 돌려주면 브라우저나
앱이 다음 화면을 정합니다. Flutter에서는 상태 객체가 바뀌면 그 값을 구독한 위젯이 rebuild됩니다. 그래서
"어느 layer가 상태를 소유하는가"와 "어느 위젯이 rebuild되는가"가 같이 중요해집니다.

## Flutter에서는 무엇이 다른가

Flutter의 선언형 UI는 `UI = f(state)`에 가깝습니다. 버튼을 눌러 Text 위젯을 직접 고치는 방식이 아니라,
상태를 바꾸고 그 상태를 반영한 새 widget tree를 다시 만듭니다.

가장 작은 로컬 상태는 `StatefulWidget`에 남깁니다.

```dart
class QuantityStepper extends StatefulWidget {
  const QuantityStepper({super.key});

  @override
  State<QuantityStepper> createState() => _QuantityStepperState();
}

class _QuantityStepperState extends State<QuantityStepper> {
  int quantity = 1;

  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        IconButton(
          onPressed: quantity == 1
              ? null
              : () => setState(() => quantity -= 1),
          icon: const Icon(Icons.remove),
        ),
        Text('$quantity'),
        IconButton(
          onPressed: () => setState(() => quantity += 1),
          icon: const Icon(Icons.add),
        ),
      ],
    );
  }
}
```

이 값은 stepper 밖에서 몰라도 됩니다. route 이동, 로그인, 장바구니 합계와도 관련이 없습니다. 이런 값을 provider로
빼면 코드는 길어지고 추적할 위치만 늘어납니다.

## 여러 화면이 읽으면 ProviderScope를 둡니다

Riverpod은 provider를 통해 값을 노출하고, widget은 `ref.watch()`로 그 값을 구독합니다. Flutter 앱에서는
provider 상태 저장소를 만들기 위해 앱 상단을 `ProviderScope`로 감쌉니다.

```dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final cartProvider = NotifierProvider<CartNotifier, Cart>(
  CartNotifier.new,
);

class CartNotifier extends Notifier<Cart> {
  @override
  Cart build() => const Cart(items: []);

  void add(Item item) {
    state = state.copyWith(items: [...state.items, item]);
  }
}

void main() {
  runApp(
    const ProviderScope(
      child: ShopApp(),
    ),
  );
}
```

여기서 `CartNotifier`는 Spring의 service와 완전히 같지는 않습니다. service는 주로 행위를 캡슐화하지만,
Riverpod notifier는 현재 state와 state 변경 method를 함께 갖습니다. 즉, "장바구니 규칙"과 "현재 장바구니
snapshot"이 한 경계 안에 있습니다.

## ConsumerWidget은 상태를 읽는 화면입니다

Riverpod 문서는 `StatelessWidget` 대신 `ConsumerWidget`을 쓰면 `build` method에서 `WidgetRef`를 받을 수
있다고 설명합니다. 이 `ref`로 provider를 읽습니다.

```dart
class CartBadge extends ConsumerWidget {
  const CartBadge({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final cart = ref.watch(cartProvider);

    return Badge(
      label: Text('${cart.items.length}'),
      child: const Icon(Icons.shopping_cart),
    );
  }
}
```

`ref.watch(cartProvider)`는 값이 바뀌면 이 widget을 다시 build하게 만듭니다. Spring의 `@Autowired`처럼
한 번 주입받고 끝나는 것이 아닙니다. 더 가까운 비유는 reactive query subscription입니다. 값이 바뀌면 UI가
다시 계산됩니다.

## 화면에서 행위를 호출할 때는 read를 씁니다

상태를 화면에 표시할 때는 `watch`를 씁니다. 버튼 handler처럼 한 번 action만 호출할 때는 notifier를 `read`로
가져옵니다.

```dart
class ProductTile extends ConsumerWidget {
  const ProductTile({
    required this.item,
    super.key,
  });

  final Item item;

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    return ListTile(
      title: Text(item.name),
      trailing: FilledButton(
        onPressed: () {
          ref.read(cartProvider.notifier).add(item);
        },
        child: const Text('Add'),
      ),
    );
  }
}
```

`watch`를 handler 안에서 남용하면 rebuild 의도를 읽기 어려워집니다. 반대로 화면이 실제로 상태를 보여주는데
`read`만 쓰면 변경 후 UI가 갱신되지 않습니다. 기준은 단순합니다.

- 화면에 표시되는 값이면 `watch`
- 이벤트에서 명령만 보내면 `read`
- 상태 변화에 따라 side effect를 실행해야 하면 별도 listener 패턴을 검토

## Provider를 repository 대체물로 만들지 않습니다

Riverpod provider가 있다고 해서 network, database, secure storage 책임까지 한 class에 몰아넣을 필요는
없습니다. 작은 예제에서는 편해 보이지만, 테스트와 재시도 정책이 섞이면 금방 무거워집니다.

```dart
abstract interface class CartRepository {
  Future<Cart> load();
  Future<Cart> save(Cart cart);
}

final cartRepositoryProvider = Provider<CartRepository>(
  (ref) => HttpCartRepository(),
);

final cartProvider = AsyncNotifierProvider<CartController, Cart>(
  CartController.new,
);

class CartController extends AsyncNotifier<Cart> {
  @override
  Future<Cart> build() {
    return ref.watch(cartRepositoryProvider).load();
  }

  Future<void> add(Item item) async {
    final previous = await future;
    final next = previous.copyWith(items: [...previous.items, item]);

    state = const AsyncLoading();
    state = await AsyncValue.guard(() {
      return ref.read(cartRepositoryProvider).save(next);
    });
  }
}
```

이 구조는 Spring Boot의 Controller, Service, Repository와 비슷한 분리감을 줍니다. UI는 provider를 보고,
controller는 state 전이를 맡고, repository는 외부 I/O를 맡습니다.

## 대응 개념 비교

| Spring Boot 관점 | Flutter/Riverpod 관점 | 주의할 점 |
|---|---|---|
| singleton service | provider 또는 notifier | UI rebuild와 연결된다는 점이 다릅니다. |
| request local variable | widget-local state | 화면 밖에서 공유하지 않습니다. |
| `@Autowired` dependency | `ref.watch`, `ref.read` | watch는 구독, read는 즉시 조회에 가깝습니다. |
| repository mock | provider override | 테스트에서 provider별로 대체할 수 있습니다. |
| transaction boundary | async state transition | loading, error, data 상태를 UI에 드러내야 합니다. |

## Java 개발자가 자주 하는 오해

첫째, "service처럼 보이니까 어디서나 호출해도 된다"고 생각하기 쉽습니다. provider는 UI rebuild와 연결되므로
어디서 읽는지가 중요합니다.

둘째, 모든 상태를 app state로 올리려 합니다. 로컬 입력값, 펼침 여부, 일시적인 선택값은 `setState()`가 더
단순합니다.

셋째, async loading과 error를 예외 처리만으로 숨깁니다. 모바일 UI에서는 로딩 중 버튼 비활성화, 실패 메시지,
재시도 버튼이 상태 모델에 포함되어야 합니다.
