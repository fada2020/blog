## 결론부터 말하면

Flutter에서 긴 화면을 만들 때 `Column` 안에 `ListView`를 억지로 끼워 넣기 시작하면 layout과 scroll 상태가 금방 꼬입니다.
`CustomScrollView`와 `Sliver*` 계열은 헤더, 그리드, 리스트, 빈 상태를 **하나의 scroll pipeline** 안에서 조립하게 해 주는
도구입니다.

Spring Boot 개발자에게 비유하면, 여러 servlet filter와 handler가 한 request를 따로 처리하는 것이 아니라 같은 request
chain 안에서 순서대로 동작하는 것과 비슷합니다. 화면 조각은 여러 개지만 scroll offset, 접근성 announcement, lazy build는
하나의 흐름으로 묶입니다.

## 이번 주 개념

공식 `CustomScrollView` 문서는 sliver를 직접 제공해 list, grid, expanding header 같은 custom scroll effect를 만든다고
설명합니다. `ListView`와 `GridView`는 편한 기본값이고, 서로 다른 scrollable 조각을 한 축으로 섞어야 할 때는
`CustomScrollView`가 더 명확합니다.

| Flutter 개념 | 역할 | Spring Boot에 비유하면 |
|---|---|---|
| `CustomScrollView` | sliver들을 하나의 viewport에 배치 | 하나의 request chain |
| `SliverAppBar` | scroll offset에 반응하는 header | 상단 공통 handler 또는 interceptor |
| `SliverList` | lazy list section | paging query 결과를 순차 render |
| `SliverGrid` | lazy grid section | 같은 response 안의 다른 projection |
| `SliverToBoxAdapter` | 일반 box widget을 sliver로 연결 | legacy adapter |
| `PageStorageKey` | scroll 위치 구분 | tab별 cursor 저장 |

## Java/Spring에서는 어떻게 다뤘는가

Spring MVC에서는 요청이 들어오면 filter, interceptor, controller, view rendering이 같은 request lifecycle 안에서 이어집니다.
각 단계가 독립적인 책임을 가져도 request 자체는 하나입니다.

```java
@GetMapping("/orders")
String orders(Model model) {
    model.addAttribute("summary", summaryService.load());
    model.addAttribute("items", orderService.findPage());
    return "orders/index";
}
```

Flutter에서도 화면의 header, summary, list가 각각 component일 수 있습니다. 하지만 각각이 별도의 scrollable이 되면
사용자는 하나의 화면을 보는데 framework는 여러 scroll state를 조정해야 합니다. 그럴 때는 `CustomScrollView` 하나를 두고
각 section을 sliver로 바꾸는 편이 단순합니다.

## Flutter에서는 무엇이 다른가

`Column`은 box layout입니다. 자식에게 남은 공간을 계산해 주지만, 화면 밖에 있는 수천 개 list item을 lazy하게 만들지는
않습니다. `ListView.builder`는 lazy build를 해 주지만 자기 scrollable을 갖습니다. 그래서 다음처럼 중첩하면 `shrinkWrap`,
고정 높이, gesture 충돌 같은 보정이 따라붙습니다.

```dart
Column(
  children: [
    const OrderHeader(),
    Expanded(
      child: ListView.builder(
        itemCount: orders.length,
        itemBuilder: buildOrderTile,
      ),
    ),
  ],
)
```

이 구조가 틀린 것은 아닙니다. 화면이 단순하면 이게 제일 쉽습니다. 다만 header도 scroll과 함께 접히고, summary card 다음에
grid와 list가 이어지고, tab별 scroll 위치를 보존해야 한다면 sliver 구조가 더 자연스럽습니다.

## 최소 실행 예제: 헤더와 리스트를 한 scroll로 묶기

```dart
class OrderFeedPage extends StatelessWidget {
  const OrderFeedPage({super.key, required this.orders});

  final List<Order> orders;

  @override
  Widget build(BuildContext context) {
    return CustomScrollView(
      key: const PageStorageKey<String>('order-feed'),
      slivers: [
        const SliverAppBar(
          pinned: true,
          title: Text('Orders'),
        ),
        const SliverToBoxAdapter(
          child: OrderSummary(),
        ),
        SliverList.builder(
          itemCount: orders.length,
          itemBuilder: (context, index) {
            final order = orders[index];
            return OrderTile(order: order);
          },
        ),
      ],
    );
  }
}
```

핵심은 `CustomScrollView.slivers`에는 일반 `Container`나 `Text`를 바로 넣지 않는다는 점입니다. 일반 box widget은
`SliverToBoxAdapter`로 감싸고, 반복되는 항목은 `SliverList.builder`처럼 sliver가 lazy하게 만들도록 둡니다.

## `SliverList`는 보이는 항목 중심으로 일합니다

공식 `SliverList` 문서는 화면 밖 child가 materialize되지 않기 때문에 scroll offset을 "dead reckoning"으로 계산한다고
설명합니다. 또 child가 화면 밖으로 나가면 element, state, render object가 제거되고 다시 보일 때 재생성될 수 있습니다.

그래서 list item 안에 서버에서 온 좋아요 수, 결제 상태, 선택 상태 같은 중요한 business state를 직접 묶어 두면 위험합니다.
그 값은 repository, state notifier, view model처럼 list item 바깥 source of truth에 둡니다. item 내부 state는 focus,
animation, 펼침 여부처럼 UI 순간 상태에만 남기는 편이 안전합니다.

| 상태 | list item 안에 둬도 되는가 | 이유 |
|---|---|---|
| 텍스트 필드 focus | 가능 | 화면 순간 상태 |
| 서버 주문 상태 | 피함 | scroll out 후 재생성 가능 |
| item 펼침 여부 | 상황에 따라 가능 | 사라져도 되는 UI 상태인지 결정 |
| paging cursor | 피함 | feed 전체의 data state |

## `SliverFixedExtentList`를 생각할 때

모든 item 높이가 같다면 `SliverFixedExtentList`가 더 효율적일 수 있습니다. Flutter 문서는 고정 main-axis extent를 가진 child는
매번 layout으로 높이를 알아낼 필요가 없다고 설명합니다.

```dart
SliverFixedExtentList.builder(
  itemExtent: 72,
  itemCount: orders.length,
  itemBuilder: (context, index) {
    return OrderTile(order: orders[index]);
  },
)
```

다만 실제 업무 앱의 주문 카드처럼 텍스트 줄 수, 상태 badge, 오류 메시지가 달라질 수 있다면 억지로 고정 높이를 잡지 않아도
됩니다. 성능 최적화보다 먼저 "item 높이가 정말 같은가"를 확인합니다.

## 접근성과 scroll 위치도 설계 대상입니다

`CustomScrollView` 문서는 TalkBack과 VoiceOver가 "현재 몇 번째 항목을 보고 있는지" 안내하려면 첫 visible child index,
전체 child 수, visible child 수 같은 정보가 필요하다고 설명합니다. `ListView`는 이런 정보를 자동으로 많이 처리하지만,
custom sliver를 섞으면 semantic index와 child count를 더 의식해야 합니다.

scroll 위치도 마찬가지입니다. 같은 화면에 tab이 있고 각 tab이 feed를 가진다면 `PageStorageKey`처럼 scroll view를 구분할
key를 둡니다. Spring에서 cache key를 대충 잡으면 다른 사용자의 값이 섞이는 것처럼, Flutter에서도 key가 모호하면 tab 전환
후 엉뚱한 scroll 위치가 복원될 수 있습니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 `shrinkWrap: true`가 만능 해결책이라는 생각입니다. 작은 설정 화면에서는 괜찮지만, 긴 list에서는 layout 비용이
커질 수 있습니다. 긴 feed라면 처음부터 sliver로 조립하는 편이 낫습니다.

두 번째 오해는 `CustomScrollView`가 무조건 고급 최적화라는 생각입니다. header 하나와 list 하나뿐이면 `Scaffold`와
`ListView.builder`가 더 읽기 쉽습니다. sliver는 여러 scroll section을 한 축으로 합칠 때 꺼냅니다.

세 번째 오해는 list item state가 영원히 살아 있다고 생각하는 것입니다. sliver child는 화면 밖으로 나가며 사라질 수 있습니다.
업무적으로 잃으면 안 되는 상태는 child subtree 밖에 둡니다.

## 연습 문제

1. 기존 Flutter 화면에서 `Column` 안의 `ListView`, `SingleChildScrollView` 안의 `Column`을 찾습니다.
2. 각 화면이 하나의 scroll axis만 가져도 되는지, 내부 scrollable이 꼭 필요한지 표시합니다.
3. header, summary, list가 한 화면에 있으면 `CustomScrollView`와 `SliverToBoxAdapter`, `SliverList.builder`로 바꿔 봅니다.
4. item 높이가 정말 같다면 `SliverFixedExtentList` 후보인지 검토합니다.
5. tab별 feed가 있으면 `PageStorageKey` 이름이 겹치지 않는지 확인합니다.
