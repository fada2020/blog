## 결론부터 말하면

React Native를 처음 볼 때 가장 먼저 잡아야 하는 개념은 **JSX로 작성한 컴포넌트가 브라우저 DOM이 아니라
Android와 iOS의 네이티브 화면 요소로 연결된다**는 점입니다.

Spring Boot 개발자는 보통 HTTP 요청이 Controller로 들어오고, Service가 값을 만들고, JSON이나 HTML
응답이 반환되는 흐름에 익숙합니다. React Native 앱은 이미 기기 안에서 실행 중입니다. 사용자가 버튼을
누르면 서버 요청이 새로 들어오는 것이 아니라 앱 내부 상태가 바뀌고, React가 필요한 화면을 다시 계산합니다.

이번 글의 목표는 단순합니다.

**React Native의 `View`, `Text`, `Pressable`, `useState`를 Spring Boot 개발자가 읽을 수 있는 첫
화면 모델로 정리합니다.**

## 이번 주 개념

React Native 화면은 React 컴포넌트로 작성합니다. 다만 웹의 `<div>`, `<p>`, `<button>`을 그대로 쓰지
않고 React Native가 제공하는 Core Components를 사용합니다.

```tsx
import { useState } from "react";
import { Pressable, SafeAreaView, StyleSheet, Text, View } from "react-native";

export default function App() {
  const [count, setCount] = useState(0);

  return (
    <SafeAreaView style={styles.screen}>
      <View style={styles.card}>
        <Text style={styles.title}>오늘 처리한 요청</Text>
        <Text style={styles.count}>{count}</Text>
        <Pressable style={styles.button} onPress={() => setCount(count + 1)}>
          <Text style={styles.buttonText}>하나 추가</Text>
        </Pressable>
      </View>
    </SafeAreaView>
  );
}

const styles = StyleSheet.create({
  screen: {
    flex: 1,
    justifyContent: "center",
    padding: 24,
  },
  card: {
    gap: 12,
  },
  title: {
    fontSize: 18,
    fontWeight: "600",
  },
  count: {
    fontSize: 40,
    fontWeight: "700",
  },
  button: {
    alignItems: "center",
    backgroundColor: "#2563eb",
    borderRadius: 8,
    padding: 14,
  },
  buttonText: {
    color: "#ffffff",
    fontWeight: "700",
  },
});
```

이 작은 예제에는 React Native 첫 학습에서 필요한 기준점이 들어 있습니다.

| 코드 | 역할 |
|---|---|
| `SafeAreaView` | 노치와 시스템 영역을 고려해 화면의 안전한 영역을 잡습니다. |
| `View` | 레이아웃 컨테이너입니다. 웹의 `div`와 비슷해 보이지만 네이티브 View로 연결됩니다. |
| `Text` | 문자열을 화면에 표시합니다. 일반 문자열을 `View` 바로 아래에 둘 수 없습니다. |
| `Pressable` | 누르기 상호작용을 감지하는 Core Component입니다. |
| `useState` | 컴포넌트가 직접 관리하는 상태를 둡니다. |
| `StyleSheet.create` | JavaScript 객체로 스타일을 정의합니다. |

## Java/Spring에서는 어떻게 다뤘는가

Spring MVC에서는 화면 또는 API 응답이 요청 단위로 만들어집니다.

```java
@RestController
@RequestMapping("/api/request-counts")
class RequestCountController {

    private final RequestCountService requestCountService;

    @PostMapping
    RequestCountResponse increase() {
        long count = requestCountService.increase();
        return new RequestCountResponse(count);
    }
}
```

이 코드는 사용자가 어떤 동작을 할 때 서버의 Controller가 호출되고, 서버 상태가 바뀌고, 응답 DTO가
돌아오는 구조입니다.

React Native에서는 버튼을 누른다고 항상 서버 Controller가 먼저 호출되지 않습니다. 위 예제의 `count`는
기기 안의 컴포넌트 상태입니다.

```text
사용자 터치
-> onPress 함수 실행
-> setCount로 상태 변경
-> React가 컴포넌트 다시 계산
-> React Native가 네이티브 화면 갱신
```

서버 API가 필요한 순간도 물론 있습니다. 하지만 첫 학습에서는 "화면 상호작용"과 "서버 트랜잭션"을
분리해서 보는 편이 안전합니다. `onPress`는 Spring Controller가 아니라 이벤트 핸들러입니다.

## React Native에서는 무엇이 다른가

React Native는 React의 컴포넌트 모델을 모바일 네이티브 화면에 연결합니다. JSX를 쓰기 때문에 웹 React와
비슷해 보이지만, 렌더링 대상은 브라우저 DOM이 아닙니다.

<Mermaid title="React Native Core Components 렌더링 흐름">
{`flowchart LR
  Code["TSX 컴포넌트"] --> React["React 렌더링"]
  React --> RN["React Native 런타임"]
  RN --> Android["Android View"]
  RN --> IOS["iOS UIView"]

  Press["Pressable onPress"] --> State["컴포넌트 상태 변경"]
  State --> React
`}
</Mermaid>

Spring Boot 개발자 관점에서 가까운 비교는 아래와 같습니다.

| Spring Boot에서 익숙한 것 | React Native에서 먼저 볼 개념 | 주의할 점 |
|---|---|---|
| Controller 메서드 | 이벤트 핸들러 `onPress` | HTTP 요청 진입점이 아닙니다. |
| DTO 필드 | component props | 부모가 자식에게 내려주는 읽기 입력입니다. |
| Service state | component state 또는 앱 상태 | UI 상태와 서버 상태를 섞지 않습니다. |
| HTML template fragment | React component | DOM 대신 네이티브 View 계층으로 연결됩니다. |
| CSS 파일 | `StyleSheet`와 style prop | CSS 전체 문법이 아니라 React Native 스타일 모델입니다. |
| 서버 validation | 입력 핸들러와 API 경계 validation | 로컬 검증과 서버 검증의 책임을 나눠야 합니다. |

## Core Components부터 시작하는 이유

React Native의 Core Components는 앱 화면을 만드는 기본 단위입니다. 처음부터 네이티브 모듈, 빌드 설정,
플랫폼별 브리지까지 들어가면 학습 범위가 너무 넓어집니다.

먼저 아래 네 가지를 익히면 충분합니다.

| Core Component | 처음 볼 때의 역할 |
|---|---|
| `View` | 화면을 나누고 배치하는 컨테이너입니다. |
| `Text` | 글자를 표시하는 전용 컴포넌트입니다. |
| `Pressable` | 누르기, 길게 누르기 같은 터치 상호작용을 다룹니다. |
| `FlatList` | 많은 항목을 효율적으로 렌더링할 때 사용합니다. |

웹 React를 조금 알고 있다면 `View`를 `div`처럼 읽고 싶어집니다. 첫 이해에는 도움이 되지만 완전히 같은
개념은 아닙니다. React Native의 `View`는 플랫폼별 네이티브 View로 이어지고, 텍스트 처리, 접근성,
터치 피드백, 레이아웃 제약이 웹과 다릅니다.

## props와 state를 구분합니다

React Native 컴포넌트의 입력은 크게 props와 state로 나눌 수 있습니다.

```tsx
type RequestSummaryProps = {
  title: string;
  count: number;
};

function RequestSummary({ title, count }: RequestSummaryProps) {
  return (
    <View>
      <Text>{title}</Text>
      <Text>{count}</Text>
    </View>
  );
}
```

`title`과 `count`는 부모가 내려준 props입니다. 이 컴포넌트가 직접 바꾸지 않습니다. Java record나 응답
DTO처럼 읽기 입력으로 받아 화면에 표현한다고 보면 이해하기 쉽습니다.

반대로 컴포넌트 안에서 직접 바뀌는 값은 state로 둡니다.

```tsx
function CounterButton() {
  const [count, setCount] = useState(0);

  return (
    <Pressable onPress={() => setCount((current) => current + 1)}>
      <Text>count: {count}</Text>
    </Pressable>
  );
}
```

`setCount`는 데이터베이스 commit이 아닙니다. "다음 화면 계산에 사용할 값이 바뀌었다"는 React 상태
갱신입니다. 저장이 필요한 값이라면 별도의 API 호출과 실패 처리, 재시도 정책이 필요합니다.

## 최소 실행 예제

공식 문서는 React Native Framework를 사용하는 경로와, 직접 네이티브 프로젝트를 관리하는 경로를 나눠
설명합니다. 처음 실습은 프로젝트 생성 도구로 시작하고, Android Studio나 Xcode 설정이 필요한 경우 공식
환경 설정 문서를 따라가는 편이 좋습니다.

```bash
npx @react-native-community/cli@latest init RnFirstStep
cd RnFirstStep
npm run android
```

macOS에서 iOS까지 확인하려면 Xcode와 CocoaPods 환경이 필요할 수 있습니다.

```bash
npm run ios
```

실습 목표는 빌드 도구를 깊게 파는 것이 아닙니다. `App.tsx`에서 아래 세 가지를 직접 바꿔 보면 됩니다.

1. `Text` 문구를 바꿉니다.
2. `Pressable`을 눌렀을 때 숫자가 증가하게 만듭니다.
3. `StyleSheet`의 `padding`, `fontSize`, `backgroundColor`를 바꿔 화면 변화를 확인합니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 `onPress`에서 바로 복잡한 서버 업무를 모두 처리하려는 것입니다. 모바일 화면의 이벤트
핸들러는 사용자 입력을 받아 UI 상태를 바꾸거나 API 호출을 시작하는 곳입니다. 서버 트랜잭션 경계,
권한 검사, 영속성 규칙은 여전히 서버 API가 책임져야 합니다.

두 번째 오해는 `View` 안에 아무 문자열이나 둘 수 있다고 생각하는 것입니다. React Native에서는 텍스트를
표시할 때 `Text` 컴포넌트를 사용해야 합니다. 이 제약은 처음에는 불편하지만, 모바일 접근성과 플랫폼별
텍스트 렌더링을 명확히 다루게 해 줍니다.

세 번째 오해는 스타일을 CSS와 동일하게 보는 것입니다. React Native 스타일은 JavaScript 객체이며,
레이아웃은 기본적으로 Flexbox 모델을 사용합니다. 다만 웹 CSS의 모든 속성이 그대로 동작하지는 않습니다.

네 번째 오해는 로컬 state를 서버의 진실 공급원처럼 다루는 것입니다. `useState`는 화면을 다시 계산하기
위한 값입니다. 주문 생성, 결제, 권한 변경처럼 서버가 최종 판단해야 하는 값은 API 응답과 동기화해야 합니다.

## 연습 문제

아래 연습은 서버 코드를 작성하지 않고 React Native 화면 감각만 익히는 데 초점을 둡니다.

1. `RequestSummary` 컴포넌트를 만들고 `title`, `count`, `status`를 props로 받게 해 보세요.
2. `Pressable`을 눌렀을 때 `count`가 1씩 증가하는 `CounterButton`을 만들어 보세요.
3. `status`가 `"ERROR"`일 때만 빨간색 문구를 표시하도록 조건부 렌더링을 추가해 보세요.
4. 서버 API 호출이 필요하다고 가정하고, `onPress` 안에서 바로 저장하지 않고 `submitCount` 함수로 책임을
   분리해 보세요.

## 마무리

React Native 첫걸음에서 중요한 것은 빌드 도구 이름을 모두 외우는 것이 아니라, 화면을 읽는 단위를 바꾸는
것입니다.

Spring Boot에서는 요청, Controller, Service, Repository의 흐름을 먼저 잡습니다. React Native에서는
컴포넌트, props, state, Core Components, 이벤트 핸들러의 흐름을 먼저 잡아야 합니다.

이 기준이 잡히면 다음 단계에서 목록 렌더링, 네비게이션, 서버 API 호출, 플랫폼별 코드 분리로 확장해도
각 코드가 어느 책임을 맡는지 덜 헷갈립니다.
