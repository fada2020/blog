> **검증 범위**
>
> 2026년 9월 3일에 AWS S3 presigned URL 공식 문서, Spring Boot 공식 문서, Spring Framework
> Error Responses 문서를 확인했습니다. Spring Boot 기준 안정 버전은 `4.1.1`입니다. 실제 업무일지의
> 서비스명, 도메인, 저장소, 계정, 사용자 식별자는 공개 글에서 제거하고 공개 자료 다운로드 설계 원리만
> 일반화했습니다.

## 결론부터 말하면

공개 파일 다운로드를 만들 때 가장 먼저 나눠야 할 것은 **식별자와 권한**입니다. 관리자는 오래 유지되는 공개
키로 자료를 관리하고, 사용자는 서버가 방금 발급한 짧은 presigned URL로 파일을 받습니다. 이 둘을 섞으면
운영이 어려워집니다.

이번 작업에서 배운 점은 세 가지였습니다.

- 공개 키는 "어떤 자료를 요청하는가"를 나타내는 영구 식별자입니다.
- S3 presigned URL은 "언제까지, 어떤 객체를, 어떤 권한으로 받을 수 있는가"를 담은 짧은 bearer token입니다.
- 기존 앱 호환 API와 새 자료 관리 API는 같은 저장 구조를 보되, 응답 계약은 각 클라이언트에 맞게 유지해야 합니다.

## 문제가 된 모양

처음에는 사용자에게 제공되는 안내 파일이 별도 고정 경로처럼 다뤄졌습니다. 관리 콘솔에는 그 파일을 바꾸는
명확한 화면이 없고, 앱 API는 기존 주소를 만들어 주는 방식이었습니다. 이 구조에서는 파일을 교체하거나 유형을
늘릴 때마다 코드와 운영 절차가 같이 흔들립니다.

필요한 것은 특정 파일 하나를 특별 취급하는 코드가 아니었습니다. 관리자가 자료 유형을 만들고, 각 자료를 공개
또는 비공개로 전환하고, 파일을 교체하고, 앱은 공개 키나 자료 유형 코드로 최신 공개 파일을 받을 수 있는 구조가
필요했습니다.

| 요구 | 잘못 섞기 쉬운 것 | 분리한 기준 |
|---|---|---|
| 자료 관리 | 파일 경로와 공개 상태 | 자료 metadata, 공개 여부, 유형 |
| 앱 다운로드 | 고정 URL과 저장소 객체 | 서버 API가 짧은 URL 발급 |
| 기존 앱 호환 | 새 관리 모델로 강제 전환 | 기존 endpoint 계약 유지 |
| 파일 교체 | 새 row 계속 추가 | 같은 자료의 metadata와 객체 교체 분리 |

## 기존 설계의 한계

고정 다운로드 주소는 단순합니다. 하지만 단순한 만큼 운영 제어가 약합니다.

```text
앱
-> 기존 다운로드 API
-> 고정 파일 URL 반환
-> 파일 저장소에서 다운로드
```

이 방식에서는 "이 파일이 지금 공개 상태인가", "최근 교체 파일인가", "어떤 자료 유형인가", "누가 마지막으로
바꿨는가" 같은 질문을 API가 잘 대답하지 못합니다. 파일을 비공개로 바꿔도 이미 노출된 URL이 계속 살아 있다면
관리 콘솔의 공개 전환은 믿을 수 없는 상태가 됩니다.

S3 객체 자체를 public으로 열어 두는 것도 답이 아닙니다. 공개 여부는 애플리케이션의 업무 상태이고, 객체 저장소의
bucket policy는 저장소 권한입니다. 업무 상태를 바꿀 때마다 bucket policy나 object ACL을 건드리는 구조는
작은 관리 기능치고 너무 큰 권한을 요구합니다.

## 선택한 설계

선택한 구조는 자료 metadata를 애플리케이션 DB에서 관리하고, 실제 파일 객체는 비공개로 유지하는 방식입니다.
다운로드 순간에만 서버가 짧은 presigned URL을 발급합니다.

<Mermaid title="공개 자료 다운로드 설계">
{`flowchart TD
  Admin["관리 콘솔<br/>자료 유형과 공개 상태 관리"] --> Metadata["자료 metadata<br/>type, public key, visible"]
  Metadata --> PrivateObject["비공개 S3 객체"]

  App["앱 또는 웹 클라이언트"] --> PublicApi["공개 다운로드 API"]
  PublicApi --> Check["공개 상태와 삭제 여부 확인"]
  Check --> Resolve["public key 또는 type code로 대상 객체 결정"]
  Resolve --> Presign["짧은 presigned URL 발급"]
  Presign --> Download["클라이언트가 S3에서 다운로드"]

  Check -->|비공개 또는 없음| NotFound["404 또는 403 계열 응답"]
`}
</Mermaid>

서버 API의 책임은 네 가지입니다.

1. 공개 키나 자료 유형 코드가 가리키는 자료를 찾습니다.
2. 삭제되지 않았고 공개 상태인 자료만 통과시킵니다.
3. 저장소 객체 key를 직접 노출하지 않고 presigned URL을 생성합니다.
4. 기존 앱이 기대하는 응답 형태는 가능한 유지합니다.

AWS S3 공식 문서 기준 presigned URL은 bucket policy를 바꾸지 않고 객체에 time-limited access를 줄 수 있습니다.
또한 URL을 가진 사람이 만료 전까지 접근할 수 있으므로 bearer token처럼 보호해야 합니다. 따라서 이 URL을 영구
식별자로 쓰면 안 됩니다.

## 구현에서 조심한 점

가장 중요한 결정은 공개 키를 사람이 직접 입력하지 않게 한 것입니다. 공개 키는 자료 유형, 프로젝트 또는 소유
범위, 무작위 값을 조합해 서버가 만들고, 관리자는 복사해서 앱이나 문서에 전달하기만 합니다. 사람이 입력하는
문자열을 신뢰하면 중복, 오타, 비슷한 접두어 충돌이 생깁니다.

자료 유형 조회도 접두어 문자열 검색에 맡기지 않았습니다. `manual`과 `manual-extra`처럼 비슷한 코드가 있을 때
문자열 prefix로 최신 파일을 찾으면 다른 유형이 섞일 수 있습니다. 자료 row는 자료 유형 row와 관계로 연결하고,
공개 다운로드는 관계 기준으로 최신 공개 자료를 고릅니다.

```text
asset_type.code
-> asset.asset_type_id
-> is_public = true
-> deleted_at is null
-> latest updated asset
-> presigned GET URL
```

이 흐름은 코드보다 데이터 모델이 중요합니다. 공개 다운로드 API가 단순해지려면 관리 데이터가 먼저 정규화되어야
합니다.

## 호환 API는 새 모델 위에 얹습니다

기존 앱이 이미 호출하는 다운로드 API가 있다면, 새 endpoint만 추가해서는 충분하지 않습니다. 구버전 앱은 계속
기존 endpoint를 호출합니다. 그래서 기존 API는 새 관리 자료를 먼저 찾아 보고, 자료가 없을 때만 예전 대체 경로를
반환하는 식으로 점진적으로 옮기는 편이 안전합니다.

| API | 역할 | 운영 기준 |
|---|---|---|
| 새 공개 자료 API | 공개 키 또는 자료 유형 코드로 다운로드 | 공개 상태, 삭제 여부, 최신 자료 검증 |
| 기존 호환 API | 구버전 앱 다운로드 계약 유지 | 새 관리 자료 우선, 없으면 기존 fallback |
| 관리자 API | 자료 유형과 자료 CRUD | 파일 교체, 공개 전환, 삭제, 감사 정보 |

이때 "기존 API가 살아 있다"와 "새 관리 기능이 운영에서 쓰인다"는 다른 상태입니다. 빌드와 테스트가 통과해도,
운영 DB migration, 관리자 화면 배포, 실제 파일 업로드, 공개 전환, 다운로드 만료 확인은 별도 완료 조건입니다.

## 오류 응답은 숨기되, 운영자는 구분할 수 있게 둡니다

공개 다운로드 API는 존재하지 않는 키, 비공개 자료, 삭제된 자료를 너무 자세히 말하지 않는 편이 안전합니다.
외부 사용자에게는 404 또는 접근 불가 응답이면 충분한 경우가 많습니다. 하지만 운영자 로그에서는 원인을 구분해야
합니다.

Spring Framework Error Responses 문서는 `ProblemDetail`과 `ErrorResponse`를 통해 RFC 9457 형태의 오류 응답을
렌더링할 수 있다고 설명합니다. 외부 응답은 단순하게 유지하되, 서버 로그와 감사 이벤트에는 다음처럼 분리된
이유를 남깁니다.

| 내부 원인 | 외부 응답 | 운영 로그 |
|---|---|---|
| 공개 키 없음 | 404 | `asset_not_found` |
| 비공개 전환됨 | 404 또는 403 | `asset_not_public` |
| 삭제됨 | 404 | `asset_deleted` |
| S3 서명 실패 | 500 | `presign_failed` |
| 권한 부족 | 500 또는 503 | `storage_permission_denied` |

사용자에게 내부 구조를 노출하지 않으면서도 운영자는 무엇을 고쳐야 하는지 알아야 합니다.

## 검증은 네 층으로 나눕니다

이 기능은 단위 테스트 하나로 끝나지 않습니다. 상태가 네 군데에 나뉘어 있기 때문입니다.

```text
DB metadata
-> 서버 API 응답
-> S3 presigned URL
-> 클라이언트 다운로드 동작
```

최소 검증은 아래 순서가 적절했습니다.

- 공개 자료는 공개 키로 presigned URL을 받습니다.
- 비공개 자료와 삭제된 자료는 다운로드 URL을 받지 못합니다.
- 자료 유형 코드로 요청하면 그 유형의 최신 공개 자료가 선택됩니다.
- 기존 호환 API는 관리 자료가 있으면 새 자료를, 없으면 기존 fallback을 반환합니다.
- presigned URL은 짧은 만료 시간으로 발급되고, 만료 후 재사용을 운영 환경에서 확인합니다.
- 관리자 화면에서는 등록, 수정, 파일 교체, 공개 전환, 삭제가 실제 파일로 동작해야 합니다.

AWS 문서 기준 presigned URL은 생성할 때 지정한 기간 동안 유효하지만, 임시 credential을 사용했다면 credential
만료가 더 빠를 수 있습니다. 따라서 "10분 URL을 만들었다"만으로 충분하지 않고, 실제 실행 role과 credential
수명도 함께 봐야 합니다.

## 실무 체크리스트

- [ ] 공개 키는 사람이 입력하지 않고 서버가 생성한다.
- [ ] 공개 자료 조회는 문자열 prefix가 아니라 자료 유형 관계로 찾는다.
- [ ] S3 객체는 비공개로 두고 서버가 짧은 GET URL을 발급한다.
- [ ] 공개 키와 presigned URL을 같은 캐시 수명으로 다루지 않는다.
- [ ] 기존 앱 endpoint는 새 관리 자료를 우선 사용하되 fallback 계약을 유지한다.
- [ ] 비공개 전환, 삭제, 파일 교체 후 새 다운로드 요청이 기대대로 막히거나 갱신되는지 확인한다.
- [ ] 배포 완료, DB migration 완료, 실제 운영 다운로드 확인을 서로 다른 상태로 기록한다.

## 배운 점

공개 파일 기능은 파일 업로드 UI보다 수명주기 설계가 더 중요했습니다. 사용자가 보는 것은 다운로드 버튼 하나지만,
운영자는 자료 유형, 공개 상태, 파일 교체, 만료 URL, 기존 앱 호환, 감사 로그를 함께 봐야 합니다.

Spring Boot 관점에서 이 문제는 익숙한 API 경계 문제입니다. controller가 저장소 객체를 바로 노출하지 않고,
service가 업무 상태를 확인하고, storage adapter가 짧은 권한을 발급합니다. 그렇게 나누면 "자료는 공개지만 객체는
비공개"라는 요구를 코드와 운영 절차 모두에서 설명할 수 있습니다.
