## 이번 주 개념

목록의 순서를 바꾸면 체크 표시도 같은 항목을 따라가야 합니다. 하지만 자식 위젯이 가진 상태는
데이터 ID를 자동으로 알지 못합니다. 이번에는 **화면 위치와 항목 식별을 분리**합니다.
[지난 글](/blog/posts/flutter-value-notifier-list-boundary-2026-11-09/)이 변경 알림을 다뤘다면,
이번 글은 새 목록이 화면에 전달된 뒤 어떤 State를 재사용할지 다룹니다.

## Java와 Spring에서의 대응 개념

JPA 엔티티의 ID는 정렬 순서가 바뀌어도 같은 레코드를 가리킵니다. 반면 목록의 인덱스 0은 정렬에 따라
다른 레코드가 됩니다. Flutter Key도 이 구분을 이해하는 데 도움이 되지만, DB 기본키나 영속성 컨텍스트와
동일한 장치는 아닙니다. 서버 DTO에 ID가 있어도 화면 위젯의 Key로 사용하지 않으면 연결이 자동 생성되지 않습니다.

| 익숙한 개념 | 화면에서의 역할 |
|---|---|
| 엔티티 ID | 항목의 안정적인 식별값 |
| 정렬된 목록의 인덱스 | 현재 표시 위치 |
| 화면의 임시 입력 | 자식 State의 체크 값 |

## Flutter에서는 무엇이 다른가

[Widget.key 공식 문서](https://api.flutter.dev/flutter/widgets/Widget/key.html)에 따르면
새 위젯과 이전 위젯의 타입과 Key가 같을 때 기존 Element를 갱신할 수 있습니다.
[ValueKey](https://api.flutter.dev/flutter/foundation/ValueKey-class.html)는 값의 동등성으로 식별합니다.
같은 부모 아래에서 순서를 바꾸는 이번 예제는 항목 ID를 Key로 사용합니다.

## 최소 실행 예제

빈 Flutter 앱의 lib/main.dart에 넣습니다. 외부 패키지나 서버는 필요 없습니다.
use_keys를 false로 바꿔 실패 동작도 비교할 수 있습니다.
직접 정의한 변수와 함수는 스네이크케이스를 쓰고 프레임워크 override 이름은 유지했습니다.

```dart
import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: ItemsPage()));

class ItemsPage extends StatefulWidget {
  const ItemsPage({super.key, this.use_keys = true});
  final bool use_keys;
  @override
  State<ItemsPage> createState() => _ItemsPageState();
}

class _ItemsPageState extends State<ItemsPage> {
  List<String> _item_ids = ['A', 'B'];
  void _reverse_items() => setState(() {
    _item_ids = _item_ids.reversed.toList();
  });
  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(title: const Text('목록 식별 실습')),
    body: Column(children: [
      ElevatedButton(onPressed: _reverse_items, child: const Text('뒤집기')),
      for (final item_id in _item_ids)
        ItemRow(
          key: widget.use_keys ? ValueKey(item_id) : null,
          item_id: item_id,
        ),
    ]),
  );
}

class ItemRow extends StatefulWidget {
  const ItemRow({super.key, required this.item_id});
  final String item_id;
  @override
  State<ItemRow> createState() => _ItemRowState();
}

class _ItemRowState extends State<ItemRow> {
  bool _checked = false;
  @override
  Widget build(BuildContext context) => CheckboxListTile(
    title: Text(widget.item_id),
    value: _checked,
    onChanged: (value) => setState(() => _checked = value ?? false),
  );
}
```

처음 A를 체크하고 뒤집기를 누릅니다. 정상 예제에서는 B는 미선택, A는 선택 상태입니다.
Key를 끄면 같은 타입의 자식 상태가 위치를 따라 재사용되어 첫 번째 B가 선택되어 보입니다.
화면을 다시 뒤집어도 ID에 연결한 상태는 유지됩니다. API 요청·응답, 상태 코드, 시간 형식, DB 저장값은 변경 없음입니다.

## 오해하기 쉬운 경계

인덱스를 Key로 쓰면 재정렬 뒤에도 위치를 식별하므로 이 문제를 해결하지 못합니다. 매 build마다
새 UniqueKey를 만들면 상태를 보존할 안정적인 연결도 사라집니다. 표시 이름은 중복되거나 수정될 수 있어
일반적인 서비스에서는 고유하고 안정적인 데이터 ID를 선택하는 편이 좋습니다.

Key는 비교되는 자식 수준에 붙여야 합니다. 예제의 ItemRow를 Padding으로 감쌀 경우에는 반복되는
바깥 Padding에 Key를 옮겨 부모가 그 자식들을 구분하도록 합니다. 임의의 깊이에 Key를 넣는 것으로
전체 트리의 재사용 정책이 해결되지는 않습니다.

이 체크 값은 화면 수명의 로컬 상태입니다. 위젯 제거, 앱 재시작, 서버 동기화까지 보존하지 않습니다.
선택을 도메인 상태로 유지해야 한다면 부모나 상태 저장소에서 ID별 선택값을 관리해야 합니다.
GlobalKey를 항목마다 도입하는 것도 기본 해법으로 삼지 않습니다. 다른 부모로 이동하는 경우와
같은 부모 안에서 정렬만 바꾸는 경우는 요구사항이 다릅니다.

## 연습과 검증

1. use_keys를 true와 false로 각각 실행하고 A 선택 뒤 재정렬 결과를 기록합니다.
2. 인덱스를 ValueKey에 넣으면 왜 선택 항목이 잘못 연결되는지 설명합니다.
3. 반복 자식을 Padding으로 감싼 뒤 Key 위치를 바깥과 안쪽으로 나누어 비교합니다.
4. 항목을 제거했다가 다시 넣을 때도 선택을 보존하려면 상태를 어디에 둘지 설계합니다.

독립 프로젝트에서 정적 분석은 진단 없이 통과했고 두 widget 테스트가 통과했습니다.
Key 유무에 따른 체크 상태, 두 번 뒤집은 결과, 화면 제거 시 예외 여부를 확인했습니다.
Padding 변형과 실제 Android/iOS 기기 동작, 대규모 목록 성능은 이번 실행 검증 범위에 포함하지 않았습니다.
