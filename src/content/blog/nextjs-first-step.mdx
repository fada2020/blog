## 결론부터 말하면

Next.js는 React로 화면을 만드는 방법에 서버 렌더링, 라우팅, 데이터 조회와 배포 규칙을
더한 프레임워크입니다. Spring Boot 개발자에게 낯선 지점은 문법보다 **한 파일이
라우트이면서 서버에서 실행되는 UI가 될 수 있다는 점**입니다.

Spring MVC에서는 요청을 Controller가 받고 Service가 업무 로직을 수행한 뒤 DTO를
반환합니다. Next.js App Router에서는 URL에 대응하는 `page.tsx`가 기본 진입점이며,
이 파일은 기본적으로 Server Component입니다. 서버에서 데이터를 가져와 HTML을 만들고,
브라우저 상호작용이 필요한 작은 부분만 Client Component로 분리합니다.

이번 글에서는 이 차이를 사용자 목록 하나로 확인합니다.

## React와 Next.js는 무엇이 다른가

React는 UI를 컴포넌트로 구성하는 라이브러리입니다. 라우팅, 서버 렌더링, 빌드 방식과
데이터 조회 규칙은 별도로 선택해야 합니다.

Next.js는 그 선택을 하나의 애플리케이션 구조로 묶습니다.

| 질문 | React만 사용할 때 | Next.js App Router |
|---|---|---|
| URL과 화면은 어떻게 연결하는가 | 라우터를 별도로 선택 | `app` 디렉터리 구조로 연결 |
| 첫 HTML은 어디서 만드는가 | 구성에 따라 다름 | Server Component에서 만들 수 있음 |
| 서버 데이터는 어디서 조회하는가 | 별도 API 계층과 상태 관리 구성 | Server Component에서 직접 `await` 가능 |
| 브라우저 상호작용은 어떻게 넣는가 | 일반 React Component | `"use client"` 경계 안의 Client Component |
| 로딩·오류 UI는 어떻게 구성하는가 | 직접 규칙을 정함 | `loading.tsx`, `error.tsx` 파일 규칙 제공 |

Next.js를 “React에 라우터를 붙인 것”으로만 이해하면 Server Component의 역할을
놓치기 쉽습니다. 반대로 “프론트엔드용 Spring Boot”라고 생각하면 서버의 책임 범위를
과대평가하게 됩니다. Next.js는 UI를 중심으로 서버와 브라우저의 실행 경계를 설계하는
프레임워크에 가깝습니다.

## Spring MVC 요청 흐름과 비교하기

먼저 익숙한 Spring MVC 흐름을 단순화해 보겠습니다.

```text
GET /api/v1/users
-> UserController
-> UserService
-> UserRepository
-> ApiResponse<List<UserResponse>>
```

Next.js에서 `/users` 화면을 그리는 흐름은 다음과 같습니다.

```text
GET /users
-> app/users/page.tsx
-> Spring Boot API 호출
-> UserList 렌더링
-> HTML과 RSC Payload 응답
```

<Mermaid title="Spring MVC와 Next.js App Router 요청 흐름 비교">
{`flowchart LR
  Browser["브라우저 /users 요청"] --> Page["app/users/page.tsx<br/>Server Component"]
  Page --> Api["Spring Boot<br/>GET /api/v1/users"]
  Api --> Controller["UserController"]
  Controller --> Service["UserService"]
  Service --> Repository["UserRepository"]
  Repository --> Service
  Service --> Controller
  Controller --> Page
  Page --> Html["HTML + RSC Payload"]
  Html --> Browser
  Browser --> Client["필요한 부분만<br/>Client Component 활성화"]`}
</Mermaid>

여기서 `page.tsx`를 Spring Controller와 완전히 같은 것으로 보면 안 됩니다.
Controller는 HTTP API 계약과 업무 흐름의 진입점을 담당합니다. `page.tsx`는 특정 URL의
UI를 조립하고 렌더링하는 진입점입니다. 인증 규칙, 트랜잭션과 핵심 업무 로직은 기존
Spring Service에 남겨 두는 편이 책임이 분명합니다.

## App Router의 최소 구조

[공식 설치 문서](https://nextjs.org/docs/app/getting-started/installation)에 따르면
현재 `create-next-app` 권장 기본값은 TypeScript, App Router, Tailwind CSS, ESLint와
Turbopack을 포함합니다. 최소 Node.js 버전은 20.9입니다.

```bash
npx create-next-app@latest next-study
cd next-study
npm run dev
```

처음에는 아래 네 파일의 역할부터 구분하면 됩니다.

```text
app/
├── layout.tsx       # 전체 화면이 공유하는 필수 레이아웃
├── page.tsx         # / 경로
└── users/
    ├── page.tsx     # /users 경로
    └── loading.tsx  # /users 로딩 UI
```

`app/users/page.tsx`가 존재하면 `/users` 경로가 만들어집니다. 별도 라우팅 테이블에
`"/users" -> UserPage`를 등록하지 않습니다. 디렉터리 구조 자체가 라우팅 계약입니다.

`layout.tsx`는 하위 페이지 사이에서 공유할 UI를 정의합니다. Spring MVC의
`HandlerInterceptor`나 Servlet Filter와 같은 요청 가로채기 계층은 아닙니다. 화면의
공통 골격을 중첩해서 구성하는 UI 개념입니다.

## Server Component로 사용자 목록 가져오기

다음 예제는 Spring Boot가 `GET /api/v1/users`를 제공하고, Next.js가 그 결과를 서버에서
조회해 목록으로 렌더링하는 상황입니다.

```tsx
// app/users/page.tsx
type User = {
  id: number
  name: string
  email: string
}

type ApiResponse<T> = {
  data: T
}

async function getUsers(): Promise<User[]> {
  const response = await fetch(
    `${process.env.API_BASE_URL}/api/v1/users`,
    { cache: 'no-store' },
  )

  if (!response.ok) {
    throw new Error(`사용자 조회 실패: ${response.status}`)
  }

  const body: ApiResponse<User[]> = await response.json()
  return body.data
}

export default async function UsersPage() {
  const users = await getUsers()

  return (
    <main>
      <h1>사용자</h1>
      <ul>
        {users.map((user) => (
          <li key={user.id}>
            <strong>{user.name}</strong>
            <span>{user.email}</span>
          </li>
        ))}
      </ul>
    </main>
  )
}
```

이 파일에는 `"use client"`가 없습니다. App Router의 페이지와 레이아웃은 기본적으로
Server Component이므로 서버에서 `await fetch(...)`를 실행할 수 있습니다.
`API_BASE_URL`도 브라우저 번들에 노출되지 않습니다.

예제에서는 동작을 분명히 하기 위해 `cache: 'no-store'`를 명시했습니다. 캐시 정책은
데이터 성격에 따라 별도로 결정해야 하며, “Server Component니까 자동으로 항상 최신”
또는 “항상 캐시된다”고 가정하면 안 됩니다.

## Client Component는 필요한 곳에만 둡니다

사용자 목록에서 검색어를 입력할 때마다 이미 받은 목록을 필터링하려면 브라우저 상태와
이벤트가 필요합니다. 이 부분만 Client Component로 만듭니다.

```tsx
// app/users/user-filter.tsx
'use client'

import { useState } from 'react'

type User = {
  id: number
  name: string
}

export function UserFilter({ users }: { users: User[] }) {
  const [keyword, setKeyword] = useState('')
  const filteredUsers = users.filter((user) =>
    user.name.toLowerCase().includes(keyword.toLowerCase()),
  )

  return (
    <>
      <input
        value={keyword}
        onChange={(event) => setKeyword(event.target.value)}
        placeholder="이름 검색"
      />
      <ul>
        {filteredUsers.map((user) => (
          <li key={user.id}>{user.name}</li>
        ))}
      </ul>
    </>
  )
}
```

공식 문서가 설명하듯 Client Component가 필요한 대표적인 경우는 다음과 같습니다.

- `useState`, `useEffect` 같은 상태와 생명주기
- `onClick`, `onChange` 같은 이벤트 처리
- `window`, `localStorage`, 위치 정보 같은 브라우저 API

`"use client"`는 “이 컴포넌트만 브라우저에서 실행한다”는 단순 표시보다
**클라이언트 모듈 그래프의 경계**에 가깝습니다. 해당 파일이 가져오는 모듈과 하위
컴포넌트도 클라이언트 번들에 포함될 수 있으므로, 페이지 최상단에 습관적으로 붙이면
서버 렌더링의 장점을 줄이게 됩니다.

## Spring Boot 개발자가 자주 하는 오해

### `page.tsx`가 Controller를 대체한다

화면 요청의 진입점이라는 점은 비슷하지만 책임은 다릅니다. 트랜잭션, 권한 판정과 핵심
업무 규칙을 `page.tsx`로 옮기지 않습니다. Next.js가 Spring API를 호출하는 구조라면
도메인 책임은 계속 Spring에 두고, Next.js는 화면에 필요한 데이터를 조합합니다.

### 서버에서 실행되면 모두 백엔드 코드다

Server Component는 서버에서 실행되지만 결과물의 목적은 UI입니다. DB에 직접 접근할 수도
있다는 사실과 그렇게 해야 한다는 판단은 별개입니다. 이미 Spring Boot가 업무 API의
소유자라면 그 계약을 재사용하는 편이 중복 규칙을 줄입니다.

### 모든 컴포넌트에 `"use client"`가 필요하다

App Router에서는 반대입니다. 먼저 Server Component로 두고, 상태·이벤트·브라우저 API가
필요한 가장 작은 경계에만 `"use client"`를 추가합니다.

### 폴더 구조는 파일 정리 방식일 뿐이다

App Router에서 폴더와 예약 파일 이름은 URL, 레이아웃, 로딩과 오류 경계를 정의합니다.
Spring의 패키지 정리보다 런타임 동작에 직접적인 영향을 줍니다.

## 직접 해볼 연습

1. `create-next-app@latest`로 프로젝트를 만들고 `/users` 페이지를 추가합니다.
2. 처음에는 고정 배열로 사용자 세 명을 Server Component에서 렌더링합니다.
3. `UserFilter`를 Client Component로 분리해 이름 검색을 추가합니다.
4. `app/users/loading.tsx`를 만들고, 데이터 조회에 의도적인 지연을 넣어 로딩 UI를
   확인합니다.
5. 최상위 `page.tsx`에 `"use client"`를 붙였을 때와 작은 검색 컴포넌트에만 붙였을 때
   브라우저로 전달되는 코드의 경계가 어떻게 달라지는지 생각해 봅니다.
