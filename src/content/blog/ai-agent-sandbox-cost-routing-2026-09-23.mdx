> **검증 범위**
>
> 2026년 9월 23일 09시 KST에 OpenAI Agents API와 Codex 안전 운영 글, Anthropic Claude Code usage 문서,
> GitHub third-party coding agents 문서, Google Gemini CLI 최신 안정 릴리스, Google Agents CLI 릴리스 노트,
> xAI Grok Code Fast 1 발표를 확인했습니다. GitHub third-party coding agents는 public preview로, OpenAI Agents
> API는 public beta 성격의 관리형 agent 경계로, Gemini CLI v0.60.0은 latest stable release로 구분했습니다.

## 결론부터 말하면

이번 주 AI agent 선택 기준은 "어느 모델이 제일 똑똑한가"보다 **어디서 실행되고, 무엇을 만질 수 있고, 비용이 어떻게
쌓이며, 결과가 PR과 audit log로 남는가**입니다.

지난주 글은 장기 실행 작업의 state, memory, approval, audit를 다뤘습니다. 이번 글은 그 다음 단계입니다. Spring Boot
팀이 Codex, Claude Code, GitHub Copilot, Gemini CLI, Grok 계열을 함께 쓴다면 작업을 하나의 순위표로 밀어 넣지 말고,
실행 위치와 비용 모델에 따라 라우팅해야 합니다.

## 이번 주 비교 축

| 후보 | 최근 확인한 공식 상태 | 먼저 볼 질문 |
|---|---|---|
| OpenAI Codex/Agents API | managed Codex harness, hosted/self-hosted sandbox, MCP, saved progress 축 | long-running 작업 상태를 플랫폼에 맡길 것인가, 자체 시스템에 둘 것인가 |
| Claude Code | seat/API key에 따라 metering이 다르고 Sonnet을 일반 코딩 기본값으로 제시 | token 단가보다 사용 한도와 reset 경험을 어떻게 운영할 것인가 |
| GitHub Copilot coding agents | Copilot cloud agent와 함께 third-party agents를 public preview로 제공 | issue/PR/review comment를 작업 상태 저장소로 쓸 것인가 |
| Gemini CLI | v0.60.0 latest stable에서 extension consent, sandbox, path boundary, MCP OAuth 보안 강화 | local CLI 확장과 sandbox boundary를 얼마나 엄격히 둘 것인가 |
| Google Agents CLI | 1.0 GA 이후 ADK agent scaffold/eval/deploy 흐름 제공 | 제품 안 agent와 코드수정 agent를 분리할 것인가 |
| Grok Code Fast 1 | agentic coding용 빠른 모델과 낮은 token 가격, partner IDE 배포를 강조 | 빠른 반복 작업에 쓰되 작업 증적은 별도 harness가 남기는가 |

## 모델보다 실행 위치를 먼저 고릅니다

같은 모델이라도 local terminal, IDE, GitHub cloud agent, managed sandbox 안에서 위험과 생산성이 다릅니다.

<Mermaid title="코딩 에이전트 라우팅 기준">
{`flowchart TD
  Task["작업 요청"] --> Classify{"작업 성격"}
  Classify -->|작은 수정/테스트| Local["Local CLI/IDE agent"]
  Classify -->|독립 issue| CloudPR["GitHub cloud PR agent"]
  Classify -->|제품 내 자동화| Managed["Managed Agents API"]
  Classify -->|빠른 반복/초안| Fast["Fast coding model"]

  Local --> Guard["sandbox, 승인, 테스트"]
  CloudPR --> Guard
  Managed --> Guard
  Fast --> Guard
  Guard --> Evidence["diff, log, 비용, review 증적"]
`}
</Mermaid>

작은 bug fix는 local agent가 현재 checkout, test fixture, 실패 로그를 바로 읽는 편이 빠릅니다. 반대로 issue 하나를
비동기로 맡기고 PR review로 받는 작업은 GitHub cloud agent 흐름이 자연스럽습니다. 제품 안에서 사용자가 요청한 문서
정리나 내부 자동화를 agent로 돌린다면 OpenAI Agents API나 Google ADK/Agents CLI처럼 runtime과 sandbox를 명시하는
도구가 더 맞습니다.

## Sandbox는 생산성 기능이 아니라 비용과 권한의 경계입니다

OpenAI의 Codex 안전 운영 글은 sandbox와 approval이 함께 작동한다고 설명합니다. sandbox는 agent가 어디에 쓸 수 있고
network에 닿을 수 있는지를 정하고, approval policy는 sandbox 밖 행동이나 높은 위험 행동에서 사람을 세웁니다.
OpenAI Agents 문서도 hosted sandbox, self-hosted sandbox, no sandbox 선택지를 구분합니다.

Gemini CLI v0.60.0 릴리스도 같은 방향입니다. extension이 환경 변경을 요청할 때 명시 consent를 묻고, sandbox container
안의 settings/temp directory를 격리하며, workspace boundary와 symlink resolution을 강화했습니다. 이 흐름은 agent가
똑똑해질수록 filesystem boundary가 더 중요해진다는 신호입니다.

Spring Boot 팀의 최소 정책은 다음 정도면 됩니다.

| 작업 | 기본 실행 위치 | 승인 기준 |
|---|---|---|
| unit test 실패 원인 조사 | local sandbox | 자율 |
| 작은 코드 수정 | local sandbox | 테스트 실행까지 자율 |
| dependency 추가 | local sandbox | 사전 승인 |
| issue 기반 독립 PR | cloud PR agent | PR 생성 후 review |
| migration 적용, 배포, secret 조회 | 사람 실행 | agent 금지 또는 제안만 |

## 비용은 token price가 아니라 완료된 변경 하나의 총비용입니다

xAI는 Grok Code Fast 1을 agentic coding에 맞춘 빠르고 경제적인 모델로 설명하며 input/output/cached input token 가격을
공개했습니다. Claude Code 문서는 로그인 방식에 따라 Enterprise seat의 rolling limit 또는 API key의 token billing이
적용된다고 설명합니다. GitHub third-party coding agents는 agent session이 Actions minutes와 AI credits를 소비한다고
안내합니다.

이 셋은 같은 단위가 아닙니다.

| 비용 단위 | 어디서 보나 | 놓치기 쉬운 것 |
|---|---|---|
| token 가격 | API/model 후보 | 재시도와 긴 context 비용 |
| 구독/seat 한도 | Claude Code, Codex 앱류 | 5시간/주간 reset과 대기 시간 |
| AI credits + Actions minutes | GitHub agent | CI 실패 반복과 PR iteration |
| 운영 비용 | 자체 sandbox/runner | compute, storage, log, egress |
| human review time | 모든 agent | 사람이 diff를 이해하는 시간 |

그래서 "가장 싼 모델"보다 "요구사항을 만족한 diff 하나를 사람이 10분 안에 review할 수 있게 만드는 총비용"을 봐야
합니다. 빠른 모델은 초안과 작은 반복에 강하고, 느리지만 강한 모델은 복잡한 설계 판단에 쓸 수 있습니다.

## PR 흐름은 agent 결과를 가장 싸게 감사하는 방법입니다

GitHub 문서는 third-party coding agents를 issue, PR comment, Agents tab, VS Code에서 시작할 수 있고, agent가 변경을
끝내면 PR을 만들어 review를 요청하는 흐름으로 설명합니다. 또한 CodeQL, secret scanning, dependency advisory 검사가
agent가 새로 만든 코드에도 적용된다고 안내합니다.

이것은 public preview라는 제한이 있지만, 운영 패턴은 배울 만합니다. agent 결과를 채팅 답변으로만 받으면 증적이
흩어집니다. PR로 받으면 다음 정보가 한 곳에 남습니다.

- 변경 diff
- test/check 결과
- reviewer comment와 agent iteration
- secret/security/dependency scan
- merge 또는 close decision

Spring Boot 팀이 사내 agent를 만들더라도 결과물은 PR, patch file, checklist처럼 기존 review tooling에 실리는 형태가
좋습니다. agent 전용 dashboard를 먼저 만들 필요는 없습니다.

## 이번 주 후보와 제외 이유

- Meta, Mistral의 최신 모델 후보는 공식 발표와 코딩 agent 배포 채널 확대를 확인했지만, 이번 주 글의 핵심인 sandbox,
  PR workflow, 비용 metering을 직접 비교할 만큼 공식 coding-agent 운영 문서가 뚜렷하지 않아 본문 후보에서 제외했습니다.
- GitHub third-party coding agents는 public preview라 production 기본값으로 권하지 않았습니다. 다만 issue/PR/review
  comment를 작업 상태로 쓰는 패턴은 본문에 포함했습니다.
- Grok Code Fast 1은 공식 발표일이 2025년 8월 28일로 오래됐지만, 낮은 가격과 partner IDE 배포가 여전히 빠른 반복
  후보를 판단하는 기준이라 비용 비교에만 포함했습니다.
- 단일 커뮤니티 순위표, 출처 없는 benchmark 캡처, 개인 사용기만으로 만든 "최고 agent" 주장은 근거로 쓰지 않았습니다.

## Spring Boot 팀의 최소 라우팅 규칙

1. 작업 시작 전 `local`, `cloud-pr`, `managed-agent`, `research` 중 하나로 분류합니다.
2. secret, production deploy, DB migration 적용은 agent 실행 경로에서 제거합니다.
3. agent 결과는 diff, test output, 비용/usage, 남은 리스크를 함께 남깁니다.
4. 빠른 모델은 초안과 작은 반복에 쓰고, 복잡한 설계와 migration은 강한 모델과 review agent를 붙입니다.
5. public preview 기능은 실험 lane에만 두고 main 개발 workflow의 기본값으로 쓰지 않습니다.
