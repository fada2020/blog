Spring Boot 서비스에서 상품 코드별 표시 문자열을 메모리에 보관한다고 해 봅시다. 요청이 한 개면 캐시가 비어 있을 때만 문자열을 계산하면 됩니다. 같은 키를 동시에 조회하는 요청이 두 개라면 질문이 하나 더 생깁니다. 저장된 값이 하나일 때 값을 만드는 함수도 한 번 실행됐을까요?

2026년 11월 12일 기준 Kotlin/JVM 최신 안정 버전 2.4.21의 문서와 JVM 구현 계약을 확인했습니다. [Kotlin 공식 릴리스](https://github.com/JetBrains/kotlin/releases/tag/v2.4.21)

## 일반 맵에서 null은 어떻게 처리될까

`MutableMap.getOrPut`은 현재 값이 존재하고 null이 아니면 그 값을 반환합니다. 키가 없거나 값이 null이면 람다를 호출하고 결과를 저장합니다. 동시에 수정하는 일반 맵에서는 이 작업의 원자성이 보장되지 않습니다. [Kotlin getOrPut API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.collections/get-or-put.html)

```kotlin
val nullable_labels = mutableMapOf<String, String?>("A" to null)
check(nullable_labels.containsKey("A"))
check(nullable_labels.getOrPut("A") { "기본 이름" } == "기본 이름")
check(nullable_labels["A"] == "기본 이름")
```

DB 조회 결과가 없어서 null을 저장했더라도 이 방식은 다음 조회에서 람다를 다시 실행할 수 있습니다. 조회 실패와 조회 결과 없음의 재시도 정책이 다르면, 결과 없음도 별도의 값으로 표현해 두는 편이 명확합니다.

## 같은 키에서 두 함수가 실행되는 실습

JVM의 `ConcurrentMap.getOrPut`은 경쟁에서 먼저 저장된 값을 유지합니다. 람다는 경쟁 중에 여러 번 호출될 수 있습니다. 아래에서는 두 요청이 람다에 들어온 뒤 진행하도록 장벽을 두어 호출 순서를 재현합니다.

```kotlin
import java.util.concurrent.ConcurrentHashMap
import java.util.concurrent.ConcurrentMap
import java.util.concurrent.CyclicBarrier
import java.util.concurrent.Executors
import java.util.concurrent.TimeUnit.SECONDS
import java.util.concurrent.atomic.AtomicInteger

fun main() {
    val labels: ConcurrentMap<String, Int> = ConcurrentHashMap()
    val calls = AtomicInteger()
    val barrier = CyclicBarrier(2)
    val pool = Executors.newFixedThreadPool(2)
    try {
        val requests = List(2) {
            pool.submit<Int> {
                labels.getOrPut("A") {
                    val candidate = calls.incrementAndGet()
                    barrier.await(5, SECONDS)
                    candidate
                }
            }
        }
        val results = requests.map { it.get(10, SECONDS) }
        check(calls.get() == 2)
        check(labels.size == 1)
        check(results.all { it == labels["A"] })
        println("calls=${calls.get()}, stored=${labels.size}")
    } finally {
        pool.shutdownNow()
    }
}
```

출력은 `calls=2, stored=1`입니다. 어느 후보가 저장될지는 스케줄링에 따라 달라집니다. 두 요청은 저장에 성공한 같은 값을 반환합니다. 예제에서 변수의 선언 타입이 `ConcurrentMap`인 이유는 Kotlin 확장 함수가 수신 객체의 선언 타입에 따라 선택되기 때문입니다. 동일한 객체를 `MutableMap`으로 받아 호출하면 일반 맵 확장 함수가 선택됩니다. [Kotlin 확장 함수의 정적 디스패치](https://kotlinlang.org/docs/extensions.html#extensions-are-resolved-statically)

## Java 코드에서 옮겨 올 때 확인할 점

| 작업 | 선택 | 확인할 계약 |
| --- | --- | --- |
| 요청 내부에서 기본값 채우기 | `MutableMap.getOrPut` | 기존 값이 null이면 다시 계산 |
| 공유 맵에 저렴한 계산 결과 넣기 | `ConcurrentMap.getOrPut` | 후보 계산 중복 허용 |
| 공유 맵에서 키별 초기화 직렬화 | `ConcurrentHashMap.computeIfAbsent` | 계산 중 다른 업데이트가 지연될 수 있어 짧은 함수 사용 |

`ConcurrentHashMap.computeIfAbsent`는 해당 메서드 호출 전체를 원자적으로 수행합니다. 함수가 null을 반환하거나 예외를 던지면 값이 저장되지 않으며, 저장된 값이 제거돼도 이후 호출은 다시 계산할 수 있습니다. Spring Boot 인스턴스가 여러 개면 각 JVM은 자기 맵을 가집니다. 주문 생성이나 알림 발송처럼 프로세스를 넘어 중복을 막아야 하는 일은 저장소의 유일성 제약과 멱등 키 등 외부 상태의 계약으로 검증해야 합니다. [JDK 21 ConcurrentHashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html#computeIfAbsent(K,java.util.function.Function))
