## 결론부터 말하면

Kotlin의 null safety는 `null`을 없애는 기능이 아닙니다. **null이 가능한 값과 불가능한 값을 타입에
드러내고, 그 경계를 컴파일러가 계속 확인하게 만드는 방식**입니다.

Java/Spring Boot 코드에서는 null 가능성이 여러 위치에 흩어집니다.

- repository가 값을 못 찾으면 `null` 또는 `Optional.empty()`를 반환합니다.
- request body의 필드는 Bean Validation 전까지 비어 있을 수 있습니다.
- 외부 API 응답은 문서와 다르게 `null`을 보낼 수 있습니다.
- JPA 지연 로딩, projection, legacy Java library는 nullability 정보를 충분히 주지 못할 수 있습니다.

Kotlin에서는 이런 경계를 `String`과 `String?`처럼 타입에 적습니다. 그리고 `?.`, `?:`, `let`,
`requireNotNull`, smart cast를 조합해 "어디서 null을 허용하고 어디서 끊을지"를 코드에 남깁니다.

## 이번 주 개념

Kotlin에서 nullable 타입은 타입 이름 뒤에 `?`를 붙입니다.

```kotlin
val requiredName: String = "kim"
val optionalNickname: String? = null
```

`String`에는 `null`을 넣을 수 없습니다. `String?`는 넣을 수 있지만, 바로 member를 호출할 수 없습니다.

```kotlin
fun display(nickname: String?): String {
    return nickname.uppercase()
}
```

위 코드는 컴파일되지 않습니다. `nickname`이 `null`일 수 있기 때문입니다. Kotlin은 이 지점을 런타임
`NullPointerException`까지 미루지 않고, 컴파일 단계에서 멈춥니다.

대신 아래처럼 null 가능성을 처리해야 합니다.

```kotlin
fun display(nickname: String?): String {
    return nickname?.uppercase() ?: "ANONYMOUS"
}
```

| Kotlin 표현 | 의미 | Java/Spring에서 가까운 감각 |
|---|---|---|
| `String` | null이 아닌 문자열 | `@NotNull String`에 가까움 |
| `String?` | null일 수 있는 문자열 | `@Nullable String` 또는 `Optional<String>` 경계 |
| `value?.length` | null이면 전체 결과도 null | null 체크 후 접근 |
| `value ?: fallback` | null이면 대체값 사용 | `Objects.requireNonNullElse` 또는 `orElse` |
| `value!!` | null이면 NPE를 던짐 | 강제 단언, 운영 코드에서는 마지막 수단 |

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 null 가능성을 타입만 보고 알기 어렵습니다. annotation과 convention을 붙일 수는 있지만,
모든 library와 모든 경계가 같은 규칙을 지키지는 않습니다.

```java
User user = userRepository.findById(id).orElse(null);
return user.getName().trim();
```

이 코드는 짧지만 위험합니다. `user`가 없으면 `getName()`에서 바로 NPE가 납니다. `name`이 null이면
`trim()`에서 다시 NPE가 납니다. 그래서 Java 서버 코드에서는 보통 아래처럼 방어 코드를 둡니다.

```java
User user = userRepository.findById(id)
    .orElseThrow(() -> new NotFoundException("user"));

String name = user.getName();
if (name == null || name.isBlank()) {
    throw new IllegalArgumentException("name is required");
}

return name.trim();
```

Kotlin으로 옮길 때 이 코드를 무작정 짧게 만드는 것이 목표는 아닙니다. 목표는 null 경계를 타입과
제어 흐름에 드러내는 것입니다.

```kotlin
fun userName(id: Long): String {
    val user = userRepository.findById(id).orElseThrow { NotFoundException("user") }
    val name = requireNotNull(user.name) { "name is required" }

    return name.trim()
}
```

여기서 `user.name`이 Java entity에서 온 platform type이면 null 가능성이 애매할 수 있습니다.
서버 경계에서는 `requireNotNull`이나 명시적인 DTO 변환으로 한 번 끊는 편이 낫습니다.

## Kotlin에서는 무엇이 다른가

Kotlin의 핵심 차이는 null 체크 이후 타입이 바뀐다는 점입니다. 컴파일러가 안전하다고 판단하면 nullable
값을 non-null처럼 사용할 수 있게 해 줍니다. 이것이 smart cast입니다.

```kotlin
fun normalizedEmail(email: String?): String {
    if (email == null) {
        return "unknown@example.com"
    }

    return email.trim().lowercase()
}
```

`if (email == null) return` 이후의 `email`은 `String?`가 아니라 `String`처럼 다뤄집니다. 이미 null이면
함수가 끝났기 때문입니다.

<Mermaid title="Kotlin null 처리 흐름">
{`flowchart TD
  Input["외부 입력: String?"] --> Check{"null인가"}
  Check -->|yes| Fallback["대체값, 예외, 조기 return"]
  Check -->|no| SmartCast["smart cast: String"]
  SmartCast --> Normalize["trim, lowercase 같은 안전한 처리"]
  Normalize --> Response["응답 DTO"]

  Input --> SafeCall["safe call ?."] --> NullableResult["결과도 nullable"]
  NullableResult --> Elvis["Elvis ?: 로 기본값 또는 예외 결정"]
`}
</Mermaid>

Spring Boot 개발자에게 중요한 지점은 Bean Validation과 Kotlin null safety의 역할이 다르다는 점입니다.
Bean Validation은 요청이 들어온 뒤 runtime에서 검증합니다. Kotlin null safety는 코드가 컴파일되는 동안
null 가능성을 추적합니다. 둘 중 하나만으로 충분하지 않습니다.

```kotlin
data class RegisterRequest(
    val email: String?,
    val name: String?,
)

fun toCommand(request: RegisterRequest): RegisterCommand {
    val email = request.email?.trim()?.lowercase()
        ?: throw BadRequestException("email is required")
    val name = request.name?.trim()
        ?: throw BadRequestException("name is required")

    return RegisterCommand(email = email, name = name)
}
```

이 예제는 request DTO에서는 nullable을 허용하고, command로 넘어갈 때 non-null로 바꿉니다. 서버 코드의
좋은 경계는 "컨트롤러 입구에서는 의심하고, 서비스 내부에서는 믿을 수 있게 만든다"에 가깝습니다.

## safe call은 흐름을 짧게 만들지만 책임을 숨기면 안 됩니다

`?.`는 값이 null일 때 호출을 건너뜁니다.

```kotlin
val city = user.profile?.address?.city
```

이 코드는 편합니다. 하지만 업무적으로 `profile`이 없는 것과 `address`가 없는 것과 `city`가 없는 것이
같은 의미인지 먼저 정해야 합니다. 모두 같은 fallback이면 safe call chain이 좋습니다.

```kotlin
fun displayCity(user: User): String {
    return user.profile?.address?.city ?: "미등록"
}
```

반대로 어느 단계가 비정상인지 구분해야 한다면 safe call chain을 길게 잇지 않는 편이 낫습니다.

```kotlin
fun shippingCity(user: User): String {
    val profile = user.profile ?: throw BadRequestException("profile is required")
    val address = profile.address ?: throw BadRequestException("address is required")

    return address.city ?: throw BadRequestException("city is required")
}
```

Kotlin 코드를 짧게 만들려고 모든 값을 `?.`로 연결하면 실패 이유가 사라집니다. 운영 API에서는 짧은 코드보다
오류 경계가 더 중요할 때가 많습니다.

## Elvis operator는 기본값보다 조기 종료에 더 자주 씁니다

`?:`는 왼쪽 값이 null이면 오른쪽 값을 사용합니다. 기본값을 넣을 수도 있고, 예외나 `return`으로 함수를
끝낼 수도 있습니다.

```kotlin
fun findDisplayName(user: User): String {
    return user.nickname ?: user.name ?: "unknown"
}
```

서비스 코드에서는 조기 종료가 더 읽기 좋을 때가 많습니다.

```kotlin
fun handle(command: UpdateUserCommand): UserResponse {
    val user = userRepository.findById(command.id).orElse(null)
        ?: throw NotFoundException("user")

    val name = command.name?.trim()
        ?: return UserResponse.from(user)

    user.rename(name)
    return UserResponse.from(user)
}
```

이 코드는 세 가지 의도를 분리합니다.

- 사용자가 없으면 404 성격의 예외를 던집니다.
- 이름 변경 값이 없으면 기존 사용자 응답을 그대로 반환합니다.
- 이름 값이 있으면 non-null `String`으로 바꾼 뒤 도메인 메서드에 넘깁니다.

## `let`은 null 블록을 만들 때만 씁니다

Kotlin을 처음 쓰면 `let`, `run`, `also`, `apply`를 많이 쓰고 싶어집니다. 하지만 scope function은 코드가
짧아지는 대신 수신 객체가 `it`인지 `this`인지 계속 추적해야 합니다.

nullable 값을 처리할 때 가장 흔한 패턴은 `?.let { ... }`입니다.

```kotlin
command.phoneNumber?.let { phoneNumber ->
    user.changePhoneNumber(phoneNumber.trim())
}
```

이 코드는 phone number가 있을 때만 변경합니다. 괜찮은 사용입니다. 하지만 아래처럼 업무 로직이 길어지면
명시적인 `if`가 더 낫습니다.

```kotlin
if (command.phoneNumber != null) {
    val normalized = command.phoneNumber.trim()
    user.changePhoneNumber(normalized)
    auditLog.recordPhoneNumberChanged(user.id)
}
```

Kotlin다운 코드는 scope function을 많이 쓰는 코드가 아닙니다. null 경계와 상태 변경이 읽히는 코드입니다.

## Java interop의 platform type을 서버 경계에서 끊습니다

Kotlin 공식 문서는 Java nullability annotation이 있으면 Kotlin 타입이 nullable 또는 non-nullable로
표현된다고 설명합니다. 반대로 annotation이 부족한 Java API는 platform type으로 들어올 수 있습니다.
IDE에서는 `String!`처럼 보이는 값입니다.

이 값은 Kotlin이 null인지 아닌지 확신하지 못합니다. 그래서 운영 서버에서는 Java library, JPA entity,
legacy SDK에서 넘어온 값을 내부 command나 domain value로 바꿀 때 확인 지점을 둡니다.

```kotlin
data class UserCommand(
    val id: Long,
    val email: String,
)

fun toCommand(entity: UserEntity): UserCommand {
    return UserCommand(
        id = entity.id,
        email = requireNotNull(entity.email) { "email is required" }.trim().lowercase(),
    )
}
```

이렇게 하면 이후 서비스 내부에서는 `email: String`으로 다룰 수 있습니다. null 처리 코드가 모든 서비스
메서드에 퍼지는 것을 막고, 잘못된 데이터는 경계에서 드러납니다.

## Java 개발자가 자주 하는 오해

| 오해 | 실제 기준 |
|---|---|
| `String?`는 Java `Optional<String>`과 같다 | nullable 타입은 wrapper가 아니라 타입 시스템의 표현입니다. |
| `!!`를 쓰면 Java처럼 간단해진다 | 실패 지점을 런타임 NPE로 미루므로 운영 코드에서는 원인을 숨깁니다. |
| Bean Validation이 있으니 non-null 타입만 쓰면 된다 | JSON 역직렬화, Java interop, legacy data 경계는 따로 확인해야 합니다. |
| safe call chain은 항상 좋은 스타일이다 | 어떤 단계가 빠졌는지 구분해야 하면 명시적 체크가 낫습니다. |
| `let`을 많이 쓰면 Kotlin답다 | 수신 객체와 반환값이 헷갈리면 `if`가 더 좋은 코드입니다. |

## 최소 실행 예제

아래 예제는 nullable request 값을 내부 command로 바꾸는 작은 코드입니다.

```kotlin
data class RegisterRequest(
    val email: String?,
    val displayName: String?,
)

data class RegisterCommand(
    val email: String,
    val displayName: String,
)

fun RegisterRequest.toCommand(): RegisterCommand {
    val normalizedEmail = email?.trim()?.lowercase()
        ?: throw IllegalArgumentException("email is required")

    val normalizedName = displayName?.trim()
        ?.takeIf { it.isNotBlank() }
        ?: "이름 미등록"

    return RegisterCommand(
        email = normalizedEmail,
        displayName = normalizedName,
    )
}

fun main() {
    val request = RegisterRequest(
        email = " USER@example.COM ",
        displayName = null,
    )

    println(request.toCommand())
}
```

실행 결과는 아래와 같습니다.

```text
RegisterCommand(email=user@example.com, displayName=이름 미등록)
```

이 예제에서 request는 외부 입력이므로 nullable을 허용합니다. command는 서비스 내부 입력이므로 non-null로
고정합니다. 이 경계가 Kotlin 서버 코드의 null safety를 실무적으로 쓰는 첫 단계입니다.

## 연습 문제

1. `nickname: String?`을 받아 빈 문자열이거나 null이면 `"guest"`를 반환하고, 값이 있으면 trim한 문자열을
   반환하는 함수를 작성해 봅니다.
2. Java repository의 `findById(id).orElse(null)` 결과를 Kotlin에서 `?: throw`로 끊는 코드를 작성해 봅니다.
3. nullable `phoneNumber`가 있을 때만 변경하고 audit log를 남기는 코드를 `?.let` 버전과 `if` 버전으로
   각각 작성한 뒤 어느 쪽이 읽기 쉬운지 비교해 봅니다.
4. request DTO에서는 nullable을 허용하고 service command에서는 non-null로 바꾸는 변환 함수를 하나 더
   작성해 봅니다.
