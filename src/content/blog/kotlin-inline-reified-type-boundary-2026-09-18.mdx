> **검증 정보**
>
> 2026년 9월 18일에 Kotlin 2.4.20 릴리스 노트, Kotlin release process, inline functions 문서,
> generics 문서를 확인했습니다. 기준 안정 버전은 `Kotlin 2.4.20`입니다. Kotlin 2.4.20에서
> JVM `when`의 `invokedynamic` 컴파일은 안정 기능이 되었지만, 이 글은 오래전부터 안정적으로 쓰는
> `inline`, `noinline`, `crossinline`, `reified`의 설계 경계만 다룹니다.

## 결론부터 말하면

Kotlin의 `inline`은 "함수 호출을 없애는 성능 키워드"로만 보면 위험합니다. Spring Boot 서버 코드에서는
대부분 성능보다 **타입 경계를 호출부에 드러내는 도구**로 보는 편이 더 실용적입니다.

특히 `reified` 타입 파라미터는 Java의 `Class<T>` 인자를 매번 넘기던 코드를 읽기 좋게 바꿔 줍니다.
다만 public API에 무작정 쓰면 호출한 모듈에 함수 본문이 복사되고, 내부 구현 변경이 binary compatibility
문제가 될 수 있습니다.

첫 기준은 단순합니다.

- JSON 변환, event payload 분기, typed attribute 읽기처럼 타입 토큰이 반복되면 `inline reified`를 검토합니다.
- 큰 함수, business rule, repository 호출, transaction 경계는 inline으로 숨기지 않습니다.
- 람다를 저장하거나 나중에 실행해야 하면 `noinline`으로 분리합니다.
- 람다가 다른 실행 컨텍스트에서 호출될 수 있으면 `crossinline`으로 non-local return을 막습니다.
- 외부 라이브러리 API로 노출하는 함수라면 `@PublishedApi`와 binary compatibility 위험을 먼저 검토합니다.

## 이번 주 개념

Kotlin의 inline 함수는 함수 본문과 전달된 람다를 call site에 펼칠 수 있게 합니다.
공식 문서는 고차 함수가 함수 객체와 closure를 만들고 virtual call 비용을 가질 수 있으며, inline으로 이 비용을 줄일 수 있다고 설명합니다.

```kotlin
inline fun <T> measure(name: String, block: () -> T): T {
    val startedAt = System.nanoTime()
    return try {
        block()
    } finally {
        val elapsed = System.nanoTime() - startedAt
        println("$name took $elapsed ns")
    }
}
```

`measure { service.load() }`처럼 호출하면 람다 호출 구조가 작아집니다. 하지만 서버 코드에서 더 자주 유용한 부분은
`reified`입니다.

```kotlin
inline fun <reified T : Any> Map<String, Any?>.getAs(key: String): T? =
    this[key] as? T
```

일반 제네릭 함수에서는 런타임에 `T`를 직접 검사할 수 없습니다. Kotlin generics 문서는 Java와 마찬가지로 generic
type parameter를 둘 수 있고, variance를 통해 읽기와 쓰기 방향을 제한한다고 설명합니다. 하지만 런타임 타입 검사가 필요하면
일반 함수의 `T`는 충분하지 않습니다.

`reified`는 inline 함수 안에서 타입 파라미터를 런타임에 접근할 수 있게 해 줍니다.

## Java/Spring에서는 어떻게 다뤘는가

Java에서는 런타임 타입을 넘기기 위해 `Class<T>`나 `ParameterizedTypeReference<T>`를 자주 씁니다.

```java
public <T> T read(String body, Class<T> type) {
    return objectMapper.readValue(body, type);
}

UserCreated event = reader.read(body, UserCreated.class);
```

Spring에서도 같은 패턴이 많습니다. bean을 타입으로 찾거나, HTTP 응답을 generic type으로 읽거나, message payload를
특정 class로 변환할 때 타입 토큰을 명시합니다.

이 방식은 명시적이라는 장점이 있습니다. 호출부에서 어떤 타입을 요구하는지 분명하고, Java와 Kotlin이 함께 쓰는 경계에서도
예측 가능합니다. 단점은 반복입니다. `UserCreated::class.java`, `OrderPaid::class.java` 같은 인자가 계속 붙으면
실제 business 흐름보다 타입 토큰이 더 크게 보입니다.

## Kotlin에서는 무엇이 다른가

Kotlin에서는 호출부의 타입 인자를 함수 안에서 쓸 수 있습니다.

```kotlin
inline fun <reified T : Any> JsonReader.read(body: String): T =
    objectMapper.readValue(body, T::class.java)

val event = reader.read<UserCreated>(body)
```

이 함수는 Java의 `read(body, UserCreated.class)`를 Kotlin스럽게 감싼 것입니다.
타입을 숨긴 것이 아니라 호출부의 `<UserCreated>`에 모은 것입니다.

Spring Boot 프로젝트에서는 이런 wrapper가 유용합니다.

```kotlin
inline fun <reified T : Any> ApplicationContext.getBeanOrNull(): T? =
    runCatching { getBean(T::class.java) }.getOrNull()
```

다만 이 함수를 아무 데나 쓰면 "bean이 없으면 null"이라는 정책이 조용히 퍼집니다. 설정 오류를 빨리 터뜨려야 하는 곳이라면
`getBean()` 예외를 그대로 두는 편이 낫습니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin inline/reified | 판단 기준 |
|---|---|---|
| `Class<T>` 인자 | `<reified T>` | Kotlin 호출부에서 타입 토큰 반복을 줄일 때 |
| `ParameterizedTypeReference<T>` | reified wrapper 또는 명시 타입 토큰 유지 | 중첩 generic이면 명시 타입이 더 안전할 수 있음 |
| utility static method | top-level inline function | 작고 타입 경계가 분명할 때 |
| callback 저장 | `noinline` lambda | 나중에 실행하거나 field에 담을 때 |
| callback 안 `return` 금지 | `crossinline` lambda | 다른 객체나 비동기 경계에서 호출될 때 |
| library public helper | 일반 함수 또는 작은 inline + `@PublishedApi` 검토 | binary compatibility가 중요할 때 |

## 최소 실행 예제

아래 예제는 Spring 없이 타입별 event를 읽는 작은 adapter입니다.

```kotlin
interface Event
data class UserCreated(val userId: String) : Event
data class OrderPaid(val orderId: String) : Event

class EventEnvelope(
    val type: String,
    val payload: Map<String, String>,
)

inline fun <reified T : Event> EventEnvelope.decode(): T? =
    when (T::class) {
        UserCreated::class ->
            payload["userId"]?.let { UserCreated(it) as T }
        OrderPaid::class ->
            payload["orderId"]?.let { OrderPaid(it) as T }
        else -> null
    }

fun main() {
    val envelope = EventEnvelope(
        type = "user.created",
        payload = mapOf("userId" to "u-123"),
    )

    val event = envelope.decode<UserCreated>()
    println(event)
}
```

이 예제에서 `decode<UserCreated>()`는 읽기 좋습니다. 하지만 실제 운영 코드라면 `else -> null`이 좋은 선택인지부터
정해야 합니다. 알 수 없는 event type이 장애인지, 무시 가능한 하위 호환 이벤트인지에 따라 반환 타입이 달라집니다.

Spring Boot에서는 아래처럼 작게 쓰는 편이 좋습니다.

```kotlin
inline fun <reified T : Any> ObjectMapper.readRequired(body: String): T =
    readValue(body, T::class.java)
```

반대로 아래처럼 transaction 안의 여러 동작을 inline helper로 감싸는 것은 피합니다.

```kotlin
inline fun <reified T> runBusinessFlow(block: () -> T): T {
    // logging, transaction-like naming, metrics, exception mapping...
    return block()
}
```

이름은 편해 보이지만 실제 lifecycle이 흐려집니다. transaction은 Spring annotation, interceptor, service 경계에서 보이게
두는 편이 팀 코드에서는 더 안전합니다.

## Java 개발자가 자주 하는 오해

첫째, inline을 붙이면 항상 빠르다는 오해입니다. 공식 문서도 generated code가 커질 수 있다고 설명합니다.
작은 고차 함수에는 도움이 되지만, 큰 business 함수에는 코드 크기와 디버깅 비용이 더 커질 수 있습니다.

둘째, reified가 Java의 type erasure를 완전히 없앤다는 오해입니다. `List<UserCreated>`의 element type까지
항상 완벽하게 보존되는 것이 아닙니다. 단순 class token이 필요한 경우에는 깔끔하지만, 중첩 generic 변환은 명시적인
type reference가 더 맞을 수 있습니다.

셋째, public inline 함수를 마음껏 바꿔도 된다는 오해입니다. public 또는 protected inline 함수는 다른 모듈 call site에
본문이 복사될 수 있습니다. 내부 private 선언을 직접 쓸 수 없는 제약도 있습니다.

넷째, `noinline`과 `crossinline`을 문법 옵션처럼 보는 오해입니다. `noinline`은 람다를 값으로 다뤄야 할 때,
`crossinline`은 람다가 다른 실행 컨텍스트에서 호출되어 non-local return이 위험할 때 쓰는 설계 표식입니다.

## 연습 문제

1. `ObjectMapper.readValue(body, SomeDto::class.java)`가 세 곳 이상 반복되는 작은 adapter를 찾고,
   `inline fun <reified T : Any> ObjectMapper.readRequired(body: String): T`로 바꿔도 정책이 흐려지지 않는지 확인합니다.
2. `runCatching { getBean(T::class.java) }.getOrNull()` 같은 helper가 설정 오류를 숨기지 않는 위치인지 적어 봅니다.
3. public module에 있는 inline 함수를 하나 고르고, 그 함수가 internal helper를 참조한다면 `@PublishedApi`가 필요한지,
   아니면 inline을 없애는 편이 더 나은지 판단합니다.

오늘의 결론은 절제입니다. `inline reified`는 Spring Boot 개발자가 Kotlin을 쓸 때 반복 타입 토큰을 줄이는 좋은 도구입니다.
하지만 타입 경계를 예쁘게 만드는 것과 lifecycle을 숨기는 것은 다릅니다. 작은 adapter에는 쓰고, 큰 business 흐름에는
평범한 함수와 명시적인 Spring 경계를 남기는 편이 좋습니다.
