## 1. Agent Plugins 1.0은 에이전트 확장을 공급망 자산으로 만듭니다

GitHub는 2026년 8월 12일 Agent Plugins 1.0이 VS Code, Copilot CLI, Copilot app에서 동작하는
흐름을 공지했습니다. 공식 설명 기준 Agent Plugins 1.0은 agent skills와 MCP 서버를 하나의
설치 가능한 plugin으로 묶는 공개 표준입니다. 한 번 만든 plugin을 호환되는 여러 agent client에서
사용할 수 있게 하려는 방향입니다.

이 발표는 편의 기능처럼 보이지만, 운영팀 입장에서는 공급망 표면이 하나 더 생긴 것입니다.
plugin 하나가 명령, 규칙, MCP 서버, 문서화된 skill을 함께 가져올 수 있다면, 단순 editor 설정이
아니라 실행 권한을 가진 개발 도구 의존성으로 봐야 합니다.

Spring Boot 팀에서는 다음 질문을 먼저 정리하는 편이 안전합니다.

| 질문 | 확인할 이유 |
|---|---|
| plugin이 어떤 명령을 실행하는가 | 로컬 파일, 테스트, 배포 스크립트 접근 범위를 확인해야 합니다. |
| MCP 서버가 어떤 데이터를 읽는가 | 이슈, PR, 로그, 내부 문서 접근 권한이 섞일 수 있습니다. |
| plugin 버전은 어떻게 고정하는가 | 개발자마다 다른 버전을 쓰면 재현 가능한 자동화가 어렵습니다. |
| 실패 시 수동 절차가 있는가 | 에이전트가 멈춰도 빌드, 테스트, 릴리스는 사람이 이어갈 수 있어야 합니다. |

Jenkins shared library나 Gradle plugin을 검토하듯이, agent plugin도 저장소별 승인 목록과
버전 고정 정책을 두는 편이 좋습니다. 생산성을 높이는 도구일수록 어떤 권한으로 실행되는지 먼저
명확해야 합니다.

## 2. Go 보안 릴리스는 "우리 주 언어가 아니다"라는 예외를 줄입니다

Go 프로젝트는 2026년 8월 13일 릴리스 기록에 Go 1.26.6과 Go 1.25.13을 올렸습니다. 공식
릴리스 기록 기준 두 라인 모두 `go` command와 `crypto/tls`, `encoding/asn1`, `encoding/xml`,
`html/template`, `net/http`, `net/url` 등 네트워크와 템플릿 처리 주변 보안 수정이 포함됐습니다.
Go 1.26.6에는 `net` 패키지 보안 수정도 함께 들어갔습니다.

Java 팀에서도 Go는 생각보다 자주 등장합니다. Kubernetes 주변 CLI, 사내 운영 도구, 배포 보조
프로그램, Terraform provider, 작은 webhook relay가 Go로 작성돼 있을 수 있습니다. 이 코드가
Spring Boot 애플리케이션과 같은 릴리스 파이프라인에 있다면 패치 우선순위도 같이 봐야 합니다.

특히 다음 위치는 점검 대상입니다.

```text
CI runner image
-> Go 기반 사내 CLI
-> Terraform 또는 Kubernetes 보조 도구
-> Spring Boot 배포 전후 자동화
```

Go 바이너리는 정적 빌드되어 오래 살아남기 쉽습니다. 그래서 `go.mod`만 보는 것으로는 부족합니다.
실제로 배포되는 binary가 어떤 Go 버전으로 빌드됐는지, Docker image 안에 오래된 binary가 남아
있는지, 릴리스 노트에 포함된 보안 패키지를 사용하는지까지 확인해야 합니다.

## 3. PostgreSQL 보안 릴리스와 PostgreSQL 14 EOL은 함께 봐야 합니다

PostgreSQL Global Development Group은 2026년 8월 13일 PostgreSQL 18.6, 17.11, 16.15, 15.19,
14.24를 공개했습니다. 공식 발표 기준 이 릴리스는 지원 중인 모든 버전의 업데이트이며, 28개
보안 취약점과 110개 이상의 버그를 수정합니다. 같은 공지는 PostgreSQL 19 Beta 3도 함께 언급했지만,
운영 기준으로는 beta가 아니라 지원 중인 stable minor 릴리스를 봐야 합니다.

더 중요한 문장은 PostgreSQL 14 EOL입니다. 공식 공지는 PostgreSQL 14가 2026년 11월 12일부터
수정을 받지 않는다고 안내합니다. PostgreSQL 14를 운영 환경에서 쓰고 있다면, 단순 minor patch
적용과 별개로 major upgrade 계획이 필요합니다.

Spring Boot와 JPA를 쓰는 팀은 DB minor 업데이트를 다음 흐름으로 검증하면 좋습니다.

| 단계 | 확인 항목 |
|---|---|
| staging 복원 | 실제 운영 스키마와 주요 인덱스가 같은지 확인합니다. |
| migration 재실행 | Flyway, Liquibase, 수동 SQL이 같은 순서로 통과하는지 봅니다. |
| JPA 쿼리 점검 | pagination, lock, JSON, array, full-text search 쿼리를 우선 확인합니다. |
| 연결 풀 확인 | HikariCP timeout, prepared statement, driver 버전을 함께 봅니다. |
| rollback 기준 | DB patch 후 되돌릴 수 있는 백업, 스냅샷, 점검 시간을 정합니다. |

보안 릴리스는 "나중에 한 번에" 처리하기 어렵습니다. 특히 EOL이 섞이면 minor patch와 major
upgrade가 같은 분기에 겹칠 수 있으므로, 이번 공지는 패치 작업과 업그레이드 로드맵을 분리해서
잡아야 한다는 신호입니다.

## 4. AWS Console-to-Code 확장은 콘솔 변경을 코드 리뷰 안으로 끌고 옵니다

AWS는 2026년 8월 17일 Console-to-Code가 26개 AWS 서비스를 추가로 지원하고, 교차 리전과
교차 브라우저 탭 작업 기록을 도입했다고 공지했습니다. 이 기능은 AWS Console에서 수행한 작업을
기록한 뒤 AWS CLI, CDK, CloudFormation 같은 코드 형태로 옮기는 데 초점을 둡니다.

이 흐름은 운영 실수 방지에 도움이 됩니다. 콘솔에서 한 번 눌러 만든 리소스가 문서에만 남는 대신,
코드 리뷰 가능한 변경으로 바뀔 수 있기 때문입니다. 다만 생성된 코드가 곧바로 운영 기준을 만족하는
것은 아닙니다.

Spring Boot 서비스의 AWS 인프라를 다룬다면 다음을 리뷰 기준에 넣어야 합니다.

| 리뷰 항목 | 이유 |
|---|---|
| 리전과 계정 경계 | 교차 리전 기록은 편하지만 잘못된 리전에 리소스를 만들 위험도 있습니다. |
| IAM 권한 | 생성 코드는 동작을 우선할 수 있으므로 최소 권한을 다시 줄여야 합니다. |
| 이름과 태그 | 임시 콘솔 값이 IaC에 그대로 들어가면 비용과 소유권 추적이 어렵습니다. |
| 상태 저장 리소스 | RDS, S3, queue 같은 리소스는 삭제 정책과 백업 정책을 별도로 봐야 합니다. |
| 재실행 가능성 | 한 번 만든 리소스를 다시 적용해도 안전한지 검증해야 합니다. |

콘솔 작업을 코드로 바꾸는 것은 좋은 출발점입니다. 하지만 최종 산출물은 여전히 사람이 읽고,
테스트하고, pull request로 검토해야 할 인프라 변경입니다.

## 5. k6의 문서 조회 흐름은 테스트 기준을 버전에 묶습니다

Grafana Labs는 2026년 8월 14일 `k6 x docs` 흐름을 소개했습니다. 공식 글 기준 이 명령은 k6
문서를 CLI에서 조회하게 해 주고, 한 번 조회한 뒤에는 로컬 캐시로 동작합니다. 더 중요한 점은
사용 중인 k6 버전에 맞는 문서를 제공한다는 것입니다. k6 2.0에서는 `k6 x docs`를 바로 사용할 수
있고, 1.7.0 이상에서는 별도 binary로 사용할 수 있습니다.

AI 코딩 에이전트를 함께 쓰는 팀에도 의미가 있습니다. 공식 글은 `docs` command가 agent skill을
포함해, 웹 검색이나 오래된 학습 데이터에 기대지 않고 k6 문서를 조회할 수 있다고 설명합니다.

성능 테스트는 작은 API 예제보다 버전 차이에 민감합니다. 옵션 이름, browser API, scenario 설정,
threshold 문법이 달라지면 테스트가 통과해도 의미가 바뀔 수 있습니다. Spring Boot API의 부하
테스트를 AI와 함께 작성한다면 다음 구조가 낫습니다.

```text
k6 버전 고정
-> k6 x docs로 해당 버전 문서 조회
-> 테스트 스크립트 생성
-> threshold와 scenario 리뷰
-> CI에서 같은 k6 버전으로 실행
```

AI가 테스트 코드를 빠르게 만들어도, 목표 처리량, 실패율, 지연 시간 percentile은 서비스 팀이
정해야 합니다. `k6 x docs` 같은 도구는 문서 추측을 줄여 줄 뿐이고, 성능 기준 자체를 대신 정해
주지는 않습니다.

## preview와 beta 발표는 운영 기준에서 분리했습니다

이번 주에는 OpenAI의 GPT-5.6 Sol Ultrafast limited preview, Grafana Cloud Frontend
Observability의 Session Replay public preview처럼 눈에 띄는 발표도 있었습니다. 둘 다 방향성은
중요합니다. 전자는 고성능 모델의 latency를 줄이는 흐름을 보여 주고, 후자는 frontend 관측성에서
사용자 여정을 시각적으로 재현하는 방향을 보여 줍니다.

다만 두 발표 모두 preview 성격이므로 이번 글의 안정 운영 체크리스트에는 넣지 않았습니다.
실무에서는 다음 정도로만 분리해 보는 편이 좋습니다.

- preview 기능은 PoC와 비용 추정에만 둡니다.
- 운영 장애 대응, 보안 감사, SLA 문서에는 stable 또는 GA 기능만 기준으로 씁니다.
- preview 결과가 좋아도 rollback 절차와 대체 경로를 먼저 정합니다.
