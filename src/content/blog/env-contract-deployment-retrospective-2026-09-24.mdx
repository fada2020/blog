> **검증 범위**
>
> 2026년 9월 24일에 Jenkins Pipeline 환경 변수 문서, Next.js 배포와 환경 변수 문서, Docker Compose 환경 변수 문서,
> Cloudflare Tunnel configuration 문서를 확인했습니다. 실제 업무일지의 회사명, 공개 도메인, 저장소명, Jenkins 작업명,
> 내부 포트, 계정, 컨테이너 이름과 운영 URL은 공개 글에서 일반화했습니다. 이 글은 관리자 콘솔 배포 설정을 정리한 실무
> 회고이며, 특정 운영 시스템의 현재 상태를 증명하는 글이 아닙니다.

## 결론부터 말하면

배포 설정이 여러 파일에 흩어지면 장애는 코드보다 설정에서 먼저 납니다. 포트는 Docker Compose에 있고, 공개 URL은
Jenkinsfile에 있고, Next.js 빌드 인자는 별도 `.env`에 있고, 터널 원본 주소는 또 다른 화면에 있으면 어느 값이 진짜인지
알 수 없습니다.

이번 회고의 핵심은 세 가지였습니다.

- 앱이 필요로 하는 실행 값을 중앙 환경 파일 한 곳에서 시작하게 했습니다.
- Jenkins, Docker, 로컬 실행, 터널 점검이 같은 값을 읽도록 맞췄습니다.
- 자동 수정하기 어려운 외부 설정은 "불일치하면 실패"하는 검증으로 분리했습니다.

처음에는 단순히 production 서버가 외부에서 열리지 않는 문제처럼 보였습니다. 실제로는 빌드 시점 값, 런타임 값, 컨테이너
바인딩, 터널 origin 주소가 서로 다른 파일에서 조금씩 어긋난 상태였습니다.

## 문제가 된 모양

관리자 콘솔 같은 작은 웹앱도 실행 경로가 몇 갈래로 나뉩니다.

| 경로 | 흔히 갖는 설정 |
|---|---|
| 로컬 개발 | `PORT`, `HOSTNAME`, API base URL |
| Next.js build | 공개 클라이언트 변수, production build mode |
| Docker runtime | 컨테이너 포트, health check, restart policy |
| Jenkins deploy | 이미지 이름, 컨테이너 이름, 배포 대상 |
| 터널 또는 reverse proxy | public hostname, service URL, health route |

각 경로가 자기 파일을 들고 있으면 처음에는 빠르게 움직입니다. 하지만 한 번 배포가 실패하면 질문이 늘어납니다.

```text
Next.js는 어느 URL을 보고 빌드됐는가
Docker 컨테이너는 127.0.0.1에만 묶였는가, 0.0.0.0으로 열렸는가
Jenkins가 넘긴 포트와 Compose가 읽은 포트가 같은가
터널의 service URL은 현재 컨테이너 주소와 같은가
아직 준비되지 않은 환경 URL을 빈 값으로 둘 수 있는가
```

이 질문에 사람이 파일 여러 개를 열어 답해야 한다면 배포 계약이 약한 상태입니다.

## 선택한 설계

중앙 설정 파일을 하나 두고, 모든 실행자가 그 파일을 읽도록 했습니다.

```text
config/app.env
-> local dev command
-> Jenkins build arguments
-> Docker runtime environment
-> health check script
-> tunnel consistency check
```

<Mermaid title="중앙 환경 설정 계약">
{`flowchart TD
  Env["Central env file"] --> Local["Local dev command"]
  Env --> Jenkins["Jenkins pipeline"]
  Env --> Docker["Docker runtime"]
  Env --> Health["Health check"]
  Env --> TunnelCheck["Tunnel consistency check"]
  TunnelCheck --> External["Externally managed tunnel config"]
  Jenkins --> Deploy["Replace container"]
  Docker --> App["Next.js production server"]
`}
</Mermaid>

중앙 파일에는 secret 값을 넣지 않았습니다. 포트, 호스트, 공개 URL, 환경별 API URL처럼 배포자가 알아야 하는 비밀이 아닌
계약만 모았습니다. Secret은 Jenkins credential, 런타임 secret store, 별도 비공개 설정 경계에 남겨야 합니다.

## Jenkins에서는 동적 설정도 명시적으로 다룹니다

Jenkins Pipeline 문서는 `environment` directive와 `withEnv`를 통해 step에 환경 변수를 줄 수 있다고 설명합니다. 또한
credential은 Jenkins가 관리하는 값으로 주입해야 하며 Jenkinsfile에 직접 쓰면 안 됩니다.

이번 유형의 배포에서 조심할 점은 "동적으로 env key를 만든다"는 편의가 Jenkins 보안 샌드박스와 충돌할 수 있다는 점입니다.
안전한 방향은 단순합니다.

```groovy
stage("Load configuration") {
    steps {
        sh "./scripts/print-runtime-env.sh config/app.env"
    }
}

stage("Deploy") {
    environment {
        APP_ENV_FILE = "config/app.env"
    }
    steps {
        sh "./scripts/deploy-container.sh"
    }
}
```

설명용 예시라 세부는 줄였지만 원칙은 같습니다. Jenkinsfile은 어떤 경로로 배포하는지 보여 주고, 설정 해석은 스크립트가
일관되게 맡습니다. 준비되지 않은 환경 URL은 `준비 중`이라는 상태로 허용할지, 배포 실패로 볼지 스크립트에서 명시해야 합니다.

## Next.js는 build-time과 runtime 값을 구분해야 합니다

Next.js 배포 문서는 Node.js server, Docker container, static export 같은 배포 선택지를 나눕니다. 환경 변수 문서에서는
브라우저로 전달되는 `NEXT_PUBLIC_*` 값이 build 시점에 고정될 수 있음을 설명합니다.

이 말은 운영에서 중요합니다.

```text
서버 런타임에서만 읽는 값
-> 컨테이너 실행 시 주입 가능

브라우저 번들에 들어가는 공개 값
-> 빌드 시점에 고정될 수 있음
```

하나의 Docker 이미지를 여러 환경에 승격하려면, 공개 클라이언트 값까지 이미지 안에 박아 넣는 설계를 피하거나, 환경별 이미지를
명시적으로 빌드해야 합니다. 어느 쪽이든 "언제 결정되는 값인가"가 문서화되어야 합니다.

관리자 콘솔에서는 공개 URL과 API 선택지가 UI와 health check에 모두 영향을 줬습니다. 그래서 중앙 설정 파일에 값을 모으되,
브라우저에 노출되는 값과 서버 내부 값은 이름과 전달 경로를 분리했습니다.

## Docker Compose의 `.env`와 컨테이너 env는 다릅니다

Docker Compose 문서는 project name, compose file, env file 등 Compose 자체가 해석하는 환경 변수와 service 컨테이너에
전달되는 환경 변수를 구분합니다. 또한 `environment`와 `env_file`을 함께 쓸 때 우선순위가 생깁니다.

혼동이 잦은 지점은 이것입니다.

```text
Compose 파일 보간에 쓰는 값
!= 컨테이너 프로세스가 런타임에 읽는 값
```

예를 들어 포트 매핑에 쓰는 `${APP_PORT}`와 Next.js 서버가 읽는 `PORT`가 서로 다른 출처에서 오면 컨테이너는 떠 있지만
외부에서는 닫힌 것처럼 보일 수 있습니다. 중앙 설정을 쓴 이유는 이 차이를 없애기 위해서가 아니라, 차이가 드러나는 위치를
한 곳으로 모으기 위해서였습니다.

## 터널 설정은 자동 수정보다 검증이 먼저입니다

Cloudflare Tunnel 문서는 public hostname을 local service에 매핑하고, ingress rule로 여러 origin을 나눌 수 있다고 설명합니다.
로컬 관리 tunnel에서는 `cloudflared tunnel ingress rule`로 어떤 rule이 적용되는지 확인할 수도 있습니다.

하지만 실제 운영에서는 tunnel 설정이 애플리케이션 저장소 밖에서 관리될 수 있습니다. 이 경우 앱 배포 자동화가 tunnel 설정을
마음대로 고치는 것은 위험합니다. 대신 앱 쪽 검증 스크립트가 이렇게 말해야 합니다.

```text
중앙 설정의 PUBLIC_URL
중앙 설정의 ORIGIN_PORT
현재 tunnel service URL
-> 일치하지 않으면 배포 전 실패
```

이 접근은 느려 보이지만, 장애 때 훨씬 낫습니다. 자동화가 외부 설정을 몰래 바꾸지 않았고, 어느 값이 맞지 않는지만 알려 주기
때문입니다.

## 검증은 상태를 나눠 기록합니다

이번 유형의 작업에서 가장 위험한 표현은 "배포 설정 완료"입니다. 실제로는 여러 상태가 있습니다.

- 설정 파일을 하나로 모았습니다.
- 로컬 개발 명령이 새 설정을 읽었습니다.
- Next.js production build가 통과했습니다.
- Docker 컨테이너가 새 설정으로 기동했습니다.
- Jenkins가 checkout, test, build, container replace를 성공했습니다.
- 외부 public hostname의 health check가 성공했습니다.
- 실제 로그인, 역할 관리, 데이터 쓰기 같은 사용자 경로를 검증했습니다.

이 상태들은 서로 다릅니다. 특히 health check HTTP 200은 실제 사용자 시나리오 성공과 같지 않습니다. 반대로 사용자 경로가
아직 미검증이라고 해서 컨테이너 교체 성공까지 부정하면 안 됩니다. 운영 기록은 상태를 정확히 나누는 편이 나중에 도움이 됩니다.

## 배운 점

첫째, 환경 설정의 진실 공급원은 적을수록 좋습니다. 파일 하나가 모든 비밀을 품어야 한다는 뜻이 아니라, 비밀이 아닌 실행
계약은 한 곳에서 출발해야 한다는 뜻입니다.

둘째, build-time 값과 runtime 값을 이름만으로 구분하지 않으면 결국 배포 이미지가 환경을 품습니다. 특히 브라우저 번들에
들어가는 공개 값은 "컨테이너 실행 때 바꾸면 되겠지"라고 생각하면 늦습니다.

셋째, 외부 설정을 자동으로 고치는 것보다 불일치를 검출하는 편이 안전할 때가 있습니다. Tunnel, DNS, 인증서, ALB listener처럼
앱 저장소 밖에 있는 설정은 자동 수정 범위를 명확히 승인받아야 합니다.

넷째, 설정 중앙화는 리팩터링이 아니라 운영 계약 정리입니다. 코드가 짧아졌는지보다, 실패했을 때 어느 값이 잘못됐는지 바로
말할 수 있는지가 더 중요했습니다.
