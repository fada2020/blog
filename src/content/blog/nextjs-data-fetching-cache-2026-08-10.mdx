## 결론부터 말하면

Next.js App Router에서 데이터 조회의 핵심은 `fetch`를 어디에 쓰느냐보다 **응답을 언제 다시
가져와야 하는지 명시하는 것**입니다.

Spring Boot 개발자는 보통 Controller가 요청을 받고 Service가 데이터를 조립한 뒤 DTO를 반환하는
흐름에 익숙합니다. Next.js App Router에서는 `page.tsx` 같은 Server Component가 렌더링 중에
백엔드 API를 호출할 수 있습니다. 이때 화면에 필요한 데이터는 브라우저로 보내기 전에 서버에서
조립할 수 있지만, 캐시 정책을 흐리게 두면 "왜 이전 값이 보이지?" 또는 "왜 매번 느리지?"라는 문제가
생깁니다.

이번 글의 목표는 단순합니다.

**목록, 상세, 대시보드 요약처럼 성격이 다른 데이터를 같은 방식으로 가져오지 않는 기준을 세웁니다.**

## 이번 주 개념

App Router에서 `page.tsx`, `layout.tsx`, Server Component는 기본적으로 서버 쪽에서 실행될 수
있습니다. 그래서 다음처럼 렌더링 함수 안에서 `await fetch(...)`를 사용할 수 있습니다.

```tsx
// app/products/page.tsx
export default async function ProductsPage() {
  const products = await getProducts();

  return (
    <main>
      <h1>상품</h1>
      <ProductTable products={products} />
    </main>
  );
}
```

이 코드는 브라우저가 처음 화면을 받은 뒤 `useEffect`로 다시 API를 호출하는 방식과 다릅니다.
서버가 화면을 만들 때 데이터를 함께 가져옵니다. React Server Components 문서도 Server Component가
빌드 시점 또는 요청 시점에 실행될 수 있고, async component에서 `await`를 사용할 수 있다고 설명합니다.

하지만 "서버에서 호출한다"는 말이 곧 "항상 최신"이라는 뜻은 아닙니다. Next.js는 서버의 `fetch`에
캐시와 재검증 옵션을 붙일 수 있습니다. 따라서 데이터 조회 코드를 작성할 때는 먼저 아래 질문에
답해야 합니다.

| 질문 | 예시 | 기본 판단 |
|---|---|---|
| 사용자마다 달라지는가 | 내 알림, 내 주문, 관리자 검색 결과 | 요청마다 새로 조회합니다. |
| 공개 데이터이고 자주 바뀌지 않는가 | 공지 목록, 상품 카탈로그, 문서 목차 | 일정 시간 캐시를 검토합니다. |
| 변경 직후 바로 반영되어야 하는가 | 저장 후 상세 화면, 운영 대시보드 카운터 | 저장 경로에서 재검증합니다. |
| 실패 시 이전 값을 보여도 되는가 | 마케팅 배너, 공개 통계 | 캐시 지속 시간을 더 길게 잡을 수 있습니다. |

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 HTTP 요청 처리와 데이터 조회 책임을 보통 이렇게 나눕니다.

```java
@RestController
@RequestMapping("/api/products")
class ProductController {

    private final ProductService productService;

    @GetMapping
    List<ProductResponse> list() {
        return productService.findVisibleProducts();
    }
}
```

여기서 Controller는 URL, 파라미터, 응답 계약을 담당합니다. Service는 도메인 규칙과 트랜잭션 경계를
담당합니다. 캐시는 별도 계층에서 명시합니다.

```java
@Service
class ProductService {

    @Cacheable(cacheNames = "visibleProducts")
    List<ProductResponse> findVisibleProducts() {
        return productRepository.findVisibleProducts();
    }
}
```

Spring에서는 `@Cacheable`, `@CacheEvict`, Redis TTL, HTTP `Cache-Control` 같은 선택지가 분리되어
있습니다. 그래서 캐시가 어디에 있는지 비교적 명확하게 말할 수 있습니다.

Next.js에서는 이 판단이 화면 렌더링 코드 근처로 내려옵니다. `fetch` 호출 하나가 "매 요청 조회",
"시간 기반 재검증", "태그 기반 재검증" 같은 정책을 함께 가질 수 있습니다. 편하지만, 정책을 쓰지
않고 암묵적으로 두면 읽는 사람이 의도를 알기 어렵습니다.

## Next.js에서는 무엇이 다른가

가장 큰 차이는 화면 서버가 직접 데이터를 가져올 수 있다는 점입니다.

```tsx
// app/products/data.ts
type Product = {
  id: string;
  name: string;
  price: number;
  updatedAt: string;
};

export async function getProducts(): Promise<Product[]> {
  const response = await fetch(`${process.env.API_BASE_URL}/api/products`, {
    cache: "no-store",
  });

  if (!response.ok) {
    throw new Error(`상품 목록 조회 실패: ${response.status}`);
  }

  return response.json();
}
```

`cache: "no-store"`는 요청마다 새로 가져와야 한다는 의도를 코드에 남깁니다. 사용자별 데이터,
권한에 따라 달라지는 목록, 운영 화면 검색 결과처럼 오래된 응답을 보여주면 안 되는 데이터에 맞습니다.

반대로 공개 카탈로그처럼 잠깐 오래된 값이 허용되는 데이터라면 시간 기반 재검증을 사용할 수 있습니다.

```tsx
export async function getPublicProducts(): Promise<Product[]> {
  const response = await fetch(`${process.env.API_BASE_URL}/api/public/products`, {
    next: {
      revalidate: 300,
      tags: ["public-products"],
    },
  });

  if (!response.ok) {
    throw new Error(`공개 상품 조회 실패: ${response.status}`);
  }

  return response.json();
}
```

이 예제의 의도는 "최대 5분 정도 오래된 공개 목록은 허용하고, 필요하면 `public-products` 태그로
무효화할 수 있다"입니다. Spring의 `@Cacheable`과 완전히 같지는 않지만, 읽는 사람이 기대 수명을
파악할 수 있다는 점이 중요합니다.

## 대응 개념 비교

Spring Boot와 Next.js를 일대일로 맞추려고 하면 오히려 혼란이 생깁니다. 가까운 역할만 비교하면
아래처럼 볼 수 있습니다.

| Spring Boot에서 하던 일 | Next.js App Router에서 가까운 위치 | 주의할 점 |
|---|---|---|
| Controller가 API 응답을 반환 | `page.tsx`가 화면을 렌더링 | `page.tsx`는 도메인 API 계약이 아니라 UI 진입점입니다. |
| Service가 도메인 규칙 수행 | 기존 Spring API에 유지 | Next.js에 검증과 트랜잭션을 복제하지 않습니다. |
| `@Cacheable`로 조회 결과 캐시 | `fetch` 옵션, 태그 재검증, Cache Components | 캐시 정책을 호출부에서 읽히게 둡니다. |
| `@CacheEvict`로 변경 후 무효화 | `revalidateTag`, `revalidatePath` | 저장 성공 이후 어떤 화면을 갱신할지 명시합니다. |
| DTO로 화면에 필요한 모양 제공 | Server Component에서 화면 전용 조립 | 비밀값과 내부 필드는 브라우저로 넘기지 않습니다. |

## 최소 실행 예제

작은 상품 목록 화면을 만든다고 가정하겠습니다. Spring Boot API는 공개 상품 목록과 관리자 상품
목록을 따로 제공합니다.

```text
GET /api/public/products
GET /api/admin/products
POST /api/admin/products
```

Next.js 쪽에서는 데이터 성격에 따라 함수를 분리합니다.

```tsx
// app/products/data.ts
type Product = {
  id: string;
  name: string;
  price: number;
  status: "VISIBLE" | "HIDDEN";
};

async function readJson<T>(path: string, init?: RequestInit): Promise<T> {
  const response = await fetch(`${process.env.API_BASE_URL}${path}`, init);

  if (!response.ok) {
    throw new Error(`API 요청 실패: ${response.status}`);
  }

  return response.json();
}

export function getPublicProducts() {
  return readJson<Product[]>("/api/public/products", {
    next: {
      revalidate: 300,
      tags: ["public-products"],
    },
  });
}

export function getAdminProducts() {
  return readJson<Product[]>("/api/admin/products", {
    cache: "no-store",
  });
}
```

공개 화면은 약간의 지연을 허용합니다.

```tsx
// app/products/page.tsx
import { getPublicProducts } from "./data";

export default async function ProductsPage() {
  const products = await getPublicProducts();

  return (
    <main>
      <h1>상품</h1>
      <ul>
        {products.map((product) => (
          <li key={product.id}>
            {product.name} - {product.price.toLocaleString()}원
          </li>
        ))}
      </ul>
    </main>
  );
}
```

관리자 화면은 요청마다 새 값을 봅니다.

```tsx
// app/admin/products/page.tsx
import { getAdminProducts } from "@/app/products/data";

export default async function AdminProductsPage() {
  const products = await getAdminProducts();

  return (
    <main>
      <h1>상품 관리</h1>
      <ProductTable products={products} />
    </main>
  );
}
```

상품 저장 이후 공개 목록을 바로 갱신해야 한다면 저장 경로에서 태그를 재검증합니다. 실제 저장 권한,
검증, 트랜잭션은 Spring Boot API가 결정하고, Next.js는 저장 성공 이후 화면 캐시를 정리하는 역할만
맡습니다.

```ts
// app/admin/products/actions.ts
"use server";

import { revalidateTag } from "next/cache";

export async function createProduct(formData: FormData) {
  const response = await fetch(`${process.env.API_BASE_URL}/api/admin/products`, {
    method: "POST",
    body: JSON.stringify({
      name: formData.get("name"),
      price: Number(formData.get("price")),
    }),
    headers: {
      "Content-Type": "application/json",
    },
  });

  if (!response.ok) {
    throw new Error(`상품 저장 실패: ${response.status}`);
  }

  revalidateTag("public-products");
}
```

여기서 중요한 것은 `createProduct`가 도메인 규칙의 최종 소유자가 아니라는 점입니다. 가격이 유효한지,
상품을 공개할 수 있는지, 현재 사용자가 저장 권한을 갖는지는 Spring Boot API가 판단해야 합니다.
Next.js의 Server Function은 화면에서 서버 동작을 호출하는 연결점으로만 둡니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 Server Component를 Spring Controller처럼 보는 것입니다. `page.tsx`는 URL에 대응하지만
JSON API 계약을 제공하는 Controller가 아닙니다. 화면을 렌더링하는 서버 컴포넌트입니다. 외부 시스템이
의존하는 API 계약은 Spring Boot에 남겨 두는 편이 안전합니다.

두 번째 오해는 `fetch` 옵션을 생략해도 의도가 전달된다고 생각하는 것입니다. 팀원은 그 호출이 매번
새로 조회되어야 하는지, 5분 캐시가 괜찮은지, 저장 후 재검증이 필요한지 알 수 없습니다. 공개 데이터와
사용자별 데이터를 같은 헬퍼로 묶고 옵션을 숨기면 이 문제가 커집니다.

세 번째 오해는 모든 데이터를 Client Component에서 `useEffect`로 가져오는 것입니다. 검색어 입력,
드롭다운, 모달처럼 브라우저 상태가 필요한 부분은 Client Component가 맞습니다. 하지만 첫 화면에 필요한
데이터까지 전부 브라우저에서 다시 가져오면 초기 HTML이 빈 상태가 되고, 서버에서 처리할 수 있는 조립
작업도 클라이언트 번들로 밀려납니다.

네 번째 오해는 캐시를 성능 기능으로만 보는 것입니다. 캐시는 사용자에게 어떤 시점의 사실을 보여줄지
정하는 제품 계약입니다. 주문 상태, 결제 상태, 관리자 승인 상태처럼 시간 차이가 문제를 만들 수 있는
데이터에는 성능보다 정확성이 먼저입니다.

## 정리

Next.js App Router의 데이터 조회는 "서버에서 fetch를 쓸 수 있다"에서 끝나지 않습니다. 진짜 설계
질문은 각 데이터가 얼마나 오래 유효한지, 변경 후 어떤 화면을 갱신해야 하는지, 도메인 판단을 어느
서버가 소유하는지입니다.

Spring Boot 개발자라면 이미 Controller, Service, Repository와 캐시 경계를 나눠 본 경험이 있습니다.
그 감각을 App Router로 가져오되, `page.tsx`를 새 도메인 서버로 키우지 않는 것이 중요합니다. Next.js는
화면에 필요한 데이터를 가까운 곳에서 조립하고, Spring Boot는 여전히 권한과 트랜잭션, 도메인 규칙을
책임지는 구조가 가장 이해하기 쉽습니다.
