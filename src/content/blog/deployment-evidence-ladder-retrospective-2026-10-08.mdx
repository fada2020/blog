> **검증 범위**
>
> 2026년 10월 8일에 Spring Boot 4.1.1 Actuator endpoint 문서, Amazon ECS service deployment
> event/API 문서, Jenkins Lockable Resources Pipeline Step 문서, Playwright assertion 문서를 확인했습니다.
> 실제 업무일지의 조직명, 저장소명, 서버명, 계정, 내부 URL, 사용자 식별자, 의료·운영 데이터는 공개 글에서
> 제거하거나 일반화했습니다. 이 글은 배포 증거를 분리해 기록하는 방법에 대한 회고이며, 특정 운영 환경의
> 성공을 증명하는 글이 아닙니다.

## 결론부터 말하면

배포 회고에서 가장 위험한 표현은 "성공했습니다" 하나로 모든 상태를 덮는 일이었습니다. 커밋이 원격에 올라간 것,
CI가 빌드한 것, 컨테이너가 새 이미지로 떠 있는 것, `/health`가 200을 준 것, 인증된 화면에서 사용자가 실제 흐름을
완료한 것은 서로 다른 증거입니다.

이번 작업을 공개 가능한 교훈으로 줄이면 이렇습니다.

- 빌드 성공은 배포 성공이 아닙니다.
- 배포 성공은 실제 화면 검증이 아닙니다.
- 읽기 전용 DB 확인은 사용자 동선 검증이 아닙니다.
- Slack, 메일, 앱 push 같은 외부 전달은 sender-side 기록과 recipient-side 확인을 분리해야 합니다.
- 회고 문서에는 "확인한 것"과 "아직 확인하지 않은 것"을 같은 표 안에 둬야 합니다.

Spring Boot 개발자에게 익숙한 말로 바꾸면, health indicator가 `UP`이라고 해서 업무 transaction 전체가 성공했다는
뜻은 아닙니다. `UP`은 그 endpoint가 정의한 준비 상태입니다. 업무 기능의 종단 성공은 별도의 테스트와 증거가 필요합니다.

## 문제가 된 모양

운영 작업은 보통 여러 저장소와 여러 환경을 지나갑니다.

```text
코드 반영
-> 테스트와 빌드
-> 배포 job 실행
-> 컨테이너 교체
-> health 확인
-> 읽기 전용 서버 확인
-> 인증된 화면 확인
-> 실제 사용자 흐름 확인
```

문제는 각 단계가 모두 초록색처럼 보인다는 점입니다. CI는 `SUCCESS`, ECS는 rollout 완료, Jenkins는 성공, health는
200, Playwright는 통과라고 말합니다. 하지만 어느 단계도 혼자서 "실제 사용자가 원하는 업무를 끝냈다"를 증명하지 않습니다.

| 증거 | 증명하는 것 | 아직 증명하지 않는 것 |
|---|---|---|
| commit SHA push | 원격 저장소에 코드가 있음 | 서버가 그 코드를 실행 중임 |
| CI build success | 산출물을 만들 수 있음 | 대상 환경 배포 완료 |
| ECS rollout completed | service가 steady state에 도달 | 업무 API가 올바른 응답을 반환 |
| Actuator health 200 | health indicator 기준 준비 상태 | 인증·권한·화면 동선 완료 |
| 읽기 전용 DB 조회 | 조회 시점의 저장 상태 | 사용자가 앱에서 성공적으로 처리 |
| Playwright 화면 통과 | 테스트 데이터의 화면 동선 | 실제 계정·실제 데이터 성공 |
| Slack/API sender record | 발송 요청 성공 | 수신자가 실제 화면에서 확인 |

이 차이를 기록하지 않으면 다음 사람이 "어디까지 끝났는가"를 다시 조사해야 합니다.

<Mermaid title="배포 증거 사다리">

## 기존 설계의 한계

기존 회고는 결과가 많은 날일수록 "성공"이라는 단어를 자주 썼습니다. 각각의 성공은 사실이지만, 의미가 달랐습니다.

- 배포 job이 성공했습니다.
- 서버 health가 200이었습니다.
- 읽기 전용 확인에서 값이 맞았습니다.
- 테스트 데이터로 화면 동선이 통과했습니다.
- 실제 계정 검증은 남았습니다.

이 문장들이 떨어져 있으면 읽는 사람이 직접 연결해야 합니다. 더 큰 문제는 남은 검증이 문서 맨 아래로 밀려난다는 점입니다.
실무에서는 남은 검증이 다음 장애를 막는 가장 중요한 정보일 때가 많습니다.

그래서 회고 문서의 기본 단위를 "성공/실패"가 아니라 **증거와 한계**로 바꾸는 것이 필요했습니다.

## 선택한 설계

작업 단위마다 작은 evidence ledger를 둡니다.

```text
대상
-> 변경한 것
-> 확인한 증거
-> 이 증거가 뜻하지 않는 것
-> 남은 검증
```

예시는 이렇게 씁니다.

| 대상 | 확인한 증거 | 아직 뜻하지 않는 것 | 다음 확인 |
|---|---|---|---|
| API 서버 | 새 이미지 실행, readiness 200 | 실제 앱 요청 성공 | 인증된 요청으로 대표 API 확인 |
| 관리자 화면 | 테스트 데이터로 화면 이동 성공 | 실제 계정 권한 검증 | 승인된 계정으로 역할별 접근 확인 |
| 알림 전달 | sender-side delivery record | 수신 채널 화면 확인 | 실제 채널에서 메시지 도착 확인 |
| DB 변경 | migration 이력과 row count 확인 | 장기 재발 방지 완료 | 재발 조건에서 부하·잠금 재확인 |

이 표의 장점은 과장하기 어렵다는 것입니다. 증거가 무엇인지 쓰면, 그 증거가 증명하지 않는 범위도 자연스럽게 드러납니다.

## 구현은 문장보다 체크포인트입니다

자동화 스크립트나 배포 문서도 이 구조를 따르게 할 수 있습니다.

```ts
type Evidence = {
  target: string;
  observed: string;
  proves: string;
  doesNotProve: string;
  nextCheck: string;
};

const evidence: Evidence[] = [
  {
    target: "app-api",
    observed: "new task definition reached steady state and /actuator/health returned 200",
    proves: "the selected runtime can start and pass configured health indicators",
    doesNotProve: "an authenticated user completed the business workflow",
    nextCheck: "run the user-visible workflow with approved test data",
  },
];
```

핵심은 `doesNotProve`를 빈칸으로 두지 않는 것입니다. "변경 없음"이라도 명시합니다. 실제로 증명하지 않는 범위를
적어 두면, 배포 후 대화가 짧아집니다.

Spring Boot 서비스에서는 Actuator health를 너무 많은 의미로 쓰지 않는 것도 중요합니다. health endpoint는 준비 상태를
확인하는 좋은 신호지만, 업무 권한과 화면 동선까지 자동으로 검증하지 않습니다. 업무 검증은 API 테스트, 브라우저 테스트,
읽기 전용 저장값 확인을 따로 둡니다.

## 시행착오

첫 번째 시행착오는 "배포 성공"을 환경별로 같은 뜻으로 쓴 것입니다. 어떤 환경은 실제 실행 배포였고, 어떤 환경은 브랜치
반영만 완료된 상태였습니다. 이 둘을 같은 줄에 놓으면 나중에 실제 운영자가 오해할 수 있습니다.

두 번째 시행착오는 "화면 확인"이라는 표현이 너무 넓었다는 점입니다. 공개 로그인 페이지 HTTP 200, 테스트 데이터 기반
Playwright 동선, 실제 계정 로그인 후 권한 확인은 서로 다릅니다. Playwright assertion 문서처럼 locator가 기대 상태가 될
때까지 재시도하는 검증은 강력하지만, 테스트 데이터의 범위를 벗어나지는 않습니다.

세 번째 시행착오는 읽기 전용 확인을 종단 성공처럼 말하기 쉬웠다는 점입니다. DB row count, migration history, job status는
매우 중요한 근거입니다. 하지만 앱이 같은 값을 실제 요청으로 만들고, 화면이 그것을 읽고, 사용자가 기대한 상태로 확인했다는
증거와는 다릅니다.

## 검증을 단계별로 씁니다

실무에서는 아래 순서로 표현을 제한하면 도움이 됩니다.

| 단계 | 쓸 수 있는 표현 | 피해야 할 표현 |
|---|---|---|
| 테스트 통과 | "로컬/CI 테스트가 통과했습니다" | "기능이 운영에서 동작합니다" |
| 배포 job 성공 | "배포 job이 성공했습니다" | "사용자 동선이 검증됐습니다" |
| health 확인 | "health indicator 기준 정상입니다" | "전체 서비스가 정상입니다" |
| 읽기 전용 확인 | "조회 시점 값이 일치합니다" | "장기 재발이 없습니다" |
| 브라우저 테스트 | "테스트 데이터 동선이 통과했습니다" | "실제 계정 검증 완료" |
| 실제 계정 검증 | "승인된 계정으로 종단 확인했습니다" | "모든 사용자 조건 완료" |

이 표는 겸손해 보이기 위한 장치가 아닙니다. 운영 판단을 더 빠르게 하기 위한 장치입니다. 다음 사람이 어디서부터 이어서
확인해야 하는지 바로 알 수 있습니다.

## 작은 실습: 배포 결과 문장을 쪼갭니다

아래 문장을 더 안전하게 바꿔 보세요.

```text
배포 성공했고 화면도 정상입니다.
```

좋은 문장은 더 깁니다.

```text
배포 job은 성공했고 새 컨테이너의 readiness와 Actuator health는 정상입니다.
테스트 데이터로 브라우저 동선 3개를 확인했습니다.
승인된 실제 계정의 권한별 조회와 실제 사용자 데이터 기반 종단 검증은 아직 남아 있습니다.
```

길어졌지만 정보량이 늘었습니다. 특히 마지막 문장이 중요합니다. 남은 검증을 숨기지 않아야 다음 작업이 정확해집니다.

## 배운 점

배포 기록은 축하 메시지가 아니라 인수인계 문서입니다. 초록색 배지가 많아도 각 배지가 무엇을 증명하는지 다릅니다.

이번 회고의 문장은 이렇습니다.

> 성공 로그는 증거의 시작점이지, 종단 검증의 대체물이 아닙니다.

그 차이를 문서와 자동화 결과에 남기면 장애 대응이 차분해집니다. 이미 확인한 것을 다시 확인하지 않아도 되고,
아직 확인하지 않은 것을 확인한 것처럼 착각하지 않아도 됩니다.

## 실무 체크리스트

- [ ] commit, build, deploy, runtime health, 화면 검증, 실제 종단 검증을 별도 상태로 기록합니다.
- [ ] 각 증거마다 "증명하지 않는 것"을 함께 씁니다.
- [ ] Actuator health와 업무 기능 성공을 같은 문장으로 합치지 않습니다.
- [ ] 읽기 전용 DB 확인과 앱 요청 성공을 구분합니다.
- [ ] 테스트 데이터 브라우저 검증과 실제 계정 검증을 구분합니다.
- [ ] sender-side 발송 기록과 recipient-side 수신 확인을 구분합니다.
- [ ] 남은 검증은 문서 맨 아래가 아니라 해당 작업 표 안에 둡니다.
