## 결론부터 말하면

요청이 취소됐다고 해서 모든 코드가 즉시 멈추는 것은 아닙니다. coroutine은 cooperative cancellation을 따르므로
취소 가능한 suspend 지점에서 취소를 관찰합니다. 그래서 리소스 반환, MDC 정리, 잠금 해제처럼 **반드시 끝나야 하는
정리**는 `try/finally`에 두는 것이 기본입니다.

`NonCancellable`은 이 기본을 대체하는 도구가 아닙니다. `finally` 안에서 suspend 호출이 꼭 필요한 아주 작은 구간에만
`withContext(NonCancellable)`로 씁니다. HTTP 요청 취소 뒤에 원격 API를 더 호출하거나 업무 데이터를 "마무리"하려는
용도로 넓게 쓰면, 요청 lifecycle과 분리된 작업을 숨기는 결과가 됩니다.

- 취소는 오류가 아니라 정상적인 lifecycle 신호일 수 있습니다.
- `finally`는 connection, semaphore, MDC처럼 지역 자원을 되돌리는 기본 위치입니다.
- suspend 정리가 꼭 필요할 때만 `withContext(NonCancellable)`로 범위를 좁힙니다.
- 재시도·영속성·사용자 영향이 있는 후속 업무는 outbox나 queue로 넘겨야 합니다.

## 취소와 정리의 경계

Spring MVC의 요청 thread는 `finally`에서 `ThreadLocal`과 MDC를 지우는 모델에 익숙합니다. coroutine도 같은
원칙을 갖지만, suspend/resume 중 thread가 바뀔 수 있어 정리를 thread에 묶어 생각하면 안 됩니다. `Job`의
취소와 자원의 생명주기를 코드 구조로 함께 표현해야 합니다.

<Mermaid title="요청 취소와 정리의 올바른 경계">
{`flowchart LR
  Request["HTTP request / Job"] --> Work["cancellable work"]
  Work -->|cancelled| Finally["finally: release local resource"]
  Finally --> NeedSuspend{"suspending cleanup needed?"}
  NeedSuspend -->|no| Done["finish"]
  NeedSuspend -->|yes, narrow| Shield["withContext(NonCancellable)"]
  Shield --> Done
  Work --> Durable["durable follow-up"]
  Durable --> Outbox["DB outbox / queue"]
  Outbox --> Worker["managed worker"]
`}
</Mermaid>

여기서 가장 중요한 질문은 "이 일이 요청 안에서 끝나야 하는가"입니다. 로그 span 종료, 파일 handle close,
임시 lock 반납은 요청과 한 몸입니다. 반면 결제 알림, 이메일 발송, 외부 시스템 동기화는 요청이 사라져도 추적·재시도되어야
합니다. 후자를 `NonCancellable`로 붙잡으면 timeout, 재시도, 운영 관측이 없는 background task가 됩니다.

## Java/Spring의 try/finally와 비교하기

Java에서는 대개 이렇게 자원을 반납합니다.

```java
public Report load(String id) {
    Lock lock = locks.acquire(id);
    try {
        return client.fetch(id);
    } finally {
        lock.release();
        MDC.remove("requestId");
    }
}
```

Kotlin의 기본형도 같습니다. 다만 `fetch()`가 suspend 함수이고 호출자가 취소할 수 있다는 점이 다릅니다.

```kotlin
suspend fun load(id: String): Report {
    val lock = locks.acquire(id)
    try {
        return client.fetch(id) // cancellation point
    } finally {
        lock.release()
        MDC.remove("requestId")
    }
}
```

`finally` 안에서 단순한 메모리 정리나 close를 수행한다면 추가 장치가 필요 없습니다. 취소를 삼켜서 성공처럼 바꾸지도
말아야 합니다. `CancellationException`을 광범위한 `catch (Exception)`으로 잡아 fallback 응답으로 바꾸면,
상위 caller가 요청 취소를 알 수 없게 됩니다.

## 정말 suspend 정리가 필요할 때

예를 들어 coroutine 기반 클라이언트의 close가 suspend 함수이고, timeout이 난 뒤에도 protocol close frame을 아주
짧게 보내야 한다고 합시다. 이때는 다음처럼 정리 블록만 보호합니다.

```kotlin
import kotlinx.coroutines.NonCancellable
import kotlinx.coroutines.withContext

suspend fun fetchWithCleanup(): Payload {
    val session = client.openSession()
    try {
        return session.fetch()
    } finally {
        withContext(NonCancellable) {
            session.closeGracefully()
        }
    }
}
```

공식 API 문서가 경고하듯 `launch(NonCancellable)`이나 `async(NonCancellable)`는 해법이 아닙니다. 부모-자식 관계가
끊어져 부모가 완료를 기다리지 못하고, 자식 실패도 부모 lifecycle에 연결되지 않습니다. 보호해야 할 것은 독립 작업이 아니라
정리 명령 한 덩어리입니다.

| 요구 | 우선 선택 | 피해야 할 선택 |
| --- | --- | --- |
| 메모리·lock·MDC 반납 | `finally` | 취소를 무시하는 새 coroutine |
| 짧은 suspend close | `finally` + 좁은 `withContext(NonCancellable)` | 전체 요청을 `NonCancellable`로 감싸기 |
| DB transaction 종료 | framework의 transaction boundary | 임의 dispatcher 전환 |
| 반드시 재시도할 후속 업무 | outbox 또는 queue | 요청 coroutine에서 무기한 실행 |
| 요청 취소 기록 | `CancellationException`을 다시 전파 | 일반 실패와 같은 fallback 처리 |

## Spring Boot 서비스에서의 실전 규칙

트랜잭션은 특히 보수적으로 다뤄야 합니다. transaction manager가 rollback/commit을 책임지는 범위 안에서 임의의
`NonCancellable` 원격 호출을 넣으면, DB commit 여부와 외부 side effect 순서가 어긋날 수 있습니다. 주문 저장 뒤
알림을 보내야 한다면 DB transaction 안에서 알림을 직접 보내는 대신 outbox record를 함께 저장하고, 별도 worker가
전송하는 구성이 관측과 재시도에 유리합니다.

```kotlin
@Transactional
suspend fun placeOrder(command: PlaceOrder): OrderId {
    val order = orderRepository.save(Order.create(command))
    outboxRepository.save(OrderPlacedEvent.from(order))
    return order.id
}
```

이 함수의 요청이 commit 전에 취소되면 framework 정책에 따라 transaction은 rollback될 수 있습니다. commit 뒤의
전송은 worker가 담당하므로, 사용자의 HTTP 연결이 끊겼다는 이유만으로 event delivery가 사라지지 않습니다. 반대로
"반드시 전송"을 controller의 `NonCancellable`에 넣는 방식은 운영 재시도와 중복 제어를 잃습니다.

## 점검표

- 이 정리가 요청의 local resource에만 관련되는가?
- suspend 호출이 없다면 평범한 `finally`로 끝낼 수 있는가?
- `NonCancellable` 범위가 하나의 close 또는 최종 상태 기록으로 충분히 작은가?
- 취소를 일반 오류로 바꾸거나 로그만 남기고 숨기지 않는가?
- 재시도·영속성·중복 제어가 필요한 후속 업무를 outbox/queue로 분리했는가?
- transaction commit과 외부 side effect의 순서를 테스트로 검증했는가?
