## 결론부터 말하면

2026년의 AI coding agent 선택은 "어느 모델이 1등인가"만으로 결정하기 어렵습니다. 같은 모델도 Codex CLI,
Codex cloud, Claude Code, Cursor, GitHub Copilot cloud agent, Gemini CLI 안에서 다르게 움직입니다. 도구가
읽을 수 있는 파일, 실행할 수 있는 명령, 승인받는 방식, 비용이 쌓이는 단위, pull request로 남는 증적이 모두
다르기 때문입니다.

Spring Boot 팀이 먼저 설계해야 할 것은 모델 순위표가 아니라 **harness**입니다. 여기서 harness는 agent가
반복해서 쓰는 작업 울타리입니다. 입력 범위, 금지 명령, 테스트 명령, 비용 한도, 승인 단계, 리뷰 기준, rollback
방법을 한 세트로 묶어 둔 운영 규칙입니다.

이번 글의 결론은 단순합니다.

- 로컬 수정과 테스트 증적은 Codex CLI나 Claude Code 같은 terminal agent가 강합니다.
- 병렬 background 작업은 Codex cloud와 GitHub Copilot cloud agent처럼 격리된 task가 맞습니다.
- IDE 안의 빠른 multi-file edit는 Cursor와 Copilot agent mode가 편합니다.
- GCP context와 quota 기반 실험은 Gemini CLI, Gemini Code Assist 흐름을 따로 봅니다.
- 어떤 agent를 쓰든 production repository에는 승인, 테스트, diff review, rollback을 harness에 넣어야 합니다.

## 이번 주 비교 대상

| 도구 | 공식 문서 기준 특징 | 잘 맞는 작업 | 운영 기준 |
|---|---|---|---|
| Codex CLI | 로컬 컴퓨터에서 실행되는 OpenAI coding agent | 저장소 수정, 테스트 실행, 승인 기반 로컬 작업 | sandbox, approval, git diff 확인을 명확히 둡니다. |
| Codex cloud | 격리된 cloud environment에서 병렬 task 실행 | 백로그 issue, 리서치, 독립 patch, 장기 작업 | 환경 변수, secrets, dependency setup을 task 단위로 관리합니다. |
| Claude Code | 코드베이스를 읽고 파일 수정과 명령 실행을 수행하는 agentic coding tool | 긴 코드 읽기, 리팩터링, 설계 검토, 대화형 구현 | token 사용량과 subagent/hook 복잡도를 비용으로 봅니다. |
| Cursor | IDE agent, model router, Auto modes, third-party model pricing | editor 안 daily coding, 빠른 context 전환 | third-party model surcharge와 team policy를 확인합니다. |
| GitHub Copilot cloud agent | repository research, plan, branch 변경, PR 흐름 | GitHub issue 기반 비동기 작업 | 모든 단계가 branch, commit, log로 남는 장점을 살립니다. |
| Gemini CLI | terminal에서 Gemini를 쓰는 open-source AI agent | GCP 친화 작업, CLI 기반 탐색, quota 실험 | daily quota와 agent mode의 다중 request 소모를 확인합니다. |

이 표는 순위가 아닙니다. 실제 선택은 "우리 팀의 반복 작업이 어디서 실패하는가"로 정해야 합니다. 예를 들어
test fixture가 복잡한 Spring Boot monorepo는 로컬 CLI agent가 유리할 수 있고, 작은 issue를 많이 쪼개는 팀은
cloud agent가 더 효율적일 수 있습니다.

## benchmark는 방향을 주지만 운영 결정을 대신하지 않습니다

SWE-bench는 실제 GitHub issue를 기반으로 coding agent와 모델의 문제 해결 능력을 비교하는 대표 benchmark입니다.
Terminal-Bench는 terminal 환경에서 agent 작업 능력을 측정합니다. Artificial Analysis도 coding agent의 성능,
비용, token 사용량, 실행 시간을 함께 비교합니다.

이 자료들은 유용합니다. 다만 운영 결정을 그대로 대신하지는 못합니다. benchmark는 보통 공개 repository,
정해진 task harness, 특정 시간의 모델 조합을 기준으로 합니다. 우리 팀의 실제 상황은 다릅니다.

- 사내 repository는 build cache, private package, DB migration, feature flag, secret 접근이 얽혀 있습니다.
- Java/Spring Boot 프로젝트는 통합 테스트와 외부 dependency가 길어 agent가 중간에 context를 잃기 쉽습니다.
- benchmark 점수가 높아도 승인 흐름이 약하면 production 권한이 있는 작업에는 부적합할 수 있습니다.
- 비용이 낮아 보여도 큰 context를 매번 다시 읽으면 한 달 비용은 빠르게 커집니다.

따라서 benchmark는 "어떤 agent를 후보에 넣을지"를 정하는 데 쓰고, 실제 도입은 팀 내부 eval로 결정해야 합니다.

## harness engineering은 agent용 CI 설계에 가깝습니다

Spring Boot 팀은 이미 CI를 운영합니다. `./gradlew test`, `./gradlew bootJar`, migration check, static analysis,
Docker build, deploy approval 같은 단계가 있을 겁니다. agent harness도 같은 사고방식으로 잡으면 됩니다.

```text
작업 입력
-> agent가 읽어도 되는 파일과 읽으면 안 되는 파일
-> 수정 가능한 경로
-> 반드시 실행할 테스트 명령
-> 실패 시 중단 조건
-> 사람 승인이 필요한 명령
-> 리뷰 기준
-> 되돌리는 방법
```

여기서 중요한 것은 agent에게 "잘 해줘"라고 말하지 않는 것입니다. agent는 기준이 모호하면 더 많은 파일을 읽고,
더 많은 추측을 하고, 더 큰 diff를 만들 가능성이 있습니다. 반대로 성공 기준이 작고 검증 명령이 명확하면 같은
모델도 훨씬 안정적으로 동작합니다.

## 비용은 token 가격보다 작업 완료 단가로 봅니다

OpenAI API pricing은 Codex 계열 모델의 token 단가를 공개하고, Anthropic pricing은 Claude Fable, Opus, Sonnet,
Haiku 계열의 입력, 출력, prompt caching, batch, long context 가격을 구분합니다. Cursor는 third-party model을
직접 선택하거나 Auto가 라우팅할 때 Cursor Token Rate가 붙는다고 설명합니다. GitHub Copilot은 AI Credits로
usage를 계산하며, 1 credit을 $0.01 USD로 설명합니다.

가격표 자체보다 중요한 질문은 이것입니다.

| 비용 항목 | 볼 질문 |
|---|---|
| 입력 token | agent가 repository를 매번 처음부터 읽는가, 필요한 파일만 읽는가 |
| 출력 token | 긴 설명을 매번 남기는가, diff 중심으로 일하는가 |
| tool call | 검색, shell, browser, code execution이 얼마나 반복되는가 |
| cloud runtime | 격리 환경이 오래 켜져 있는가, 병렬 task가 과도한가 |
| 실패 재시도 | 같은 실패를 agent가 반복하는가, 빠르게 중단하는가 |
| review 비용 | 사람이 diff를 이해하는 시간이 줄었는가 늘었는가 |

가성비는 "한 달 구독료가 싼가"가 아니라 "완료된 안전한 변경 하나의 총비용"입니다. agent가 20분 만에 코드를
고쳤어도, 사람이 2시간 동안 diff를 해석해야 한다면 harness가 실패한 것입니다.

## 승인 흐름은 작업 종류별로 달라야 합니다

AI agent에게 모든 명령을 같은 승인 수준으로 주면 둘 중 하나가 됩니다. 너무 막혀서 일을 못 하거나, 너무 열려서
위험해집니다. Spring Boot 팀에서는 작업을 다음처럼 나누는 편이 실용적입니다.

| 작업 | 권장 승인 수준 |
|---|---|
| 파일 읽기, `rg`, `git diff`, unit test | 기본 허용 |
| dependency 설치, build, formatting | repository별 허용 |
| DB migration 생성, Docker build, e2e test | 명시 승인 또는 제한 허용 |
| production secret 읽기, 배포, Terraform apply | 사람 승인 필수 |
| 계정 삭제, 결제 변경, production data export | agent 금지 |

Codex CLI처럼 로컬에서 실행되는 agent는 사용자의 실제 checkout과 연결됩니다. Claude Code도 파일 수정과 명령 실행이
가능합니다. GitHub Copilot cloud agent와 Codex cloud는 격리된 environment에서 background 작업을 맡기기 좋지만,
그만큼 environment setup과 secret 노출 범위를 별도로 설계해야 합니다.

## Spring Boot 팀용 최소 eval

처음부터 모든 agent를 production에 붙이지 말고, 같은 task 5개로 작은 eval을 돌리는 편이 낫습니다.

1. 단순 버그 수정: 실패하는 unit test 하나를 고치게 합니다.
2. API contract 변경: DTO field 하나를 추가하고 controller, test, 문서를 맞추게 합니다.
3. 리팩터링: 중복 validation logic을 한 helper로 줄이되 public behavior는 유지하게 합니다.
4. 운영 문서: 실제 로그 샘플에서 민감정보를 제거하고 runbook을 갱신하게 합니다.
5. 실패 복구: 일부러 깨진 dependency나 migration 오류를 진단하게 합니다.

각 task는 같은 rubric으로 봅니다.

| 평가 항목 | 측정 방식 |
|---|---|
| 정확도 | 테스트 통과와 요구사항 충족 여부 |
| diff 크기 | 요청과 무관한 파일 변경 수 |
| 실행 증적 | 어떤 명령을 실행했고 실패를 어떻게 처리했는가 |
| 비용 | token, cloud runtime, 재시도 횟수 |
| 리뷰 가능성 | 사람이 diff를 10분 안에 이해할 수 있는가 |
| 중단 판단 | 불명확한 요구에서 멈추고 질문했는가 |

이 eval을 통과한 agent만 반복 업무에 붙입니다. 실패한 agent를 완전히 버릴 필요는 없습니다. 예를 들어 어떤 도구는
리팩터링에는 약하지만 문서 갱신에는 충분히 좋을 수 있습니다.

## 본문에 넣지 않은 후보와 제외 이유

- Grok Bot과 Grok 4.6은 직전 AI agent 글에서 가격, context, Cursor 연동을 이미 중심 주제로 다뤘기 때문에 이번
  글에서는 반복하지 않았습니다. Cursor의 model 목록에는 계속 포함되므로 후보 검토에는 남겼습니다.
- Claude in Chrome은 9월 1일 IT 동향 글에서 브라우저 agent GA로 다뤘기 때문에 이번 글에서는 coding harness
  범위 밖의 browser automation 주제로 분리했습니다.
- Devin류 완전 위임형 제품은 공개 비교 후보로는 중요하지만, 이번 글의 초점이 Spring Boot 팀이 바로 따라 할 수
  있는 CLI, IDE, cloud agent harness라서 본문 핵심 표에서 제외했습니다.
- 단일 블로그의 "최고 agent 순위"는 공식 문서나 공개 benchmark와 교차 확인되지 않으면 근거로 쓰지 않았습니다.

## 오늘 바로 적용할 운영 규칙

1. repository root에 agent 작업 규칙을 둡니다. 수정 가능한 경로, 금지 경로, 테스트 명령, PR 설명 형식을 적습니다.
2. agent에게 한 번에 issue 하나만 줍니다. "전체 리팩터링" 같은 요청은 작은 task로 쪼갭니다.
3. 실패한 test log를 그대로 다시 붙이지 말고, 기대 결과와 실제 결과를 짧게 요약해 재시도시킵니다.
4. dependency upgrade, DB migration, 배포 작업은 agent가 제안만 하고 사람이 승인하게 둡니다.
5. agent별 완료 단가를 기록합니다. 구독료, token, 실행 시간보다 merged change 기준으로 봅니다.
6. 같은 task를 두 agent에게 반복시키지 않습니다. 하나는 구현, 하나는 리뷰처럼 역할을 분리합니다.
