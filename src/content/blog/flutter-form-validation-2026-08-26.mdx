## 결론부터 말하면

Flutter의 form은 **서버 요청 객체를 검증하는 코드가 아니라, 사용자가 입력하는 동안 화면 상태와
오류 메시지를 함께 관리하는 UI 경계**입니다.

Spring Boot에서는 `@Valid`, DTO, Bean Validation, Controller advice로 요청 검증을 서버 진입점에
모읍니다. Flutter에서는 사용자가 아직 입력 중인 값, focus, cursor, validation message, submit
button 상태가 화면 안에서 계속 변합니다. 그래서 검증 규칙을 넣는 것만큼 중요한 일이 있습니다.
`TextEditingController`를 어디서 만들고 언제 버릴지, `GlobalKey<FormState>`를 언제 생성할지,
제출 직전에 어떤 상태를 서버 요청으로 바꿀지 정하는 일입니다.

이번 글에서는 Flutter 세 번째 단계에서 본 비동기 데이터 표시 위에 입력 흐름을 얹습니다.

- `Form`과 `TextFormField`가 어떤 책임을 갖는가
- `GlobalKey<FormState>`는 왜 `StatefulWidget`의 state 안에 두는가
- `TextEditingController`는 언제 쓰고 왜 `dispose()`해야 하는가
- Spring Boot 개발자가 validation을 어디까지 믿어야 하는가

## 이번 주 개념

Flutter 공식 cookbook은 form validation 흐름을 세 단계로 설명합니다. `Form`을 만들고,
`TextFormField`에 validation logic을 붙인 뒤, button에서 validate와 submit을 실행합니다.

작은 예제는 다음처럼 시작할 수 있습니다.

```dart
class SignInForm extends StatefulWidget {
  const SignInForm({super.key});

  @override
  State<SignInForm> createState() => _SignInFormState();
}

class _SignInFormState extends State<SignInForm> {
  final _formKey = GlobalKey<FormState>();
  final _emailController = TextEditingController();

  @override
  void dispose() {
    _emailController.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Form(
      key: _formKey,
      child: Column(
        children: [
          TextFormField(
            controller: _emailController,
            decoration: const InputDecoration(labelText: 'Email'),
            keyboardType: TextInputType.emailAddress,
            validator: (value) {
              final email = value?.trim() ?? '';
              if (email.isEmpty) {
                return '이메일을 입력해 주세요.';
              }
              if (!email.contains('@')) {
                return '이메일 형식을 확인해 주세요.';
              }
              return null;
            },
          ),
          FilledButton(
            onPressed: _submit,
            child: const Text('로그인'),
          ),
        ],
      ),
    );
  }

  void _submit() {
    if (!_formKey.currentState!.validate()) {
      return;
    }

    final email = _emailController.text.trim();
    // 서버 요청 DTO로 변환하는 경계입니다.
  }
}
```

여기서 중요한 점은 `_formKey`와 `_emailController`를 `build()` 안에서 만들지 않는 것입니다.
`build()`는 여러 이유로 다시 호출됩니다. key와 controller를 그때마다 새로 만들면 form 상태,
cursor 위치, validation 결과가 흔들릴 수 있습니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 form 입력을 서버 요청 DTO로 받은 뒤 검증하는 흐름이 익숙합니다.

```java
record SignInRequest(
    @NotBlank
    @Email
    String email,

    @NotBlank
    String password
) {
}

@RestController
class SignInController {

    @PostMapping("/api/sign-in")
    SignInResponse signIn(@Valid @RequestBody SignInRequest request) {
        return signInService.signIn(request);
    }
}
```

이 구조에서 검증의 기준점은 요청이 서버에 들어온 순간입니다. HTTP body가 DTO로 변환되고,
Bean Validation이 실패하면 Controller method의 본문에 들어가기 전에 오류 응답으로 바꿀 수 있습니다.

Flutter의 form validation은 이보다 앞단에 있습니다. 사용자가 이메일을 한 글자씩 입력하고,
비밀번호 field로 focus를 옮기고, submit button을 누르는 동안 화면이 계속 변합니다. Flutter
validation은 서버 검증을 대체하는 것이 아니라, 사용자에게 빠르게 피드백을 주고 잘못된 요청을 줄이는
클라이언트 경계입니다.

```text
Spring Boot
-> HTTP 요청 수신
-> DTO 변환
-> 서버 validation
-> service 호출 또는 오류 응답

Flutter
-> 사용자가 입력
-> controller와 field state 갱신
-> local validation message 표시
-> submit 시 서버 DTO로 변환
```

## Flutter에서는 무엇이 다른가

Flutter에서 form은 widget tree 안에 있는 상태 관리 단위입니다.

<Mermaid title="Flutter form validation 흐름">
{`flowchart TD
  Input["사용자 입력"] --> Controller["TextEditingController<br/>현재 text 보관"]
  Input --> Field["TextFormField<br/>표시와 validator"]
  Field --> Form["Form<br/>FormState로 field 묶기"]
  Button["Submit button"] --> Validate["FormState.validate()"]
  Validate -->|fail| Message["오류 메시지 표시"]
  Validate -->|pass| Request["서버 요청 DTO 생성"]
  Request --> Api["POST /api/sign-in"]
  Controller --> Dispose["dispose()에서 정리"]
`}
</Mermaid>

`TextFormField`는 `TextField`와 form validation을 이어 주는 편의 widget입니다. `validator`는
문자열 오류 메시지나 `null`을 반환합니다. `null`은 통과를 뜻합니다. `FormState.validate()`를 호출하면
form 아래 field들의 validator가 실행되고, 실패한 field는 오류 메시지를 표시합니다.

`TextEditingController`는 입력값을 읽거나 programmatic update가 필요할 때 씁니다. 예를 들어 submit
직전에 현재 text를 읽거나, 검색어를 초기화하거나, listener로 button 활성화를 바꿀 때 필요합니다.
공식 문서는 controller를 다 쓴 뒤 `dispose()`하라고 안내합니다. controller는 단순 문자열 변수가 아니라
selection, composing range, listener 같은 UI 리소스를 붙잡기 때문입니다.

| Spring Boot에서 익숙한 것 | Flutter에서 가까운 개념 | 주의할 점 |
|---|---|---|
| Request DTO | submit 직전에 만든 Dart request object | controller 값을 그대로 전역에 흘리지 않습니다. |
| Bean Validation annotation | `TextFormField.validator` | UX 피드백용이며 서버 검증을 대체하지 않습니다. |
| Controller method | submit handler | 화면 상태 확인 후 서버 요청을 시작하는 경계입니다. |
| BindingResult 또는 error response | field error text, dialog, snackbar | 사용자 메시지와 개발 로그를 분리합니다. |
| Bean lifecycle | `State.dispose()` | controller, focus node 같은 리소스를 정리합니다. |

## controller 없이도 되는 값과 필요한 값을 나눕니다

모든 field에 controller를 붙일 필요는 없습니다. 값이 submit 시점에만 필요하고, 초기값만 있으면 되는
간단한 field는 `TextFormField`의 `onSaved`나 `initialValue`만으로도 충분합니다. 반대로 다음 조건이면
controller를 쓰는 편이 낫습니다.

- submit 전에 입력값을 계속 읽어 button 활성화를 바꿔야 합니다.
- 외부 이벤트로 field 값을 바꿔야 합니다.
- 검색창처럼 입력값을 clear하거나 selection을 다뤄야 합니다.
- lazily built list 안에서 text field 상태를 잃지 않아야 합니다.

작은 로그인 form은 email field만 controller로 읽고, password field는 validator와 submit 경계에서
필요한 만큼만 다룰 수도 있습니다. 중요한 것은 "controller를 많이 쓰는가"가 아니라 "생명주기를 누가
소유하는가"입니다.

```dart
class SignInDraft {
  const SignInDraft({
    required this.email,
    required this.password,
  });

  final String email;
  final String password;
}

SignInDraft _toDraft() {
  return SignInDraft(
    email: _emailController.text.trim(),
    password: _passwordController.text,
  );
}
```

이렇게 submit 직전에 Dart object로 바꾸면 Spring Boot의 request DTO와 비슷한 경계를 만들 수 있습니다.
화면 내부의 controller는 UI 리소스이고, `_toDraft()` 이후의 값은 서버 요청 모델입니다.

## 최소 실행 예제

Flutter 3.47.1 stable SDK가 준비되어 있다면 아래처럼 작은 form 화면을 만들 수 있습니다.

```bash
flutter create form_lab
cd form_lab
flutter run
```

`lib/main.dart`를 다음처럼 바꿉니다.

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const FormLabApp());
}

class FormLabApp extends StatelessWidget {
  const FormLabApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Form lab',
      theme: ThemeData(
        colorScheme: ColorScheme.fromSeed(seedColor: Colors.teal),
      ),
      home: const Scaffold(
        body: SafeArea(
          child: Padding(
            padding: EdgeInsets.all(24),
            child: SignInForm(),
          ),
        ),
      ),
    );
  }
}

class SignInForm extends StatefulWidget {
  const SignInForm({super.key});

  @override
  State<SignInForm> createState() => _SignInFormState();
}

class _SignInFormState extends State<SignInForm> {
  final _formKey = GlobalKey<FormState>();
  final _emailController = TextEditingController();
  final _passwordController = TextEditingController();
  bool _canSubmit = false;

  @override
  void initState() {
    super.initState();
    _emailController.addListener(_refreshSubmitState);
    _passwordController.addListener(_refreshSubmitState);
  }

  @override
  void dispose() {
    _emailController.dispose();
    _passwordController.dispose();
    super.dispose();
  }

  void _refreshSubmitState() {
    final canSubmit =
        _emailController.text.trim().isNotEmpty &&
        _passwordController.text.length >= 8;
    if (canSubmit != _canSubmit) {
      setState(() => _canSubmit = canSubmit);
    }
  }

  @override
  Widget build(BuildContext context) {
    return Form(
      key: _formKey,
      child: Column(
        crossAxisAlignment: CrossAxisAlignment.stretch,
        children: [
          TextFormField(
            controller: _emailController,
            decoration: const InputDecoration(labelText: 'Email'),
            keyboardType: TextInputType.emailAddress,
            validator: (value) {
              final email = value?.trim() ?? '';
              if (email.isEmpty) return '이메일을 입력해 주세요.';
              if (!email.contains('@')) return '이메일 형식을 확인해 주세요.';
              return null;
            },
          ),
          const SizedBox(height: 16),
          TextFormField(
            controller: _passwordController,
            decoration: const InputDecoration(labelText: 'Password'),
            obscureText: true,
            validator: (value) {
              if ((value ?? '').length < 8) {
                return '비밀번호는 8자 이상이어야 합니다.';
              }
              return null;
            },
          ),
          const SizedBox(height: 24),
          FilledButton(
            onPressed: _canSubmit ? _submit : null,
            child: const Text('Submit'),
          ),
        ],
      ),
    );
  }

  void _submit() {
    if (!_formKey.currentState!.validate()) {
      return;
    }

    final email = _emailController.text.trim();
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text('$email 요청을 보낼 준비가 됐습니다.')),
    );
  }
}
```

이 예제는 서버 요청을 실제로 보내지 않습니다. 핵심은 input state, validation state, submit state를
한 화면 안에서 분리해 보는 것입니다. 이후 `FutureBuilder`나 repository 함수와 연결하면 submit
handler에서 비동기 요청을 시작하고 loading/error/data 상태를 표시할 수 있습니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 client validation을 서버 validation처럼 믿는 것입니다. Flutter validation은 사용자가
좋은 입력을 하도록 돕는 장치입니다. API는 여전히 잘못된 body, 오래된 앱 버전, 조작된 요청을 받을 수
있습니다. 서버의 DTO validation과 권한 검사는 그대로 필요합니다.

두 번째 오해는 controller를 model처럼 오래 들고 있는 것입니다. controller는 화면 리소스입니다.
domain object나 repository로 넘기지 말고, submit 직전에 문자열이나 request object로 바꾸는 편이
경계가 선명합니다.

세 번째 오해는 `build()` 안에서 key와 controller를 만드는 것입니다. Spring Bean을 요청마다 새로
만드는 구조가 아닌 것처럼, Flutter에서도 state가 소유해야 할 리소스는 state의 field로 만들고
`dispose()`에서 정리해야 합니다.

2. password 확인 field를 추가하고 두 password가 다르면 field error를 표시해 보세요.
3. submit handler에서 request object를 만들되 controller 자체는 repository 함수로 넘기지 않게 바꿔 보세요.
4. `TextEditingController`를 `build()` 안에서 만들면 어떤 현상이 생길 수 있는지 직접 재현해 보세요.
5. 같은 validation 규칙을 Spring Boot DTO annotation과 Flutter `validator`로 각각 표현하고, 두 검증의 목적 차이를 한 문장으로 정리해 보세요.

## 정리

Flutter form은 입력 UI, validation message, controller lifecycle, submit boundary가 만나는 지점입니다.

Spring Boot 개발자에게 익숙한 DTO validation 감각은 도움이 됩니다. 다만 Flutter에서는 요청이 서버에
도착하기 전부터 사용자의 입력 과정이 화면 상태로 존재합니다. form field는 사용자에게 피드백을 주고,
controller는 현재 입력값을 잡고, submit handler는 그 값을 서버 요청 모델로 바꾸는 경계입니다.

이 경계를 지키면 다음 단계에서 로그인, 회원가입, 검색, 필터 같은 실제 화면을 만들 때도 validation과
네트워크 요청이 한 함수에 뒤섞이지 않습니다.
