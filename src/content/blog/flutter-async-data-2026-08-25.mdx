## 결론부터 말하면

Flutter에서 서버 데이터를 처음 다룰 때 가장 중요한 습관은 **HTTP 요청을 `build()` 안에서 새로 만들지
않고, `FutureBuilder`에는 이미 준비된 `Future`를 넘기는 것**입니다.

Spring Boot 개발자는 서버에서 비동기 처리를 해도 요청 진입점과 응답 생성 위치를 비교적 명확히 봅니다.
Controller가 요청을 받고, Service가 외부 API나 데이터베이스를 호출하고, 실패하면 예외를 응답으로
바꿉니다. Flutter에서는 화면이 계속 다시 그려질 수 있기 때문에, 네트워크 호출과 화면 선언을 같은
함수에 섞으면 요청이 반복되거나 loading 상태가 흔들립니다.

이번 글에서는 Flutter 두 번째 단계에서 본 state와 layout 감각 위에 서버 데이터 표시 흐름을 얹습니다.

- Dart의 `Future`, `async`, `await`는 무엇을 표현하는가
- `FutureBuilder`가 loading, error, data 상태를 어떻게 나누는가
- HTTP 요청은 어디에서 만들고 어디에서 표시해야 하는가
- Spring Boot 개발자가 자주 하는 오해는 무엇인가

## 이번 주 개념

Dart에서 비동기 작업은 보통 `Future<T>`로 표현합니다. 네트워크 요청, 파일 읽기, 데이터베이스 작업처럼
바로 끝나지 않는 일은 지금 값이 아니라 "나중에 끝날 값"을 반환합니다.

```dart
Future<String> loadMessage() async {
  await Future<void>.delayed(const Duration(milliseconds: 300));
  return '서버에서 받은 메시지';
}
```

`async` 함수는 항상 `Future`를 반환합니다. 함수 안에서 `await`를 만나면 결과가 올 때까지 해당 async
함수의 진행을 잠시 멈추지만, Flutter UI thread 전체를 막는 방식은 아닙니다. 그래서 사용자는 loading
indicator를 볼 수 있고, 앱은 다른 이벤트를 계속 처리할 수 있습니다.

Flutter에서 이 값을 화면에 붙일 때 자주 쓰는 도구가 `FutureBuilder`입니다.

```dart
FutureBuilder<String>(
  future: messageFuture,
  builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) {
      return const CircularProgressIndicator();
    }

    if (snapshot.hasError) {
      return Text('오류: ${snapshot.error}');
    }

    if (!snapshot.hasData) {
      return const Text('데이터가 없습니다.');
    }

    return Text(snapshot.data!);
  },
);
```

핵심은 `future`에 무엇을 넘기느냐입니다. Flutter API 문서는 `FutureBuilder`에 넘기는 `Future`를
`build()` 안에서 새로 만들지 말고, `initState`, `didUpdateWidget`, `didChangeDependencies` 같은
이전 단계에서 얻어야 한다고 설명합니다. 부모가 다시 build될 때마다 네트워크 요청이 다시 시작될 수
있기 때문입니다.

## Java/Spring에서는 어떻게 다뤘는가

Spring Boot에서는 서버가 HTTP 요청을 받고 응답을 끝내는 구조가 기본입니다.

```java
@RestController
class OrderController {

    private final OrderService orderService;

    OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping("/orders/{orderId}")
    OrderResponse findOrder(@PathVariable String orderId) {
        return orderService.findOrder(orderId);
    }
}
```

Controller는 요청마다 한 번 호출됩니다. 외부 API를 호출하든 데이터베이스를 조회하든, 그 요청 흐름 안에서
성공과 실패를 응답으로 정리합니다.

Flutter 화면은 다릅니다. `build()`는 요청 핸들러가 아닙니다. parent widget의 상태 변경, 화면 크기 변경,
theme 변경, `setState()` 호출 등 여러 이유로 다시 호출될 수 있습니다. 그래서 `build()` 안에 "서버에서
데이터를 가져오는 일"을 직접 넣으면 Spring Controller를 여러 번 중복 호출하는 것과 비슷한 문제가 생깁니다.

```text
Spring Boot 요청
-> Controller 한 번 진입
-> Service 조회
-> Response 반환

Flutter 화면
-> State가 Future를 준비
-> build()가 현재 snapshot을 화면으로 변환
-> Future 완료 후 다시 build()
```

## Flutter에서는 무엇이 다른가

Flutter에서는 데이터 조회와 화면 표시를 분리해서 생각해야 합니다.

<Mermaid title="Flutter 비동기 데이터 표시 흐름">
{`flowchart TD
  Init["initState()"] --> Future["Future<OrderSummary> 준비"]
  Future --> Request["HTTP 요청"]
  Request --> Decode["JSON decode와 DTO 변환"]
  Future --> Builder["FutureBuilder"]
  Builder --> Loading["ConnectionState.waiting<br/>loading UI"]
  Builder --> Error["snapshot.hasError<br/>error UI"]
  Builder --> Data["snapshot.hasData<br/>data UI"]
  Data --> Screen["화면 표시"]
`}
</Mermaid>

Spring Boot에서 Controller가 DTO를 만들고 View가 그 DTO를 표시하듯이, Flutter에서도 repository 함수가
모델을 만들고 widget은 snapshot 상태에 맞는 UI만 반환하게 두는 편이 좋습니다.

| Spring Boot에서 익숙한 것 | Flutter에서 가까운 개념 | 주의할 점 |
|---|---|---|
| Controller method | `FutureBuilder`의 `builder` | 요청 진입점이 아니라 현재 상태를 UI로 바꾸는 함수입니다. |
| Service의 외부 API 호출 | repository 함수의 `http.get` | `build()` 안에서 새 Future를 만들지 않습니다. |
| Response DTO | Dart model class | JSON map을 그대로 화면 전체에 흘리지 않습니다. |
| Exception handler | `snapshot.hasError` 분기 | 사용자 메시지와 개발 로그를 분리합니다. |
| Loading response | `ConnectionState.waiting` | loading, empty, error, data를 같은 문구로 뭉개지 않습니다. |

## HTTP 요청을 작은 repository 함수로 뺍니다

처음에는 복잡한 architecture가 필요하지 않습니다. 다만 네트워크 요청과 JSON 변환은 widget의
`build()` 밖으로 빼는 편이 좋습니다.

```dart
import 'dart:convert';

import 'package:http/http.dart' as http;

class OrderSummary {
  const OrderSummary({
    required this.id,
    required this.title,
    required this.status,
  });

  final int id;
  final String title;
  final String status;

  factory OrderSummary.fromJson(Map<String, dynamic> json) {
    return OrderSummary(
      id: json['id'] as int,
      title: json['title'] as String,
      status: json['status'] as String,
    );
  }
}

Future<OrderSummary> fetchOrderSummary(int orderId) async {
  final uri = Uri.https('example.com', '/api/orders/$orderId');
  final response = await http.get(uri);

  if (response.statusCode != 200) {
    throw Exception('주문 요약을 가져오지 못했습니다.');
  }

  final json = jsonDecode(response.body) as Map<String, dynamic>;
  return OrderSummary.fromJson(json);
}
```

여기서 `example.com`은 공개 예시용 도메인입니다. 실제 서비스 주소나 내부 API 경로를 글과 테스트에
그대로 넣지 않는 습관이 필요합니다.

이 함수는 Spring Boot의 Service나 HTTP client adapter에 가깝습니다. 실패 기준, JSON 변환, model 생성
책임을 한곳에 둡니다. 화면은 이 함수의 결과를 표시할 뿐입니다.

## Future는 State에서 한 번 준비합니다

이제 `StatefulWidget`에서 `Future`를 한 번 준비하고 `FutureBuilder`에 넘깁니다.

```dart
class OrderScreen extends StatefulWidget {
  const OrderScreen({
    required this.orderId,
    super.key,
  });

  final int orderId;

  @override
  State<OrderScreen> createState() => _OrderScreenState();
}

class _OrderScreenState extends State<OrderScreen> {
  late Future<OrderSummary> orderFuture;

  @override
  void initState() {
    super.initState();
    orderFuture = fetchOrderSummary(widget.orderId);
  }

  @override
  void didUpdateWidget(OrderScreen oldWidget) {
    super.didUpdateWidget(oldWidget);
    if (oldWidget.orderId != widget.orderId) {
      orderFuture = fetchOrderSummary(widget.orderId);
    }
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Order detail')),
      body: Center(
        child: FutureBuilder<OrderSummary>(
          future: orderFuture,
          builder: (context, snapshot) {
            if (snapshot.connectionState == ConnectionState.waiting) {
              return const CircularProgressIndicator();
            }

            if (snapshot.hasError) {
              return const Text('주문 정보를 불러오지 못했습니다.');
            }

            final order = snapshot.data;
            if (order == null) {
              return const Text('표시할 주문이 없습니다.');
            }

            return OrderSummaryView(order: order);
          },
        ),
      ),
    );
  }
}
```

`initState()`에서 처음 Future를 만들고, `orderId`가 바뀔 때만 `didUpdateWidget()`에서 새 Future를
만듭니다. 이렇게 하면 theme 변경이나 부모 rebuild 때문에 같은 HTTP 요청이 불필요하게 반복되는 일을 줄일 수
있습니다.

## 표시 위젯은 데이터만 받습니다

데이터 표시 책임은 더 작은 `StatelessWidget`으로 분리합니다.

```dart
class OrderSummaryView extends StatelessWidget {
  const OrderSummaryView({
    required this.order,
    super.key,
  });

  final OrderSummary order;

  @override
  Widget build(BuildContext context) {
    return Padding(
      padding: const EdgeInsets.all(16),
      child: Column(
        mainAxisSize: MainAxisSize.min,
        crossAxisAlignment: CrossAxisAlignment.start,
        children: [
          Text(
            order.title,
            style: Theme.of(context).textTheme.titleLarge,
          ),
          const SizedBox(height: 8),
          Text('상태: ${order.status}'),
        ],
      ),
    );
  }
}
```

이 위젯은 네트워크를 모릅니다. `FutureBuilder`도 모릅니다. 이미 성공한 `OrderSummary`를 받아 그리는
일만 합니다. Spring Boot에서 Controller, Service, DTO, View template의 책임을 나누듯이 Flutter에서도
repository, async state, 표시 widget을 나누면 테스트와 수정이 쉬워집니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 `FutureBuilder`의 `builder`를 Controller처럼 보는 것입니다. Controller는 요청마다
의도적으로 한 번 들어오는 경계지만, Flutter의 `builder`는 framework가 필요할 때 다시 호출할 수 있는
화면 선언 함수입니다.

두 번째 오해는 loading과 error를 임시 문구 하나로 처리하는 것입니다. 서버 개발자는 HTTP status와 exception
type을 구분하면서, 모바일 화면에서는 loading, empty, error, retry 가능 상태를 하나로 뭉치기 쉽습니다.
사용자 입장에서는 네 상태가 전혀 다릅니다.

세 번째 오해는 JSON map을 화면까지 그대로 넘기는 것입니다. 작은 예제에서는 편하지만, 화면이 늘어나면 key
문자열과 null 처리 규칙이 여러 widget에 흩어집니다. Java에서 Map 기반 응답을 Service 전체에 흘리지 않는
것처럼 Dart에서도 model class를 두는 편이 낫습니다.

네 번째 오해는 `async`가 자동으로 취소까지 해 준다고 보는 것입니다. 사용자가 화면을 떠났을 때 오래 걸리는
요청을 어떻게 다룰지, retry 버튼을 어디에 둘지, 같은 화면에 다시 들어왔을 때 캐시를 쓸지 별도 판단이
필요합니다.

## 마무리

Flutter에서 서버 데이터를 다룰 때는 `FutureBuilder` 사용법보다 먼저 책임 경계를 잡아야 합니다.

`Future`는 비동기 결과를 표현하고, repository 함수는 HTTP와 JSON 변환을 맡고, `State`는 화면에 필요한
Future를 준비하며, `FutureBuilder`는 현재 snapshot을 UI로 바꿉니다. 이 구분을 지키면 Spring Boot에서
요청 처리 흐름을 나누던 감각을 Flutter 화면 코드에도 이어갈 수 있습니다.
