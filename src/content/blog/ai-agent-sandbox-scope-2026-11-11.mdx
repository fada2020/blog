>
> 공식 제품 문서와 11월 5일 Google 발표를 확인했습니다. Agent Substrate 발표의 1.0과
> CNCF **Sandbox** 프로젝트 성숙도는 별개입니다. 모든 관련 서비스의 GA를 뜻하지 않습니다.
> 아래 비교는 문서와 실험 설계이며 세 제품을 같은 환경에서 실행한 성능 순위가 아닙니다.

## 이번 주 질문

에이전트가 sandbox 안에서 실행된다는 설명만으로 파일·네트워크·외부 도구가 같은 경계에 들어간다고
가정할 수 있을까요. **무엇을 격리하는지와 어떤 실행 경로가 예외인지**를 먼저 확인해야 합니다.
[지난주](/blog/posts/ai-agent-single-loop-subagent-eval-2026-11-04/)의 단일 loop·하위 agent 선택에서
이번에는 실행 경계와 중단 후 재개로 주제를 옮겼습니다.

Spring Security의 HTTP 필터를 적용했다고 배치 프로세스나 별도 메시지 소비자의 권한까지 자동으로 같아지지는 않습니다.
agent의 shell 정책과 MCP 도구의 권한도 같은 방식으로 따로 추적해야 합니다.

## 세 접근은 서로 다른 층을 다룹니다

| 접근 | 격리·정책의 단위 | 먼저 확인할 경계 |
|---|---|---|
| Codex | 실행 권한과 승인 정책 | workspace·network와 연결 도구 |
| Claude Code | sandboxed Bash와 도구별 권한 | 내장 파일 도구·MCP·hooks |
| Agent Substrate | 상태 있는 실행 환경과 worker | 저장 상태·복원·egress 정책 |

[Codex 공식 권한 문서](https://learn.chatgpt.com/docs/agent-approvals-security)는 sandbox와 승인 정책을
구분합니다. workspace-write 기본 설정은 작업 공간의 쓰기와 네트워크 접근을 다르게 처리합니다.
호스트·설정·연결 도구마다 조건이 있으므로 모드 이름만 기록하면 재현에 필요한 정보가 부족합니다.
승인 요청을 끄는 것과 OS 격리를 없애는 것도 같은 조작이 아닙니다.

[Claude Code 공식 sandbox 문서](https://code.claude.com/docs/en/sandboxing)는 shell 경계 밖의 경로를
명시합니다. 내장 파일·웹 도구는 별도 permission 규칙을 따르고, 로컬 MCP 서버와 hooks도 Bash sandbox와
동일하게 제한된다고 가정할 수 없습니다. 따라서 Bash에서 읽기가 차단됐다는 결과 하나로 Read 도구까지
검증했다고 보고하면 안 됩니다. 환경변수로 전달되는 자격증명도 별도로 점검할 대상입니다.

[Google의 11월 5일 발표](https://opensource.googleblog.com/2026/11/sandboxing-untrusted-ai-agents-at-scale.html)는
agent 세션 상태를 가진 Actor와 실행 자원을 제공하는 Worker를 분리합니다. gVisor나 microVM 경계를 쓰고
유휴 상태를 저장했다가 복원하는 접근입니다. 대규모 환경을 위한 설계이며 CLI의 승인 설정을 대체하는 기능은 아닙니다.
공급사가 제시한 복원 지연을 이 글의 자체 벤치마크 결과로 사용하지 않았습니다.

## 재개는 새 작업과 다릅니다

같은 상태를 되살리면 미커밋 파일과 실행 문맥을 이어 갈 수 있습니다. 하지만 중단 전에 외부 서비스가 이미
쓰기 요청을 처리했는지까지 메모리 스냅샷만으로 결정할 수는 없습니다. 다음은 특정 제품의 보장 설명이 아닌
**애플리케이션 설계 제안**입니다.

- 파일 상태와 별도로 외부 쓰기의 작업 ID·확인 결과를 기록합니다.
- 복원 후 권한·자격증명 만료·정책 버전을 재확인합니다.
- 응답을 받지 못한 쓰기는 무조건 다시 보내지 않고 서버의 멱등키나 조회로 결과를 대조합니다.
- 상태 캡슐에 자격증명이 들어갈 수 있으므로 저장 접근·보존 기간도 설계합니다.

Spring 서비스의 트랜잭션 복구에서도 로컬 재시작과 외부 결제의 재실행은 분리합니다.
agent의 재개 역시 같은 경계를 요구합니다. 스냅샷 복원이 exactly-once 외부 쓰기를 제공한다는 뜻은 아닙니다.

## 실습: 실행 경로별로 같은 정책을 검사합니다

비밀값 없는 임시 저장소와 합성 데이터만 사용합니다. 운영 호스트에서 권한을 완화하며 시험하지 않습니다.
외부 전송은 실제 요청 대신 테스트 서버로 대체하고, 허용·거절을 모두 관찰합니다.

| 시험 | 기대 결과 | 증거 |
|---|---|---|
| 허용된 작업 폴더 쓰기 | 성공 | 파일 diff |
| 허용 범위 밖 합성 파일 읽기 | 정책에 따른 거절 | 해당 도구의 결과 |
| 같은 읽기를 shell·파일 도구로 반복 | 경로별 정책 확인 | 도구 이름·설정 |
| 허용하지 않은 테스트 목적지 연결 | 거절 | 프록시·도구 기록 |
| 승인 전 외부 쓰기 | 미실행 | 테스트 서버 요청 수 |
| 응답 유실 후 재개 | 중복 효과 없음 | 작업 ID별 처리 수 |

두 번째 행의 거절을 세 번째 행 전체의 성공으로 복사하지 않습니다. MCP 도구를 붙였다면 같은 시험을
그 도구에서도 별도로 실행합니다. 지원하지 않는 경로는 통과가 아니라 `not_tested`로 기록합니다.

다음 JSON은 벤더 API 요청이나 응답이 아닌, 제안하는 **합성 실험 저장값**입니다.
기존 서비스의 필드·상태 코드·시간 계약 변경은 없습니다.

```json
{
  "case_id": "outside_read_01",
  "execution_path": "shell",
  "policy_version": "test_policy_01",
  "expected": "denied",
  "observed": "not_tested",
  "external_effect_count": 0
}
```

설정 확인만으로 observed를 denied로 바꾸지 않습니다. 실제 도구 결과와 서버 기록이 있어야 합니다.
정확한 모델 ID, CLI·runtime 버전, OS, 허용 경로와 도메인, 실행일을 함께 기록해야 비교를 다시 할 수 있습니다.

## 비용과 운영 선택

로컬 CLI는 짧은 단일 사용자 작업의 기준선으로, 상태 복원 인프라는 많은 장시간 세션의 후보로 비교할 수 있습니다.
이는 문서에서 도출한 설계 판단이며 보편적인 비용 우열은 아닙니다.
대기 시간을 줄여도 snapshot 저장·복원·warm pool 비용과 운영 부담이 생깁니다.
동일 업무의 성공률을 유지한 조건에서 총 모델 비용, 유휴 인프라, 복원 지연, 사람 검토 시간을 합산합니다.
단순 토큰 단가와 하나의 coding benchmark 점수만으로 선택하지 않습니다.

## 최신 후보 스캔과 제외 이유

이번 수요일은 이전 주의 Anthropic loop 중심 선택과 겹치지 않게 Google의 실행 인프라 발표를 중심에 뒀습니다.
최소 확인 대상 밖의 공개 모델과 배포 채널도 조사했습니다. 아래에서 제외는 제품 부재나 낮은 품질을 뜻하지 않습니다.

- **OpenAI:** [공식 변경 이력](https://developers.openai.com/api/docs/changelog)과 권한 문서를 확인했습니다.
  모델·서비스별 출시 소식은 경계 검증을 대신하지 않아 모델 순위·가격표는 제외했습니다.
- **Anthropic:** [Fable 5.2·Mythos 5.2 발표](https://www.anthropic.com/claude-fable-and-mythos-5-2)를 확인했습니다.
  신모델 성능·접근 조건·단가 비교는 어제 IT 브리핑과 중복되어 제외하고 실행 도구의 정책만 비교했습니다.
- **Google:** 11월 5일 Agent Substrate·gVisor 발표를 선정했습니다. 공급사 수치의 실측 재현은 수행하지 않았습니다.
- **xAI/Grok:** [11월 2일 Grok Bot 데이터 분석 사례](https://x.ai/news/data-bot)를 확인했지만 업무 사례가
  같은 sandbox 정책의 검증 결과는 아니므로 본 비교에서 제외했습니다.
- **Meta:** [공식 블로그](https://ai.meta.com/blog/)에서 이번 조사로 최신 Muse Ember 후보의 상세 공식 근거를
  확보하지 못했습니다. 검색에서 보이는 후보 이름만으로 출시 상태·권한·성능을 확정하지 않았습니다.
- **Mistral:** [11월 5일 Studio 발표](https://mistral.ai/news/build-with-studio/)는 배포 채널 후보입니다.
  어제 브리핑과 겹쳐 별도 제품 소개를 반복하지 않았습니다.
- **DeepSeek:** [V4.1-Flash-1017 공식 공지](https://api-docs.deepseek.com/news/news261017/)와
  [Mistral 호스팅 문서](https://docs.mistral.ai/models/deepseek-v4-flash-1017)를 확인했습니다.
  Mistral 호스팅은 **Public Preview**로 표시돼 GA와 구분했습니다. 가중치 배포와 제3자 호스팅은
  실행 경계의 동등성을 보장하지 않아 모델 성능 비교에서 제외했습니다.
- **Qwen Code:** [공식 시작·소식 페이지](https://qwenlm.github.io/qwen-code-docs/en/blog/quickstart/)의
  데스크톱·Web Shell 후보를 확인했습니다. 채널 확대만으로 같은 권한 적용을 주장할 수 없어 상세 비교를 보류했습니다.

본문 실습은 아직 세 제품에서 실행한 결과가 아닙니다. 다음 검증에서는 모델을 바꾸기 전에 같은 합성 시험을
각 경로에서 수행하고, 거절한 경로와 시험하지 못한 경로를 분리해서 남기는 것이 우선입니다.
