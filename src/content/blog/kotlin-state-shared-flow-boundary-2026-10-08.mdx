## 결론부터 말하면

지난 글에서 본 `Flow`가 "collector가 붙을 때 실행되는 cold stream"이었다면, 오늘의 `StateFlow`와
`SharedFlow`는 이미 살아 있는 **hot stream**입니다. Spring Boot 개발자에게는 `ApplicationEventPublisher`,
Reactor `Sinks`, `AtomicReference`, `BlockingQueue`를 한꺼번에 떠올리게 만드는 지점입니다.

하지만 이 셋은 같은 도구가 아닙니다.

- `StateFlow`는 현재 상태가 항상 하나 있고, 새 구독자도 최신 값을 즉시 읽습니다.
- `SharedFlow`는 여러 구독자에게 이벤트를 방송하지만 완료와 실패를 타입 자체로 표현하지 않습니다.
- `Channel`은 sender와 receiver 사이의 작업 전달 큐에 가깝고, 닫힘과 buffer 정책을 신경 써야 합니다.
- 서버 내부 상태를 노출할지, 일회성 이벤트를 방송할지, 작업을 소비시킬지 먼저 정해야 합니다.

## 이번 주 개념

Kotlin Flow 문서는 hot flow를 collector와 독립적으로 값을 emit하는 공유 stream으로 설명합니다.
일반 `flow { ... }`는 collect할 때마다 새로 실행되지만, hot flow는 활성 인스턴스가 먼저 존재합니다.

<Mermaid title="Cold Flow와 hot flow 경계">
{`flowchart LR
  Cold["cold Flow"] --> Collect["collector마다 새 실행"]
  Cold --> ToHot["stateIn / shareIn"]
  ToHot --> State["StateFlow: latest state"]
  ToHot --> Shared["SharedFlow: broadcast events"]
  Producer["producer coroutine"] --> Channel["Channel: work handoff"]
  Channel --> Worker["single or multiple receivers"]
`}
</Mermaid>

`StateFlow`는 `SharedFlow`의 특수한 형태입니다. 항상 최신 값을 하나 갖고, `value`로 현재 상태를 읽을 수 있습니다.
설정 상태, 연결 상태, feature flag snapshot처럼 "지금 값"이 중요한 곳에 어울립니다.

`SharedFlow`는 여러 subscriber가 같은 emission을 받는 방송 흐름입니다. 알림, 내부 domain event, 상태 변화 신호처럼
시간에 따라 일어나는 event에 어울립니다. 단, 공식 문서가 말하듯 `SharedFlow`는 정상 완료되지 않고 실패를 직접 표현하지
않습니다. 완료와 실패가 업무 의미를 가진다면 별도 sealed class로 materialize해야 합니다.

`Channel`은 조금 다릅니다. 공식 channels 문서는 `Channel`을 `BlockingQueue`와 비슷하지만 blocking `put/take` 대신
suspending `send/receive`를 가진 primitive로 설명합니다. 여러 구독자가 모두 받아야 하는 event bus라기보다,
작업 하나를 누군가 소비하는 handoff에 더 가깝습니다.

## Java/Spring에서는 어떻게 다뤘는가

Java/Spring 코드에서 비슷한 요구는 보통 이렇게 흩어져 있었습니다.

```java
class FeatureFlagRegistry {
    private final AtomicReference<FeatureFlagSnapshot> current =
        new AtomicReference<>(FeatureFlagSnapshot.empty());

    FeatureFlagSnapshot current() {
        return current.get();
    }

    void refresh(FeatureFlagSnapshot next) {
        current.set(next);
        publisher.publishEvent(new FeatureFlagChanged(next));
    }
}
```

현재 상태는 `AtomicReference`에 두고, 변경 event는 `ApplicationEventPublisher`로 보냅니다.
작업 큐가 필요하면 `BlockingQueue`, `ExecutorService`, message broker가 등장합니다. Reactor를 쓰는 팀은
`Flux`, `Sinks.Many`, `Sinks.One` 같은 표현으로 이 경계를 다뤘습니다.

Kotlin에서는 coroutine scope와 hot flow가 이 역할 일부를 더 작은 타입으로 표현합니다. 하지만 Spring 서버에서는
"Kotlin이니까 모든 event를 SharedFlow로"가 아니라, 기존 Spring event, transaction, broker, Reactor stack과 경계를
어디에 둘지 먼저 결정해야 합니다.

## Kotlin에서는 무엇이 다른가

서버 코드에서 좋은 출발점은 "값을 다시 읽을 수 있어야 하는가"입니다.

| 요구 | 우선 후보 | 이유 |
|---|---|---|
| 현재 설정 snapshot을 즉시 읽어야 함 | `StateFlow` | 최신 값이 항상 존재하고 `value` 접근이 가능함 |
| 여러 구독자가 같은 event를 받아야 함 | `SharedFlow` | broadcast 의미가 타입에 드러남 |
| 작업 하나를 worker 하나가 가져가야 함 | `Channel` 또는 broker | 소비와 닫힘, buffer 정책을 다룸 |
| HTTP streaming response | `Flow` | 요청 collector와 lifecycle이 묶임 |
| 서비스 간 안정적 event 전달 | message broker | process 종료, 재시도, 영속성이 필요함 |

`StateFlow`와 `SharedFlow`는 process 내부 primitive입니다. 서버가 재시작되면 메모리 상태는 사라집니다.
결제, 알림, 의료 기록, 주문처럼 잃어버리면 안 되는 업무 event는 DB outbox나 message broker를 함께 검토해야 합니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin 표현 | 조심할 점 |
|---|---|---|
| `AtomicReference<T>` + getter | `MutableStateFlow<T>` | 상태가 process-local인지 확인 |
| `ApplicationEventPublisher` | `MutableSharedFlow<Event>` | transaction commit 이후 emit 여부를 구분 |
| `BlockingQueue<T>` | `Channel<T>` | buffer overflow와 close 처리 |
| Reactor `Sinks.Many<T>` | `MutableSharedFlow<T>` | backpressure와 subscriber 수 비용 비교 |
| DB outbox | outbox 유지 + Flow로 읽기 | 영속 event를 memory flow로 대체하지 않기 |

특히 `SharedFlow`는 실패를 stream에 내장하지 않습니다. "동기화 성공", "동기화 실패", "더 이상 event 없음"이 업무적으로
중요하다면 이런 식으로 명시합니다.

```kotlin
sealed interface SyncEvent {
    data class Started(val requestId: String) : SyncEvent
    data class Completed(val requestId: String) : SyncEvent
    data class Failed(val requestId: String, val reason: String) : SyncEvent
}
```

예외를 flow 자체의 완료로 기대하지 말고, subscriber가 이해할 수 있는 event로 바꾸는 편이 운영 로그와 테스트가 선명합니다.

## 최소 실행 예제

아래 예제는 서버 내부 feature flag 상태와 변경 event를 분리합니다.

```kotlin
import kotlinx.coroutines.flow.MutableSharedFlow
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.SharedFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asSharedFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update

data class FeatureFlags(
    val newCheckoutEnabled: Boolean = false,
    val auditMode: Boolean = false,
)

sealed interface FeatureFlagEvent {
    data class Refreshed(val snapshot: FeatureFlags) : FeatureFlagEvent
}

class FeatureFlagRegistry {
    private val state = MutableStateFlow(FeatureFlags())
    private val events = MutableSharedFlow<FeatureFlagEvent>(
        replay = 0,
        extraBufferCapacity = 16,
    )

    fun current(): StateFlow<FeatureFlags> = state.asStateFlow()

    fun changes(): SharedFlow<FeatureFlagEvent> = events.asSharedFlow()

    suspend fun refresh(next: FeatureFlags) {
        state.update { next }
        events.emit(FeatureFlagEvent.Refreshed(next))
    }
}
```

읽는 쪽은 현재 상태와 변경 event를 다르게 봅니다.

```kotlin
class CheckoutPolicy(
    private val registry: FeatureFlagRegistry,
) {
    fun isNewCheckoutEnabled(): Boolean =
        registry.current().value.newCheckoutEnabled
}
```

현재 설정만 필요한 서비스는 `StateFlow.value`를 읽습니다. 변경 event를 구독하는 별도 worker는 `changes()`를 collect합니다.
이 둘을 나누면 "상태 조회"와 "event 반응"이 같은 collector에 묶이지 않습니다.

작업 큐가 필요하면 `SharedFlow`보다 `Channel`이 더 직접적일 수 있습니다.

```kotlin
import kotlinx.coroutines.channels.Channel

data class ReindexCommand(val userId: String)

class ReindexQueue {
    private val commands = Channel<ReindexCommand>(capacity = 100)

    suspend fun enqueue(command: ReindexCommand) {
        commands.send(command)
    }

    suspend fun take(): ReindexCommand =
        commands.receive()
}
```

다만 운영 서버에서 중요한 작업 큐라면 메모리 `Channel`만으로 끝내지 않습니다. process가 죽어도 복구해야 하면
DB outbox, Kafka, SQS 같은 영속 큐가 더 맞습니다.

## Java 개발자가 자주 하는 오해

첫째, "`StateFlow`는 캐시라서 DB를 대체한다"는 오해입니다. `StateFlow`는 process 내부 최신 상태 표현입니다.
재시작 뒤 복구해야 하는 값은 원천 저장소가 따로 있어야 합니다.

둘째, "`SharedFlow`는 Spring event bus와 완전히 같다"는 오해입니다. Spring event는 transaction listener,
application context, synchronous/asynchronous multicaster 설정과 얽힙니다. `SharedFlow`는 coroutine subscriber와
buffer 정책을 직접 설계해야 합니다.

셋째, "`Channel`은 여러 consumer에게 모두 event를 뿌린다"는 오해입니다. channel은 기본적으로 handoff입니다.
모든 subscriber가 같은 event를 받아야 한다면 `SharedFlow`나 broker fan-out을 검토합니다.

넷째, "hot flow는 자동으로 시작과 종료가 관리된다"는 오해입니다. `shareIn`과 `stateIn`은 주어진 `CoroutineScope`에서
upstream sharing coroutine을 시작합니다. 그 scope의 생명주기와 취소 경계를 명확히 하지 않으면 process 내부 누수처럼
보이는 흐름이 생깁니다.

## 연습 문제

다음 요구를 세 타입으로 나누어 보세요.

```text
1. 현재 점검 모드가 켜져 있는지 빠르게 읽는다.
2. 점검 모드가 바뀌면 접속 중인 관리자 화면에 알려 준다.
3. 오래 걸리는 색인 재생성 작업은 worker 하나가 순서대로 처리한다.
```

한 가지 답은 이렇습니다.

| 요구 | 타입 |
|---|---|
| 현재 점검 모드 | `StateFlow<MaintenanceState>` |
| 관리자 화면 알림 | `SharedFlow<MaintenanceEvent>` |
| 색인 재생성 작업 | `Channel<ReindexCommand>` 또는 영속 queue |

마지막 질문은 꼭 붙여야 합니다.

```text
이 값이나 event가 process 재시작 뒤에도 남아야 하는가?
```

답이 "예"라면 hot flow는 전달 경계일 뿐이고, 저장소나 broker가 진짜 계약입니다.
