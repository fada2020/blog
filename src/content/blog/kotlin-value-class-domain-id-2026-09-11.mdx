## 결론부터 말하면

Kotlin의 `value class`는 `String`, `Long`, `Int` 같은 값에 도메인 이름을 붙이되, 가능한 경우 런타임 wrapper 비용을 줄이도록 설계된 타입입니다.
Spring Boot 개발자에게 가장 쉬운 첫 사용처는 `UserId`, `OrderId`, `MoneyWon`, `Percent`처럼 서로 섞이면 안 되는 값입니다.

반대로 `typealias`는 새 타입을 만들지 않습니다. 긴 함수 타입이나 복잡한 제네릭 이름을 줄이는 별명입니다.
그래서 `typealias UserId = Long`은 읽기에는 좋아도 `OrderId`와 섞이는 실수를 막지 못합니다.

오늘의 기준은 단순합니다.

- 도메인 값이 서로 섞이면 장애가 되는 곳에는 `@JvmInline value class`를 고려합니다.
- 단지 긴 타입 표현을 줄이고 싶을 때만 `typealias`를 씁니다.
- JPA entity, Jackson request/response, Java 호출자와 만나는 경계는 wrapper 노출 방식을 따로 확인합니다.
- 값 검증은 생성 시점에 작게 넣되, DB 조회나 권한 판단은 넣지 않습니다.
- public API에서는 JVM name mangling과 Java 호출 모양까지 API로 봅니다.

## 이번 주 개념

Kotlin 공식 문서는 inline class를 value-based class의 일부로 설명합니다. JVM backend에서는 `value` modifier와 `@JvmInline` annotation을 함께 씁니다.
primary constructor에는 하나의 property만 둘 수 있고, 컴파일러는 가능한 경우 그 값을 underlying type으로 표현합니다.

```kotlin
@JvmInline
value class OrderId(val value: Long) {
    init {
        require(value > 0) { "OrderId must be positive" }
    }
}
```

이 타입은 `Long` 하나를 감싸지만 호출부에서는 새 타입입니다.

```kotlin
data class LoadOrderCommand(
    val orderId: OrderId,
)

fun loadOrder(command: LoadOrderCommand) {
    println("load ${command.orderId.value}")
}
```

`OrderId` 자리에 그냥 `Long`을 넘길 수 없습니다. 이 불편함이 장점입니다. Controller, service, repository를 지나며 ID가 섞이는 실수를 컴파일 단계에서 줄일 수 있습니다.

## Java/Spring에서는 어떻게 다뤘는가

Java/Spring Boot에서는 보통 `Long id`, `String email`, `BigDecimal amount`를 그대로 DTO와 service에 넘겼습니다.

```java
public record ChangeOrderQuantityRequest(
    Long orderId,
    Long productId,
    Integer quantity
) {
}
```

이 코드는 간단합니다. 하지만 service method가 길어지면 인자 순서와 의미를 사람이 계속 기억해야 합니다.

```java
orderService.changeQuantity(request.productId(), request.orderId(), request.quantity());
```

위 코드는 컴파일됩니다. `productId`와 `orderId`가 모두 `Long`이기 때문입니다. 테스트가 좋으면 잡히지만, 타입 시스템은 도와주지 못합니다.

Java record로 감싸면 비슷한 문제를 풀 수 있습니다.

```java
public record OrderId(long value) {
    public OrderId {
        if (value <= 0) {
            throw new IllegalArgumentException("OrderId must be positive");
        }
    }
}
```

Kotlin `value class`는 이 방향을 더 가볍게 표현합니다. 다만 Java record와 완전히 같은 객체 모델은 아닙니다.
Kotlin 문서 기준 inline value class는 wrapper로 표현될 때도 있고 underlying type으로 표현될 때도 있습니다.

## Kotlin에서는 무엇이 다른가

Kotlin에서 request DTO를 바로 `value class`로 받는 것은 항상 최선이 아닙니다.
외부 JSON은 여전히 숫자와 문자열입니다. 입력 검증 메시지, Jackson module 설정, OpenAPI schema, Java client가 얽히면 경계가 복잡해질 수 있습니다.

실무에서는 먼저 request DTO를 평범하게 두고, service command로 넘어갈 때 도메인 타입을 만드는 방식이 안전합니다.

```kotlin
data class ChangeOrderQuantityRequest(
    val orderId: Long?,
    val productId: Long?,
    val quantity: Int?,
)

data class ChangeOrderQuantityCommand(
    val orderId: OrderId,
    val productId: ProductId,
    val quantity: Quantity,
)

@JvmInline
value class ProductId(val value: Long) {
    init {
        require(value > 0) { "ProductId must be positive" }
    }
}

@JvmInline
value class Quantity(val value: Int) {
    init {
        require(value in 1..99) { "Quantity must be between 1 and 99" }
    }
}
```

변환 함수는 I/O 없이 입력을 command로 바꿉니다.

```kotlin
fun ChangeOrderQuantityRequest.toCommand(): ChangeOrderQuantityCommand =
    ChangeOrderQuantityCommand(
        orderId = OrderId(requireNotNull(orderId) { "orderId is required" }),
        productId = ProductId(requireNotNull(productId) { "productId is required" }),
        quantity = Quantity(requireNotNull(quantity) { "quantity is required" }),
    )
```

이제 service는 의미가 분리된 타입을 받습니다.

```kotlin
class OrderService {
    fun changeQuantity(command: ChangeOrderQuantityCommand) {
        println("${command.orderId.value} ${command.productId.value} ${command.quantity.value}")
    }
}
```

이 구조의 장점은 controller 경계와 도메인 경계가 분리된다는 것입니다. JSON 바인딩과 사용자 입력 오류 메시지는 DTO 쪽에서 다루고,
service 안에서는 이미 의미가 붙은 값만 받습니다.

## typealias는 언제 쓰는가

`typealias`는 새 타입이 아니라 별명입니다.

```kotlin
typealias Validator<T> = (T) -> List<String>
typealias Headers = Map<String, String>
```

이런 경우에는 좋습니다. 함수 타입이나 제네릭 표현이 길어서 글을 읽기 어렵다면 별명만으로도 충분합니다.

하지만 아래 코드는 ID 섞임을 막지 못합니다.

```kotlin
typealias UserId = Long
typealias OrderIdAlias = Long

fun loadOrder(userId: UserId, orderId: OrderIdAlias) {
    println("$userId $orderId")
}

fun main() {
    loadOrder(userId = 10L, orderId = 20L)
    loadOrder(userId = 20L, orderId = 10L) // 컴파일됩니다.
}
```

Kotlin 공식 문서도 type alias는 underlying type과 서로 호환된다고 설명합니다. 이름만 좋아졌을 뿐 타입 경계는 생기지 않습니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin 표현 | 판단 기준 |
|---|---|---|
| `Long id`를 여러 곳에 전달 | `@JvmInline value class OrderId` | 서로 섞이면 안 되는 값이면 새 타입 |
| `record OrderId(long value)` | `value class OrderId(val value: Long)` | Java 호출자와 serialization 경계 확인 |
| `@Positive Long orderId` | DTO 검증 + command 변환 | 외부 입력 오류는 DTO에서 먼저 정리 |
| 긴 `Map<String, List<...>>` | `typealias` | 타입 안정성보다 가독성이 목표일 때 |
| JPA entity ID field | entity 내부는 기존 primitive 유지 가능 | ORM, proxy, converter 비용을 먼저 확인 |

## 최소 실행 예제

아래 코드는 Spring 없이 실행할 수 있습니다.

```kotlin
@JvmInline
value class OrderId(val value: Long) {
    init {
        require(value > 0) { "OrderId must be positive" }
    }
}

@JvmInline
value class ProductId(val value: Long) {
    init {
        require(value > 0) { "ProductId must be positive" }
    }
}

@JvmInline
value class Quantity(val value: Int) {
    init {
        require(value in 1..99) { "Quantity must be between 1 and 99" }
    }
}

data class ChangeOrderQuantityCommand(
    val orderId: OrderId,
    val productId: ProductId,
    val quantity: Quantity,
)

fun describe(command: ChangeOrderQuantityCommand): String =
    "order=${command.orderId.value}, product=${command.productId.value}, quantity=${command.quantity.value}"

fun main() {
    val command = ChangeOrderQuantityCommand(
        orderId = OrderId(1001),
        productId = ProductId(501),
        quantity = Quantity(2),
    )

    println(describe(command))
}
```

`OrderId(1001)`와 `ProductId(501)`의 underlying type은 둘 다 `Long`입니다. 하지만 타입이 다르므로 실수로 바꿔 넣으면 컴파일러가 막습니다.

## Java 호출자를 고려합니다

Kotlin 공식 문서는 inline class가 JVM에서 underlying type으로 컴파일될 수 있기 때문에 signature clash가 생길 수 있고,
이를 줄이기 위해 name mangling을 사용한다고 설명합니다. Java에서 호출해야 하는 함수라면 `@JvmName` 같은 노출 이름도 검토해야 합니다.

```kotlin
@JvmInline
value class CustomerId(val value: Long)

@JvmName("loadCustomerByCustomerId")
fun loadCustomer(id: CustomerId): String =
    "customer=${id.value}"
```

Kotlin module 안에서만 쓰는 도메인 타입이라면 편합니다. 하지만 Java module, Spring bean, generated client가 직접 호출해야 한다면
호출 모양을 테스트로 고정하는 편이 좋습니다.

## Java 개발자가 자주 하는 오해

첫 번째 오해는 `value class`가 항상 객체를 만들지 않는다고 믿는 것입니다. Kotlin 문서 기준 generic, interface, nullable 같은 상황에서는 boxed wrapper가 필요할 수 있습니다.

두 번째 오해는 모든 원시값을 감싸는 것입니다. `Page`, `Size`, `Offset`처럼 이미 호출부가 명확하고 검증 규칙이 단순한 값까지 모두 감싸면 코드가 무거워집니다.

세 번째 오해는 JPA entity field를 바로 value class로 바꾸는 것입니다. converter, query parameter binding, schema generation, equals/hashCode 영향이 생길 수 있으므로
먼저 service command나 domain method 경계부터 적용하는 편이 작습니다.

네 번째 오해는 `typealias`가 타입 안전성을 준다는 생각입니다. `typealias`는 별명입니다. ID 섞임을 막고 싶다면 `value class`가 맞습니다.

## 연습 문제

아래 두 타입을 만들어 보세요.

```kotlin
@JvmInline
value class Email(val value: String)

@JvmInline
value class DiscountRate(val value: Int)
```

조건은 세 가지입니다.

1. `Email`은 빈 문자열을 거부합니다.
2. `DiscountRate`는 `0..100` 범위만 허용합니다.
3. `typealias Email = String`으로는 왜 같은 검증을 강제할 수 없는지 한 문장으로 적습니다.

다음으로 기존 service method 하나를 골라 primitive 인자 세 개를 command data class와 value class 조합으로 바꿔 보세요.
Controller JSON 모양을 바꾸지 않고 service 안쪽 타입만 단단하게 만드는 것이 목표입니다.
