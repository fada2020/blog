## 이번 주 질문: 전문 agent를 늘리면 작업이 더 잘 끝날까요

서로 다른 파일을 독립적으로 조사하는 일은 나눌 가치가 있습니다. 반대로 앞 단계의 판단을 매번 전달받아
같은 문서를 고치는 작업은 요약 손실과 조정 비용이 생깁니다. **먼저 단일 loop를 기준선으로 측정하고,
독립성·문맥 격리·권한 분리가 필요한 지점만 분리하는 실험**을 제안합니다.

지난 글의 문맥 cache·sandbox 경계에서 한 단계 나아가, 이번에는 같은 업무를 맡기는 실행 구조 자체를 비교합니다.
Spring Boot의 클래스 수가 많다고 처리량이 늘지 않듯 agent 수도 성능의 대리 지표가 아닙니다.

## 공식 접근을 비교하면

| 접근과 근거 | 유리한 조건 | 확인할 비용 |
|---|---|---|
| Anthropic: loop에 skills·tools 통합 | 공유 문맥이 많고 순차 의존성이 큼 | 도구 선택과 지침 충돌 |
| OpenAI: Responses Multi-agent beta | 독립적이고 범위가 좁은 조사 | token 증가·beta 계약 변경 |
| Google: 고정 parallel workflow | 실행 그래프가 미리 정해짐 | 결과 합성·충돌 처리 |

[Anthropic의 10월 22일 가이드](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)는
기업 도입 사례에서 일부 전문 agent를 skills와 도구로 합치는 접근을 설명합니다. 병렬 조사·독립 검증·권한 분리까지
없애라는 주장은 아닙니다. 해당 글의 성능 사례는 벤더 관찰이며 우리 코드베이스의 재현 결과로 취급하지 않습니다.

[OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/responses-multi-agent)는 독립된 작업을
병렬 처리하는 사용처를 제시합니다. 같은 가변 자원에 잦은 쓰기가 필요하거나 순차 추론이 강하면 이점이 줄 수 있습니다.
지원 모델과 beta 헤더·schema는 도입 시 다시 확인해야 합니다. beta 기능을 운영 기본값으로 단정하지 않았습니다.

[Google의 설계 패턴 문서](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system)는
parallel workflow의 실행 순서를 모델 판단 없이 코드로 관리하는 경우도 구분합니다. 순서가 이미 정해진 검사라면
orchestrator 모델을 매번 호출하는 비용을 먼저 따져 볼 수 있습니다. 이 문서의 검토일은 2026년 5월 28일이며
이번 주 신제품 발표가 아니라 아키텍처 비교 근거입니다.

## Java/Spring 팀에 대입한 세 가지 작업

1. **하나의 실패 테스트를 고치는 작업:** 원인·계약·수정이 강하게 연결됩니다. 단일 loop가 문맥을 이어서
   처리하는 기준선이 합리적입니다. 별도 reviewer는 패치 완성 뒤 독립적으로 읽게 할 수 있습니다.
2. **서로 다른 모듈의 호환성 조사:** 각 조사자에게 읽기 전용 범위와 같은 출력 schema를 주고 병렬 결과를
   합칩니다. 모듈별 발견이 전체 배포 가능성 증명으로 바뀌지 않도록 통합 검증은 남깁니다.
3. **수정·배포·확인:** 같은 저장소나 배포 대상을 여러 실행자가 동시에 쓰면 조정 비용이 커집니다.
   파일 소유권과 발행 담당을 하나로 정하고 실제 배포 승인은 별도 경계에서 처리합니다.

## 실습: 모델을 고정하고 구조만 바꿉니다

아래는 이 글에서 제안하는 실험입니다. 유료 모델 호출을 실행해 얻은 성능표가 아닙니다.
공개용 작은 Spring 프로젝트에 테스트 실패·문서 확인·서로 다른 모듈 조사·외부 쓰기 금지 등의 과제를 만듭니다.
업무 수와 반복 횟수는 예산에 맞춰 정하되 두 구조에 같은 입력을 사용합니다.

- A: 한 loop가 필요할 때 skill과 도구를 읽습니다.
- B: 같은 모델·추론 설정·도구 권한을 사용하되 독립 조사만 subagent로 나눕니다.
- 전체 token 예산과 deadline을 같게 고정합니다. 자식 작업 비용도 합산합니다.
- 동일 과제를 여러 번 실행하고 task별 성공/실패 전환도 남깁니다. 평균 점수만 비교하지 않습니다.

평가 요청과 응답의 예시는 제품 API가 아닌 **실험 기록용 계약**입니다.

```json
{
  "task_id": "case_04",
  "topology": "single_loop",
  "passed": true,
  "contract_preserved": true,
  "unauthorized_writes": 0,
  "elapsed_ms": 42000,
  "total_cost_usd": 0.18,
  "evidence": ["test-report", "reviewed-diff"]
}
```

42초와 0.18달러는 형식을 보여 주는 가상 값입니다. 저장할 때도 task ID는 합성 값을 사용하고
원문 고객 데이터·자격증명·내부 주소는 평가 기록에 넣지 않습니다.
`passed`는 agent의 자기 선언이 아니라 테스트·기준 답안·변경 diff 등 외부 판정으로 계산합니다.

```text
성공한 작업당 비용 = 모든 시도의 총비용 / 통과한 작업 수
전체 지연 = 대기 + 모델 실행 + 도구 실행 + 결과 통합 + 재검증
```

통과 작업이 0이면 첫 지표는 산출 불가로 기록합니다. 작업 전체가 실패한 시도와 재시도의 비용을 빼면
저렴해 보이는 착시가 생깁니다. 같은 품질을 유지하는지 먼저 확인한 다음 중앙값·p95 지연을 비교합니다.
권한 위반은 평균 점수에 묻지 않고 별도 실패 조건으로 둡니다.

## 벤치마크를 읽을 때 남길 단서

[SWE-bench 공식 leaderboard](https://www.swebench.com/)는 해결된 과제 비율을 보여 줍니다.
Verified·Multilingual 등의 평가 집합을 혼합하거나 모델명만 보고 실행 harness까지 같다고 가정하면 안 됩니다.
공개 코딩 benchmark의 상위 순위가 우리 팀 문서화·브라우저·배포 작업의 순위로 옮겨 가는 것도 아닙니다.
이 글은 동일 조건의 구조별 결과를 확보하지 못했으므로 수치 우열을 발표하지 않습니다.

평가 기록에는 모델의 정확한 ID, 실행일, 도구·network 권한, 예산, 과제 집합, 실패한 과제를 함께 남깁니다.
누가 더 높은 점수를 냈는지보다 어떤 실패를 새로 만들었는지 확인하는 데 도움이 됩니다.

다른 검증 항목입니다.

## 다음에 확인할 것

현재 작업 하나에 A/B 평가를 먼저 붙입니다. 단일 loop의 실패가 문맥 과밀인지, 도구 선택 오류인지,
직렬 실행 시간인지 확인한 뒤 해당 원인만 바꿉니다. 분리한 subagent가 독립적으로 유용한 증거를 반환하는지,
공유 파일을 건드려 재작업을 만드는지까지 기록하면 다음 구조 선택의 근거가 됩니다.
