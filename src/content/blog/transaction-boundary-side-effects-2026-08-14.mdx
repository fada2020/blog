## 이번 주에 이 기술이 중요했던 이유

이번 주에는 화면 데이터 조회, 도메인 흐름 분리, 운영 API 드라이런을 다뤘습니다. 주제는 달랐지만
반복해서 같은 질문이 나왔습니다.

**이 작업은 지금 커밋해야 하는 상태인가, 아니면 커밋 이후에 붙여도 되는 부작용인가**입니다.

Spring Boot에서는 `@Transactional`이 편리합니다. 서비스 메서드에 붙이면 여러 저장소 호출을 하나의
작업처럼 묶을 수 있습니다. 하지만 이 편리함 때문에 모든 일을 한 메서드 안에 넣기 쉽습니다. 상태 저장,
감사 로그, 외부 알림, 파일 생성, 웹훅 호출, 검색 인덱스 갱신이 한 흐름 안에 섞이면 문제가 생겼을 때
무엇이 확정됐고 무엇이 보류됐는지 알기 어렵습니다.

트랜잭션은 비즈니스 성공을 대신 정의해 주지 않습니다. 트랜잭션은 정해진 경계 안의 리소스 변경을 함께
완료하거나 되돌리는 도구입니다. 그래서 설계의 첫 질문은 "어디에 `@Transactional`을 붙일까"가 아니라
"이 유스케이스가 반드시 함께 확정해야 하는 상태는 무엇인가"여야 합니다.

## 핵심 개념

트랜잭션 경계는 데이터베이스 커밋 경계와 유스케이스 책임 경계를 동시에 읽게 해 줘야 합니다. 아래처럼
나누면 판단이 단순해집니다.

| 구분 | 트랜잭션 안에 두기 좋은 작업 | 밖으로 빼야 하는 작업 |
|---|---|---|
| 도메인 상태 | 주문 확정, 검사 결과 저장, 재고 차감 | 메일 발송, 메시지 전송, 검색 색인 반영 |
| 실패 의미 | 실패하면 전체 명령이 실패해야 함 | 실패해도 핵심 상태는 이미 확정될 수 있음 |
| 재시도 방식 | 같은 명령을 다시 검증해야 함 | outbox, 큐, 스케줄러로 재시도 가능 |
| 테스트 기준 | 커밋/롤백 후 저장소 상태 | 커밋 이후 이벤트 발행과 중복 처리 |
| 운영 설명 | 이 API가 확정한 상태 | 후속 처리의 성공, 실패, 보류 상태 |

Spring Framework의 기본 rollback 규칙도 이 구분을 요구합니다. 기본 설정에서는 unchecked exception과
`Error`가 rollback 대상입니다. checked exception은 별도 규칙을 두지 않으면 기본적으로 rollback을
일으키지 않습니다. 즉 예외 타입 하나만 바꿔도 커밋 여부가 달라질 수 있습니다.

전파 방식도 마찬가지입니다. 기본적인 `REQUIRED`는 바깥 트랜잭션에 참여할 수 있고, 내부 논리 범위에서
rollback-only가 표시되면 바깥 호출자는 커밋을 기대하다가 `UnexpectedRollbackException`을 받을 수
있습니다. `REQUIRES_NEW`는 독립 물리 트랜잭션을 만들지만, 그만큼 별도 커밋과 별도 커넥션 비용을 만듭니다.
따라서 "감사 로그는 무조건 남겨야 하니까 `REQUIRES_NEW`"처럼 습관적으로 고르면 실제 상태와 감사 상태가
서로 다른 시점에 확정됩니다.

## 내부 동작 원리

트랜잭션 안에서 실행된 코드는 모두 같은 의미의 작업처럼 보입니다. 하지만 실제로는 세 종류가 섞입니다.

1. 반드시 함께 커밋되어야 하는 도메인 상태
2. 커밋 결과를 보고 실행해야 하는 후속 작업
3. 요청 전후의 보안, 로깅, 관측성 처리

이 셋을 같은 서비스 메서드에 넣으면 테스트가 어려워집니다. 테스트가 성공해도 무엇을 검증했는지 흐려집니다.

Spring Framework의 `@TransactionalEventListener`는 이 경계를 표현할 때 유용합니다. 기본 phase는
`AFTER_COMMIT`이므로 현재 트랜잭션이 성공적으로 완료된 뒤에 리스너가 동작합니다. 실패한 명령의 이벤트를
잘못 처리하지 않으려면 "이 이벤트는 커밋 전에도 의미가 있는가"를 먼저 따져야 합니다.

다만 이벤트 리스너가 모든 문제를 해결해 주지는 않습니다. 커밋 이후에 애플리케이션이 내려가면 메모리 안의
이벤트는 사라질 수 있습니다. 반드시 전달해야 하는 작업이라면 이벤트 자체를 같은 트랜잭션 안에서 outbox
테이블에 기록하고, 별도 워커가 커밋된 outbox를 읽어 처리하는 쪽이 더 안전합니다.

## 실무 설계 선택지

가장 보수적인 시작점은 하나의 application service가 하나의 명령을 확정하게 하는 것입니다. 아래 예시는
정산이나 예약 같은 특정 도메인이 아니라, 승인 요청을 확정하고 후속 알림을 준비하는 일반적인 형태입니다.

```java
@Service
public class ApprovalService {
    private final ApprovalRepository approvals;
    private final OutboxRepository outbox;

    @Transactional
    public ApprovalResult approve(ApproveCommand command) {
        Approval approval = approvals.getById(command.approvalId());

        approval.approveBy(command.operatorId(), command.reason());
        approvals.save(approval);

        outbox.save(DomainMessage.approvalCompleted(approval.id()));

        return ApprovalResult.completed(approval.id());
    }
}
```

이 코드에서 트랜잭션 안에 들어가는 것은 승인 상태와 outbox 기록입니다. 알림 전송은 아직 하지 않습니다.
승인이 롤백되면 outbox도 같이 사라져야 하기 때문입니다.

```java
@Component
public class ApprovalMessageWorker {
    public void publishPendingMessages() {
        for (DomainMessage message : outbox.findPending()) {
            messageClient.publish(message.toPayload());
            outbox.markPublished(message.id());
        }
    }
}
```

이 워커는 별도 트랜잭션과 별도 재시도 정책을 가질 수 있습니다. 중요한 점은 실패 의미가 달라졌다는
것입니다. 승인 실패는 API 실패입니다. 메시지 발행 실패는 후속 처리 실패입니다. 둘을 같은 예외 처리로
묶으면 운영자가 원인을 잘못 읽습니다.

간단한 시스템이라면 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`로 시작할 수
있습니다.

```java
@Component
public class ApprovalEventHandler {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void handle(ApprovalCompleted event) {
        notificationClient.send(event.approvalId());
    }
}
```

이 선택은 "실패해도 재처리 손실을 감수할 수 있는가"라는 질문에 예라고 답할 때만 적합합니다. 반드시 한 번은
처리해야 하는 업무라면 outbox가 더 단순하고 검증하기 쉽습니다.

## 흔한 실패 사례

첫 번째 실패는 감사 로그를 무조건 별도 트랜잭션으로 저장하는 것입니다. 독립 감사가 필요한 경우는 있습니다.
하지만 아무 기준 없이 `REQUIRES_NEW`를 붙이면 도메인 상태는 롤백됐는데 감사 로그만 성공한 것처럼 남을 수
있습니다. 그 로그가 "시도"인지 "성공"인지 분리하지 않으면 운영 화면에서 잘못 해석됩니다.

두 번째 실패는 외부 호출을 트랜잭션 안에서 실행하는 것입니다. DB는 롤백돼도 이미 보낸 HTTP 요청, 메시지,
메일, 파일 생성은 함께 되돌아오지 않습니다. 특히 드라이런 기능을 만들 때 이 차이를 무시하면 "롤백했으니
안전하다"는 설명이 거짓이 됩니다.

세 번째 실패는 checked exception을 업무 실패로 던지면서 rollback 규칙을 확인하지 않는 것입니다.
`BusinessException extends Exception` 같은 설계는 읽기에는 명확해 보일 수 있지만, 기본 rollback
규칙과 맞지 않으면 커밋이 일어날 수 있습니다. checked exception을 쓰려면 `rollbackFor`를 명시하거나
예외 계층 자체를 다시 검토해야 합니다.

네 번째 실패는 보안 필터와 서비스 트랜잭션의 책임을 섞는 것입니다. Spring Security의 Servlet 지원은
FilterChain을 기반으로 인증과 인가를 먼저 다룹니다. 서비스 트랜잭션은 그 뒤에 도메인 상태를 확정합니다.
운영자 화면에서 버튼을 숨겼다는 이유로 서비스 권한 검증을 생략하면, 트랜잭션 경계가 아무리 좋아도 잘못된
사용자가 올바르게 커밋할 수 있습니다.

## 독립 실행 실습

작은 승인 API를 하나 만든다고 가정하고 아래 순서로 테스트를 잡아 봅니다.

1. 승인 성공 시 `approval.status`와 `outbox`가 같은 트랜잭션에서 커밋되는지 확인합니다.
2. 승인 검증 실패 시 `approval.status`와 `outbox`가 모두 남지 않는지 확인합니다.
3. 메시지 발행 실패가 승인 상태를 되돌리지 않는지 확인합니다.
4. 같은 outbox 메시지를 두 번 처리해도 외부 메시지가 중복 발행되지 않도록 멱등 키를 둡니다.
5. 운영 화면에는 승인 성공, 메시지 발행 대기, 메시지 발행 실패를 다른 상태로 보여 줍니다.

테스트 이름은 구현이 아니라 경계를 말하게 둡니다.

```java
@Test
void approvalAndOutboxAreCommittedTogether() {
    ApprovalResult result = approvalService.approve(validCommand());

    assertThat(approvals.get(result.id()).status()).isEqualTo(APPROVED);
    assertThat(outbox.findByAggregateId(result.id())).hasSize(1);
}

@Test
void messageFailureDoesNotRollbackCommittedApproval() {
    ApprovalResult result = approvalService.approve(validCommand());

    messageClient.failNextPublish();
    messageWorker.publishPendingMessages();

    assertThat(approvals.get(result.id()).status()).isEqualTo(APPROVED);
    assertThat(outbox.findByAggregateId(result.id()).getFirst().status()).isEqualTo(PENDING);
}
```

이 정도 테스트만 있어도 경계가 흔들릴 때 바로 드러납니다. 누군가 외부 호출을 다시 서비스 트랜잭션 안으로
넣으면 두 번째 테스트가 깨져야 합니다.

## 정리하면

트랜잭션 설계는 `@Transactional`을 많이 붙이는 일이 아닙니다. 한 명령이 반드시 함께 확정해야 하는
상태를 좁히고, 커밋 이후에 처리할 수 있는 일을 밖으로 밀어내는 일입니다.

이 구분이 되면 운영 설명도 선명해집니다. API는 어떤 상태를 확정했는지 말할 수 있고, 후속 작업은 성공,
대기, 실패를 따로 보고할 수 있습니다. 롤백은 데이터베이스 안의 약속이고, 외부 부작용은 별도 계약입니다.
그 둘을 섞지 않는 것이 Spring Boot 서비스의 트랜잭션 경계를 오래 유지하는 가장 현실적인 방법입니다.
