주문 두 건과 상태 두 건을 `zip`으로 묶을 때, 다른 정렬 기준으로 조회했다면 길이가 같아도 상태가 뒤바뀝니다. [토요일 zip 실습](/blog/posts/kotlin-zip-length-2026-11-14/)에서 짧은 쪽의 길이까지만 결과가 만들어지는 것을 확인했습니다. 이번에는 짝의 정체성을 어떻게 검증할지 살펴봅니다.

2026년 11월 15일 기준 공식 문서의 최신 안정 버전은 Kotlin 2.4.21입니다. [Kotlin 릴리스](https://kotlinlang.org/docs/releases.html)

## 두 이터레이터가 만나는 지점

`Iterable.zip`은 같은 위치의 원소를 짝지은 결과 목록을 만들고, 한쪽이 끝나면 멈춥니다. `Sequence.zip`은 소비할 때 같은 규칙으로 짝을 만듭니다. 일부 결과만 소비하는 파이프라인에서 유용하지만, 입력 순서가 바뀌었거나 끝에 누락이 생겨도 그 자체로 오류가 되지는 않습니다. Java의 두 이터레이터를 동시에 전진시키는 루프를 떠올리면 검증이 어느 지점에서 필요한지 보입니다. [Iterable API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.collections/zip.html) · [Sequence API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.sequences/zip.html)

| 입력 계약 | 결합 방법 | 확인할 조건 |
| --- | --- | --- |
| 같은 순서를 유지하는 두 열 | 위치 기준 `zip` | 결합 전 행 수 일치 |
| 입력 순서가 독립적인 두 조회 | ID 기준 조회 | 중복 ID, 누락 ID, 여분 ID |
| 일부 미매칭을 허용하는 배치 | ID 기준 조회와 누락 목록 | 누락의 처리 정책과 재시도 단위 |

Spring Boot에서 별도 쿼리로 두 목록을 가져올 때는 각각의 조회에 정렬 조건이 있어도 조회 조건과 시점까지 맞는지 확인해야 합니다. 같은 데이터베이스에서 처리한다면 조회 시점과 조인 카디널리티를 관리할 수 있는 SQL 조인도 검토할 수 있습니다. 서로 다른 시스템에서 읽는다면 매칭된 행과 누락된 ID를 별도로 집계해야 재시도 범위를 정할 수 있습니다.

## 독립 실행 실습

다음 코드를 `Main.kt`로 저장하고 `kotlinc Main.kt -include-runtime -d demo.jar`, `java -jar demo.jar` 순서로 실행합니다.

```kotlin
data class Status(val id: String, val value: String)

fun match_by_id(ids: List<String>, rows: List<Status>): List<String> {
    val requested_ids = ids.toSet()
    val by_id = rows.associateBy { it.id }
    require(requested_ids.size == ids.size) { "duplicate requested id" }
    require(by_id.size == rows.size) { "duplicate status id" }
    require(by_id.keys == requested_ids) { "missing or extra status id" }
    return ids.map { by_id.getValue(it).value }
}

fun main() {
    val ids = listOf("A", "B")
    val rows = listOf(Status("B", "READY"), Status("A", "FAILED"))
    check(ids.zip(rows) { _, row -> row.value } == listOf("READY", "FAILED"))
    check(match_by_id(ids, rows) == listOf("FAILED", "READY"))
    check(runCatching { match_by_id(ids, rows + rows.first()) }.isFailure)
    check(runCatching { match_by_id(ids, rows.take(1)) }.isFailure)
    check(runCatching { match_by_id(ids, rows + Status("C", "READY")) }.isFailure)
    println("5 checks passed")
}
```

맵을 만들고 조회하는 비용은 일반적인 해시 분포에서 입력 크기에 비례하고, ID 인덱스를 위한 메모리가 필요합니다. `associateBy`에서 같은 키의 마지막 값이 남으므로 원래 행 수와 맵 크기를 비교해야 중복을 감지할 수 있습니다. 배치에서 중복이 정상이라면 중복을 거부하는 대신 어느 버전이 유효한지 별도의 규칙이 필요합니다.
