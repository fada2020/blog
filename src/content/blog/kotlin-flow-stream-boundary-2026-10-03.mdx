## 결론부터 말하면

Kotlin `Flow`는 "비동기 `List`"가 아닙니다. Spring Boot 개발자에게 더 가까운 비교 대상은
Java `Stream`, Reactor `Flux`, 그리고 데이터베이스 cursor 사이 어딘가입니다. 값을 한꺼번에 들고 오는 대신
시간에 따라 emit하고, 누군가 collect해야 실행되며, 취소와 예외가 coroutine 경계 안에서 전파됩니다.

오늘의 핵심은 세 가지입니다.

- `flow { ... }`로 만든 기본 Flow는 cold stream이라 collect할 때마다 다시 실행됩니다.
- `map`, `filter` 같은 중간 operator만 붙인 상태로는 실제 작업이 시작되지 않습니다.
- Spring 서버에서는 "응답으로 흘릴 stream"과 "내부 배치 파이프라인"을 분리해서 설계해야 합니다.

## 이번 주 개념

Kotlin Flow API 문서는 Flow를 비동기 데이터 스트림으로 설명합니다. 값은 순서대로 emit되고, 정상 완료되거나 예외로
끝납니다. 이 설명에서 중요한 단어는 "비동기"보다 "스트림"과 "완료"입니다.

```kotlin
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

fun auditEvents(userId: String): Flow<AuditEvent> =
    flow {
        emit(AuditEvent.Login(userId))
        emit(AuditEvent.ViewedDashboard(userId))
    }
```

이 함수는 `List<AuditEvent>`를 반환하지 않습니다. 아직 이벤트를 만든 것도 아닙니다. 호출자는 Flow라는 실행 계획을 받은
상태이고, `collect`, `toList`, `first` 같은 terminal operator가 호출될 때 실제 emit이 시작됩니다.

## Java/Spring에서는 어떻게 다뤘는가

Java `Stream`은 lazy pipeline이라는 점에서 Flow와 닮았습니다.

```java
List<OrderSummary> summaries = orders.stream()
    .filter(Order::isPaid)
    .map(OrderSummary::from)
    .toList();
```

`filter`와 `map`을 붙이는 동안에는 pipeline을 만들고, `toList()`에서 실행합니다. 다만 Java `Stream`은 기본적으로
동기 collection 처리에 가깝습니다. 외부 API, DB cursor, 메시지 stream, SSE 응답처럼 시간이 걸리는 비동기 값 흐름을
다루려면 `CompletableFuture`, Reactor, scheduler, queue가 함께 등장합니다.

Reactor `Flux`에 익숙하다면 Flow를 더 빨리 이해할 수 있습니다. 하지만 Flow는 Kotlin coroutine cancellation과
suspending function을 자연스럽게 품습니다. 서버 코드에서는 "Reactive stack으로 전부 바꾼다"가 아니라,
비동기 흐름을 함수 경계에 드러내는 선택지로 보는 편이 안전합니다.

## Kotlin에서는 무엇이 다른가

가장 먼저 구분할 것은 cold와 hot입니다.

| 구분 | 실행 시점 | Spring Boot에서 떠올릴 예 |
|---|---|---|
| cold `Flow` | collector가 붙을 때마다 새로 시작 | DB page를 읽어 변환하는 내부 pipeline |
| `SharedFlow` | collector와 별개로 살아 있는 공유 흐름 | 서버 내부 이벤트 bus |
| `StateFlow` | 현재 값을 가진 hot state | 설정 상태, 연결 상태, UI state |

대부분의 서버 학습에서는 cold Flow부터 시작하면 됩니다. 매 요청마다 사용자별 데이터를 새로 읽어야 한다면 cold Flow가
더 명확합니다. 반대로 시스템 전체 이벤트를 여러 consumer에게 방송해야 한다면 `SharedFlow`나 외부 메시지 브로커의
책임을 검토해야 합니다.

## 대응 개념 비교

| Java/Spring 습관 | Kotlin Flow 표현 | 판단 기준 |
|---|---|---|
| `Stream<T>` lazy pipeline | `Flow<T>` + operator | 값 흐름을 늦게 실행하고 싶을 때 |
| `Flux<T>` | `Flow<T>` 또는 Reactor 유지 | Spring WebFlux stack과의 경계를 먼저 결정 |
| `CompletableFuture<List<T>>` | `Flow<T>` 또는 `suspend fun List<T>` | 결과가 전체 목록인지, 흐름인지 구분 |
| `try/catch` around pipeline | `catch { ... }` + terminal 처리 | upstream 예외와 downstream 예외를 섞지 않기 |
| 무제한 병렬 처리 | `buffer`, `flatMapMerge` 신중 사용 | preview/실험 API 여부와 동시성 상한 확인 |

Spring MVC 애플리케이션에서 모든 반환 타입을 Flow로 바꿀 필요는 없습니다. 한 번에 20개 결과를 JSON으로 내려주는 API라면
`suspend fun`이 `List<T>`를 반환해도 충분합니다. Flow는 다음 조건에서 더 값이 있습니다.

- 결과가 많아서 내부 처리 중간에 취소될 수 있어야 한다.
- upstream 값을 읽으며 변환하고 downstream으로 넘기는 구조가 더 자연스럽다.
- timeout, cancellation, 예외 처리를 pipeline 단위로 보고 싶다.
- future 목록을 만들고 한꺼번에 await하는 코드가 복잡해졌다.

## 최소 실행 예제

아래 예제는 주문 이벤트를 읽어 결제 완료 이벤트만 요약하는 내부 pipeline입니다.

```kotlin
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.catch
import kotlinx.coroutines.flow.filter
import kotlinx.coroutines.flow.flow
import kotlinx.coroutines.flow.map
import kotlinx.coroutines.flow.toList

sealed class OrderEvent {
    data class Created(val orderId: String) : OrderEvent()
    data class Paid(val orderId: String, val amount: Long) : OrderEvent()
    data class Cancelled(val orderId: String) : OrderEvent()
}

data class PaidOrderSummary(
    val orderId: String,
    val amount: Long,
)

class OrderEventReader {
    fun readRecent(): Flow<OrderEvent> =
        flow {
            emit(OrderEvent.Created("order-1"))
            emit(OrderEvent.Paid("order-1", 42_000))
            emit(OrderEvent.Cancelled("order-2"))
        }
}

class OrderReportService(
    private val reader: OrderEventReader,
) {
    suspend fun paidSummaries(): List<PaidOrderSummary> =
        reader.readRecent()
            .filter { event -> event is OrderEvent.Paid }
            .map { event ->
                val paid = event as OrderEvent.Paid
                PaidOrderSummary(
                    orderId = paid.orderId,
                    amount = paid.amount,
                )
            }
            .catch { error ->
                throw IllegalStateException("order event stream failed", error)
            }
            .toList()
}
```

중요한 점은 `paidSummaries()`가 `suspend`라는 사실입니다. 서비스 바깥에서는 그냥 목록을 받지만, 내부에서는 stream처럼
읽고 변환합니다. API 계약이 꼭 streaming response가 아니어도 내부 구현에는 Flow를 쓸 수 있습니다.

응답 자체를 stream으로 열 때는 더 조심해야 합니다. HTTP client가 끊기면 collector가 취소될 수 있어야 하고,
중간 buffer가 너무 크면 서버 메모리나 DB cursor를 오래 잡을 수 있습니다.

## Java 개발자가 자주 하는 오해

첫째, "`Flow<T>`를 반환하면 자동으로 비동기 실행된다"는 오해입니다. cold Flow는 collect 전까지 실행되지 않습니다.
함수를 호출했다는 사실과 pipeline이 실행됐다는 사실을 구분해야 합니다.

둘째, "`map` 안에서 오래 걸리는 일을 마음껏 병렬로 해도 된다"는 오해입니다. Flow operator는 순차 처리와 취소 전파를
이해한 뒤 병렬화를 추가해야 합니다. `flatMapMerge` 같은 일부 operator는 preview 표기가 있으므로 기준 버전과 API 상태를
확인해야 합니다.

셋째, "예외는 마지막 `catch` 하나면 전부 잡힌다"는 오해입니다. Flow의 `catch`는 upstream 예외를 다루는 operator입니다.
collector 내부에서 던진 예외나 cancellation을 업무 실패처럼 바꾸면 장애 원인을 숨길 수 있습니다.

넷째, "Reactor를 모두 Flow로 바꿔야 Kotlin답다"는 오해입니다. 이미 Spring WebFlux와 Reactor 기반 operator, backpressure,
라이브러리 통합이 핵심인 서비스라면 Reactor를 유지하는 편이 낫습니다. Kotlin Flow는 경계가 분명한 곳부터 작게 들이는 것이 좋습니다.

## 연습 문제

다음 요구사항을 Flow pipeline으로 바꿔 보세요.

```text
1. 최근 결제 이벤트를 읽는다.
2. 취소 이벤트는 제외한다.
3. 10만원 이상 결제만 뽑는다.
4. 주문 ID와 금액만 요약한다.
5. 읽기 실패는 report generation 실패로 감싼다.
```

힌트는 이렇습니다.

```kotlin
reader.readRecent()
    .filter { event -> event is OrderEvent.Paid }
    .map { event -> event as OrderEvent.Paid }
    .filter { event -> event.amount >= 100_000 }
    .map { event -> PaidOrderSummary(event.orderId, event.amount) }
    .catch { error -> throw ReportGenerationException(error) }
```

마지막에 `toList()`를 붙이면 내부 pipeline 결과를 일반 JSON 응답으로 만들 수 있습니다. `collect { ... }`를 붙이면 각 값을
하나씩 처리하는 worker 흐름이 됩니다. 반환 타입을 먼저 고르지 말고, "호출자가 값을 한 번에 원하는가, 흐름으로 원하는가"를
먼저 정하세요.
